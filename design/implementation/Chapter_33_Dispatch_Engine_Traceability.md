## Major implementation gaps

1. **No persisted Dispatch Decision record.** Rationale and evaluation criteria live only in event payloads (Participant id + strategy name); there is no queryable record of which candidates were considered or why losers lost (§13, DE-005, FR-33.4/33.7, AC "traceable").
2. **No parallel dispatch.** `dispatchEngine.dispatch()` is strictly one Work Item → at most one Participant per call; §8's Parallel Assignment, §10, and the matching Acceptance Criterion are unbuilt.
3. **Redispatch covers only the "Participant unavailable" trigger.** Execution failure (`failed`/`blocked`) and governance/capability-availability/priority changes do not redispatch; they (or nothing, for the latter three) route to a human Attention Item instead (§11).
4. **Dispatch strategies are not Pack-extensible.** `STRATEGY_FUNCTIONS` is a fixed in-code registry; only the *ordering/preference* among the seven built-in strategies is Profile/Pack-configurable, contradicting §9's "Strategies are contributed through Packs" and the matching §16 Acceptance Criterion and §17 Deliverable.
5. **No Dispatch registry deliverable.** §17 lists one; none exists as a DB-backed artefact.
6. **Dispatch inputs are narrower than §7.** Only the eligible pool and Participant availability are read directly by Dispatch; Authority, Policy, Obligations, and most organisational constraints are enforced upstream and never independently checked by Dispatch itself (acceptable by construction, but not what §7 literally lists as Dispatch's own inputs).

Note: this supersedes the chapter's own §18 "Implementation Specifics" section on every point where the code has materially changed since that section was recorded (strategy framework, redispatch, and event coverage are now substantially more built than §18 describes). §18 itself was not modified by this analysis.
