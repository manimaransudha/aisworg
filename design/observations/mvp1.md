Participant assignment — what exists today vs. the fuller model
In the MVP as built: assignment is a flat, manual act. A Capability is required by an SEU (seeded from the Template). Someone — a human at the admin UI, or an API caller — picks that Capability and says "this Participant (AI/Human/External) fulfils it," via POST /capabilities/:id/fulfil. That creates a Participant record and a Capability Fulfilment record, and marks the Capability Fulfilled for that SEU. That's it. There's no pool of candidates, no scoring, no "who's best suited," and critically — the Participant is never bound to a specific Deliverable or unit of work. It's bound to the Capability only. Nothing routes a particular piece of work to a particular Participant.

That's a deliberate simplification (Build Plan §5, item 3: "no Dispatch Engine"), but it means something important: in the MVP, a Participant is a record, not an actor. Creating one doesn't invoke an LLM, doesn't queue a task for a human, doesn't call an external system. It just says "eligibility exists."

In Book 3's fuller model, assignment is two separate steps that we collapsed into one:

Capability Fulfilment (Ch.12) — establishes eligibility: which Participant Types/Instances are even qualified for a Capability, based on capability compatibility, behavioural compatibility with the EBM, required knowledge, required authority, availability. This produces a pool, not a binding.
Dispatch Engine (Ch.33) — picks a specific Participant Instance from that pool for a specific Work Item, right now. This is the actual "who does this piece of work" decision (round-robin, load-based, specialization-matched — Book 3 leaves the algorithm unspecified).
We only built step 1, and even that's simplified to "whoever the caller names."

Work orchestration — the intended shape
The organising idea (and it's a real departure from task-list thinking, stated explicitly in the design notes): the system never asks "which tasks are ready?" — it continuously asks "which Deliverables are now achievable?" There's no central scheduler or project-manager role. The loop, per Capability, looks like:

Dependency Engine continuously re-evaluates the Deliverable Dependency Graph. When a Deliverable's dependencies (other Deliverables in required states, or Services from other Capabilities) are all satisfied, it becomes Ready.
A Ready Deliverable's required Capabilities get identified, and Capability Fulfilment supplies the eligible-Participant pool for each.
The Execution Engine (Ch.31) generates a Command — expressing what engineering action is needed, not how. This is deliberate: Commands are participant-agnostic.
A participant-specific service expands that Command into one or more Work Items (Ch.32) — and this is the one genuinely interesting design choice in Book 3: Work Items are explicitly not persistent business objects. They're described as closer to a query optimizer's execution plan — generated on demand, discardable, never the thing you query history through (Deliverables are that thing).
Dispatch Engine binds a specific Participant Instance to that Work Item.
The Participant executes — for an AI Participant this is where an actual model gets invoked with context (the Deliverable's current state, satisfied dependencies, relevant Knowledge/Evidence); for a Human Participant it's a queued notification (Attention Management, Ch.34); for an External Participant it's a call through an Interaction Adapter (Ch.36).
The output runs through the Trust Pipeline: Information → Evidence → Knowledge → Decision → Deliverable State Transition. The Participant doesn't just declare "done" — it produces Evidence, which justifies a Decision, which justifies the transition request.
The transition itself is gated by a Transition Definition — Authority + Policy + (in the full model) Quality Gates + Reviews + Evidence + Obligations. Same mechanism we built, just with more prerequisite types wired in.
On success, an Event publishes. This is the only way other Capabilities learn anything changed.
The coordination model is the important part. Capabilities never talk to each other directly — no participant-to-participant messaging, ever. Everything routes through shared state: the Deliverable, its dependency edges, Services, Evidence, Knowledge, Decisions, and the Event Bus. A Capability's Participant produces a Deliverable → an Event publishes → the Dependency Engine re-evaluates → some other Capability's Deliverable may now be Ready → that triggers its Capability Fulfilment/Dispatch/Execution cycle. This is Book 1's Capability Reasoning Network: many independent per-Capability reasoning loops (Organisational Reasoning Cycles), coupled only through shared state, never through conversation. It's also why Participants are swappable without breaking anything — none of them hold state that matters; the Deliverable graph and Knowledge model do.

So "the organisation as a construct" is the Dependency Graph plus the set of Capabilities it requires plus the governance layered on transitions. There's no orchestrator role sitting above it deciding what happens next — "what happens next" is just whatever the graph says is Ready.

The actual gap between that and what we built
Being precise about it: we have the Dependency Graph, the readiness evaluation, and the governed-transition mechanism — the skeleton. What's entirely missing:

Nothing watches for "Ready." No automatic trigger fires Capability Fulfilment or Dispatch when a dependency becomes satisfied. A human has to notice and act, via the UI or API, for every step.
No Execution Engine, no Commands, no Work Items. We go straight from "someone decided to transition this Deliverable" to "check if it's allowed" — there's no modeled step of work actually happening in between.
No Dispatch Engine. "Assignment" is a person naming a Participant, not the system selecting one from eligible candidates for a specific piece of work.
No executor. This is the biggest one. Nothing in the codebase actually invokes an AI model, queues a human task, or calls an external system. Creating an "AI" Participant today doesn't make anything AI happen — it's a label on a row.
Closing that gap, in rough order, would mean: an event-subscriber (our eventBus already supports this) that reacts to dependency-satisfied events and runs Capability Fulfilment automatically; a minimal Dispatch step (round-robin over the eligible pool is explicitly sanctioned as MVP-acceptable); a genuinely ephemeral Work Item representation (not a table — just a context object passed to whatever executes it); and, the real substance, an executor per Participant Type — an LLM-invocation adapter for AI Participants that takes the Work Item's context and produces Evidence, a notification/queue for Human Participants, and an Interaction Adapter for External ones. Only once that exists does "commissioning an SEU" turn into work actually getting produced rather than a governed but inert data model.
