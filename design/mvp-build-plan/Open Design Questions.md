

# Open Design Questions

*Running log of design questions surfaced by building and testing the MVP, deliberately not resolved now — each is a real fork in how the full system (beyond this MVP) should behave, not a bug. Resolve these when the relevant fuller subsystem gets built, not before; recorded here so they aren't lost or silently decided by accident.*

---

## 1. Does a Deliverable's dependency gate *every* transition of it, or only the specific transition that needs the dependency?

**Surfaced:** 2026-08-03, while investigating a reported "Dependency Engine doesn't gate transitions" observation (see `design/observations/mvp1.md`) that turned out to be a display bug, not a gating bug (fixed same day — `getSeuDetailView` now recomputes edge readiness against live data before rendering, instead of reading the stored `readiness_state` column raw). Fixing that display bug is what surfaced this separate, still-open question underneath it.

**The question:** Architecture Document has one dependency edge — on Requirements Specification reaching `Approved`. As implemented, `dependencyEngine.isDeliverableReady()` checks *all* of a Deliverable's outgoing edges before allowing *any* transition of it, regardless of which target state is being requested. So today, Architecture Document can't even move `Defined → In Progress` (start work) until Requirements Specification is fully `Approved` — not just its own eventual `→ Approved` step.

Is that the right semantics, or should starting work be allowed to proceed in parallel, with only the transition that actually *needs* the upstream artefact gated on it?

- **Current MVP behavior (conservative):** nothing about a Deliverable moves until every one of its dependencies is satisfied. Simple, safe, but doesn't reflect how engineering often actually proceeds — architecture drafting frequently starts against a not-yet-finalized requirements spec.
- **Alternative (per-transition scoping):** a dependency edge would need to declare *which* transition it gates (e.g., "requires Requirements Specification Approved before Architecture Document can reach `Approved`", not before it can even reach `In Progress`). This is a real schema change — `dependency_edges` would need to carry a target transition (or target state), not just apply blanket-wide to the owning Deliverable.

**Why this waits for the full system, not this MVP:** the honest answer depends on machinery this MVP doesn't have yet — Work Items/Commands (Ch.31/32) that would let multiple Participants work on dependent Deliverables concurrently, and the Workflow Runtime that the platform's own dashboard already labels "partial" for exactly this reason ("Dependency Engine sequences Deliverables; no separate Workflow abstraction"). Deciding this now, against the MVP's flat two-Deliverable seed data, risks guessing at a shape the fuller execution model would just have to redo.

**Resolve when:** the Execution Engine / Work Item / Dispatch Engine layer gets built (see the orchestration-gap discussion in this session — Book 3 Ch.31–33), since that's what would actually let "start work in parallel, gate only the final transition" mean something operationally, rather than being a schema change with no behavior behind it.

## 2. Reactivating a terminal-state Pack: is a bare patch-version bump the right default, and should it repoint anything that referenced the old Version?

**Surfaced:** 2026-08-04, Phase 9 (Pack Platform maturity), fixing a bug where `compositionEngine.compose` silently composed Deprecated/Retired/Archived Packs exactly like Active ones. Making composition Active-only correctly meant `platform-core-engineering` — genuinely `Archived` in the dev DB by that point, from hand-testing the Pack Registry's lifecycle controls — could no longer be composed, and every fresh commissioning against `template-web-application` stopped including it at all. Fixing *that* required allowing a terminal-state Pack to come back to Active, which this entry covers.

**What was decided for now:** `transitionPack` (`core/packs.ts`) allows `Deprecated`/`Retired`/`Archived` → `Active`, gated by the same `power`-role Authority Rule as every other "elevated" Pack transition. Per Ch.41 VM-002 ("Versions are immutable"), this never flips the old row's status back to Active in place — `reactivateAsNewVersion` publishes a **new** Version carrying the same `name`/`category`/`installationClassification`/`contributions`/`dependencies` as the old row, with the patch number auto-bumped (`1.0.0 → 1.0.1`, walking forward past any collisions) until an unused `(code, packVersion)` is found, then runs it through the normal Draft → Validated → Published → Active pipeline — which also supersedes whatever else is currently Active for that code, same as any other activation. The original row is never touched.

**One thing this left genuinely open is now resolved; one remains:**

1. **Is "always bump the patch number" the right default?** Reactivating a Pack is really "republish what used to be there" — a patch bump matches semver convention for "no functional change, just republishing" as long as that's actually true. But nothing here checks whether the *reason* something was Deprecated/Archived (e.g. a real defect, a security issue in a contributed Policy) still applies to the reactivated content — it silently republishes the exact same `contributions` payload with a new label. Should reactivation require re-authoring through the SDK (Draft, edit, then publish as an intentionally-new Version), rather than being available as a one-click "bring it back" transition at all? **Still open.**
2. ~~Reactivation doesn't repoint anything.~~ **Resolved 2026-08-05** (`013_template_profile_pack_by_code.sql`). `template_packs`/`profile_packs` pinned a *specific Pack row id*, not a code — reactivating (or, the actual bug report that forced this fix: archiving-then-republishing) `platform-core-engineering` created a new Active row with a new id, but anything still pointing at the old id via row-pinning found nothing to fall back to and just silently stopped composing. Fixed by storing the Pack's `code` instead: `compositionEngine.compose` now resolves each Template/Profile Pack reference via `packsDB.findActiveByCode` fresh at every commissioning (the same lookup `publishPack`'s own supersede step already used), not a frozen row. A new Active Version under an existing code — whether from reactivation or an ordinary new release — now composes automatically, with zero manual repointing and no separate "report which Templates are stale" mechanism needed, since there's nothing left to go stale. Existing SEUs are unaffected either way: an EBM's `composedPacks` is a permanent snapshot taken once at commissioning, never re-read against a Pack's live status afterward — this only changes how a *future* commissioning resolves a Template/Profile's Pack references.

**Why item 1 still waits:** it's about what "Pack Platform maturity" means once Packs are authored and republished by real operators over time, not at first-publish — squarely Phase 9/10 territory (Pack SDK authoring workflow, and whatever Phase 10's Security Architecture depth ends up saying about who's allowed to make this kind of call). Deciding it now, against a single hand-tested repro, risks guessing at a shape a fuller Pack-authoring workflow would just have to redo.

**Resolve when:** revisited during Phase 9 (if extended) or Phase 10, per the request that logged this question.

## 3. Quality Gates now apply to every SEU-scoped entity type — except Pack and Objective, which structurally can't

**Surfaced:** 2026-08-04. A direct code-reading finding, not a repro: `qualityGateEngine.evaluate` was called from exactly one place in the entire codebase — `transitionDeliverable`. Every other governed entity type (Pack, Objective, Obligation, Evidence, Knowledge, Decision, Attention Item, External Interaction) transitioned on Authority + Policy alone, with no Quality Gate or mandatory-Evidence/blocking-Obligation precondition possible, even though `quality_gates.entity_type` was never actually restricted to `'Deliverable'`. Ch.29 §10 states every Transition Definition **shall** specify "applicable Quality Gates," "required Reviews," "mandatory Evidence," and "blocking Obligations" — not just Deliverable's.

**What was fixed:** two changes, chosen as the largest of three offered scope options (wire the call everywhere / also make Obligation-Evidence-Decision polymorphic / just log it):

1. **Obligation, Evidence and Decision became polymorphic.** The real reason Quality Gates could only ever mean anything for Deliverable transitions: `qualityGateEngine`'s two criteria types (`no_unresolved_obligations`, `requires_accepted_evidence_or_approved_decision`) resolved these three by a single required `deliverable_id` FK — nothing could attach an Obligation to a Knowledge Item, an Attention Item, or anything else. `obligations`/`evidence`/`decisions` now carry `related_object_type`/`related_object_id` instead (migration `011_polymorphic_governance_objects.sql`), the same pattern `attention_items` already used and for the same reason — no FK constraint is possible once the related object can be any governed entity type. Every existing row was Deliverable-attached (the only shape the old schema allowed), so the migration backfills `related_object_type = 'Deliverable'` before dropping the old column. Web forms are unchanged (Obligations/Evidence/Decisions are still only ever created against a Deliverable through the UI) — the polymorphism is available to any caller, but nothing yet exercises it except the SDK/API layer and this fix's own tests.
2. **`qualityGateEngine.evaluate` is now called from every SEU-scoped `transition*` core function** — Obligation, Evidence, Knowledge, Decision, Attention Item, External Interaction — the same two-call pattern (`qualityGateEngine.evaluate` before `transitionEngine.evaluate`) `transitionDeliverable` has always used. Proven end-to-end (not just wired-and-hoped) in `tests/quality-gate-generalization.test.ts`: a real Obligation attached directly to an Attention Item genuinely blocks that Attention Item's own transition, using a real Quality Gate row, and unblocks once resolved.

**What's still structurally impossible, not just deferred:** **Pack and Objective transitions cannot go through `qualityGateEngine.evaluate` at all**, discovered while implementing this fix, not before. `quality_gate_evaluations.seu_id` is `NOT NULL` — every evaluation must be attributed to a SEU. Pack has no `seu_id` at all (it's platform-wide, not SEU-scoped); Objective has no `seu_id` either (an Objective can precede, or outlive, any number of SEUs commissioned against it). There is nowhere to record an evaluation for either. This is documented directly in `core/packs.ts`'s and `core/objectives.ts`'s own `transitionPack`/`transitionObjective` doc comments, not silently skipped.

**Why this waits:** making Pack/Objective Quality-Gate-capable means either (a) making `quality_gate_evaluations.seu_id` nullable and deciding what a SEU-less evaluation record even means for Telemetry/Attention Item raising (both currently assume a SEU), or (b) inventing a different evaluation-record shape for SEU-less entities — either is a real, separate design decision, not a follow-on of this fix.

**Resolve when:** revisited during Phase 10 (Security Architecture depth) or whenever Pack/Objective governance actually needs a real precondition beyond Authority + Policy — nothing built so far needs it.

## 4. Template and Profile are now authored under real governance (SDK UI Layer Plan) — but the underlying row still isn't immutably versioned like Pack

**Surfaced:** 2026-08-06, building the SDK UI Layer Plan's Template/Profile authoring surfaces. The plan's own Template section says "reaching Baselined is what registers the real, immutable Template version" — but `templatesDB.upsert`/`profilesDB.upsert` still do a plain `ON CONFLICT (code) DO UPDATE`, overwriting the same row in place. Re-publishing a Template/Profile through the new authoring UI (`publishTemplate`/`publishProfile`, `core/templates.ts`/`core/profiles.ts`) mutates the existing row exactly like the old seed-script path always has — `template_version`/no version column at all on `profiles` sit unused. Pack's own `(code, packVersion)` immutable-versioning (Ch.41 VM-002) was never retrofitted onto either.

**What was fixed:** the authoring *workflow* now has real governance — Create/Review/Approve/Publish through Deliverable's own lifecycle, Quality-Gate- and Authority-checked, exactly like the plan specifies. What wasn't touched: the *artifact's* own mutability. A second "Publish" of the same Template code today still silently overwrites the first version's row, with no history kept and no `findActiveByCode`-equivalent needed (there's only ever one row per code).

**Why this waits:** giving Template/Profile the same `(code, version)` immutable-versioning as Pack — a new composite key, a real `findActiveByCode`-style resolution, deciding what "Active" even means for a Template that nothing else references by version — is real, separate schema and engine work the SDK UI Layer Plan doesn't spec out. Deciding it now, against the first two authoring surfaces built, risks guessing at a shape Pack's own Ch.41 pattern would just have to redo.

**Resolve when:** a real re-publish scenario actually needs history (someone wants to see what a Template looked like before an edit, or two SEUs need to have been commissioned against provably different Template versions) — nothing built so far needs it, same reasoning as item 2's still-open first question.
