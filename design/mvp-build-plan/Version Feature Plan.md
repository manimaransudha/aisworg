# Implementation of Version Management

This refers to the specifications in design/foundations/03_Book 3 (Refined)/06_Part 6/Chapter 41.md and design/foundations/03_Book 3 (Refined)/06_Part 6/Chapter 29.md

Revision and Versioning is happening at the point where engineering artifacts are created and transition happens. 

Version management has to be a service. Whenever a version is required, requireVersion() has to be used. 

What this also implies is to review the lifecycle states of the entities and the Events & makr which ones go through revision vs versioning. I took a stab at the Objectives (Chapter 1) design/foundations/03_Book 3 (Refined)/Events and Lifecycles.md

The codebase realizes Version Management in `ebmsDB.ts`, `packsDB.ts`, `templatesDB.ts`, `profilesDB.ts`, and `policyDefinitionsDB.ts`.


## Resolved framing

Chapter 41 §9's 7-stage chain is a generic vocabulary for explaining the chapter, not a literal state machine every artefact walks — each entity's own chapter lifecycle is final (Sudha). What matters is Version *event* emission: each entity's own Versioning column (Events and Lifecycles.md) says which Version event, if any, its domain event also constitutes.

**Governing rule**: the entity chapter's own defined lifecycle always supersedes Chapter 41's generic one. If a generic stage (e.g. "Validated") has no corresponding real state in that entity's own chapter, it does not apply to that entity — it is not a gap to fill in. Objective is the concrete case: its chapter-defined lifecycle is Proposed→Active directly, with no Validated state in between, full stop (Sudha).

## Design

### 1. Versioning column convention

Each transition row in Events and Lifecycles.md carries one of:
- **blank / `No`** — a pure Revision. Mutable, untraceable, no event of any kind (per the note at the top of that file).
- **a literal Version event name** — `VersionCreated`, `VersionValidated`, `VersionPublished`, `VersionActivated`, `VersionDeprecated`, `VersionSuperseded`, `VersionArchived` (Chapter 41 §15's own vocabulary). When the transition's domain event fires (e.g. `ObjectiveActivated`), this Version event fires alongside it.

This column is the single source of truth for "does this transition touch Version Management," per entity, per transition.

### 2. Where the declaration lives in the schema

Rather than a new registry to keep in sync with Events and Lifecycles.md by hand, the Versioning column should become a real column: `transition_definitions.version_event` (nullable text, one of the 7 names above). Every transition already resolves through `transition_definitions` (`transitionEngine.evaluate`, `transitionDefinitionsDB`) — this makes "mints a version" a property of the transition itself, next to `verb`, `required_policy_ids`, `creates_obligation`, not something re-derived per entity or per DB file.

### 3. Schema change: `transition_definitions.event_type` + `version_event`

No new table. Two new nullable columns on `transition_definitions`, replacing the hardcoded per-entity event maps (`OBJECTIVE_TRANSITION_EVENT` in `objectives.ts`, and its sibling maps for Pack/Template/etc.):
- **`event_type`** — the literal domain event name this transition produces (e.g. `ObjectiveActivated`). This has to live in data, not be derived from `toState` at call time, because it isn't mechanical for every transition — Reject→`ObjectiveRejected` is fine, but Achieved/Retired/Archived are past-tense-verb exceptions the `objectives.ts` code already calls out explicitly. Once it's a column, `transitionObjective` (and its equivalents) publish whatever `event_type` the resolved definition carries — the local map goes away entirely.
- **`version_event`** — nullable, one of the seven Chapter 41 §15 names (`VersionCreated`, `VersionValidated`, `VersionPublished`, `VersionActivated`, `VersionDeprecated`, `VersionSuperseded`, `VersionArchived`), or null for a transition that's a pure Revision.

`transitionEngine.evaluate`'s returned `TransitionOutcome` needs both surfaced — it already resolves the `transition_definitions` row internally but today only returns `createsObligation` and `authorityBadge` from it. Callers need `event_type` to publish and `version_event` to know whether the transition is version-significant.

**Submit/queue steps are a separate case.** Row 3 (Objective's "Queue to Validate") isn't its own `transition_definitions` row — it's the `submit_verb` attribute already living on the Proposed→Active row, and it's fired by `submitObjective` → `triggerEngine.submit()`, which publishes `${entityType}${fromState}` directly and never calls `transitionEngine.evaluate()` at all. Now that `VersionCreated` is confirmed to sit on this step (not on row 1/creation), that row needs a `submit_version_event` column alongside its existing `submit_verb`, and `triggerEngine.submit()` (or its caller) needs to read and act on it — the `TransitionOutcome` surfacing above doesn't cover this path.

### 4. Version history — a read, not a write path

With `event_type` and `version_event` both real columns, "the version history of entity X" is answered by filtering `events` for `originating_object_id = X` down to the `event_type`s that `transition_definitions` marks with a non-null `version_event` for that entity type, ordered by `created_at`. Each row already carries actor, authority badge, and timestamp (`eventBus.publish`'s existing `PublishInput`), and is already immutable once published (Ch.30 §9). No `versions` table, no `requireVersion()` write path, no new service — the two declared columns plus this read pattern are the whole mechanism.

The entity's own row remains the version's content and identity (`id`, its own `version` field, `status`, `created_at`, `requested_by`/publisher) — already frozen the moment it leaves its editable draft state, by whatever edit guard that entity already enforces (e.g. `updateObjective`'s `status !== "Proposed"` check). Nothing new needs to freeze it.

**Deferred**: Chapter 41 §8's "Parent Version" / "Superseded By" fields don't have a home on any entity table yet. Since Supersede (row 7) and Retire (row 8) aren't implemented for Objective yet either, that linkage is deferred alongside that work rather than designed now.

## Implementation steps

Done once, platform-wide, already in place: `transition_definitions.event_type` / `.version_event` / `.submit_version_event` (migration 183) and `transitionEngine.evaluate()` surfacing `eventType`/`versionEvent` on its outcome. A new entity needs none of that added — only its own rows populated and its own `core/<entity>.ts` wired to use them.

For every chapter defining lifecycle states and events (Chapter 1 – Objective is the worked reference; Chapter 5 – Pack is the second):

Use the worked examples tests/objective-event-lifecycle-table.test.ts, tests/pack-event-lifecycle-table.test.ts for reference. 

1. **Create/correct the States and Transitions section** in Events and Lifecycles.md against the actual Book 3 chapter — not against another entity's already-drafted table. Read the chapter's own lifecycle (§11-ish), events (§15-ish), and — if it has one — its own "Implementation Specifics" (§19-ish) section; the latter is often more reliable than re-deriving badges/events from code by hand (Chapter 5 §19.13 gave Pack's real badge table directly). Watch for copy-paste leftovers from whichever entity's table was drafted first (Pack's rows 9-10 were literally Objective's "Achieved" content, and its Implementation notes said "objective" — both wrong).
2. **Identify implementation gaps — concur before closing any.** Check the entity's real TS status/type union, its live `transition_definitions` rows (query the DB directly), and any hardcoded per-status event map in `core/<entity>.ts`. A gap the table implies isn't necessarily real: Objective's "Validated" state and Pack's "Queue to Validate" submit step both turned out to be *not* gaps once checked against the entity's own chapter/decision — always confirm before building. Whether the entity gets a submit/queue step at all is its own decision per entity, not automatic from Objective's precedent.
3. **Update `transition_definitions` rows for the entity** — a migration (new numbered file, applied *directly*, never via `pnpm migrate:seu`'s full replay — fragile against a live DB) with `UPDATE ... SET event_type = ..., version_event = ...` for each real row, plus the JSON seed (`src/dblayer/seed/data/transitionDefinitions.json`) so a future `db:clean-slate` also picks it up.
   **Gotcha**: if you reseed via `pnpm seed:transition-definitions` (wipes + rebuilds the *whole* table from the JSON) to pick up a JSON edit, it does **not** set `verb` — that's `pnpm seed:authority-vocab`'s job, and it must run immediately after, in that order, or every entity's badge checks go dark (`verb` NULL) until it does. Prefer a narrow, hand-written `UPDATE` on just the entity's own rows over a full reseed when possible.
4. **Code changes, mirroring `objectives.ts`**: remove the entity's own hardcoded `*_TRANSITION_EVENT`/`EVENT_BY_TARGET_STATE`-style map; publish `gate.eventType` (from `transitionEngine.evaluate()`'s outcome) instead. If the entity's `transition*()` function doesn't pass `entityId` to `evaluate()`, add it — Pack's didn't (a latent bug, harmless until something needs the `submit_verb` gate, then silently blocking).
5. **Check the event pub/sub rule — actually re-read every function that calls `eventBus.publish()` for this entity** (creation + every transition), don't assume it's clean. If there's code after the publish call, fix by *reordering* (move it before publish) when it doesn't actually depend on the event having fired — that was sufficient both times so far. Don't convert it into an async subscribed handler unless callers genuinely don't need it to have finished synchronously; Pack's `materializeContributions` (renamed from `seedContributions` — a naming collision with the unrelated `db:clean-slate` seed scripts, not itself a seed script) is relied on synchronously by `advancePackLifecycle`'s next hop, so reordering was the only safe fix.
6. **Update/create the test file**, mirroring `tests/objective-event-lifecycle-table.test.ts` / `tests/pack-event-lifecycle-table.test.ts`: a DEFINITION test (loop the entity's real `transition_definitions` rows, assert `event_type`/`version_event`/`submit_verb` against the corrected table) plus DRIVEN tests (call the real create/edit/transition functions, assert the actual published events via `eventsDB.findByOriginatingObject`). Use `actorId: "1001"` to drive governed transitions — the existing test fixture actor every other test file already uses, holds broad/root badges.
7. **Run the test suite** — the full suite and `db:clean-slate` are run manually by the user, not started by Claude unprompted; Claude runs the new/targeted test file(s) plus `pnpm typecheck` directly during implementation, as normal build-it-correctly diligence.
8. **Update the chapters** (manual, not by Claude) — once tested, the corrected States/Transitions section moves into the real Book 3 chapter file as source of truth.
