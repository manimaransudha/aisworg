# Participant Lifecycle Governance — Plan

*Book 3 Ch.13 (Participant Model). Written 2026-08-06 after reading the actual live code — `participants` already carries Ch.13's exact lifecycle as a schema constraint, but nothing governs it. Same shape of gap Phase 1 (Objective) and Phase 9 (Pack) already fixed elsewhere: the schema anticipated real governance before any of it was wired up.*

***Done, 2026-08-06 — all four Build order steps, full regression suite green (110/110, up from 104/104 before this plan). Verified against real dev data (`tests/participant-lifecycle.test.ts`, 5 tests) and a live DB spot-check: real Participants created in the same session now land across `Available`/`Idle`/`Archived`, not uniformly `Assigned` as before the fix.***

## What's already real

- **`participants`** (`002_seu_platform.sql`) — real identity: `id`, `seu_id`, `type` (`AI`/`Human`/`External`), `display_name`, and a `state` column whose `CHECK` constraint is *exactly* Ch.13 §9's lifecycle (`Created`, `Available`, `Assigned`, `Executing`, `Idle`, `Released`, `Archived`). `user_id` (added `014_sdk_authoring.sql`) links a Human Participant to a real platform login.
- **`capability_fulfilments`** (Ch.12) — the eligible-Participant pool: `seu_capability_id`, `participant_id`, `fulfilment_strategy`, `established_at`, `revoked_at`. `revoked_at` is already a real revoke primitive, just never called by anything today.
- **`fulfilCapability`** (`core/capabilities.ts`) is the only place a Participant is created — always bundled 1:1 with establishing a Capability Fulfilment in the same call. There's no standalone "create a Participant" path, by design.
- **`dispatchEngine`** reads `capabilityFulfilmentsDB.findActiveBySeuCapabilityId` to get a `participant_id` for a Work Item, and publishes `ParticipantSelected` when it does — but never reads or writes `participants.state` anywhere. That event is about a Work Item's dispatch selecting *a* participant, not about the Participant's own lifecycle — a distinction that matters for step 2 below.

## What's missing — the real gap

1. **`Participant` isn't a governed `TransitionEntityType`.** The union has 11 values; `Participant` isn't one of them. `participantsDB` has only `create`/`findById` — no update, no transition function. Nothing validates that a state change follows Ch.13 §9's legal lifecycle graph the way `transitionEngine` already validates it for every other entity type.

   **Correction, 2026-08-06 — the original draft of this item was wrong about what `state` actually does at creation, and the error changes what step 1 needs to do.** `participants.state` does have `DEFAULT 'Available'`, but that default is dead code: `participantsDB.create`'s `INSERT` hardcodes `state, ... VALUES ($1, $2, $3, 'Assigned', $4)` — a literal, not a parameter — at both of its only two call sites (`fulfilCapability`, `sdkAuthoring.ensureParticipantFulfilment`). So every real Participant today is born already `Assigned`, never `Created`, never `Available` — not "defaults to Available and never changes" as this section first claimed.

   This isn't cosmetic, and it lines up with Ch.13 §10 in a telling way: §10 draws a real distinction the current code collapses — "A Participant becomes eligible for a Capability only through Capability Fulfilment" (→ `Available`) versus "A Participant is assigned to a specific Deliverable or Work Item only through the Dispatch Engine" (→ `Assigned`). `fulfilCapability` *is* Capability Fulfilment; per §10 it should land a Participant at `Available`, not `Assigned` — the real `Assigned` transition belongs where step 3 already puts it, at `dispatchEngine` dispatch time. Today's code has two gaps (creation skips past the real first state; dispatch never sets `Assigned` at all) that happen to cancel out into something superficially plausible, not something that matches the chapter.

   **Decided:** `participantsDB.create`'s `INSERT` changes from a hardcoded `'Assigned'` to relying on the column's own `DEFAULT 'Available'` (i.e., drop `state` from the column list entirely, the same shape every other entity's `create` already uses — confirmed: `evidenceDB.create` and `obligationsDB.create` neither one lists `status` in their `INSERT` column list either, both rely purely on the table's own default, `'Collected'` and `'Identified'` respectively, their real Ch.17/Ch.23 first states). `Created` stays a conceptual-only node, the same way "before the row exists" is for every other entity in this codebase — none of them has a governed null-to-first-state transition, so Participant shouldn't either. This is folded into step 1 below, not a separate step: adding the governed lifecycle and fixing what creation writes are the same piece of work, since building step 1 against the current wrong initial value would just encode the bug into `transition_definitions`.

2. **None of Ch.13 §16's real events are published.** `ParticipantSelected` exists, but it's a Work Item dispatch event, not one of the eight Ch.13 actually names: `ParticipantCreated`, `ParticipantAssigned`, `ParticipantReleased`, `ParticipantActivated`, `ParticipantIdle`, `ParticipantReplaced`, `ParticipantArchived`, `ParticipantUnavailable`. None of these fire anywhere today.

   **One of the eight doesn't correspond to any node in §9's graph, and Ch.13 gives no further definition — noted here, resolved as held under step 5.** `ParticipantUnavailable` has no matching state; §9's graph is exactly the seven listed above, nothing named "Unavailable." §12 Participant State lists "availability" among several runtime-state fields a Participant maintains alongside `state` itself ("availability; assigned Deliverables; current Work Items; execution history; pending decisions; outstanding obligations") — read together with §9's silence, this points to `ParticipantUnavailable` being a runtime/health signal orthogonal to the governed lifecycle graph (an External/AI Participant found unreachable, say), not a transition. Ch.13 defines neither what would set it nor what "unavailable" concretely means operationally, so building real meaning for it here would be inventing behaviour the chapter doesn't specify — held, same treatment `createsObligation` got in the SDK plan (named, stored conceptually, not wired).

3. **No replacement mechanism** (Ch.13 §13, PM-001, FR-13.5/FR-13.6). `capability_fulfilments.revoked_at` is the closest existing primitive, but nothing calls it — there's no governed "replace this Participant" action.

4. **Assignment/Executing/Idle happen to the Work Item, not the Participant.** `dispatchEngine`'s Generated→Assigned→Executing→Completed→Disposed sequence (Phase 3) is the *Work Item's* lifecycle (Ch.32) — a different state machine, on a different row, from `participants.state` (Ch.13 §9). Easy to conflate reading the Phase 3 log casually; they're two separate chapters' worth of states. Nothing today moves the Participant's own `state` when its Work Items do.

5. **Multiple-fulfilment / a real Dispatch Strategy is separate, later scope** — `dispatchEngine`'s own comment already says so (Ch.33 §9, once more than one Participant can fulfil the same Capability). Participant lifecycle governance doesn't need that solved first; a governed lifecycle is meaningful even at today's 1:1.

6. **Autonomous AI execution is out of scope here too, and out of Ch.13's own scope.** §7: "the implementation technology is outside the scope of this specification" for AI Participants. This plan governs the lifecycle *record* — Created/Available/Assigned/Executing/Idle/Released/Archived as real, checked states — not what an AI Participant actually does while Executing.

## Principles (Ch.13 §5) — most already hold structurally; noted, not all need building

- **PM-001 Replaceable** — the real build item (step 4).
- **PM-002 Identity stable throughout lifecycle** — already true (`id`/`type`/`seu_id` are never written after `create`); state transitions in step 1 must not touch them.
- **PM-003 Shall not own engineering knowledge** — already true and confirmed, not assumed: `deliverables`, `obligations`, `evidence`, `knowledge_items`, `decisions` carry no `participant_id` anywhere in the schema. Only `capability_fulfilments.participant_id` and `work_items.participant_id` reference a Participant at all — nothing to build here, just worth having actually checked before relying on it in step 4.
- **PM-004/PM-005** (execute behaviour and fulfil Capabilities, don't define or own them) — already true architecturally; `participants` has no behaviour-defining or Capability-owning fields. No change needed.
- **PM-006 Independent of AI technologies** — same "small core" discipline used everywhere else in this codebase: the state machine built here is generic across all three Participant Types; whatever an AI Participant's actual execution logic eventually is stays outside this table.

## Build order

1. **Done, 2026-08-06. Fix creation, then make Participant a governed `TransitionEntityType`.** First, `participantsDB.create`'s `INSERT` stops hardcoding `'Assigned'` and relies on the column's own `DEFAULT 'Available'` instead (drop `state` from the column list, matching `evidenceDB.create`/`obligationsDB.create`'s shape) — a Participant becomes eligible for a Capability (`fulfilCapability`) at `Available`, per §10, not pre-assigned to anything. Then add `'Participant'` as the 12th `TransitionEntityType` value, same "zero new evaluation code" pattern every phase since Phase 1 has used — new `transition_definitions` rows encode Ch.13 §9's real graph (`Created→Available→Assigned→Executing→Idle→Released→Archived`, with the explicit repeat-cycle among `Assigned`/`Executing`/`Idle` §9 names; `Created` stays conceptual-only, matched by no row ever actually sitting in that state, the same as every other entity's unrepresented "before creation" point). `participantsDB` gains a `transition` method shaped like every other entity's (`obligationsDB`/`decisionsDB`, etc.). Migration widens the now-familiar `entity_type` CHECK union on `transition_definitions`/`quality_gates` — the same rerun-safety fix the last several migrations have each had to repeat for the same reason (`021_participant_lifecycle.sql` plus the same-union edit repeated across 003/006/007/008/009/010, matching the established discipline exactly). `participantsDB` gained `updateStatus`/`findBySeuId` (`transition` itself lives in the new `core/participants.ts`, matching where every other entity's own governed action lives — `transitionObligation`/`transitionEvidence`, not the dblayer). `transitionParticipant` (`core/participants.ts`) calls `transitionEngine.evaluate` directly with no separate legacy `qualityGateEngine.evaluate` pre-check — Participant is a brand-new entity type added after the SDK UI Layer Plan's generic Quality-Gate-in-`transitionEngine` mechanism existed, so there's no coincidental-match `quality_gates` row from before that mechanism to preserve. Verified live: a fresh Participant now lands at `Available` (`tests/participant-lifecycle.test.ts`), and a DB spot-check across Participants created in this session shows a real spread across `Available`/`Idle`/`Archived`, not uniformly `Assigned`.

2. **Done, 2026-08-06. Wire seven of Ch.13 §16's eight events**, off the new transition function from step 1 — the same way every other entity's transition function already publishes its own `<Entity>Transitioned` event, just under Participant's chapter-specific names (`ParticipantActivated`/`ParticipantIdle`/`ParticipantAssigned`/`ParticipantReleased`/`ParticipantArchived`). Publish `ParticipantCreated` at `fulfilCapability`'s existing create call too, alongside the `CapabilityFulfilled` event already there — not replacing it, since they're about different things (one is about the Capability being fulfilled, one is about the Participant now existing). `ParticipantUnavailable` is the eighth — not wired here, see held items below. Built as a lookup table (`CH13_EVENT_BY_TRANSITION` in `core/participants.ts`) rather than a 1:1 event-per-edge assumption, since the mapping genuinely isn't 1:1: `Available→Assigned` and the repeat-cycle `Idle→Assigned` both fire `ParticipantAssigned` (both mean "now Assigned"), and `Assigned→Executing` fires nothing — Ch.13 §16's own event list has no "started executing" event at all, so none was invented. Verified live: both `Available→Assigned` and `Idle→Assigned` fire `ParticipantAssigned` in the same test run, and `ParticipantCreated` fires from `fulfilCapability` alongside (not instead of) `CapabilityFulfilled`.

3. **Done, 2026-08-06. Connect Participant state to Work Item execution** — the one genuinely new piece of logic in this plan; everywhere else here is "the same pattern every other entity already has." When `dispatchEngine` moves a Work Item through its own Generated→Assigned→Executing→Completed→Disposed sequence, it should also move the assigned Participant's `state`: `Assigned` on dispatch (now the *only* place `Assigned` is ever set, per step 1's fix — not competing with a wrong initial value anymore), `Executing` when the Work Item starts, back to `Idle` (not `Available`) once Completed/Disposed — `Idle` vs. `Available` is exactly the distinction §9 draws between a Participant still held by an open Capability Fulfilment and one that's actually been Released. Implemented as direct `participantsDB.updateStatus` + direct `eventBus.publish` calls inside `dispatchEngine` itself, not a call into `core/participants.ts`'s governed `transitionParticipant` — this is an automatic system-driven state sync off dispatch's own simulated execution, the same "engine writes state, engine publishes its own events, engine never calls back into core" shape `workItemsDB`'s own state updates in this same file already use. Verified live over a real `transitionDeliverable` call (not just the engine in isolation): the fulfilling Participant ends the call at `Idle`, having passed through `Assigned` and `Executing`, with `ParticipantAssigned`/`ParticipantIdle` both observed on the event bus.

4. **Done, 2026-08-06. Replacement** (Ch.13 §13, PM-001, FR-13.5/FR-13.6). A governed old-Participant `Released → Archived` plus new-Participant creation, re-pointing the existing `capability_fulfilments` row's `participant_id` — reusing the `revoked_at` primitive already on that table rather than inventing a second one. Confirmed above, not assumed: `deliverables`/`obligations`/`evidence`/`knowledge_items`/`decisions` reference no `participant_id` anywhere, so nothing needs re-pointing there. `work_items.participant_id` on already-`Disposed` rows is a historical record of who executed a completed Work Item (Ch.32 WI-001/WI-003's transience) — correctly left untouched, not re-pointed. Replacement is structurally free at the data level; this step is the governed action plus its `ParticipantReplaced` event, not a data-migration problem.

   **Real gap found while building this step, resolved before writing code, not silently assumed:** Ch.13 §13 states "the platform shall permit replacement of *any* Participant" — but §9's own diagram draws only one edge into `Released` (from `Idle`), which would make replacement of an `Available`, `Assigned`, or `Executing` Participant ungoverned-impossible (`transitionParticipant` would reject it as `no_transition_definition`). Fixed by widening the seeded graph with three more edges into `Released` (`Available→Released`, `Assigned→Released`, `Executing→Released`, alongside the original `Idle→Released`) — `replaceParticipant` drives the old Participant to `Released` from whatever state it's actually in, then `Released→Archived`, both real governed `transitionParticipant` calls, never a bypass. `capability_fulfilments` gained `findActiveByParticipantId` and a real `revoke` method (the column existed since MVP; nothing had ever called it) — replacement revokes the old fulfilment row and creates a new one pointing at the new Participant, rather than mutating `participant_id` in place, which would have conflated two Participants' tenure into one row's `established_at`/`revoked_at` history. Verified live, including the case the graph fix exists for: replacing a Participant while it's `Executing` (mid-work, not just `Idle`) succeeds, ends the old Participant at `Archived`, and re-points the Capability Fulfilment to the new one.

5. **Decided 2026-08-06, not yet built: a small UI for step 4, framed explicitly as a placeholder adapter, not the final design.** `replaceParticipant` currently has no web/API route — the dry run flagged this as a real gap, not by itself a reason to build a UI. The actual reason: this is the seam where a deployment plugs in its own Participant-*sourcing* adapter — call the company's HR system to find the next available Human, call an AI orchestration platform to provision an agent instance — instead of a person typing a display name into a form. That's a genuinely different framing from "convenient manual testing," and it's not a new idea in this codebase: `dispatchEngine`'s trivial `sole-eligible-participant` strategy is already the same shape of thing for Participant *selection* (which existing Participant handles this Work Item) — an explicitly-named placeholder for a future Pack-contributed Dispatch Strategy framework (Ch.33 §9), deliberately held until there's a second implementation to generalise from. Sourcing is the same concern one level earlier, and correctly outside Ch.13's own scope too (§7: "the implementation technology is outside the scope of this specification").

   Build the manual form now — small, mirrors the existing Capability Fulfilment "Assign" form on the SEU detail page (participant type + display name → submit) almost exactly, one new route calling `replaceParticipant` directly, no new core logic. Do **not** build a generic adapter/plugin framework now — there's no second sourcing mechanism yet to generalise from, same discipline `dispatchEngine`'s own comment already applies to Dispatch Strategy. `core/participants.ts`'s `fulfilCapability`/`replaceParticipant` are already the stable interface a future adapter would call into instead of the manual form — building the form now doesn't foreclose that, the same way the trivial Dispatch Strategy didn't foreclose a real one.

6. **Held, explicitly out of this plan's scope:**
   - **`ParticipantUnavailable`** — no matching node in §9's graph, and Ch.13 defines neither its trigger nor what "unavailable" means operationally. Reads as a runtime/health signal (§12's "availability" runtime-state field) orthogonal to the lifecycle graph, not a transition — building real meaning for it now would be inventing behaviour the chapter doesn't specify. Same treatment `createsObligation` got in the SDK plan: named, not wired.
   - **Real Dispatch Strategy / multi-Participant-per-Capability (Ch.33 §9)** — already named as future scope by `dispatchEngine`'s own comment; not a prerequisite for lifecycle governance.
   - **Autonomous AI execution** — Ch.13 §7 itself puts "implementation technology" for AI Participants outside this chapter's own scope; this plan governs the lifecycle record, not what happens during `Executing`.
   - **Participant Type / Participant Instance split** — `002_seu_platform.sql`'s own comment already notes Ch.12 proposes this split but Ch.13's normative body never delivers it as two entities; not revisited here, same call the original schema already made.
