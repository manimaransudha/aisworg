# Participant Integration & Attestation — Plan

*Produced 2026-08-11. This resolves item 1 / line 122 of `Spec Gap Analysis and Remaining Build Plan.md` — the §3.5 "autonomous runtime" scope decision — and specifies the build that follows from it. Planning document, no code. Chapter references are to `03_Book 3 (Refined)`.*

## Resolved 2026-08-11 (review + decisions)

The original draft below was reviewed against the live code and refined. The resolutions supersede the specific decisions they name:

1. **Every transition is a dispatchable, async Work Item — there is no special "producer" vs "reviewer" machinery.** A Work Item is assigned to a Participant (human or AI) to drive a Deliverable toward one target state, carrying a VCS reference bound to that state. Producer and approver are the *same* mechanism; they differ only in which authority their transition requires. This replaces the producer/reviewer framing in Decisions 2–3 with one uniform rule. Approval is not a special path — it is just another transition, dispatchable to whoever holds the approver authority. (Confirmed with a worked example: a tenant user marks a Deliverable `In Progress`, hands an AI agent the input reference, the agent returns `reference + complete`, and the platform can then dispatch the *approval* as its own Work Item to a human.)

2. **The organising spine is "the state attached to the reference."** A reference is always bound to the state its Work Item drove toward. The Deliverable's authoritative state advances only when a governed *acceptance* transition actually fires; intermediate completions attach references without moving the authoritative state (a Deliverable stays `In Progress` until an approval transition lands).

3. **Raw reference and attestation are two distinct artifacts** (this corrects Decisions 4–5, which conflated them):
   - **Raw VCS reference** — candidate output the Participant supplies at completion. Nothing is certified; the platform just holds a pointer. Attached at production completion, stored durably (Work Items are transient per Ch.32, so the reference cannot live only on the Work Item).
   - **Attestation** — minted only at an *acceptance* transition (`In Progress → Approved`, `Approved → Baselined`), recording the governance outcome: "under SEU X's governance, this commit reached state Z by this authority." **New `attestations` table.**
   - *[Built 2026-08-11 (step 2), migration `023_attestation.sql`: the durable raw-reference home is a new append-only `deliverable_references` table (a row per completion, production and acceptance alike; also the Ch.20 traceability backbone for step 3). `attestations` is minted only at acceptance transitions and additionally records the certifying authority — `acting_badge_grant_id`, resolved at dispatch in `transitionDeliverable` and carried on `commands.acting_badge_grant_id` so `completeWorkItem` can stamp it. The empty-centre presence check reads `deliverable_references` for a real reference at `In Progress` before an approval can be dispatched (new `empty_centre` failure reason).]*

4. **The empty-centre bug is a separate, small fix, distinct from attestation.** It is a **presence check** on the acceptance transition (`In Progress → Approved`): a real reference must be attached before an approver can approve, so emptiness cannot be certified. Not a new gate criteria family, not attestation — just "you cannot approve nothing."

5. **The existing state machine is untouched — no new states.** `Defined → In Progress → Approved → Baselined` as seeded, with its already-distinct authorities (`authority-deliverable-creator` on `Defined → In Progress`, `authority-deliverable-approver` on the two acceptance transitions) providing separation of duties for free. `In Progress` *is* the "work underway / awaiting approval" state; no `In Review`/`Submitted` states are added. New transitions, if ever wanted, are authorable through the existing Transition Definition SDK UI (`/aisworg/seu/sdk/transition-definition-authoring`), not code.

6. **Async is uniform (human path too, no synchronous fast-path) but scoped to the Deliverable dispatch pipeline only.** Every other governed transition (Obligation, Evidence, Knowledge, Decision, Objective, Pack, Participant) is a direct synchronous state change with no Work Item and is untouched. The real cost is a contract change: `transitionDeliverable` stops returning the *moved* Deliverable — dispatch returns "outstanding," the transition lands later in the callback. This touches the Deliverable-transition tests and the SEU-detail UI. Bounded (one pipeline), named here so step 1 owns it.

7. **Attestation acts as accepted Evidence — the Baselining gate is extended, not moved.** The existing `requires_accepted_evidence_or_approved_decision` gate on `Approved → Baselined` is taught to also accept an attestation. No gate placement changes. *[Refined 2026-08-11 during step-2 build: the attestation is **not** accepted as satisfying the Baselining gate after all. Reaching `Approved` always mints an attestation, so accepting it would make the Baselining evidence gate a no-op for the normal flow — collapsing Approval and Baselining into one bar. Worse, an attestation certifies the specific commit that reached `Approved`; a later CR can change that code, so auto-baselining off the approval attestation would certify a stale artifact. Baselining stays a genuine second bar requiring its own fresh accepted Evidence or approved Decision. The attestation's role in step 2 is therefore **provenance + the empty-centre presence check on approval**, not Baselining-gate satisfaction.]*

8. **Minimal Phase-12 slice pulled forward.** The deployment-time config that this feature needs is genuinely tenant-scoped. A new `(tenant_id, capability_code, mode, adapter…)` execution-target table plus a `tenant_id` on `seus` (defaulting to a single seeded default tenant) so runtime can resolve "which tenant owns this SEU → which VCS binding / execution target." This is the *only* Phase-12 scope pulled forward; SEU/Deliverable/etc. do not otherwise gain tenancy here.

9. **`turnaround_time` is net-new (small), not reuse.** Ch.11 §8 names it and `service_level` is a permissive JSONB, but no seeded Service declares it — only `qualityBar` is ever populated. It is added as a real Service Level field; the SLA/timeout rides on it.

10. **The human-on-UI completion surface is a labelled stub.** Built now so the async loop is exercisable, but visibly marked in the UI as a tenant-specific placeholder — real tenants will replace it under the contract with their own callbacks/webhooks (and AI participants convey completion differently). Called out on the page itself.

11. **Model A — the callback drives the transition, uniformly (chosen 2026-08-11 on the decoupling test, not preference).** Every Work Item is outstanding *for* a target transition; when a `result-in {workItemId, outcome, ref}` arrives — from any edge (webhook, human form, agent, manual) — the core applies that transition on `done` or raises Attention on `failed`/`blocked`. The core never branches on *how* the result arrived or on *which kind* of transition it is; production, approval, and baselining completions are handled identically. This was chosen over Model B (dispatch sets `In Progress`; production completions only attach a reference and don't move state; only acceptance completions drive transitions) specifically because Model A keeps the core tenant- *and* transition-type-invariant: the edge only ever has to emit `{workItemId, outcome, ref}`, so a new tenant callback style or a manual path is a new edge adapter with zero core change. Model B would leak transition semantics (production vs. acceptance) into the core's completion handler and split state changes across two moments — the opposite of §0.1. "Stays `In Progress` until approval" (Resolution 2) still holds: a production completion lands the Deliverable at `In Progress`, and it does not advance to `Approved` until a separate approval Work Item completes.

## 0. The decision this settles

§3.5 of the gap analysis flagged the platform's "empty centre": commissioning, governance, dispatch, and state tracking are all real, but at the point where an assigned Participant would *do the engineering work*, `dispatchEngine` simulates the Work Item lifecycle synchronously (confirmed live: `WorkItemStarted → WorkItemCompleted` in ~100 ms, and an "Approved" Requirements Specification holding a state but no content). The open question was whether real execution belongs *in* the platform or *outside* it.

**Decision: execution is external, by design.** The platform is a governance, orchestration, and institutional-memory system. It never executes engineering work and never builds or deploys. Participants — human or AI orchestrator — execute in their own environment, which the platform is deliberately blind to. The "gap" is therefore not a missing execution engine; it is a missing **integration seam** between the platform and external Participants. This is consistent with the platform's own theory (Book 1: the organisation governs *behaviour*, not *competence*; Book 3 Ch.32: the Work Item is a transient artefact and the Deliverable's state is the sole authoritative record) and it makes the remaining work a bounded extension of machinery that already exists, not a green-field build.

## 0.1 Governing principle: stable core, replaceable edge

**The modules built for Participant Integration must stay as decoupled as they can be, because every tenant runs its own process in its own environment.** This is not a preference; it is the property that lets the platform take on new contracts without being rebuilt.

Think of a services firm. When Accenture contracts with Cigna, the Accenture team works inside Cigna's environment; when the client is KP, the same firm works inside KP's environment. The firm's identity, method, and governance do not change from one engagement to the next — only the environment it plugs into does. The platform must have that same advantage. Onboarding a new tenant, a new technology stack, or a new orchestrator must be an act of **plugging in a new edge**, never of changing the core.

The consequence for the build is a hard seam:

- **The core stays the same.** The state machine, dependency resolution, governance (authority/policy/obligation/quality gate), the attestation record, and the two-sided contract (assignment-out / result-in) are tenant-invariant. They must contain nothing specific to any tenant's VCS, orchestrator, auth scheme, or environment.
- **The edge is where everything tenant-specific lives, and it is expected to change.** Adapters, callback formats, VCS bindings, auth mechanisms, and signing formats will evolve as technologies and clients evolve. That churn must be absorbed entirely at the edge — new adapter, new callback shape, new credential type — with **zero change to the core**.
- **The test of the seam:** adding a tenant, swapping an orchestrator technology, or changing a callback format touches only edge modules and configuration. If any such change forces an edit inside the core, the seam is in the wrong place and must be moved before shipping.

Everything in §1 and §2 below is subordinate to this principle: the contract is defined once and held stable *so that* the edge can be replaced freely.

## 1. Decisions made (the design, and why)

1. **Execution is external.** Platform = governed state machine + dependency resolver + dispatcher + institutional memory + attestation authority. It governs and records; it does not perform, build, or deploy.

2. **Participants report outcome, not state.** A Participant marks a Work Item `done | failed | blocked` and attaches an output reference. It never names or proposes a target state. The platform decides and applies the transition — and it already knows the intended transition, because the Work Item was generated *for* a specific target transition (the Command that spawned it encodes it, Ch.31/Ch.32). The Participant stays ignorant of the state machine, exactly as an engineer joining an organisation doesn't need to know its internal governance graph.

3. **Separation of duties is preserved by authority-per-transition, not by asking the Participant to be modest.** "The platform decides the transition" honours no-self-certification *because* producer-completion and approval are modelled as **distinct transitions requiring distinct authorities**. A producer's `done` can only cause a transition its authority grant permits; the approval transition requires a different authority, so a producer's completion mechanically cannot land on `Approved`. It lands on a reviewable state (`In Review` / `Submitted`); a separate reviewer's Work Item or an evidence-backed Quality Gate performs the approval. The authority model that already enforces this everywhere else must hold at this boundary too. *[Superseded by Resolutions 1 & 5: there is no separate `In Review`/`Submitted` state. `In Progress` is the work-underway/awaiting-approval state, and producer versus approver differ only by the authority their transition requires, not by special machinery.]*

4. **VCS is the artifact substrate; the platform holds references, not bodies.** Whatever a Participant produces lives in the tenant's version control system. The platform holds a reference. The dry-run observation "the Deliverable has no content column" is correct-by-design; "the Deliverable has no *reference* either" is the actual gap this plan closes.

5. **The reference is per-Work-Item, and it is an attestation — not a build.** Each Work Item completion produces an immutable record binding *(SEU, Deliverable, transition, Participant, governance outcome, commit reference, timestamp)*. It is deliberately distinct from a build artefact: the same code line may have many commits/versions in many states, and a tenant's CI/CD may choose to "pull only platform-attested items at state X." The platform binds each *governed state change* to the exact commit that caused it. *[Superseded by Resolution 3: the raw VCS reference and the attestation are two distinct artifacts. The reference is candidate output attached at completion; the attestation is minted only at an acceptance transition. The reference is not itself an attestation.]*

6. **The platform records the SEU-scoped governance outcome; it is not a universal trust root.** The attestation is the platform's authoritative statement *about governance* — "under SEU X's governance, Deliverable Y reached state Z, produced by Participant P, referencing commit C." It makes no claim about build-worthiness or deploy-worthiness. What the tenant does with an attested Deliverable is the tenant's call. Cryptographic signing/verification format (so an offline CI/CD can verify without querying the platform) is a **tenant-driven consumption concern layered on top of the governance-outcome record**, not a core platform mandate — some tenants will simply query the platform; some will want a verifiable signed statement. The platform's responsibility ends at recording the outcome. This keeps the platform out of universal-PKI-trust-root scope while still supporting "pull only attested items."

7. **Attestation owns Traceability (Ch.20) as an explicit responsibility, not a byproduct.** Ch.20's functional requirements — forward navigation (FR-20.3), backward navigation (FR-20.4), impact analysis (FR-20.5), permanent provenance (FR-20.6/20.7) — become the **acceptance criteria of the attestation feature**. Each attestation is a provenance edge in the Engineering Knowledge Graph. Because attestations are immutable, "historical relationships never lost" and "provenance permanently available" come from the record's construction, not a separate retention mechanism. **Scope boundary:** attestation owns the *execution/artifact provenance backbone* — the previously-missing "who produced what, under what governance, at which commit." The traceability *query* joins that backbone with the structural relationships already in the schema (Objective→Capability derivation, Deliverable dependency edges, Evidence→Knowledge→Decision links, Obligation attachments). Attestation is the new edge type, not a replacement for the existing ones. Consequence: **Ch.20 is no longer a standalone phase** — it is delivered as this feature's query surface.

8. **Async failure and stalls are first-class.** Out-of-process execution can stall (a human on leave, an agent that hangs) or fail. A dispatched Work Item is now dispatched-and-waiting, not simulated. This pulls forward the Attention/scheduler escalation work the gap analysis had deferred (§4.5): a heartbeat/timeout on outstanding Work Items raises an Attention Item on stall (Ch.34), and an explicit failure follows the Ch.36 `Failed → Attention Item` path (partly built). The timeout budget is declared per Capability via the **Service Level** already on Service (Ch.11 §8, `turnaround_time`), not hardcoded. *[Refined by Resolution 9: `turnaround_time` is named in Ch.11 but never seeded, so it is added as a net-new Service Level field, not reused.]*

9. **Orchestrator-agnostic: one contract, thin adapters, tenant chooses the execution environment.** This is §0.1 applied. The platform defines one Participant Integration Contract. Each execution environment — a LangGraph agent, a bespoke orchestrator, or a human team on the platform UI — sits behind a thin adapter implementing that contract. The human path and every AI path are *identical from the platform's side*, which is the participant interchangeability Book 1 requires. Which environment fulfils a given Capability is a **per-tenant, per-Capability** choice — a Phase 12 (Multi-Tenancy) touchpoint — but the contract must be defined before tenancy so tenancy merely registers against it. The adapter, the callback shape, and the credential type may all change per tenant and over time; the contract and the core do not.

## 2. The Participant Integration Contract

### 2.1 Deployment-time declaration (what a tenant provides)

Four of these five extend models that already exist; only attestation config is genuinely new, and it is now light.

| # | Declaration | Where it lives | Notes |
|---|---|---|---|
| 1 | **VCS binding** | new tenant-scoped config | Provider/type; repo topology (how a per-Work-Item reference resolves — repo + ref + path); credentials for the platform to *read* input refs and *record* attestations. |
| 2 | **Per-Capability execution target** | extends **Capability Fulfilment (Ch.12)** | Fulfilment mode: `human-on-UI` or `external-orchestrator`. If external: adapter type + endpoint + outbound auth. Capability Fulfilment already binds a Participant to a Capability; this also binds *how that Participant is reached*. |
| 3 | **Callback authentication** | new, small | A credential the Participant uses to authenticate its result callback, so `done` is provably *this* Participant's — accountability at the boundary. |
| 4 | **Attestation config** | new (light — see Decision 6) | The governance-outcome record is always produced. This declares only what the *tenant* needs to consume it: query-only, or a signed/verifiable statement and its format. Not a platform-mandated PKI. |
| 5 | **Per-Capability SLA / timeout** | extends **Service Level (Ch.11)** | Max outstanding time before a stalled Work Item escalates to an Attention Item. Rides on `turnaround_time`. |

*Reconciled with the resolutions above: the row 2 execution target lives in a new tenant-scoped `(tenant_id, capability_code, mode, adapter…)` table (Resolution 8), not as an extension of `capability_fulfilments`; and row 5's `turnaround_time` is a net-new Service Level field (Resolution 9), not an existing populated one.*

### 2.2 Runtime contract (the two halves)

- **Assignment-out (platform → Participant):** Work Item id, the target transition, the input VCS references to pull (resolved from the upstream Deliverables' attestations via the dependency graph), the output location, the applicable EBM behavioural rules for this SEU, and the acceptance criteria.
- **Result-in (Participant → platform):** Work Item id, outcome ∈ `{done, failed, blocked}`, the output VCS reference, and optional evidence. Authenticated per declaration #3.

On `done`, the platform: records the attestation → treats the VCS reference as the accepted Evidence for the Trust Pipeline (Ch.17) → runs governance (dependency + authority + policy + quality gate, all built) → applies the transition *if the Participant's authority permits it* → the dependency engine surfaces newly-ready Deliverables → dispatch fires for the next Work Items. On `failed`/`blocked` or on timeout, the transition is not applied and an Attention Item is raised.

*[Superseded by Resolutions 2–4 & 7: a `done` attaches the raw VCS reference, but the authoritative state advances only when a governed acceptance transition fires (Resolution 2). An attestation is minted only at an acceptance transition, and the attestation (not the raw reference) is what the Baselining gate accepts as Evidence (Resolutions 3 & 7).]*

## 3. What is new vs. what is extension

**Extension of existing machinery:** the dispatch seam (`dispatchEngine`, `work_items`), the Command/Work Item generation (Ch.31/32), the dependency engine, the Evidence model and Quality Gate (Ch.17/26), the authority model (Ch.22), Capability Fulfilment (Ch.12), Service Level (Ch.11), and the Attention `Failed →` path (Ch.34/36). The state machine, governance, and dependency resolution are untouched.

**Genuinely new:**
- Making the Work Item **asynchronous** — dispatched-and-waiting rather than `simulate()`d synchronously (the one line that is fake today).
- The **per-Work-Item attestation** record (immutable, SEU-scoped governance outcome + commit binding).
- The authenticated **participant callback API** (`result-in`).
- The **orchestrator adapter interface** (tech-agnostic) plus the human-on-UI target.
- The **timeout/heartbeat** on outstanding Work Items → Attention Item.
- The **traceability query surface** over attestation + structural edges (owns Ch.20).
- The **deployment-time contract config** per tenant (the five declarations).

## 4. Build sequence

Naming continues the platform's phase scheme; this is the resolved form of the gap plan's §7 item 1, and it absorbs former §7 item 2 (standalone Traceability).

**Standing gate (§0.1 enforcement).** No step is done until its **core-invariance check** passes as well as its functional "done when." The core-invariance check is a single question asked of every step: *did this change touch only the tenant-invariant core (state machine, dependency resolution, governance, attestation record, the two-sided contract), or did any tenant-specific concern — a VCS, an orchestrator, an auth scheme, a signing format — leak into it?* Any leak fails the step regardless of whether the feature works. The check is enforced by keeping tenant-specific code in edge modules the core does not import, so a leak shows up as a forbidden import direction, not as a judgement call.

1. **Async Work Item + participant callback API.** Replace `dispatchEngine.simulate()` with dispatch-and-wait; add the authenticated `result-in` endpoint; a Work Item now has a real outstanding state. *Done when:* a Work Item can be dispatched to an external stub, left outstanding, and completed by an out-of-process callback that drives the governed transition — with a producer's `done` landing on a reviewable state, never `Approved`. *Core-invariance check:* the callback endpoint parses to the tenant-invariant result shape `{workItemId, outcome, ref, evidence?}` before anything downstream sees it; no VCS, orchestrator, or auth detail reaches the dispatch/transition core.
2. **Per-Work-Item attestation + VCS reference.** The immutable governance-outcome record bound to a commit reference; wired so the reference is the Evidence the Quality Gate consumes. *Done when:* completing a Work Item records an attestation, and the same reference satisfies an approval gate on that Deliverable. *[Superseded by Resolutions 3, 4 & 7: attestations are minted at acceptance transitions only. The empty-centre fix is a presence check on `In Progress → Approved` requiring a reference to exist before approval, and the Baselining gate is extended to accept the resulting attestation as Evidence; the raw reference does not by itself satisfy an approval gate.]* *Core-invariance check:* the attestation record stores the commit reference as an opaque, provider-agnostic value — the core never parses or resolves it; reference resolution lives in the VCS-binding edge module.
3. **Traceability query surface (owns Ch.20).** Forward/backward navigation, impact analysis, and provenance over attestation edges joined with existing structural edges. *Done when:* Ch.20's FRs pass against a real commissioned SEU — you can navigate a Deliverable to the commit and Participant that produced each state, and forward from a changed upstream artifact to everything it impacts. *Core-invariance check:* the query reads only platform-held records (attestations + structural edges) and makes no live call into any tenant VCS or orchestrator; it works identically regardless of which provider produced the references.
4. **Async failure/stall handling.** Heartbeat/timeout on outstanding Work Items → Attention Item; explicit failure → Ch.36 `Failed →` path; SLA sourced from Service Level. *Done when:* a Work Item that neither completes nor fails within its Capability's declared SLA raises an escalation Attention Item unattended. *Core-invariance check:* the timeout/heartbeat logic keys off the Work Item's outstanding state and the declared SLA only — it embeds no assumption about how or where the Participant executes.
5. **Orchestrator adapter interface + human-on-UI target.** One contract, two initial adapters (a reference external-orchestrator webhook adapter, and the human path). *Done when:* the same Capability can be fulfilled by either an external orchestrator or a human on the UI with no change to the platform-side flow. *Core-invariance check (the decisive one):* the two adapters share the same contract interface, the core imports the interface and never a concrete adapter, and adding a hypothetical third adapter would require no core edit. If wiring either adapter forced a core change, the seam is misplaced — fix it here before proceeding.
6. **Deployment-time contract config.** The five tenant declarations, per Capability where applicable. *Done when:* a tenant can register a VCS binding + per-Capability execution targets + callback auth + SLA + attestation config, and a commissioned SEU dispatches real work against them. *Core-invariance check:* two tenants with entirely different VCS providers, orchestrators, and auth schemes run on the same core with only their edge configuration differing — demonstrated by standing up a second tenant that shares no edge choice with the first.

## 5. Open decisions still to make

- **Attestation verification format (Decision 6).** The governance-outcome record is settled; whether the platform also emits a cryptographically-verifiable signed statement (and in what format — signed provenance, signed tag, sigstore-style) is a tenant-consumption question. It can be deferred to the first tenant that needs offline verification, but the record's *fields* should be designed now so a signature can wrap them later without reshaping.
- **Repo topology conventions.** One repo per SEU, per Capability, or bring-your-own-coordinates per Deliverable. Shapes declaration #1 and the reference format. Recommend leaving it tenant-declared (bring-your-own-coordinates) rather than imposing a convention.
- **Do the human path and AI path share one adapter interface, or two?** They share the contract; the question is whether the human UI is literally an adapter implementation or a first-class internal path. Recommend one interface, human as an internal adapter, to keep interchangeability real.
