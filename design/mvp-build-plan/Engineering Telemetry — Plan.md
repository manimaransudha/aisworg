# Engineering Telemetry — Plan

*Book 3 Ch.35. Separated out from `SDK UI Layer Plan.md` per Sudha's instruction not to combine the two. Written 2026-08-06 after reading the actual live code, not just the chapter or the `Post-MVP Build Sequence.md` phase list — that document still describes Phase 7 as future work; it isn't. A real baseline is already running.*

## What's already live — this corrects the "not yet built" framing

`Post-MVP Build Sequence.md`'s Phase 7 entry says Telemetry is deferred until Phases 3–6 exist to measure. Phases 3–6 are now built, and so is a real slice of Phase 7 itself — not a stub:

- **Flow Telemetry (Ch.35 §7) — Deliverable cycle time.** `deliverablesDB.findCycleTimes()` derives it from the `events` table (`DeliverableTransitioned` rows), platform-wide. Live.
- **Governance Telemetry (§7) — Quality Gate latency.** `qualityGateEvaluationsDB.findLatencies()` measures Blocked→Passed friction per gate, platform-wide. Live.
- **Sustained-pattern detection → Organisational Learning Obligation (§11, Ch.23 §7).** `checkSustainedQualityGateBlocking` — called from `deliverables.ts` on every Quality-Gate-blocked transition — raises an Obligation and an Escalation Attention Item (Ch.34 §7) once a gate has blocked the same SEU 3+ times. Live, one bottleneck type.
- **A real dashboard**, not just an API: `/aisworg/seu/telemetry` (web) and `/telemetry` (api), showing both categories.
- **The substrate this all reads from already exists and isn't being rebuilt**: the `events` table + `eventBus`, populated by Phases 3–6's own work. This is why ET-002 ("no engineering metric shall require duplicate data entry") is already satisfied for what's built — the plan below keeps reading from what's already recorded, never adds a parallel manual-entry path.

Everything below is genuinely the remaining gap against what Ch.35 itself specifies, not a restatement of Phase 7 as if it hadn't started.

## Principles carried forward from Ch.35 (§5) — nothing here should violate these

- **ET-001 Passive** — Telemetry never writes engineering state. The one existing exception, raising an Obligation on a sustained pattern, is the chapter's own mandated exception (§11), not a precedent for anything else to also write state.
- **ET-002 Derived** — every metric added below reads from data Phases 3–6 already produce (`events`, `quality_gate_evaluations`, Evidence/Decision/Knowledge rows, Command/Work Item records). None of this needs a new manual-entry screen.
- **ET-003 Systems, not individuals** — every new metric stays scoped to a Deliverable, SEU, Gate, Service, or Capability, never to a named Participant's throughput.
- **ET-005 / FR-35.2 Historical trends preserved** — not actually true yet even for the two live metrics: they're computed fresh from raw rows on every request, with no snapshot mechanism, so "historical" only holds as long as the raw `events`/`quality_gate_evaluations` rows are never pruned. Worth naming now so it isn't silently assumed solved.

## The real gap, mapped to Ch.35's own structure

1. **Metric structure isn't data yet — no Metric Registry (§8).** The two live metrics are hardcoded TypeScript functions, not declarative rows carrying Identifier, Name, Description, Category, Measurement Method, Aggregation Strategy, Time Window, Unit of Measure, Provenance, Version — the shape §8 actually specifies. FR-35.4 ("Telemetry shall support custom metrics contributed through Packs") can't be satisfied while metrics are compiled code — a Pack can't contribute a TypeScript function at install time.

   **Scope, resolved 2026-08-06:** this is a metadata catalog, not a computation DSL. The precedent isn't the Schema Registry (that generalises document *shape*) — it's `qualityGateEngine.ts`'s own `criteria.type` dispatch, already live: a metadata value (`criteria.type`) selects hardcoded evaluator code per type, and an unrecognised type fails closed. Metric Registry is the same shape: `metric_definitions` rows carry Identifier/Name/Description/Category/Unit/Version/Aggregation-Strategy-as-enum plus a `calculationMethod` code; the actual read-query stays a hardcoded TS function registered under that code. A Pack contributing a "custom metric" (FR-35.4) means a Pack declares a `metric_definitions` row naming a `calculationMethod` — same as a Pack declaring a Quality Gate that uses an existing `criteria.type` — not a Pack supplying a runtime-interpreted aggregation formula. A full computation DSL is explicitly out of scope.

2. **Only 2 of 6 telemetry categories exist (§7).** Flow and Governance are live. Of the rest, only what's actually backed by an existing entity or event is in scope here — named per category, not assumed wholesale from the chapter text:
   - **Knowledge Telemetry** — narrowed to **growth** and **Evidence generation**, both backed by real events (`KnowledgeObserved`/`KnowledgeUpdated`, `EvidenceCollected`). **Decision reuse and ontology expansion are dropped from this category, not deferred.** `decisions` rows carry one `deliverable_id` each — nothing tracks the same Decision being independently reached across more than one row, so "reuse" has no structure to read from yet. Ontology (Ch.18) isn't a smaller version of this problem, it's a different one: `007_trust_pipeline.sql`'s own comment says Ontology is "deliberately out of scope," so there is, by design, no entity there to ever measure under the current model — not a gap, a boundary. (Worth flagging forward, not building now: the matching logic "Decision reuse" would need — same content independently reached across rows — is the same matcher §11 bottleneck type (a) needs. If step 5 ever builds that matcher for pattern-detection, this metric likely falls out of it for free rather than needing its own build.)
   - **Runtime Telemetry** — narrowed to **Command generation rate, dispatch latency, Work Item execution duration**, all real signals off Phase 3's existing Command/Work Item event timestamps regardless of dispatch sophistication. **Participant utilisation is held, not built.** `dispatchEngine.ts:4-7`'s own comment: Capability Fulfilment is 1:1 per SEU Capability today ("nothing to optimise yet"), no real Dispatch Strategy (Ch.33 §9) until more than one Participant can fulfil the same Capability. Under 1:1, every Work Item trivially dispatches to the sole eligible Participant — there's no comparative load to measure, just a constant, not a curve. (Not the same blocker as §11 bottleneck type (d) capability shortage, below — shortage is `seu_capabilities.status = 'Unfulfilled'` persisting, which needs zero candidates, not comparison across multiple; it isn't held on this same dependency.)
   - **Quality Telemetry** — narrowed to **rework rate** and **Deliverable acceptance rate**, both derivable from data that already exists: rework rate is a count of Blocked evaluations before the eventual Pass per entity, sitting in the same `quality_gate_evaluations` rows Governance latency already reads (a different aggregation over the same table, not new data); acceptance rate is the `deliverables.lifecycle_state` distribution (% reaching `Baselined` vs. stuck/Archived), also already there. **Review effectiveness and defect escape rate are held, not built here** — there is no `Review` entity anywhere in `TransitionEntityType`, and the Deliverable lifecycle has no governed backward transition, so neither metric as Ch.35 names it has anything to measure yet. Introducing a real Review concept is bigger scope than this plan.
   - **Collaboration Telemetry** — lowest priority of the four; the least-defined measurement method in the chapter itself, held until the others are proven.

3. **Sustained-pattern detection covers one of the four bottleneck types §11 names.** The chapter's own examples: (a) the same architectural Decision independently reached across many Deliverables — not detected; (b) a Service chronically missing its declared Service Level — not detected; (c) a Policy repeatedly waived — not detected; (d) a capability shortage recurring across multiple SEUs — not detected, and would need cross-SEU scope (see 5, below). Only "Quality Gate blocked 3+ times in one SEU" is wired.

   **(b) and (c) aren't just undetected — nothing records the underlying occurrence at all, resolved 2026-08-06 as two different sizes of gap:**
   - **Policy waiver (c) is small and legitimately in scope for step 5.** `transitionEngine.ts:117-122` already evaluates a Standard policy's `satisfied` condition and, by its own comment, silently discards the result: *"Standard (non-blocking) deviations proceed — Ch.24 §11: they surface through Engineering Telemetry, which is deferred for MVP."* Recording that discarded value as an event is a one-line addition at a point that already runs and already has the value in hand — finishing a promise the code already names, not new manual data entry, so it doesn't strain ET-001/ET-002 the way genuinely new instrumentation would.
   - **Service SLA breach (b) is not.** `service_level` is a bare declared JSONB target on the Service row with no read path anywhere measuring actual performance against it, and no defined notion of what "breach" even means for an arbitrary declared target. That's a Service-model design question, not a Telemetry one — closing it is a real prerequisite, held out of step 5 into its own item below, not folded into "generalise the mechanism."

4. **The "sustained" threshold is a hardcoded constant, not the Pack-contributed policy §11 explicitly calls for.** `SUSTAINED_BLOCK_THRESHOLD = 3` in `core/telemetry.ts` — the code's own comment already flags this as a known simplification, blocked on Policy not yet having a general config-carrying role beyond gating transitions. Not solved by this plan; named so it isn't lost.

5. **No per-SEU breakdown — only platform-wide pooling, and no Cross-SEU Analytics (§13).** This is a deliberate, documented MVP scoping choice (`deliverablesDB.findCycleTimes`'s own comment: "same scoping choice as Engineering Capital, Phase 6"), not an oversight — but it means the chapter's own framing (*"the platform cares whether the SEU is healthy"*) isn't actually answerable per-SEU today, only in aggregate across every SEU at once. §13 Cross-SEU comparison needs per-SEU numbers to exist first; right now there's nothing to compare.

6. **No Engineering Health assessment (§10), no Predictive Telemetry (§12).** Both explicitly synthesize over categories and history that don't exist yet — correctly not attempted, listed for sequencing, not urgency.

7. **Telemetry Traceability (§14) and most of the Events list (§15) are thin.** Displayed metrics carry no calculation version or provenance. Of the seven events §15 names, only `SustainedPatternDetected` is published; `MetricCalculated`, `HealthAssessmentUpdated`, `BottleneckDetected`, `TrendIdentified`, `ThresholdExceeded`, `TelemetrySnapshotGenerated` don't exist yet.

## Build order

1. **Done, 2026-08-06.** `metric_definitions` table (`017_metric_registry.sql`), seeded with the two existing metrics against their own already-live computations. `metricRegistryEngine.compute(identifier)` (`domain/engine/metricRegistryEngine.ts`) dispatches `calculation_method` to hardcoded evaluator code, same shape as `qualityGateEngine`'s `criteria.type`; fails closed on an unknown identifier or an unrecognised method. `getFlowMetrics`/`getGovernanceMetrics` (`core/telemetry.ts`) now read through it — output shape kept identical on purpose, so the web dashboard, the API route, and the existing `tests/telemetry.test.ts` all needed zero changes and still pass. Publishes `MetricCalculated` on every computation (confirmed over real HTTP, not just in tests). New coverage in `tests/metric-registry.test.ts` proves the dispatch mechanism itself, isolated from the two real metrics' own numbers.
2. **Done, 2026-08-06.** `deliverablesDB.findCycleTimes`/`qualityGateEvaluationsDB.findLatencies` both gained an optional `seuId` filter (omitted = original platform-wide pooling, unchanged); `metricRegistryEngine.compute` threads it through as a `MetricScope`. The web dashboard gained a SEU picker (`All SEUs` default); the API route reads the same `?seuId=` query param. Confirmed over real HTTP that a scoped call returns strictly that SEU's own rows (1 of 1335 platform-wide Deliverables, in the smoke test) — not just that the code compiles. `MetricCalculated`'s payload now carries `seuId` too. §13 Cross-SEU Analytics remains held — this is per-SEU numbers existing, not a comparison view over them.
3. **Done, 2026-08-06.** `runtimeTelemetryDB.ts` — Command generation count, dispatch latency (`CommandGenerated` → `WorkItemDispatched`, correlated by `correlationId`), Work Item execution duration (`WorkItemStarted` → `WorkItemCompleted`, per Work Item id). Same `MetricScope`/`seuId` pattern as Flow/Governance, same `metricRegistryEngine` dispatch. Confirmed over real HTTP against real dev data: 2413 Commands, ~0.3s average dispatch latency, ~0.1s average Work Item duration — small, as expected (synchronous simulated execution), but genuinely non-zero and real, not degenerate the way participant utilisation would be. Dashboard gained a third section; API response gained `runtimeMetrics`.
4. **Done, 2026-08-06.** `knowledgeItemsDB.countByAcquisitionScope`/`evidenceDB.count` — growth is every Knowledge Item broken down by Acquisition Scope (deliberately distinct from Engineering Capital, which excludes SEU-scoped items), Evidence generation is a plain count. Confirmed over real HTTP against real dev data: 424 Knowledge Items (140 SEU / 239 Capability / 0 Enterprise / 45 Platform), 200 Evidence records. Same `MetricScope`/registry pattern as the other three categories.
5. **Done, 2026-08-06.** Prerequisite: `transitionEngine.ts` now publishes `StandardPolicyDeviation` at the exact point it already evaluated and discarded the value. `core/telemetry.ts`'s `checkSustainedQualityGateBlocking` was split into a shared `raiseSustainedPatternObligation` helper plus three thin callers — the original (unchanged behavior, still triggered inline from `transitionDeliverable`), `checkSustainedPolicyWaivers` (platform-wide scan of `StandardPolicyDeviation` events grouped by Policy+SEU), and `checkSustainedCapabilityShortages` (platform-wide scan of `seu_capabilities` grouped by Capability, across SEUs). **A real tension found and resolved while building, not anticipated by the plan's own text:** `obligations.seu_id` and `attention_items.seu_id` are both `NOT NULL` — a genuinely cross-SEU pattern (capability shortage) still needs *one* SEU to attach its Obligation to. Resolved by attaching to the most recently affected SEU as a representative instance, with the description naming the true cross-SEU count. Known, accepted limitation from that choice, confirmed happening exactly as predicted during smoke testing: if the "most recent" SEU changes between two checks, a second Obligation can get raised for the same underlying shortage under a different representative SEU — no platform-wide dedup registry was built to prevent this. Policy waiver and capability shortage are both triggered from the Telemetry web dashboard's own GET handler (non-fatal on error) — Telemetry itself is the natural trigger point for a pattern with no single owning transition to hang the check off, not a side effect threaded through the 9 already-migrated entity types' own core functions. Confirmed over real HTTP: a real Policy waiver correctly raised (and deduplicated on repeat) exactly one Obligation; capability shortage correctly detected "Requirements Analysis"/"Architecture"/"Development" each missing across 800+ real SEUs accumulated by this whole session's own test runs. Decision-reuse pattern-matching (a) remains a natural, not-yet-built follow-on.
6. **Done, 2026-08-06 — Quality Telemetry only; Collaboration Telemetry stays held**, per its own lowest-priority/least-defined status named earlier. Rework rate: `qualityGateEvaluationsDB.findReworkByEntity` — per entity that eventually Passed at least one gate, how many Blocked evaluations it accumulated first; `entitiesNeedingRework / totalEntitiesMeasured` is the rate. Acceptance rate: `deliverablesDB.findLifecycleStateDistribution` — `Baselined` count against the full distribution, not "accepted vs. rejected" (Deliverable has no Archived/rejected terminal state, unlike the plan's own "vs. stuck/Archived" phrasing — noted directly in the calculation method's own comment rather than silently building a bucket that doesn't exist). Confirmed over real HTTP against real dev data: 51% rework rate across 745 measured entities, 3% Deliverable acceptance rate (8222 Deliverables, most still `Defined`/`In Progress` — expected, given how this whole session's own testing accumulated data). Same `MetricScope`/registry pattern as every other category.
7. **Engineering Health (§10), Predictive Telemetry (§12)** — held. Both explicitly synthesize over categories that need to exist first; do not start these before step 6.
8. **Held, explicitly out of this plan's scope, each for a different reason:**
   - **The Pack-contributed "sustained" threshold (§11)** and the rest of §14 Traceability (calculation version, provenance) — revisit once Policy has a general config-carrying role, per the existing code comment's own note.
   - **Service SLA breach detection (b)** — blocked on a real Service-model concept of what "meeting the declared `service_level`" even means; a Service-model design question, not a Telemetry build.
   - **Review effectiveness, defect escape rate** — blocked on a real `Review` entity and a governed backward Deliverable transition, neither of which exists; bigger scope than this plan.
   - **Ontology-based metrics** — not held, dropped. Ch.18 is deliberately out of scope per Phase 5/6's own migration comment; there is no entity here to ever measure under the current model.
   - **Participant utilisation** — blocked on Ch.33 §9's real Dispatch Strategy framework; under today's 1:1 Capability Fulfilment there's nothing comparative to measure. This is a different blocker from capability-shortage detection (step 5) — shortage reads `seu_capabilities.status = 'Unfulfilled'`, which needs zero candidates to be meaningful, not multiple; it isn't gated on dispatch sophistication the way utilisation is.
