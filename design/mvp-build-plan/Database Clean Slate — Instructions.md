# Database Clean Slate — Instructions for the Other Session

*Written 2026-08-06 for whoever implements the actual reset script — not the script itself. Goal: a repeatable command (e.g. `pnpm db:clean-slate`) that wipes demo/usage data and test-fixture pollution, while leaving the platform in exactly the state it needs to be in for the SDK UI and every governed entity type to work immediately afterward — safe to run every time a clean slate is needed, not just once. This script has to be reviewed an updated every time we change the code/data model going forward to stay in sync*

## Update — 2026-08-12 (users + tenants now wiped; ownership prerequisite)

*Supersedes the "users … tenants must survive" guidance further down (§"What must survive every reset" and the sequence-reset note under §"Not addressed here").* Clean-slate is **dev/test-only — never run in production**, so it now wipes these too:

- **`users` — fully truncated (`cleanSlate.ts` step 1b, `TRUNCATE ... RESTART IDENTITY CASCADE`).** The god identity (`SUPERUSER_EMAIL`) is not a fixture to preserve — it is re-created automatically on the next login (`passportConfig` upsert + `badgeBootstrap` grants it `root`). `RESTART IDENTITY` resets the serial so that login comes back as **id 1**, matching the `NODE_ENV=test` auto-login shim and the `holder_id '1'` root grant `012_badge_model` seeds every boot. `CASCADE` covers the `requested_by`/`user_id` FKs (already emptied in step 1). This corrects the old "leave `users` alone / it's shared infrastructure" claim: `aisworg.public.users` is **this platform's own** auth table — the other application's users live in a **separate `endow` database** (Postgres-isolated), so wiping here cannot touch them.
- **Non-default `tenants` — deleted (`cleanSlate.ts` step 2d), plus their FK-bound dependents** (`tenant_contracts`, `execution_targets`, `tenant_concept_aliases`, tenant-variant `badge_types`/`badge_tiers`), in FK order. Only the migration-seeded `default` tenant survives. (`seus.tenant_id` is handled by step 1's truncate, which runs first.)
- **`badge_grants` is intentionally still left untouched** (per owner: "the badge can stay for now"). Grants whose `holder_id`/`scope_id` referenced a wiped user or tenant become harmless orphaned text (no FK); the `holder_id '1'` root grant remains valid for the re-seeded god user.

**Environment prerequisite (one-time per database, NOT tracked in code):** `RESTART IDENTITY` alters the sequence `users_id_seq`, which must be owned by the app role. If `users`/`users_id_seq` are owned by `postgres` (the original setup), clean-slate fails at step 1b with `must be owner of sequence users_id_seq` and rolls back cleanly (nothing wiped). Fix once, as the `postgres` superuser against the `aisworg` DB:

```sql
ALTER TABLE public.users OWNER TO weirdo;
ALTER SEQUENCE public.users_id_seq OWNER TO weirdo;
```

Any new dev/CI database must have this applied before `pnpm db:clean-slate` will run. (If changing ownership is not possible in some environment, the fallback is to swap step 1b's `TRUNCATE ... RESTART IDENTITY` for a plain `DELETE FROM users`, which needs only DELETE rights — but then the re-created god user will not be id 1.)

## Update — 2026-08-13 (CR-006/CR-007: transition_definitions now wiped + reseeded; authority vocabulary added)

*Supersedes the "`transition_definitions` survives wholesale, unfiltered" claim in the top finding and in §"What must survive every reset".* Two CR-006/CR-007 changes altered what clean-slate does:

- **`transition_definitions` is now WIPED and reseeded fresh**, not preserved. It had accumulated hundreds of test-fixture rows (`StdFrom-*`/`PolFrom-*`/`policy-waiver-from-*`), so `cleanSlate.ts` **step 5** calls `seedTransitionDefinitions()` (`pnpm seed:transition-definitions`) — an **atomic** `DELETE` + reseed of the 78-row graph from `seed/data/transitionDefinitions.json` (now the complete source, including the Review/Finding rows that migrations 027/028 also seed via `ON CONFLICT DO NOTHING`). The referenced authority rules/policies still survive the vocabulary-table filtering (base-pack-attributed or migration-seeded), so the reseed resolves every code. Wipe+reseed is atomic inside the module so the app-critical graph is never left empty. The **rows** are recreated (not preserved); nothing else FKs `transition_definitions.id`, so the wipe is safe.
- **New authority-vocabulary tables (migration 035): `authority_nouns`, `authority_verbs`, `authority_noun_verbs`.** `cleanSlate.ts` **step 6** calls `seedAuthorityVocabulary()` (`pnpm seed:authority-vocab`) — atomic wipe (`TRUNCATE authority_nouns, authority_verbs CASCADE`) + reseed from `seed/data/authorityVocabulary.json`, and back-fills `transition_definitions.verb`. Must run **after** step 5 (verbs land on the fresh rows). Nouns/verbs/mapping carry an `is_active` retire flag (migration 036); a fresh reseed re-activates everything — that's the intended reset-to-platform-baseline. UI-added nouns/verbs/mappings/transitions are **deltas** wiped by a dev reset (they persist in prod; Phase 12 moves tenant deltas to `tenant.schema`).
- **Migration 036 also drops `transition_definitions_entity_type_check`** — the noun vocabulary is data now, so entity_type is validated against `authority_nouns` in code, not a hardcoded CHECK. Nothing in clean-slate depends on the CHECK.
- **Suggested order of operations** gains: **5.** `seedTransitionDefinitions()` then **6.** `seedAuthorityVocabulary()` (both after the SDK-authoring bootstrap + identity baseline). Both are idempotent and standalone-runnable.
- **`seedIdentityBaseline` now also seeds fixture test users + `noun_verb` grants (CR-006).** Three non-root testers — `tester-all` (1001, every `noun_verb`), `tester-creator` (1002, `deliverable_create`), `tester-approver` (1003, `deliverable_approve`) — with `badge_grants` rows (idempotent: it clears these holders' grants then re-inserts, since clean-slate truncates `users` but not `badge_grants`). This is what lets the regression act as a non-root, badge-holding actor after a reset. `badge_grants` still isn't wiped wholesale — only these fixture holders' rows are managed by the baseline.

## The one real finding that shapes everything below

**A blind `TRUNCATE` of every table will permanently break the SDK UI Layer, with no automatic recovery.** Checked directly: neither `run.ts`'s migrations nor `seedSeu.ts` create the four bootstrap Templates the SDK UI depends on (`sdk-authoring-pack`, `sdk-authoring-template`, `sdk-authoring-profile`, `sdk-authoring-transition-definition`) or their four Profiles. Querying the current database, their `created_at` timestamps are scattered across the build (Aug 5 22:57, Aug 6 00:30 ×2, Aug 6 04:45) — each was created once, ad hoc, while that authoring surface was being built. If these 8 rows are lost, every "Create" action in the SDK UI throws `"no bootstrap Template seeded for {kind}"` immediately, and nothing re-creates them the way migrations re-seed `root` or `platform-core-engineering`.

**Recommended fix, not a workaround: write a real seed script for these 8 rows, not just "remember not to delete them."** `sdkAuthoring.ts` already exports the exact codes needed (`BOOTSTRAP_TEMPLATE_CODE`, `bootstrapProfileCode()`, `AUTHORING_CAPABILITY_CODE`) — a new script (same "standalone, not part of the regular pipeline" shape as `seedEbookLibraryPilot.ts`) should call `templatesDB.upsert`/`profilesDB.upsert` for all 4 kinds, using those existing constants so it can't drift from what `sdkAuthoring.ts` actually looks up. Idempotent (`upsert`, not `create`), so it's safe to run every time the clean-slate script runs, not just once — this closes the gap permanently instead of leaving it as "don't touch these rows" tribal knowledge.

## What must survive every reset (never truncated)

- **`users`, `badge_grants`, `badge_types`, `tenants`.** *(Partly superseded — see "Update — 2026-08-12" above: `users` and non-default `tenants` are now wiped; `badge_grants` and `badge_types` platform defaults still survive.)* Touching these risks breaking the dev auto-login shim, which fabricates `{ id: 1, role: 'super' }` for every unauthenticated request in non-production — that identity never goes through a real login, so nothing re-provisions it (`badgeBootstrap.ts`'s `ensureBadgeBootstrap` only runs from `buildSessionUser()`, which the shim bypasses entirely). Its root grant is a one-time hardcoded migration `INSERT` for `holder_id = '1'` with no FK to `users` — but `objectives.requested_by` and `participants.user_id` **do** have a real FK to `users(id)`, so if the shim's `id: 1` doesn't correspond to an actual `users` row, every Objective/Participant creation under the dev session will fail on that FK. Leave this whole layer alone.
- **`platform-core-engineering` and `technology-nodejs`** specifically within `packs` (everything else in that table should go). Confirmed via migration schema: `capabilities`, `services`, `authority_rules`, `policies`, `quality_gates`, and `metric_definitions` all carry a real `originating_pack_id` FK back to `packs(id)`. Deleting these two base Packs risks either an FK failure or orphaning the governance vocabulary every entity type's transitions depend on. `domain-ebook-library` (and anything else) should go — that's the whole point, it gets rebuilt fresh through the real SDK UI this time.
- **`capabilities`, `services`, `authority_rules`, `policies`, `transition_definitions`, `schema_definitions`.** The governed-lifecycle graph for all 12 entity types, the Schema Registry grammars the SDK UI's form generator reads, and the base Pack-contributed vocabulary. Without these, nothing can transition and nothing can render a form.
- **`metric_definitions`** — the 9 seeded Telemetry metrics (Ch.35 §8 Metric Registry rows). Not usage data; deleting them breaks the Telemetry dashboard the same way losing `schema_definitions` breaks the SDK UI.
- **`canonical_ranks`, `badge_tiers`** — reserved, unused, harmless either way; simplest to leave alone.

## What gets wiped every time (the actual point of the reset)

- **All usage/instance data**: `seus`, `deliverables`, `deliverable_authoring_content`, `objectives`, `capability_fulfilments`, `seu_capabilities`, `participants`, `obligations`, `evidence`, `knowledge_items`, `decisions`, `attention_items`, `external_interactions`, `commands`, `work_items`, `events`, `quality_gate_evaluations`. Standard `TRUNCATE ... CASCADE` territory — needs FK-dependency-aware ordering or `CASCADE`, whichever the implementer finds cleaner; not prescribing the exact SQL here since it should be verified against the real schema while writing it, not assumed from this document.
- **Non-bootstrap rows in `templates` and `profiles`** — everything except the 4 `sdk-authoring-*` codes (or, once the new seed script from above exists, just re-run it after a blanket wipe of these two tables — simpler than a `WHERE code NOT IN (...)` filter, and self-verifying).
- **Non-bootstrap rows in `packs`** — everything except `platform-core-engineering`/`technology-nodejs`.
- **Test-fixture rows in `quality_gates`** specifically — this table is real-data-plus-junk, not clean either way: keep `qg-deliverable-in-progress-to-approved` and `qg-deliverable-approved-to-baselined` (the two seeded Trust Pipeline / Governance gates every Deliverable transition depends on), delete everything matching `qg-test-%`, `qg-wire-test-%`, `td-%-gate-%` (confirmed test-suite fixtures, 70+ rows as of this session).

## Suggested order of operations

1. Truncate the usage-data tables (list above), CASCADE as needed.
2. Delete non-bootstrap rows from `quality_gates`, `templates`, `profiles`, `packs` (the selective deletes above).
3. Run the new SDK-authoring bootstrap seed script (upsert semantics — safe even if step 2 didn't touch these rows, and self-healing if it ever does by mistake).
4. Sanity-check before calling it done: hit `/aisworg/seu/sdk/pack-authoring` and confirm the "New Pack" button still works (proves the bootstrap Templates survived), and confirm `/aisworg/seu/telemetry` renders with zero Deliverables measured (proves the usage-data wipe actually worked) — the same "audit as a real user, don't just trust it ran" discipline every phase in this project has used.

## Keeping this in sync — concrete triggers, not just a reminder

Everything above is a snapshot of the schema as of 2026-08-06. It will drift the moment the schema does, and "review it periodically" tends to quietly not happen unless something specific forces it. Three concrete triggers to actually watch for:

- **Any new migration that adds a table** needs one explicit line added to this document: usage data (goes in the wipe list) or bootstrap/vocabulary (goes in the survive list). No new table should go unmentioned by default.
- **Any new migration that adds an `originating_pack_id`-shaped FK to `packs`** (or any other FK *into* a table this document currently says survives) needs the "must survive" Pack list re-checked — that's exactly the class of thing that made `platform-core-engineering`/`technology-nodejs` non-optional here, found by grepping the schema, not assumed.
- **Any new `TransitionEntityType`** (the 12th, `Participant`, was the most recent) needs its own answer to "does this entity type's bootstrap/seed data have a real, repeatable seed path, or was it created ad hoc like the SDK-authoring Templates were" — that's the exact gap this document exists because of, and it's a class of bug, not a one-off.

**A structural fix worth considering, not just a maintenance habit:** the junk-pattern list in `quality_gates` (`qg-test-%`, `qg-wire-test-%`, `td-%-gate-%`) already needed three different prefixes to cover what's actually there, and the Template/Pack pollution found in other dry runs this session added at least two more (`test-archived-template-*`, `webflow-phase9-pack-*`). That's not a stable list — it's evidence the test suite has no single, consistent naming/tagging convention for fixture data, so this document's "delete matching junk" section will keep needing new patterns added by hand indefinitely. The more durable fix is upstream of this script entirely: either the test suite runs against its own isolated database (removing the need for this filtering altogether), or every fixture the suite creates adopts one consistent marker a single filter can catch. Worth raising as its own decision, separate from getting this script working.
