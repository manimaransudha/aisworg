# Post-MVP Build Sequence — SEU Commissioning Platform

*Paste this as the opening message of a new session, or point that session at this file. It is self-contained — the new session has no memory of the work that produced it.*

## Where things stand

The MVP is built and running (`localhost:4800/aisworg`). A full commissioning cycle was audited live, as a real user, and confirmed working end to end: Objective statement → Template match against required Capabilities → Profile applied → Composition Engine composes the EBM from the one seeded Pack → SEU walks its lifecycle unattended (`Commissioned → Configured → Activated → Operational`) → Capability Fulfilment (assign an AI/Human/External participant) → Deliverable lifecycle transitions, validated against real Transition Definitions (invalid transitions are correctly rejected with a specific error, not silently accepted). Acquisition Scope (SEU/Capability/Enterprise/Platform) is a real, displayed field on every Deliverable.

One real bug was found and is now fixed: the Dependency Engine was not actually gating Deliverable transitions on unmet dependencies (a dependency note would show "Pending" while the blocked transition was allowed to proceed anyway). Confirm this fix still holds — re-run the same test: approve a Deliverable another Deliverable depends on, then verify the dependent Deliverable's transition is genuinely blocked until that dependency is satisfied, not just cosmetically flagged.

The platform's own home page (`/aisworg`) is a self-reported architecture status dashboard, mapped against Book 3's own layered diagram, labelling every component **live / partial / deferred**. Trust it as a starting inventory, but re-verify anything material by using the feature as a real user before building on top of it — the same audit discipline that found the Dependency Engine gap.

Everything below this line is scope confirmed *not yet built*, in the order to build it. **Multi-Tenancy is deliberately last** — see the note at the end of the list for why that's also the technically sound place for it, not just a preference.

## Build sequence

### Phase 1 — Formalize Objective ✅ Done (2026-08-03)
Currently just a free-text "Objective statement" field on the commissioning form. Book 3 Chapter 1 specifies Objective as its own entity: tiers (Strategic/Operational/Engineering), parent/child decomposition, a governed lifecycle (Proposed → Active → Achieved/Superseded/Retired → Archived), and — most importantly — the thing that should *derive* required Capabilities rather than have them hand-picked via checkboxes. Small in scope, foundational in position: everything downstream reads from Objective.
**Done when:** Objective is a persistent, versioned record with a tier and decomposition support; the commissioning form derives required Capabilities from it (checkbox selection can remain as an override/review step, not the sole mechanism).

**What was built, audited as a real user (create → decompose → reject-bad-tier → suggest → block-when-not-Active → activate → commission → edit-and-reversion):**
- Full Ch.1 lifecycle (`Proposed → Active → Achieved/Superseded/Retired → Archived`) runs through the same generic `transitionEngine` SEU and Deliverable already use — `transition_definitions.entity_type` extended to admit `'Objective'` (`003_objective_lifecycle.sql`), not a bespoke mechanism.
- Tier (`Strategic`/`Operational`/`Engineering`) and parent/child decomposition are real and validated: creating a child whose tier is "more strategic" than its parent's is rejected with a clear error (confirmed: Strategic under Operational → `400`). A new Objectives admin UI (list/detail/new) shows the tree and exposes lifecycle actions.
- Versioning is real, not a placeholder integer: editing statement/tier increments `version` (confirmed v1 → v2 on edit), exposed via `POST /objectives/:id/update` (API + web).
- **New governance point**: `commissionSeu` now requires the Objective to be `Active` — confirmed blocking a `Proposed` objective (`422`, clear reason) and succeeding once activated. This is a no-op for the existing one-shot "Commission new SEU" quick-path (which still creates an Objective `Active` by default, unchanged), and a real check for the new Objective-first flow.
- **Capability derivation**: word-overlap heuristic against each Capability's name/description (`suggestCapabilityCodes`), exposed via `GET /objectives/suggest-capabilities` and wired into the New Objective form as a live (debounced) suggestion that pre-checks boxes — never the sole mechanism, always human-reviewable before submit. This stands in for Book 3's own undefined "Capability Pack" derivation mechanism (Ch.1 §10 references it; Ch.5's Pack taxonomy never defines it — a real spec gap, not an MVP shortcut). **Known limitation found during audit**: the heuristic matches on any capability whose name/description shares a word with the statement, which can false-positive — e.g. a statement mentioning "architecture" also suggested the `development` Capability, because `development`'s own seeded description happens to mention "architecture". Acceptable given suggestions are explicitly reviewable, not authoritative, but worth a better heuristic (or an actual Capability Pack, once Phase 9 exists) if this becomes a real usability problem.
- Two commissioning paths now exist: the original one-shot "Commission new SEU" quick-path (unchanged, still creates its Objective inline and `Active`), and a new Objective-first path (`Objectives → New Objective → Activate → "Commission an SEU from this Objective"`) that reuses an existing Objective's already-declared Capabilities rather than re-picking them.
- **Test coverage added** (the manual audit above was captured as automated regression tests, not left as a one-off check): `tests/objective-lifecycle.test.ts` — decomposition/tier-ordering validation (both accept and reject), versioning, the full lifecycle transition (including a rejected undefined transition), the Active-gate on `commissionSeu` (blocks then succeeds), `commissionFromExistingObjective`, and the suggestion heuristic. `tests/engine.test.ts` gained a case exercising `transitionEngine` against the `Objective` entity type specifically (allow / authority-deny / no-transition-definition), since until now only `SEU` had that three-way coverage. Full suite: 16/16 passing.

### Phase 2 — Wire Service into the Dependency Engine ✅ Done (2026-08-04)
The seeded Pack already declares 2 Services, but nothing consumes them — Capability Dependency edges currently reference bare Capabilities, not specific Services. Book 3 Chapter 9 §8 and Chapter 11 §9 specify that a dependency should reference the specific contracted Service (e.g. "the Approved Solution Architecture service"), not the Capability in the abstract.
**Done when:** Dependency edges name a Service, and a Service's declared Service Level (Chapter 11 §8) is visible somewhere, even if nothing evaluates it yet.

**Correction to this phase's own framing, found before writing any code:** the premise above was stale. `dependencyEngine`'s Capability-branch and `dependencyEdgesDB.createCapabilityEdge` already referenced a specific Service (`to_service_id`), not a bare Capability — built and unit-tested during the original MVP. What was actually true, and the real scope of this phase: **no real commissioning run ever created one.** `commissioning.ts` only ever called `createDeliverableEdge`; `createCapabilityEdge` was reachable only via a manual API call with no UI, so every commissioned SEU in practice had zero Capability-type edges, and Services were invisible everywhere (no list page, no Service Level display). "Even if nothing evaluates it yet" was also stale — evaluation already existed. Corrected the doc so the next phase doesn't inherit the same stale premise.

**What was built, audited as a real user (Services page → commission a real SEU → confirm both edge types appear named on its detail page):**
- Template's `deliverableCatalogue` gained a `dependsOnCapabilityServiceCodes` field (distinct from `dependsOnDeliverableCodes`) and a third seeded Deliverable, **Source Code** (produced by `development`), completing the 3-Capability chain that was previously only 2/3 covered. `commissionSeu` now resolves each capability code to its Service and creates a real Capability-type edge — confirmed on a freshly commissioned SEU: Architecture Document carries both a Deliverable edge ("Requirements Specification → Approved") **and** a Capability edge ("Service: Approved Requirements Specification"), and Source Code the same one level up.
- New **Services** admin page + `GET /api/seu/services`, listing every declared Service with its full Service Level (`qualityBar`, and whatever other keys a Pack declares — rendered generically, not hardcoded to today's one key) and providing Capability.
- SEU detail page's dependency notes were previously bare labels ("Deliverable → Approved: Pending", "Capability: Pending") that named nothing — now show the actual target ("Requirements Specification → Approved", "Service: Approved Architecture"), which is what "Dependency edges name a Service" actually requires to be true as a UI fact, not just a schema fact.
- **Real bug found and fixed, pre-existing since the original MVP build, surfaced only because this phase made Services visible for the first time:** `servicesDB.upsertFromPack` was a plain `INSERT` with no `ON CONFLICT`, unlike every other seed-upserted table. Every `pnpm seed:seu` re-run (there had been ~6 across this session) silently created two new duplicate Service rows — 12 total by the time this was caught. Fixed with `004_service_code.sql`: added the `code` column every other Pack-contributed table already had, deduped existing rows by re-pointing any `dependency_edges` referencing a duplicate onto the earliest-created row first (zero orphaned edges after), then added the missing unique constraint. Confirmed idempotent: re-ran `pnpm seed:seu` twice after the fix, still exactly 2 Services.
- **Test coverage added**: `tests/service-dependency.test.ts` — a real `commissionFromForm` run produces the named Capability edge and the Source Code deliverable (not just the isolated engine-level unit test from Phase 0, which only ever proved the mechanism worked in isolation, never that commissioning used it); the edge resolves Pending → Satisfied against a real fulfilled Capability; `listServices` exposes Service Level. Full suite: 19/19 passing.

### Phase 3 — Command / Work Item / Dispatch Engine pipeline ✅ Done (2026-08-04)
The dashboard self-reports this accurately: "No Command/Work Item/Dispatch Engine pipeline — direct API/UI actions instead." Book 3 Chapters 28-33 specify the real chain: Execution Engine observes state and generates Commands → Work Item Generator produces participant-specific execution artefacts → Dispatch Engine selects who executes. Replacing direct UI-triggered transitions with this pipeline is the largest single piece of remaining scope, and most later phases (Telemetry, Attention Management) assume it exists.
**Done when:** a Deliverable state change goes through Command generation and dispatch rather than a direct form POST, even if dispatch selection logic starts out trivial (whoever's assigned).

**What was built, audited as a real user (commission → attempt a transition with nobody assigned → confirm deferred, not applied → fulfil the Capability → retransition → confirm dispatched, Command/Work Item trail visible → repeat the whole cycle via curl against the running dev server, not just tests):**
- Read Ch.28 (Runtime Kernel), Ch.31 (Execution Engine), Ch.32 (Work Item Model), Ch.33 (Dispatch Engine) in full before designing anything — the ADRs embedded in Ch.31/Ch.33's own drafting notes turned out to matter directly: **Command-Driven Execution** (the Execution Engine generates Commands, never Work Items directly) and the **Capability Fulfilment vs. Dispatch split** (Ch.33's own resolution: Capability Fulfilment is the slow-moving eligible-Participant pool, Dispatch is the fast per-Work-Item selection from that pool — composition, not merger).
- New tables `commands` and `work_items` (`005_command_pipeline.sql`). `commands.entity_type` mirrors `transition_definitions.entity_type` (SEU/Deliverable/Objective) so the pipeline can extend past Deliverable later without a schema change — Phase 3 itself only ever generates `'Deliverable'` commands, per the "Done when" scope. `work_items` is genuinely a transient-artefact log (Ch.32 WI-001/WI-003): the Deliverable's `lifecycle_state` remains the sole authoritative record; nothing reads a Work Item back as business truth.
- Three new generic engine modules, same "small core" discipline as `dependencyEngine`/`transitionEngine`: `src/domain/engine/executionEngine.ts` (Ch.31 — generates the Command, then calls the next two in sequence), `workItemGenerator.ts` (Ch.32 — one Work Item per Command; Ch.32 §9's "different Participants may receive different Work Items for the same Command" doesn't apply yet since Capability Fulfilment is still 1:1 per SEU Capability), `dispatchEngine.ts` (Ch.33 — trivial `sole-eligible-participant` strategy: look up whoever currently fulfils the Deliverable's producing Capability via `capabilityFulfilmentsDB.findActiveBySeuCapabilityId`, new this phase).
- `transitionDeliverable` (`routes/seu/core/deliverables.ts`) now calls `executionEngine.execute(...)` after governance (dependency + Authority/Policy, unchanged) passes, instead of writing `lifecycle_state` directly. **Real behavioural change, confirmed live**: transitioning a Deliverable whose producing Capability nobody currently fulfils now returns a new `dispatch_deferred` reason (409/flash error) and the Deliverable's state does not move — previously this always succeeded regardless of whether anyone was assigned. Fulfilling the Capability and retrying dispatches and applies the transition as before.
- No autonomous Participant runtime exists yet (unchanged MVP gap), so once dispatched, `dispatchEngine` simulates execution synchronously in the same call — Generated → Assigned → Executing → Completed → Disposed, matching Ch.32 §8's full Work Item lifecycle. Ch.32 WI-005 still holds structurally: Work Item completion doesn't itself change engineering state; `executionEngine` returns to the caller, which applies the actual Deliverable transition afterwards.
- **Design decision, not in the source chapters**: if a Deliverable has no `producing_capability_id` declared at all (nothing for Dispatch to gate on), `dispatchEngine` dispatches immediately rather than deferring forever on a requirement that was never declared. Covered by a dedicated engine-level test.
- SEU detail page gained a new **Command / Work Item / Dispatch Pipeline** section — every Command against that SEU, its transition, status, and Work Item(s) with assigned Participant and dispatch strategy. The general Events log also now surfaces `CommandGenerated`/`WorkItemGenerated`/`ParticipantSelected`/`WorkItemDispatched`/`WorkItemStarted`/`WorkItemCompleted`/`WorkItemDisposed`/`DispatchDeferred` — pulled in by Correlation Id (`eventsDB.findByCorrelationId`, new this phase) since Command/WorkItem events publish against their own id, not the SEU's or Deliverable's. Confirmed via curl against the running dev server: a deferred attempt shows `Deferred`/`Generated` with no Participant; the successful retry shows `Completed`/`Disposed` with the fulfilling Participant and `sole-eligible-participant` strategy, and both appear in the event log in the correct order.
- Dashboard's self-reported status updated: "Work Item Runtime" moved from `deferred` to `partial` (the pipeline is real; dispatch strategy is still trivial — no cost/load/locality strategies per Ch.33 §9, since only one Participant can fulfil a Capability today), "Capability Runtime"'s note corrected to stop claiming "no Dispatch Engine."
- **Test coverage added**: `tests/command-pipeline.test.ts` — a real `transitionDeliverable` call defers when unfulfilled and dispatches once fulfilled (state genuinely doesn't move while deferred), the resulting Command/Work Item trail is correct end-to-end (`Completed`/`Disposed`, correct Participant label, correct dispatch strategy), plus two focused `executionEngine`-level tests for the deferred-no-participant and no-producing-capability-declared branches. Full suite: 23/23 passing.

### Phase 4 — Governance depth ✅ Done (2026-08-04)
Currently: "minimal Authority + Policy checks only." Book 3 Chapters 20, 22, 23, 24, 25, 26 specify Quality Gate, Review, Obligation, and a fuller Authority Model (more than one rule type) and Policy (including the Constraint Type distinction between mandatory Policy and non-blocking Standard). Without this, Deliverable transitions are state-machine-valid but not actually *governed*.
**Done when:** at least one Quality Gate blocks a real transition until its criteria are met, and at least one Obligation can block a Deliverable independently of the dependency graph.

**What was built, audited as a real user (commission → fulfil Capability → move Deliverable to "In Progress" → create an Obligation against it → attempt "Approved" → confirm blocked, gate + Obligation named in the flash message, Deliverable state unchanged → walk the Obligation to "Verified" → retry → confirm it now succeeds — all via curl against the running dev server, not just tests):**
- Read Ch.20 (Traceability), Ch.22 (Authority), Ch.23 (Obligation), Ch.24 (Policy), Ch.25 (Review), Ch.26 (Quality Gate) in full before designing anything. Two things changed the plan from what the "Done when" line alone implied: (1) the **Constraint Type distinction (Ch.24)** — Policy vs. Standard — turned out to already be real, built into `transitionEngine` since the original MVP schema (`policies.constraint_type`, and the branch in `transitionEngine.evaluate` that only blocks on a failing `constraint_type = 'Policy'`); it had just never been exercised by a test. (2) The Review Model (Ch.25) is real scope but not in this phase's "Done when" line, so it stays deferred — Quality Gate criteria reference Obligations directly for MVP, not Review outcomes, per Ch.26 §9's own list of possible criteria.
- New tables `obligations`, `quality_gates`, `quality_gate_evaluations` (`006_governance_depth.sql`), plus `transition_definitions.entity_type` extended to admit `'Obligation'` — a fourth entity type on the same generic `transitionEngine` SEU/Deliverable/Objective already used, with zero new transition-evaluation code (Ch.23 §9's 8-state lifecycle — `Identified → Analysed → Assigned → In Progress → Resolved → Verified → Closed → Archived` — is just seven more `transition_definitions` rows). `obligations.deliverable_id` is a single required FK, not Ch.23 §8's plural "Related Deliverables" — MVP scope matches the "Done when" line's "block *a* Deliverable," not a many-to-many model.
- New engine module `src/domain/engine/qualityGateEngine.ts` (Ch.26), same "small core" discipline as `dependencyEngine`/`transitionEngine`: a gate is scoped to one specific `(entityType, fromState, toState)` triple, same granularity as `transition_definitions`. MVP implements exactly one declarative criteria type — `{ "type": "no_unresolved_obligations" }`, Ch.23 §11's own worked example ("a Deliverable cannot be approved until an associated security Obligation is verified") — richer criteria (Evidence/Decision/Review-based, per Ch.26 §9) are additive once Phase 5 exists, not a rewrite. One Quality Gate is seeded via the Pack contribution mechanism (`PackContributions.qualityGates`, new this phase — Ch.26 FR-26.2 "Quality Gates shall be contributed through Packs"): `qg-deliverable-in-progress-to-approved`, gating the existing seeded Deliverable "In Progress" → "Approved" transition.
- `transitionDeliverable` (`routes/seu/core/deliverables.ts`) gained a new gate — `qualityGateEngine.evaluate(...)` — sequenced *after* dependency readiness and *before* Authority/Policy. That ordering is what makes "an Obligation blocks independently of the dependency graph" both true and testable: dependency readiness has already unconditionally passed by the time the Quality Gate runs, so a block past that point can only be the gate. Confirmed directly: Requirements Specification has zero dependency edges in the seeded Template, and `dependencyEngine.isDeliverableReady` returns `ready: true` throughout every test in this phase. New failure reason `quality_gate_blocked` (with the gate's name and the specific unresolved Obligations), threaded through both the API (409 JSON) and web (flash message naming the gate and Obligation titles) layers.
- Admin UI: an **Obligations** section on the SEU detail page — inline create form (Deliverable picker, Ch.23 §7's eight categories, title, severity) and a list with the same possible-next-states transition control every other governed entity gets. New API routes `POST /obligations`, `GET /obligations?seuId=`, `POST /obligations/:id/transition`. Dashboard's self-reported Governance Runtime status corrected from "Minimal Authority + Policy checks only" to name what's now real and what (Review, Compliance Packs) still isn't.
- **Test coverage added**: `tests/governance-depth.test.ts` — the Quality Gate blocks then unblocks as an Obligation moves to Verified, with an explicit `dependencyEngine.isDeliverableReady` check proving the Dependency Engine has nothing to do with the block; the Obligation lifecycle runs through `transitionEngine` and rejects a skipped-state transition; and a previously-untested but pre-existing behaviour — a Standard-type Policy violation doesn't block a transition, a Policy-type violation does. One further HTTP-level test in `tests/web-flow.e2e.test.ts`, per `Integration Test Handoff Brief.md`'s own Phase 4 pointer, walking the same block-then-unblock cycle over real HTTP with CSRF, confirming the web route contract stays a graceful `302` + flash even when blocked, never a `500`. Full suite: 33/33 passing.

### Phase 5 — Knowledge, Evidence, Decision Models ✅ Done (2026-08-04)
Currently fully deferred. Book 3 Chapters 14-19 specify the Trust Pipeline (Information → Evidence → Knowledge → Decision → Deliverable State Transition). This phase has no dependents yet in the running app, which is exactly why it's sequenced after Governance rather than before — Governance gives Knowledge/Evidence/Decision something real to attach to (a Quality Gate requiring Evidence, a Review producing a Decision).
**Done when:** a Deliverable transition can require accepted Evidence or a recorded Decision as a real precondition, not just a Transition Definition state check.

**What was built, audited as a real user (commission → fulfil Capability → walk Requirements Specification to "Approved" → attempt "Baselined" → confirm blocked, no accepted Evidence or approved Decision → collect Evidence → walk it to "Accepted" → retry → confirm it now succeeds — all via curl against the running dev server, not just tests):**
- Read Ch.14 (Collaboration), Ch.15 (Deliverable — already built), Ch.16 (Knowledge), Ch.17 (Evidence), Ch.18 (Ontology), Ch.19 (Decision) in full before designing anything. Two chapters turned out to need no new code at all: **Ch.14** (Engineering Collaboration Model) is purely descriptive of an architecture already in place — "Participants collaborate through published engineering state, not direct interaction" is exactly what `eventBus` + Deliverable/Obligation/Command/WorkItem artefacts have done since Phase 0, so there was nothing to build, only to recognise. **Ch.15** (Deliverable) is already built from the original MVP — `acquisition_scope` has existed on `deliverables` since `002_seu_platform.sql` — this phase only added the one new transition its fuller lifecycle names but the MVP never seeded (`Approved → Baselined`).
- **Ch.18 (Ontology) deliberately out of scope**, same discipline as Phase 4's Review cut: Evidence/Knowledge/Decision reference free-text `category` fields, not Ontology concepts — identical to how `deliverables.category` already works. Revisit only if multiple Packs contributing conflicting terminology becomes a real problem, not before.
- New tables `evidence`, `knowledge_items`, `decisions` (`007_trust_pipeline.sql`), each following the exact shape Obligation established in Phase 4: single required `deliverable_id` FK (not the chapters' plural "Related Deliverables"), free-text `category`, `status` with no CHECK (validated dynamically by `transitionEngine`). `evidence` deliberately has **no update-content function anywhere in the dblayer or core layer** — not even once Accepted — so Ch.17 EM-002/FR-17.5 ("Evidence shall remain immutable after acceptance") holds architecturally, because nothing can ever edit it, rather than needing a runtime check guarding a field that could otherwise change. `knowledge_items.acquisition_scope` reuses the existing `AcquisitionScope` CHECK and is inherited by default from the producing Deliverable at creation (Ch.16 FR-16.8), confirmed by test — overridable per Deliverable if a caller judges the understanding generalises further. `decisions` carries nullable `knowledge_id`/`evidence_id` FKs (Ch.19 DM-002/DM-003 say a Decision "shall" reference them; MVP doesn't enforce that as NOT NULL, same precedent as Deliverable's non-empty-acceptance-criteria not being enforced either).
- `transition_definitions.entity_type` extended to a seventh value (`Evidence`/`Knowledge`/`Decision` added together), each running its full chapter-specified lifecycle through the same generic `transitionEngine` every other entity type already uses — zero new transition-evaluation code: Evidence (`Collected → Validated → Accepted → Referenced → Archived`), Knowledge (`Observed → Proposed → Validated → Accepted → Published → Deprecated → Archived`), Decision (`Identified → Analysed → Proposed → Reviewed → Approved → Applied → Superseded → Archived`).
- `qualityGateEngine` gained a second criteria type, `requires_accepted_evidence_or_approved_decision` (Ch.17's own Trust Pipeline ADR: "Deliverable State Transitions occur only after sufficient evidence and approved decisions"), qualifying Evidence at `Accepted`/`Referenced` and Decision at `Approved`/`Applied` (Superseded/Archived no longer count — no longer the current decision). Seeded on a **new** Deliverable transition (`Approved → Baselined`) rather than reusing Phase 4's already-seeded `In Progress → Approved` gate, specifically to avoid coupling this phase's new precondition onto every existing Phase 3/4 test that already exercises that transition without any Evidence attached.
- **Refactored `qualityGateEngine`'s result shape while adding the second criteria type**: Phase 4's `Blocked` outcome carried an Obligation-specific `unresolvedObligations: ObligationRow[]` field baked into the type signature — a second, differently-shaped criteria type made that untenable. Generalised to a single human-readable `reason: string`, matching every other governance failure reason (`authority_denied`, `policy_blocked`, `dispatch_deferred`) which were already just a message string, not structured data. `TransitionDeliverableResult`'s `quality_gate_blocked` variant simplified to match (`{ reason: "quality_gate_blocked", detail: string }`); the rendered flash-message text is byte-identical to before, confirmed by keeping Phase 4's existing test assertions passing against the new field.
- **Real, pre-existing bug found and fixed, surfaced only because this phase re-ran migrations against an already-seeded database**: `run.ts`'s own header comment promises every migration file is "safe to run repeatedly," but `003_objective_lifecycle.sql`'s `DROP CONSTRAINT` + `ADD CONSTRAINT` on `transition_definitions_entity_type_check` re-applied a narrower value list than migration `006` had already widened it to — harmless the first time (no data existed yet to violate it), but a hard failure once real `Obligation`-typed rows existed and migrations were re-run from scratch, which is exactly what happened building this phase. Fixed by making every migration that touches this constraint (`003`, `006`) declare the same final union of values, so `DROP`+`ADD` is a true no-op regardless of run order or how much data already exists. Verified by running the full migration suite twice in a row against the already-seeded database.
- Admin UI: **Evidence**, **Knowledge** and **Decisions** sections on the SEU detail page, same inline-create-form-plus-transition-list pattern as Obligations — Knowledge's create form offers a dropdown of that SEU's Evidence to optionally link as support; Decision's offers a dropdown of Knowledge Items. New API routes for all three (`POST`/`GET`/`POST .../transition`, mirroring Obligation's route shape exactly). Dashboard's self-reported Knowledge Runtime status corrected from "fully out of MVP scope" to `partial`, naming what's real (Evidence/Knowledge/Decision, the new precondition) and what's still deferred (Ontology, Engineering Capital querying — Phase 6).
- **Test coverage added**: `tests/trust-pipeline.test.ts` — the Quality Gate blocks "Approved → Baselined" until Evidence reaches Accepted then allows it; a second test proves the "or" — an Approved Decision alone, no Evidence at all, also satisfies the same gate; Evidence/Knowledge/Decision each reject a skipped-state transition through `transitionEngine`; Knowledge Item Acquisition Scope inheritance (and override) from its producing Deliverable. One further HTTP-level test in `tests/web-flow.e2e.test.ts`, per `Integration Test Handoff Brief.md`'s own Phase 5 pointer, walking the same block-then-unblock cycle over real HTTP with CSRF. Full suite: 38/38 passing.

### Phase 6 — Organisational Learning Obligation + Engineering Capital surfaces ✅ Done (2026-08-04)
Now that Knowledge exists (Phase 5), wire up the actual learning loop: Chapter 23 §7's Organisational Learning Obligation category, triggered by Knowledge Acquisition Scope promotion (Book 1 Chapter 21 §21.6; Book 3 Chapter 16 §12-§13). Acquisition Scope is already a displayed field — this phase makes it *do* something: give Engineering Capital a real query/screen (Knowledge filtered to Capability/Enterprise/Platform scope), and let a promoted Knowledge Item actually raise an Obligation.
**Done when:** promoting a Knowledge Item's scope produces a visible Organisational Learning Obligation, and there's a screen showing the organisation's accumulated Engineering Capital.

**What was built, audited as a real user (commission → create Knowledge Item → attempt scope promotion before Published → confirm blocked → walk to Published → promote to Capability scope → confirm a real, actionable Organisational Learning Obligation appears in the Obligations section → confirm the Knowledge Item now appears on the Engineering Capital screen — all via curl against the running dev server, not just tests):**
- Read Book 1 Ch.21 §21.6 (Acquisition Scope and Engineering Capital) alongside Book 3 Ch.16 §12-§13 (already read in Phase 5) before designing anything. Book 1's own framing settled the key design question directly: "[Acquisition Scope] may be widened accordingly — a governed organisational judgement, like any other, rather than something left informal" — confirming promotion belongs behind the same Authority/Policy machinery every other governed action uses, not an ungoverned field edit.
- **Acquisition Scope promotion modelled as its own governed transition track** — a new `TransitionEntityType`, `'KnowledgeScope'`, deliberately separate from `'Knowledge'` (which continues to govern `knowledge_items.status`). This mirrors Ch.24's own "different axes" pattern (Constraint Type vs Severity) from Phase 4, and means promotion reuses `transitionEngine`/Authority/Policy verbatim with **zero new validation code**: the only seeded transitions are `SEU → Capability → Enterprise → Platform`, so Ch.16 §12's "may not be silently demoted" rule and the "one tier at a time" rule both fall out of the existing generic "no_transition_definition" rejection path for free, confirmed by test (a direct SEU→Enterprise skip and a Capability→SEU demotion are both rejected the same way any undefined transition is). No new table needed — `008_engineering_capital.sql` only widens the `entity_type` CHECK on `transition_definitions`/`quality_gates` and adds an index.
