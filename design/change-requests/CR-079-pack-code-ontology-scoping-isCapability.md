## The gap (confirmed live, 2026-08-29)

CR-015's original design ("`code` is a system UUID") is dead — confirmed directly against the running DB: zero Packs, Templates, or Profiles, any status including Draft, have ever had a UUID-shaped `code`. CR-020 Part 2 (2026-08-19) replaced it with an Ontology-backed `capability-name` dropdown on the interactive form; CR-046 then closed the gap CR-020 itself had flagged, adding real server-side enforcement — `assertCanonicalCategory("capability-name", seed.code, …)` inside `validatePackSeed`, run **unconditionally, for every Pack regardless of category**. (CR-015 itself has been updated in place with a deprecation note recording this; `toPackSeedInput`'s dead `randomUUID()` fallback and the stale "Code is a system UUID" comment in `createAuthoringDraft` were also corrected — see that CR file.)

Consequence, confirmed live: `capability-name` (85 rows) is polluted. 44 of 85 (52%) are one-off test-fixture UUIDs (`test-comp-arity-5d8b360e-…`) that composition-engine tests (`tests/pack-composition.test.ts`'s `freshCode`/`registerTestOntologyCode`) are forced to register as permanent "canonical" concepts just to get a collision-free Pack code past validation. The other 41 are simply every real Pack's own code (`technology-nodejs`, `domain-ebook-library`, …), registered there purely to satisfy the check — not because any of them are semantically a capability. Nothing else consumes `capability-name`; not even the real, separate `capabilities.code` column (Ch.10 §18.4, built via CR-065) that the concept type's own name implies it should relate to. Root cause: a Pack's own identity code is being validated against a vocabulary meant to name capabilities, when a Pack is categorically not a capability.

## Design

**1. Capability is a term, not a kind of Pack.** Owner: *"Capability is just a term. Development, Requirements-specification, growth-optimisation are capabilities. Capability is not a pack."* `capability-name` stays exactly what its name says — the vocabulary a Pack's **contributed** Capabilities are drawn from, nothing else. No flag, no Pack-level notion of "being" a capability.

**2. Two fixed, non-overlapping tracks — never conditional, never crossing:**

   - **Track A — `contributionCapabilities[].code`** (a Pack's own declared Capability contributions) is sourced from `capability-name`. Owner's worked example: *"technology-nodejs pack contributes to the development capability"* — i.e. `contributionCapabilities: [{code: "development", …}]`, referencing an existing term, not minting one. Today this field is plain free text (`{"type": "string", "x-help": "A short, unique identifier for this Capability, scoped to this Pack."}`, no referential marker at all, confirmed live) — becomes a real Ontology-backed dropdown.
   - **Track B — Pack's own top-level `code`** is sourced from a **category-scoped** vocabulary, determined purely by that Pack's `category` — never `capability-name`, for any Pack, ever. Owner: *"Packs define the capabilities. The pack code is unique and has to come from Ontology and that is what we have to build."* Six new concept types, sibling to `capability-name`, one per current `category:pack` value: `domain-name`, `technology-name`, `compliance-name`, `organisation-name`, `integration-name`, `engineering-name`.

**3. Dependencies stay exactly as they are — no capability-based filtering added.** Owner: *"Dependencies can be any other packs belonging to the same set of capabilities or otherwise or none."* A Pack dependency is a general Pack-to-Pack reference; whether the two share a contributed capability is incidental, not a picker constraint. (This drops the earlier draft's "filtered Dependencies picker" idea entirely — it doesn't apply once Capability isn't a Pack-level property.)

**4. Free-text entry, publish-time gate — unchanged from the earlier draft.** `code`'s dropdown (Track A or Track B, whichever applies) allows an author to type a value not yet on the list at Draft time; a Pack cannot reach Published/Active unless that value already resolves to a real concept in the relevant vocabulary — same shape as today's `assertCanonicalCategory` gate inside `validatePackSeed`, just correctly scoped per track instead of universally `capability-name`. Owner: *"The pack cannot be published till the Ontology is fixed or the record uses one of the existing ontology."* Two ways off a blocked Draft: whatever process eventually promotes the typed value into a real concept (out of scope, point 6 below), or the author edits the Draft to reference an existing one instead. Either way **the typed text itself is saved as-is on the Draft** — free-text entry was never conditional on the concept existing yet, only publish is.

**5. Tenant relabeling already covers this, for free.** Owner: *"capability-names can be renamed by a tenant. So the platform says 'Development'. The tenant might want to call it as 'EM5040'… I believe this is already in place."* Confirmed — `tenant_concept_aliases` (`tenant_id, concept_type, canonical_code, display_label`) and `resolveLabels(tenantId, conceptType)` (`core/ontology.ts:147`) are fully generic, with no restriction to specific `concept_type` values. The canonical `code` is what's stored and governed everywhere (dependency wiring, traceability, attestation); a tenant's `display_label` is resolved only at the view/serializer edge. `capability-name` already gets this; the six new category vocabularies inherit it identically with zero additional work — same table, same resolver, just a different `concept_type` string. Platform governance is untouched by any tenant's relabeling, by construction (`Ontology Plan.md` §0.1's own "canonical identity, tenant label" discipline).

**6. Entering an unregistered `code` publishes `ConceptCreated` to the Event Bus — emission only, not consumption.** Owner: *"when a new pack code is entered, ConceptCreated event has to be triggered in the Event bus. (who consumes is the part that is not in scope for this CR)."* `ConceptCreated` is not a new event invented for this CR — it's already named in Ch.18 §14's own list of 7 events the Ontology subsystem "shall publish," and Ch.18's own audit (§18.9) confirms **zero of the 7 exist anywhere today** — no `eventBus` import at all in `ontologyDB.ts`/`core/ontology.ts`. This CR would be the first of the 7 to actually fire, narrowly scoped: publish `ConceptCreated` (with the typed code, the target `concept_type`, and enough context to identify the originating Draft) at the moment an author's `code` entry doesn't resolve to an existing concept. What consumes it — the mechanism that eventually turns a pending `ConceptCreated` into a real, active `ontology_concepts` row — is explicitly out of scope (see below; Ch.18/`Ontology Plan.md` territory). Stated for Pack's own `code` (Track B); whether Track A (`contributionCapabilities[].code`) free-text entry gets the identical treatment is the same open question, not decided here.

**7. A `code` correction alone never bumps the Pack's version.** Owner: *"Just the code change will not change the version of the record."* Editing `code` — whether fixing an unregistered value to an existing concept, or the initial free-text entry — is an ordinary Draft field edit like any other, not a version-triggering event. `packVersion` only advances through its existing, separate mechanism (the "Next version" button / a real content-defining change), never as a side effect of resolving a `code` value.

## Worked examples (owner's own, recorded verbatim so the intent isn't lost)

1. **`web-standards`** — a Technology Pack (`category: Technology`), contributing to the `development` and `code-review` capabilities: `contributionCapabilities: [{code: "development"}, {code: "code-review"}]` (Track A, `capability-name`). It has its own Policies, Checklists, etc. — an ordinary Pack in every other respect. `web-standards` itself is **not** a capability — its own top-level `code` ("web-standards") comes from `technology-name` (Track B), never `capability-name`.
2. **`icd-10`** — a Compliance Pack (`category: Compliance`), contributing to the `requirements-specification` capability (Track A). It has its own Dependencies, Checklists, etc. `icd-10` itself is **not** a capability either — its own top-level `code` comes from `compliance-name` (Track B), never `capability-name`.

Both examples land on the same shape: **category decides which Track-B vocabulary the Pack's own `code` is drawn from; what the Pack contributes (Track A) is separate and can name any number of capabilities regardless of the Pack's own category or code.** Neither Pack "is" a capability — confirming point 1 concretely, not just in the abstract.

## Explicitly out of scope for this CR

Owner: *"who consumes is the part that is not in scope for this CR"* / *"'How do these codes get back into Ontology' is a separate layer (Chapter 18 and design/mvp-build-plan/Ontology Plan.md)."* Noted in passing, not decided here: that plan already has a deferred, generic hook that may be the right mechanism — step 5, "Pack-contributed concepts… union into the registry at composition," explicitly left unbuilt ("recommend deferring step 5 until a Domain Pack actually needs to add a concept"). This CR does not choose that mechanism, and does not build the other 6 named Ontology events (§14) either — `ConceptCreated`, for this one trigger, only.
