## The gap, precisely

Grounded directly in live code and the running database — full findings written into Chapter 11 §18, its first-ever audit section (this CR's own companion).

**Database** (`services` table, 10 columns): `id`, `providing_capability_id` (FK, `NOT NULL`), `name`, `contract_description`, `service_level` (`JSONB DEFAULT '{}'`), `status` (`CHECK IN` the chapter's own exact 6 lifecycle states — `Defined`/`Published`/`Active`/`Deprecated`/`Retired`/`Archived` — but `DEFAULT 'Active'`, never transitioned by anything), `version` (`INTEGER DEFAULT 1`, never incremented), `originating_pack_id`, `created_at`, `code` (added by migration `004_service_code.sql`, **globally unique** — `services_code_key UNIQUE (code)`, not Pack-scoped).

**Authoring schema** (`contributionServices[]`, live-queried, unchanged since migration `040_pack_structured_contributions.sql`): `code`, `capabilityCode`, `name`, `contractDescription` only. No `serviceLevel` field at all — despite `service_level` being a real column and `servicesDB.setServiceLevel` being real code, **nothing anywhere ever calls it**; every one of the 122 live Service rows has `service_level = {}`. No x-referential/x-ontology, no x-property-order, no per-field help — the pre-CR-058 raw shape every other contribution kind had before its own CR.

**The single most consequential finding — the Dependency Engine's "Capability" dependency type is already Service-keyed internally, just not author-facing.** Chapter 11 §9's own worked example (a Deliverable depends on "the Approved Solution Architecture Service," not "the Architecture Capability" in the abstract) is functionally real at the data layer: `dependency_definitions` rows for a Capability-type dependency are resolved by matching `services.code`, not a Capability's own identity (`dependencyDefinitionEngine.ts`'s `resolveNamedNode`). But a Template/Pack author can only ever pick a **Capability** when authoring this kind of dependency (`fromCapabilityCode`) — there is no way to author "depends on this one specific Service." `materialiseDependencyGraph.ts` (CR-042) silently expands one authored "depends on Capability X" row into **one `dependency_definitions` row per Service that Capability X currently exposes** — an implicit AND across every Service, not the single named Service the chapter's own example describes.

**Service Lifecycle (§13) and Versioning (SVC-005) — schema exists, governance doesn't.** The `status` CHECK constraint lists the chapter's exact 6 states, but zero `transition_definitions` rows exist for `entity_type='Service'`, and `"Service"` isn't even a member of `TransitionEntityType` — the generic governed-transition engine every other lifecycle entity (Obligation, Review, Template, Profile, Pack) uses cannot reach it. `version` is the identical story: a real column, never incremented, since `upsertFromPack` overwrites every field in place on every republish (`ON CONFLICT (code) DO UPDATE`) — the opposite of SVC-005's "immutable once published."

**Zero of the chapter's 9 named events (§14) exist anywhere.** No Telemetry integration exists either (§11) — `telemetry.ts` has zero references to Service. Both are mutually reinforcing gaps (no events to derive Telemetry from, either way).

**Zero Composition Engine involvement (§12).** Worse than Policy/Quality Gate's own same-code collision handling (which at least logs an "Override" warning) — a same-`code` Service collision across two different Packs produces silent overwrite with no warning at all, and `code`'s bare global uniqueness (not `(originating_pack_id, code)`, unlike Policy/Checklist post-CR-060/061) makes this a live structural risk, not just theoretical. No collision exists in the live data today (122 rows, 122 distinct codes), but nothing prevents one.

**Consuming Capabilities (§7) isn't tracked in any form** — no column, no join table, no way to answer "which Capabilities actually consume this Service" at all.

## Design, as settled

### `code` — Pack-scoped identity, AND drawn from a new, freely-extensible Ontology concept type

Two separate corrections, both confirmed. **Identity**: owner — "service code will be unique within a pack and not unique across packs" — `(originating_pack_id, code)`, the same fix Checklist/Policy each got, replacing today's bare `services_code_key UNIQUE (code)`.

**Vocabulary**: owner — "I can have service code 'turnaround-time' defined for a severity high and severity low within the same capability. They have to come from the ontology layer... This service code turn-around-time-high can be declared in development pack and deployment pack with different service levels." The whole point of the worked example is that two *different* Packs deliberately declare the *same* code as the *same* canonical concept, each with their own content — which only works if the code itself is a shared, governed term, not free text each Pack author might spell differently. `code` becomes a new Ontology concept type (`service-name`), following the **`capability-name`/`feature-flag` pattern** — a simple, freely-extensible vocabulary any Pack author can add a new value to inline or pick an existing one from — **not** `deliverable-name`'s heavier graduated-entity treatment (CR-049 pulled `deliverable-name` out of plain Ontology CRUD into a full real entity, `deliverable_definitions`, specifically because it needed Draft→Active lineage tracking; nothing here calls for that — two Packs independently declaring their own row under a shared code is exactly what a plain, open concept type already supports).

### Authoring structure — two-level, same nested-list mechanism as Checklist

Owner: "Services should be authorable similar to what we have done for quality gates, checklists etc. The metadata will be a code, a name and a contract description, version number. The items will be the declared service level." This is Checklist's own two-level shape (CR-060's `"nested-list"` capability) applied to Service: a top-level card (`code`, `name`, `contractDescription`, `version`) containing its own repeatable `serviceLevel[]` sub-list. Worked example: `{code: turn-around-time-high, name: "...", description: "...", service_level: [{offshore: 3 days}, {onsite: 1 day}]}`.

**Service Level item shape — confirmed.** The example's per-item keys (`offshore`, `onsite`) vary, which a fixed-schema nested-list item can't do directly (item fields need fixed names). Owner: "{label, target} pair instead - i agree." A generic `{ label: string, target: string }` pair per item — `label` free text ("Offshore," "Onsite," "Quality bar," "Availability," anything §8's own open "may specify" list calls for), `target` the value ("3 days," "99.9% uptime") — so one Service can carry as many differently-labelled Service Level rows as it needs, matching §8's own non-exhaustive framing rather than hardcoding turnaround/quality-bar/availability/exceptions as four fixed fields up front.

### Versioning — real, definition-side, new row per version (Quality Gate's own precedent, not Checklist/Policy's)

Owner: "Versioning is definition side. You dont version the service levels at execution." Chapter 11 §13 itself says "Historical Service versions remain available for reconstructing past dependency evaluations" — the same requirement Quality Gate/Review Gate's own chapters state, and the reason those two get **real** versioning (a new row per real content change, an active-slot flag marking the current one) rather than Checklist/Policy's in-place-upsert, no-version treatment. Service follows Quality Gate/Review Gate's precedent, not Checklist/Policy's: real identity becomes `(originating_pack_id, code, version)`, `version` an author-declared field (per the owner's own "metadata will be... a version number," listed alongside the other author-input fields), a republish with a new `version` value creates a new, immutable row rather than overwriting the prior one in place.

**Not the same as the chapter's own 6-state `status` lifecycle (§13's Defined→Published→Active→Deprecated→Retired→Archived).** Quality Gate/Review Gate don't use the governed `transition_definitions` engine for their own versioning either (neither is a `TransitionEntityType` member) — just version-increment + active-slot. Service follows the identical, lighter mechanism. The chapter's own full governed lifecycle stays exactly as unbuilt as Ch.11 §18 found it — not this CR's job, not contradicted by "versioning is definition side" either (versioning and the 6-state status lifecycle are different mechanisms, per the Quality Gate precedent this design now follows).

### Consuming Capabilities (§7) — dropped

Owner: "Consuming capabilities can be dropped. we can get this information by querying." No column, no join table — answerable from `dependency_definitions` directly whenever needed.

### The Dependency Engine gap (CR-042, §9) — dropped from this CR's scope

Raised in the original gap write-up because Ch.11 §18's audit found the Dependency Engine's `"Capability"`-typed dependency is *already* internally Service-keyed (via CR-042's own expansion mechanism) but not author-facing — a real, adjacent finding, but about the Dependency Graph *authoring widget* (Ch.9/CR-041's own territory), not about `contributionServices[]` itself. Owner didn't see its relevance to the conversation at hand, and every concrete decision above is squarely about Service's own authoring structure — so this stays out of CR-064 entirely. If a specific-Service dependency picker is ever wanted, it's its own separate CR against Ch.9/the Dependency Graph widget, not folded in here.

## Scope (once built)

1. `services` table: drop `services_code_key`; add `(originating_pack_id, code, version)` as the real identity, plus an active-slot mechanism (`is_active`-style) matching Quality Gate/Review Gate's own versioning precedent.
2. New Ontology concept type `service-name`, freely-extensible (`capability-name`/`feature-flag` pattern, not `deliverable-name`'s graduated treatment).
3. `contributionServices[]` schema: `code` becomes a real `service-name`-backed referential-select; `version` added as a real authored field; `serviceLevel[]` added as a nested repeatable sub-list (`{label, target}` items, pending confirmation above); per-field help, `x-property-order`, same discipline CR-058–062 established.
4. `servicesDB.upsertFromPack` → real versioned upsert (new row per `(originating_pack_id, code, version)`, not in-place overwrite), mirroring `qualityGatesDB`/`reviewGatesDB`'s own upsert shape.
5. `core/packs.ts`: `validatePackSeed` validates each declared Service (code resolves against `service-name`, capabilityCode still same-Pack-only per today's existing rule, version required).
6. Test seeds/scripts updated in the same change, not after (standing discipline, restated in every CR since CR-058).
