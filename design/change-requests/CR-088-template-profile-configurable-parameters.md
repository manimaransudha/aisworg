# CR-088 — Template/Profile configurable parameters (Book 3 Ch.6 §13)

**Raised:** 2026-09-05 · **Origin:** owner, reviewing Chapter 6 (Template) §18 Acceptance Criteria before moving to Profile — "There is a gap that is required for profiles to work correctly." · **Status:** ✅ Closed 2026-09-05 — every one of Pack's component types walked (Capability: none; Service Level, Policy's `constraintType`/applicability, and Checklist's own new `configurableKey`/`configurableValue` tag all built end to end; Review Gate/Quality Gate/Authority Rules/Pack Dependency each confirmed to need nothing new). Built: Checklist's `configurable` field (migration 171, Ontology-backed `checklist-configurable-dimension`/`checklist-configurable-value`), Template's own "Exposable Parameters" tab (migration 172, `core/templates.ts`'s `deriveExposableParameterCandidates`, full `web/sdkAuthoring.ts` wiring, bespoke `_generatedFieldGroups.ejs` rendering) — value-plus-checkbox for single-value parameters, checkbox-only for list/filter ones, default-checked, candidate-driven not author-typed. Development Methodology's home — one of the three original open items — was settled 2026-09-05 in CR-091: a Configuration Parameter, not a Pack-selection slot. Profile's own override-storage mechanism — a second open item, briefly left deferred past its reason for being so — was itself built 2026-09-05, same day: `exposedParameterOverrides` (migration 176), scoped to Service Level/Policy's value-bearing candidates, its own "Parameter Overrides" tab (see "Explicitly not decided here" below for the full build note). **Updated 2026-09-06, from CR-092 Part 7's own TCS analogy** (*"When you commission from a profile, you are basically taking everything that is used for creating the profile in the first place. And if there are overrides, you take the overrides."*): the effective-value resolution itself — override if the Template left it overridable and the Profile actually set one, else the Template's own default — is now built, `resolveEffectiveParameters` (`core/profiles.ts`), and surfaced to the human on the Validation page (`extractProfileDetails`'s own `effectiveParameters`) before they commission. A fourth exposable-parameter source type, `dependency` (the Template's own deliverable dependency graph, one edge's `requiredState` per candidate), was added alongside Service/Policy/Checklist the same day — see CR-092 Part 7. **Still genuinely open, narrower than before**: `resolveEffectiveParameters`'s own output is not yet threaded into `compositionEngine.compose()`'s real EBM-building path — it is a pre-commissioning, human-facing preview only, not (yet) part of what gets persisted onto the composed EBM itself; and the still-unbuilt filter-shaped mechanism (Policy applicability, Checklist `configurableKey`/narrowing which items apply) remains exactly as unbuilt as before.

## The gap (confirmed live, 2026-09-05)

Chapter 6 §13: "Templates may expose configurable parameters. Examples: Development methodology, Technology stack, Target environment, Domain selection, Compliance requirements, Organisation Packs. These parameters are supplied during commissioning." Checked against the actual build — not partially built, entirely unbuilt:

- **Template's schema has nothing for it.** `schema_definitions` (Template v1) properties are just `code, name, purpose, templateVersion, deliverableCatalogue, dependencyGraph`, plus the six category-scoped mandatory-Pack fields. No declared parameter slots anywhere.
- **Profile's `configParameters` is untyped, unvalidated, free-form JSON.** `core/profiles.ts`/`profilesDB.ts` just `JSON.stringify` whatever's submitted straight into the `config_parameters` column — no schema check, no connection back to whatever Template `baseTemplateCode` points at.
- **Nothing downstream ever reads it.** Grepped `compositionEngine`/`commissioning.ts`/the whole `domain/` layer — the only other hit is `formGenerator.ts` bucketing it into the generic metadata field group so it renders as a plain JSON textarea in the authoring form. Accepted, stored, never consumed again.
- **Packs have no parameter concept either**, which is *why* Template can't expose anything: a Pack's own shape (`code, name, category, packVersion, installationClassification, description, owner, publisher, dependencies`, plus its `contributions`) has no configurable slot a consumer fills in — it's a fixed, versioned, published unit. Template, as "just a group of Packs and Deliverables," has nothing upstream of it to reach into and expose downstream (owner: "The template is just a group of packs and deliverables. It does not know what the parameters of the pack are for it to expose it downstream").
- §13's own five examples split once checked this way: **Technology stack, Domain selection, Compliance requirements, Organisation Packs** already exist as *which Pack, from a category, gets selected* — the category-scoped `technologyPackCodes`/`domainPackCodes`/`compliancePackCodes`/`organisationPackCodes` fields on both Template (mandatory) and Profile (optional). **Development methodology** doesn't map onto anything built.

## Design (owner, settled so far)

> "This is how we are going to fix it. For each of the component of a pack, we are going to define if that component has a configurable parameter."

Walking Pack's component types one at a time:

- **Capability — no configuration.** "Capability is just an ontology term - so no configuration there." A Capability is a pure Ontology `capability-name` shell (code + label), no shape of its own to parameterize.
- **Service — the Service Level *is* the configurable parameter.** "Service levels are the configurable parameters. Service definition can say 90% (that is the enterprise goal). A template can say 80% (just being realistic). The profile should be able to say 60% (tuned further for specific nature of work)." Refined after cross-checking against the Pack-level SLA override that already exists (`contributionServices[].serviceLevel[]`, target-only override, `label`/`units`/`target_level` inherited read-only from the Service Definition, the Definition's own row never overwritten) into a **four-layer cascade**, corrected once mid-discussion (owner: "Let me correct myself. I might have mixed things up"):
  1. **Service Definition** — the canonical/enterprise value (e.g. 90%). Definition.
  2. **Pack** — may override it with its own real value (already built, unchanged, no conflict with this design after the correction).
  3. **Template** — does not supply a number. Its job is to *flag* which of its selected Packs' service-level metrics are open for further tuning — a declaration ("this one is a configurable parameter"), not a value.
  4. **Profile** — supplies the actual override *value* for whichever metrics Template exposed as configurable. This is where the "60%" in the example actually lands, not at Template.
- **All four layers stay Definition, not Execution** — no matter how many layers of override stack up, none of it is an execution-dimension fact by itself (owner: "The override is all still definition unless something is commissioned against the profile"). Resolution into one concrete, effective value only happens once a specific SEU is actually commissioned (Template + Profile + resolved Packs → EBM) — the same moment `compositionEngine.compose` already resolves Authority Rules/Policies/Quality Gates into an EBM's own execution-facing shape today. Checked directly: `compositionEngine.ts` currently has zero handling of `serviceLevel` at all — this resolution doesn't exist anywhere yet, not even partially.

This reframes the real gap as two concrete pieces, not one: **Template needs an authoring surface** to mark specific service-level metrics (from whatever its selected Packs actually carry) as configurable — nothing like that exists today. **Profile's `configParameters` needs to become a structured mechanism** that supplies values *against exactly those flagged parameters* — replacing the current free-form, unvalidated, never-read JSON blob with something that has a real source and a real consumer.

**Settled, restated precisely (owner): "Template has to expose the configurable parameters (not values). Only Services allow edit of the values also."** Template's role never changes across Service/Checklist/Policy — it exposes *which* parameters are configurable, never a value; different Profiles built off the same Template can each supply a *different* value against the same exposed dimension, so Template flagging something as tunable is not itself a reusability problem. The one real exception is Service, where **Pack** additionally gets to edit/set a real value (`contributionServices[].serviceLevel[]`) — a capability unique to Service, not something Checklist or Policy have. (An earlier version of this CR briefly, incorrectly, read the "non-reusable" concern below as ruling out Template's own flagging step for Policy — corrected; see Policy's own entry.)

**The Template authoring mechanism itself, settled (2026-09-05) — closes open question 1.** Owner: *"When a template exposes both parameter and value (for service) — 1) value can be changed. 2) add a checkbox to the parameter. If this is checked, profile override on the value is allowed, otherwise it is not allowed. When a template exposes only parameter, only add a checkbox to the parameter. If this is checked, profile override on the values is allowed. By default all of the parameters are checked."* Two cases, distinguished by exactly the "Service-Level-shaped vs. Checklist-shaped" split this CR already draws:

- **A single tunable value** (Service Level metrics; Policy's `constraintType`) — Template's own form shows the current value (inherited from Definition, or Pack's own override where Service allows one) **and lets Template itself change it too**, plus **one checkbox per parameter**: checked = a Profile built off this Template may go on to override that value; unchecked = fixed, no Profile may touch it.
- **A parameter with no single value to show** (Checklist's own `configurable` tags; Policy's three applicability lists) — Template's form shows **just the checkbox**, nothing to edit at Template's own level (there's no one "value," only membership in a list) — checked = a Profile may narrow/filter it; unchecked = fixed as authored.
- **Default: every checkbox starts checked** — the same "absence/default means open, not closed" convention already established for Checklist's own missing-`configurable` and Policy's own empty applicability lists. A Template author has to actively *uncheck* a parameter to lock it away from Profile-level tuning; the safe, permissive default is always "configurable."

This also settles the shape of Profile's own side of open question 2: a Profile only ever sees, and can only ever act on, parameters whose checkbox is checked — supplying a replacement value for the first case, a filter selection for the second. Anything Template left unchecked is invisible to Profile, not just inert.

**Field placement, settled (2026-09-05) — closes the last piece of open question 1: a new "Exposable Parameters" tab.** Owner: *"create a tab Exposable parameters."* Not a sub-field bolted onto the existing category-scoped Pack-selection fields — its own dedicated tab on Template's authoring form, the same way Pack Codes/Deliverable Catalogue/Compatibility/Dependencies each already get their own tab rather than being folded into Identity & Metadata. Every value-plus-checkbox (Service Level metrics, Policy's `constraintType`) and checkbox-only (Checklist's `configurable` tags, Policy's three applicability lists) control, across every Pack/Service/Policy this Template actually resolves, lives there — one place to see and set everything this Template exposes, rather than scattered across each contribution type's own tab.

- **Checklist — a filterable tag per item, not a value override.** A different shape from Service Level: the configurable thing isn't a single number to tune, it's *which items even apply*. A Checklist item today is exactly `statement` (required, markdown) + `group` (optional, organisational label — confirmed against the live schema, `schema_definitions` Pack v1, `contributionChecklists.items.items.properties`) — nothing else. Owner: "In addition to group and a statement of the item, let us add an object called `{configurable: {type: required/mandatory/conditional, property2: config1/config2..}}`" — a third field, `configurable`, an object whose keys are whatever named dimensions a Pack author chooses per item (not a fixed set — one Pack might tag `type`, another might tag something unrelated).
  - **Template exposes every key under `configurable` mechanically** — unlike Service Level, there's no separate Template-level "pick which ones matter" step; whatever properties exist on any item from its selected Packs' Checklists all surface as configurable parameters automatically. Owner's own framing: "Imagine the configuration parameters to be excel columns that are filterable."
  - **Profile picks a filter value per exposed property** (e.g. `type = required`), and at commissioning the EBM includes only the checklist items whose `configurable.type` matches — "So when a profile says required, then the EBM picks all checklist items filtered for 'required'."
  - **Default is "all," on both sides** (owner: "When there is no configurable object or no configurable parameter, it is 'all'"): an item with no `configurable` object at all is always included, unconditionally, regardless of any filter a Profile applies. A property an item *does* carry but a Profile never sets a filter value for behaves the same way for that one dimension — unset means pass-through, not exclude. Filtering only narrows the set when a Profile actively selects a value *and* the item actually carries that same property to compare against; absence on either side always defaults to inclusion — the same behaviour an unset Excel column filter has (shows every row, hides none).
  - **`configurable`'s own values must be Ontology-driven, settled (2026-09-05) — closes open question 4.** Owner: *"All enums have to be ontology driven."* `type: required/mandatory/conditional` isn't free text a Pack author types — each named dimension a Pack author tags (`type`, or whatever else a Pack invents) resolves to a real Ontology concept type, the same discipline every other controlled vocabulary on this platform already follows, so two Packs contributing Checklists to the same Template can't drift onto `"Required"` vs. `"required"` vs. `"mandatory"` for what's meant to be the identical value — Profile's own filter picker sources from the same concept type, guaranteeing the two always line up. (Ch.24's own `applicabilityDeliverableLifecycle` stays the one standing exception, not overridden by this — it isn't free text either, it names real `transition_definitions` states, a different but equally real controlled source, per CR-089's own reasoning; `applicabilityDeliverableNames`/`applicabilityEnvironments` were already Ontology-backed before this instruction.)

- **Policy — two shapes at once, walked as part of [CR-089](../../change-requests/CR-089-canonical-policy-definitions.md)'s own canonical-catalog build (2026-09-05); the schema markers are real, the cascade/filter behind them is not.** Ch.24's new `policy_definitions` catalog carries four fields relevant here, splitting into the same two shapes already settled above — not a third, new one:
  - **`constraintType` (Policy/Standard, Ch.24 §4) is Service-Level-shaped** — a single value to tune, not a set to filter. Same three-layer shape as Service Level's own Template/Profile half, and the same "value + checkbox" authoring mechanism (above): Template's form shows the current value (e.g. "Policy," mandatory) and lets Template itself change it, plus a checkbox — checked (the default) means a Profile may go on to override it; unchecked locks it for every Profile built off this Template. **The one real difference from Service: no Pack-level edit step before Template's own.** Owner: *"Template has to expose the configurable parameters (not values). Only Services allow edit of the values also."* — that extra step (`contributionServices[].serviceLevel[]`) is a capability unique to Service; Policy's own adoption mechanism (`contributionPolicies[]`, CR-089, a plain `{code}` checkbox) was never meant to carry an equivalent, and that's not a gap to close.
  - **`applicabilityDeliverableNames` / `applicabilityEnvironments` / `applicabilityDeliverableLifecycle` (Ch.24 §9) are Checklist-shaped** — each a *list*, narrowed by which values apply rather than tuned to one number, and each already defaults empty-means-"all" (Ch.24's own established convention, the same default rule Checklist's own `configurable` settled on independently). Same "checkbox only" authoring mechanism as Checklist's own tags (above) — no value to show at Template's own level, just a per-field checkbox (default checked) gating whether a Profile may narrow that list.
  - **Built so far**: all four fields carry `x-configurable: true` on the real schema (`167_policy_definitions.sql`) — the same "discoverable by inspecting the schema, not a comment" marker this CR's own Checklist design already achieves via its `configurable` object, satisfying "how will downstream systems know this is configurable" structurally.
  - **Not built**: Template's own authoring surface to expose these four as configurable, any Profile-side override/filter mechanism for them, and `compositionEngine` resolving any of it. Chapter 24 §19.12 tracks this same gap from the Policy side; recorded here too so it isn't lost from the Template/Profile side of the design.

- **Review Gate — needs nothing new.** Review Gate's own participant-facing axis (`participant`/`assurance`) is thin, and its real content is a reference to something already configurable: `checklistIds`/`recommendedChecklistIds` point at Checklist, which already carries the `configurable` filterable-tag mechanism above. Owner: *"Review gates use checklists and checklists have configurable parameters. So review gates as such do not need any more configurations."*

- **Quality Gate — needs nothing new, for a related but distinct reason.** Unlike Review Gate, Quality Gate isn't participant-facing at all — it's evaluated automatically by `qualityGateEngine`, not performed by anyone (its own `participant`/`assurance`/`classification`/`outputContract` fields are inherited from the shared §20 shape but read by nothing in the engine). Its real content is just `category` (identity) and one of 4 `criteriaType`s, each either a fixed, binary check (`no_unresolved_obligations` — nothing to tune) or a reference to something already configurable: `requiredPolicyCodes` → Policy (CR-089's own `x-configurable`), `checklistIds`/`recommendedChecklistIds` → Checklist, `deliverableName` → Review Gate, which itself defers to Checklist. Nothing here has content of its own left to tune.

- **Pack Dependency (the category-scoped mandatory Pack fields) — no new *design* needed; the authoring surface already exists — but checked deeper and it doesn't actually work through to commissioning yet.** Owner: *"One more configurable for a template should be the pack dependencies. For example, a domain pack dependency should be configurable. So a template can have it empty. But a profile can choose a HIPAA pack."* — then, on reflection: *"we do not have to change anything at the template level. We just expose this in the profile."* Checked against the live code: Template's six category-scoped fields are already optional (`validateTemplateSeed` never requires a slot to be non-empty), so a Template leaving `compliancePackCodes` empty is already valid, no schema change needed. Profile already has its own matching category-scoped fields (`compliancePackCodes`/`domainPackCodes`/`technologyPackCodes`/`integrationPackCodes`, `core/profiles.ts`) to *author* a real Pack for exactly that kind of open slot — a HIPAA compliance Pack, in the owner's own example.
  **Corrected 2026-09-05, same day, on a deeper check prompted by reviewing Book 3 Chapter 7 §19.7 against this same conclusion:** authoring isn't the whole path — `compositionEngine.compose()` was checked directly, and it only ever resolves the *original* flat `optionalPackCodes` (`list_kind = 'optional'`); it never calls `getPackSelection` for `'technology'`/`'domain'`/`'compliance'`/`'integration'` at all. So a Profile author's HIPAA Compliance Pack choice is validated, stored, and correctly re-displayed/inherited — and then silently never reaches the composed EBM. This CR's own "needs nothing new" verdict was about the *authoring/design* question only (should Template flag this the way it flags Service/Policy/Checklist — no, Profile's fields already give a Profile author the picker it needs) and that verdict still stands; it does not mean the feature works end-to-end today. The actual gap — `compositionEngine.compose()` not resolving four of its five Profile Pack-selection list_kinds — is a *composition-engine* defect, not a configurable-parameter design gap, and was logged at Chapter 7 §19.7/§19.11 (owner: *"Log it for now"*, not fixed at the time) rather than reopened here. **Fixed 2026-09-06** (found again independently, mid-CR-092-Part-7 work, while chasing why a Profile's own category-scoped Pack picks weren't showing up in a composed Validation preview): `compositionEngine.compose()` now calls `getProfilePackSelections(profileId)`, which unions all seven `list_kind`s (the original `optional` plus all six categories, including Engineering/Organisation — Profile's own four-of-six authoring gap this same bullet flagged is moot now too, since `core/profiles.ts` already covers all six), instead of the old `optional`-only `getOptionalPackCodes`. The composition-engine defect this bullet described no longer exists.

- **Authority Rules — no new implementation planned, therefore nothing to make configurable either.** Walked separately and in depth against Chapter 22's own requirements (Book 3, Chapter 22 §19.16): every apparent gap in the noun×verb badge model (contextual authority, tenant composition, delegation, non-binary outcomes, declared Separation of Duties, per-SEU Capability-scoped authority) closes with a bounded, identified extension to the existing model — none require Pack-authored custom nouns/verbs, and the live Pack-contributed `authority_rules` table already exists but is confirmed structurally disconnected from real enforcement (Ch.22 §19.3/§19.9). Owner: *"No new implementation for authority rules unless we encounter a situation. So no configurable parameters either."* This stays out of scope until one of those extensions is actually triggered by a real requirement — not because Authority has no configurable dimension in principle, but because nothing is being built for it to configure.

## Explicitly not decided here

- **Deferred to Profile's own review, not undecided-and-open:** the concrete shape Profile's parameter-value mechanism should take for Service Level (a value per checked metric), Checklist (a filter value per checked property), and Policy (an override value per checked `constraintType`/applicability dimension) — replacing today's free-form `configParameters` blob, and whether that blob is retired outright or migrated, or whether one structure ends up covering all three shapes. Owner: *"2 & 3 will get addressed when we review profile."*
- **Deferred to Profile's own review, not undecided-and-open** *(partially built 2026-09-06 — see the corrected status line above)*: how `compositionEngine.compose` needs to change to actually resolve the Service Level cascade into one effective value, filter Checklist items by Profile's selected values, and apply Profile's Policy overrides against whatever Template left checked — all per SEU at commissioning time. The "resolve every value-bearing exposed parameter (Service Level, Policy `constraintType`, and now `dependency`'s `requiredState`) to override-or-default" half is now built as `resolveEffectiveParameters`, but only reached from the Validation page's own preview (`extractProfileDetails`) — `compositionEngine.compose()` itself still does not call it or fold its output into the composed EBM. The Checklist filter-narrowing half (which items even apply, per Profile's own filter selections) remains fully unbuilt, as does threading either resolution into the EBM that actually gets persisted at commissioning.
- **One constraint on that future shape, settled 2026-09-05 (found while auditing Ch.8 Commissioning): whatever value a Profile sets to override an exposed parameter must be stored as part of the Profile's own definition, not computed or left implicit anywhere else.** Owner: *"When an exposed parameter is modified, profile should store it as part of the profile definition. It is meaningless otherwise."* Consistent with — and now stated explicitly ahead of — the design above ("Profile supplies the actual override value"): the override is real Profile data, the same way CR-091's Configuration Parameters are, not a value derived at commissioning time or held anywhere outside the Profile row itself.
- **Built 2026-09-05, same day — the storage half of the constraint above.** Not deferred any further: the original reason (this was Template-focused work, "2 & 3 will get addressed when we review profile") stopped applying once CR-091 opened as the dedicated Profile CR, and should have been picked up there — a lapse, corrected here instead of on the closed CR. Owner, on being asked why it hadn't been: *"what nonsense CR88 defered bcz that was template changes. why did you decided itto be defere on a profile CR?"* then, confirming the fix: *"yes. the overrides have to be saved in the profile."* Built: Profile's own `exposedParameterOverrides` field (migration 176), scoped to value-bearing candidates only (Service Level metric, Policy `constraintType` — the two shapes a Template can itself set a value for; the list/filter-shaped ones, Policy applicability and Checklist `configurableKey`, have no value at all to override, only a permission-to-filter that still has nowhere to apply), sparse by design (an omitted candidate keeps the Template's own value, unlike Template's own non-sparse `exposedParameters`), candidates derived fresh from the Profile's base Template's saved `exposedParameters` (`deriveOverridableParameterCandidates`, `core/templates.ts`), its own "Parameter Overrides" tab (`_generatedFieldGroups.ejs`, mirroring Template's Exposable Parameters tab exactly). **Still not built** — bullets above, unchanged as of 2026-09-05: the `compositionEngine` resolution that would make a stored override actually take effect at commissioning. **Partially built 2026-09-06** (CR-092 Part 7): the resolution *algorithm* now exists (`resolveEffectiveParameters`, override-or-default per value-bearing exposed parameter) and is shown to the human on the Validation page ahead of commissioning — but `compositionEngine.compose()` itself does not yet call it, so it does not yet "take effect" on the composed EBM in the sense this line originally meant; the gap is now specifically "wire the preview's own resolution into the real composed output," not "build the resolution at all."
- ~~Whether Development Methodology (the one §13 example that maps onto nothing built) is a missing sixth category-scoped Pack-selection slot, or something this new configurable-parameter mechanism should carry instead.~~ **Settled 2026-09-05, in [CR-091](CR-091-profile-structure-completion.md)'s own §10 Configuration Parameters design**: a Configuration Parameter (`development-methodology`, under the new `profile-configuration` Ontology concept type), not a Pack-selection slot — a Profile picks a methodology the same way it picks a cloud provider or a language.

Field placement (a new "Exposable Parameters" tab) and the free-strings-vs-Ontology question are now both settled — see above.

Not building yet — recorded so the settled parts of the design (Capability/Review Gate/Quality Gate/Authority Rules need nothing new; Service/Checklist/Policy each have a real, fully-designed Template-side exposing mechanism now) and the genuinely open parts (Profile's own side, and Development Methodology's home) aren't lost before Profile itself gets looked at. Every one of Pack's component types has now been walked, and Template's own half of the mechanism is settled end to end.
