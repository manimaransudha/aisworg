# CR-081 — Pack "New" form: version is a computed sequence, existing-code branch picker, Copy removed

**Raised:** 2026-08-29 · **Origin:** owner, testing CR-079's new Category-driven Code combo box live — noticed `packVersion` shows `1.0.0` before anything is even chosen, and asked what actually happens when an existing code is picked on the "New Pack" form. · **Status:** ✅ Built 2026-08-29, layout corrected 2026-08-30.

## The gap

1. **`packVersion` was a hardcoded literal (`web/sdkAuthoring.ts`'s own `contentForForm`), shown before Category/Code are even chosen.** Owner: *"Version should not be shown in the form by default that is wrong."* Harmless while Code was free text with no real meaning yet (CR-015 era); actively misleading now that Code can resolve to an *existing* Pack with its own real version history — `1.0.0` implies "this will be the first version," which is often false.
2. **Picking an existing code on "New Pack" had undefined behavior.** `assertPackCodeVersionFree` only fires at submit time, as a flat refusal if the exact `(code, packVersion)` you happened to land on collides — nothing in the form told the author *what already exists* under that code beforehand, or what a sane next version even is.
3. **Registry "Copy"** (`copyPackAsNewDraft`) — pick a Pack, get a new Draft pre-filled with its content at the next patch version — turned out to be a subset of what the redesigned "New Pack" flow needed to do anyway (worked through in conversation, owner: *"which also means copy itself is redundant"*).

## The model, as settled (owner, worked through step by step)

- **Version is a single sequence per `(code, tenant)`, not a semver tree.** Owner: *"version is to be treated like a 'sequence'. If it['s] taken, assign the next."* A new Draft's version is always `(highest existing version for this code+tenant, across every status) with patch +1` — computed automatically, **never hand-typed**, regardless of which existing version's *content* the author chose to start from. Concretely: Active is `8.1.1`, author branches from Archived `1.2.3` for its content → the new Draft is `8.1.2`, not `1.2.4`.
  - This single rule closes two correctness gaps for free, worked through in conversation before building: (a) it makes a runtime "block Published→Active unless this is the highest version" guard unnecessary — a Draft is *assigned* the next-highest number the moment it's created, so it can never later turn out lower than something else; (b) it makes the "an invisible in-progress Draft could reserve a version number nobody sees" race harmless — `nextAvailablePatchVersion`'s own "if taken, try the next patch" loop already covers every status, seen or not.
- **The version list shown to branch from is Published-through-Archived only — never Draft or Validated.** Owner: *"Those are still 'draft'... they should be clickable and you should be able to continue edits"* — an in-progress Draft/Validated row isn't a finished thing to branch a new Version off of; the correct action for one of those is to go edit it directly (already possible from the author's own per-verb tab), not spawn a sibling.
- **Two scenarios on "New Pack," after Category is chosen:**
  1. **Type a new code** (doesn't resolve to any existing Pack for this tenant) — blank form, version computed as `1.0.0` (nothing exists yet), `ConceptCreated` fires as already built (CR-079) if the code isn't yet a registered Ontology concept.
  2. **Pick an existing code** — a small picker shows every Published-through-Archived version + its status for that code (this tenant's own lineage only — Platform's and a tenant's own lineage under the identical code text are independent series, same scoping `nextAvailablePatchVersion` already uses). The author can click one to **pre-fill the whole form from that version's content** (a real page reload with `?fromPackId=`, mirroring Template Inheritance's own `?parentTemplateId=` mechanism exactly — deliberately not a client-side JSON-rehydration exercise, since Pack's contributions are deep/nested and a real server render is the robust way to repopulate them), or continue with a blank form. Either way, the new Draft's version is the computed next-in-sequence number, not the source row's own version.
- **Registry "Copy" removed entirely** — `copyPackAsNewDraft`, its route, and its Registry button. Its exact job (pick an existing Version, land in a new Draft pre-filled with its content, at the next version) is now reachable through the one "New Pack" entry point instead of two.
- **"+ New Pack" visibility** — owner asked to confirm this is `pack_define`-gated. Checked: already was (`web/sdkAuthoring.ts`'s `canCreate = isRoot || held.has(authoringBadge(kind, "define"))`, already wired into `authoring/index.ejs`'s button). No change needed — confirmed, not built.

## Explicitly out of scope

- Any change to Template/Profile/DeliverableDefinition's own version-default behavior — `contentForForm`'s `1.0.0` default stays for those; this is scoped to Pack only, since only Pack's Code field is now Ontology-driven-by-category with a real branch-picker.
- A runtime guard on Published→Active comparing versions — settled as unnecessary given the sequence-assignment rule above (see "The model," bullet 1).

## Built 2026-08-29

> **`core/packs.ts`** — new `packCodeVersionSummaries(tenantId)`, returning `Record<code, { versions: Array<{id, version, status}>; nextVersion }>` for every code this tenant actually has a Pack row under: `versions` filtered to Published/Active/Retired/Archived only (Draft/Validated excluded, per the owner's own rule), sorted newest-first by real semver comparison (`compareSemver`, new — string comparison would sort `"10.0.0"` before `"2.0.0"`); `nextVersion` computed by finding the highest version among *every* status for that code, then reusing the existing `nextAvailablePatchVersion` (already does "if taken, try the next patch," now doing double duty as the sequence's own collision-safe increment). `copyPackAsNewDraft` deleted outright, along with `nextAvailablePatchVersion`'s now-single remaining caller wired through the new function instead of a second copy of the same logic.
>
> **`packsDB.ts`** — new `findAllForTenant(tenantId)` (`WHERE tenant_id = $1`, no Platform-visibility merge — Platform's and a tenant's own lineage under the identical code text are independent series, so the version picker must never blend them).
>
> **`web/sdkAuthoring.ts`** — `GET /sdk/:slug/new` gained `?fromPackId=` handling for Pack, mirroring `?parentTemplateId=`/`?parentProfileId=` exactly: loads the source Pack, builds `prefill.content` from it with `packVersion` overwritten to the freshly computed next-sequence value (never the source's own version). `renderAuthoringForm`'s `contentForForm` no longer defaults `packVersion` to `"1.0.0"` when no draft/prefill content exists — Template/Profile/DeliverableDefinition keep their own defaults unchanged. `req.vm.opt.packCodeVersions` (the new summaries map, Pack only) threaded to the view.
>
> **`_generatedFieldGroups.ejs` / `dynamicOntologyField.js`** — the Code combo box (built for CR-079/CR-080's earlier "this is really very bad" fix) now also drives a small version panel under the field: on selecting/typing a code, if `packCodeVersions[code]` exists, shows its version+status list as links to `?fromPackId=<id>` (the server derives code/category/content straight from the source Pack, so the link needs nothing else) and sets the Version field to the computed `nextVersion`, read-only; an unmatched (genuinely new) code sets it to `1.0.0` instead. Gated on `isNew` (a new `locals.isNew` param threaded through the include) — never rendered on an existing Draft's own edit page, where a `?fromPackId=` link would dead-end (only `/sdk/:slug/new` handles it) and touching Code could otherwise silently clobber that Draft's own already-saved version. The Version field itself no longer renders a literal default — blank until Code resolves to something, matching the owner's own "should not be shown by default" call; `updateVersionPanel` only ever runs off a real `input` event (typing, or picking a suggestion), never on page load, so an existing Draft's saved version is never touched just by the page rendering with Code pre-filled.
>
> **Copy removed** — `web/packs.ts`'s `POST /packs/:id/copy` route, its `router.param("id", ...)` (now unused — no other `:id` route exists in this file), `GET /packs`'s `canCopy` badge check, the Copy button in `seu/packs/index.ejs`, and the now-stale `canCopy` entry in `seu_packs_index.js`'s viewModel declaration, all deleted.
>
> **Test fixtures**: `pack-sdk.test.ts` gained a new test (`packCodeVersionSummaries: version is a sequence per code...`) proving both halves of the sequence rule directly against real data — a Draft sitting at a *higher* version than anything Published/Active still drives `nextVersion`, but never appears in the branch list; a different tenant's own lineage under the identical code text never leaks in. New migration `139` (`test-pack-sequence`, `engineering-name`) for it, same stable-concept discipline as 134–138. Also cleaned up: `bumpPatch`'s now-fully-unused import (its only callers were the reactivation tests CR-080 already deleted); the `copyPackAsNewDraft`/`nextAvailablePatchVersion` comment cross-references in `pack-sdk.test.ts` and `core/profiles.ts`.
>
> **`cleanSlate.ts`**: found and closed a real, pre-existing gap while checking it for this CR — `CATEGORY_SCOPED_PACK_NAME_CONCEPTS` (the dual-source-of-truth list a from-scratch `db:clean-slate` run depends on) had never been kept in sync with migrations 134–136's own stable test-Pack codes, only migration 132's. On a genuinely fresh database (one that never had 134–139 individually applied via `psql`), every test in `pack-composition.test.ts`/`engine.test.ts`/`governance-ebm-sharpening.test.ts`/`pack-sdk.test.ts`/`web-flow.e2e.test.ts`/`sdk-authoring.test.ts` relying on those codes would fail `code is not a canonical {category}-name concept`. Added all 34 missing `engineering-name` + 2 `organisation-name` entries (134/135/136/138/139's codes) in one pass rather than one CR at a time, per the same "known, accepted drift risk" this list's own header already names. (A related gap in the same file — CR-080's new `pack_comments` table never being cleared ahead of `DELETE FROM packs` — was found and fixed the same day, in direct response to the owner's own "does clean-slate need update?" check, before this CR was opened.)

> **Bug fix, found live in the browser (owner: "there is a nextversion button on the form. is that required?"): removed for Pack specifically.** `_generatedFieldGroups.ejs`'s "Next version" button (CR-024) is a pure client-side +1-patch bump with no server/collision check at all — harmless when a fresh draft always started at a hardcoded `1.0.0` (Template/Profile/Deliverable, unchanged, still use exactly that model), but actively wrong for Pack now: clicking it on the already-correct, computed sequence value would silently produce an arbitrary uncomputed one, and clicking it while the field is still blank (before Code is even chosen) would wrongly reintroduce "1.0.0 shown before it should be" — the exact thing this CR was built to fix. Excluded via `f.name !== 'packVersion'`, scoped to Pack's own field name only (Template/`templateVersion`, Profile/`profileVersion`, Deliverable/`definitionVersion` all keep the button, unaffected).

## Layout corrected 2026-08-30

The 2026-08-29 build above put the whole version story (computed value + branch-picker) into `packVersion`'s own column, next to Code. Owner testing against the live page (booted for real, per the owner's own insistence — *"why dont you do this? run a smoke test against the page... look at what is in the page"* — after the first read-the-code-only pass missed the real layout) surfaced that the page was, in the owner's words, *"extremely hard to even understand what is happening"*, and walked the layout to its final, precise shape across several corrections:

- **Category is forced full-width (`col-12`)** — its own row, not sharing with Code. Name-checked (`f.name === 'category'`), so Template/Profile (no `category` field) are unaffected.
- **There are two separate pieces of version information, not one** (owner: *"there are 2 version information on the page. do you recognise that in the first place?"*), and they go to two separate places:
  1. **The version *selector*** — the clickable list of existing Published-through-Archived versions to branch content from — renders in `packVersion`'s own column, alongside Code (same row), now labelled "Existing versions" since that column no longer shows a version value at all, only choices. `isNew`-gated, unchanged from the 2026-08-29 build.
  2. **The computed version *value* itself** — what this Draft's version will actually be — renders as a muted `(v1.0.1)` span next to Name's own label (`#packVersion-display`), not in its own column. A hidden `<input type="hidden" name="packVersion">` (also in `packVersion`'s old column-slot, always rendered regardless of `isNew`) carries the actual value to the server — needed because, unlike the 2026-08-29 build, `packVersion`'s own column no longer renders any visible control at all when continuing to edit an existing Draft (nothing to branch from, so the "Existing versions" block is skipped, and prior to this fix that column rendered nothing whatsoever — silently dropping `packVersion` from the submitted form).
  3. **Name moved to its own row**, immediately after the Code/selector row, pairing with Description.
- **Redundant help text suppressed** — Code's own driven-combo already had its own inline help line; the schema's generic `f.help` for that same field was a third stacked block of muted text underneath, purely redundant. Suppressed for that one case (`f.kind === 'referential-select' && f.ontology && f.dynamicSourceField`) only.
- **Dropdown-overlay fix** — the underlying cause (owner: *"why can't you show the version selector alongside the code? ... whatever you are doing is not solving the dropdown overlay"*) was that the selector previously never actually left Code's own column; Code's suggestion menu (`position: absolute`, extends downward within its own column) could overlay it regardless of anything else moved around it. Moving the selector into `packVersion`'s own column — a structurally separate column, not just a differently-styled element in the same one — is what actually fixes it, not any restyling within Code's column.
- **`dynamicOntologyField.js`'s `updateVersionPanel`** now updates three things off the same `input` event, all form-wide lookups (none are DOM-proximity-based to the combo, since none are siblings of it any more): the hidden `packVersion` input's value, the `#packVersion-display` span's text, and the `.pack-code-versions` selector panel's contents.

Verified directly against a live `NODE_ENV=test` app instance (`app.listen(0)`, real `fetch()`, real rendered HTML — not reasoning from the template source): Category renders alone in a `col-12`; Code's combo and the "Existing versions" `col-md-6` land in the same `row g-3` block with nothing between them; the hidden `packVersion` input is present (blank on a genuinely new Draft, `1.0.1` when prefilled via `?fromPackId=`); the muted `#packVersion-display` span sits inside Name's own `<label>`, tracking the hidden input's value exactly (`(version pending)` blank, `(v1.0.1)` prefilled); the old dead "Computed automatically once Code is chosen" copy (now unreachable for Pack, since `packVersion`+`Pack` no longer reaches the generic `f.kind === 'version'` branch at all) is gone. `pnpm typecheck` and `ejs.compile` clean.
