# CR-027 — SDK / Authoring surfaces: horizontal tabs → vertical side tabs

**Raised:** 2026-08-19 · **Origin:** owner — "on all the pages on SDK / Authoring, move the horizontal tabs to vertical ones on the side. There are too many tabs in some pages and the tab styling is so bad it reads like plain text." · **Status:** ✅ Built 2026-08-19

> **Built 2026-08-19.** Presentation-only — no route, authorization, or data change anywhere. Verified over real HTTP (booted the real app, no mocking): all three original index pages (`pack-authoring`, `template-authoring`, `profile-authoring`, `transition-definition-authoring`, `ontology` at both a chosen and a default concept type, `authority/nouns`, `authority/verbs`, `authority/mapping`) return 200 with the new `vertical-tabs` markup present; the three `new`-draft authoring forms (which exercise the generated form's own section tabs, added to scope mid-CR) return 200 with 9–18 occurrences of the same class (Pack's Draft form renders it twice, once per Meta/Items stepper pane). `<div>`/`</div>` balance checked on every edited file after each change.

### What's built here
- **One new shared partial, [`verticalTabs.ejs`](../../src/views/partials/verticalTabs.ejs)**, replacing four independent horizontal `nav-tabs` blocks. Two modes: **link tabs** (each tab a real `<a href>` navigation, `active` names the current key — used by Ontology and Authority) and **pane tabs** (`paneMode: true`, Bootstrap's own vertical-pills `data-bs-toggle="tab"` pattern switching a sibling `.tab-content` in place — used by the per-verb authoring tabs and the generated form's own section tabs). `paneIdPrefix` (default `"tab"`) and `activePaneIndex` (default `0`) exist specifically for the generated-form case: two copies of the same tab set render per page (the Meta/Items stepper), needing distinct pane ids, and the active pane isn't always the first one (jumps to whichever section already has real content).
- **[`authorityTabs.ejs`](../../src/views/partials/authorityTabs.ejs)** now delegates to `verticalTabs.ejs` — same 4 tabs (Nouns / Verbs / Mapping / Transition Definition), vertical instead of horizontal. Callers (`authority/index.ejs`, `authoring/index.ejs`'s Transition Definition case) wrap it alongside their own content in a `d-flex flex-column flex-md-row` row — the tab column is a sidebar, not a page-top bar.
- **[`authoring/index.ejs`](../../src/views/seu/sdk/authoring/index.ejs)** — unified the two tab situations that page could show (the per-verb Draft tabs for Pack/Template/Profile, up to 7; or, Transition-Definition-only, the authority tabs) into one left sidebar, with the tab content *and*, for Transition Definition, the "Current Transition Definitions" table below it, both in one content column beside the sidebar.
- **[`ontology/index.ejs`](../../src/views/seu/sdk/ontology/index.ejs)** — concept-type tabs are now the same vertical sidebar. This surface benefits most structurally: the concept-type list is an open, tenant-extensible vocabulary (Ch.18), so its tab count has no ceiling the way Pack's 7 lifecycle verbs do.
- **[`_generatedFieldGroups.ejs`](../../src/views/seu/sdk/_generatedFieldGroups.ejs)** — added to scope mid-build (see *Design decisions*): the generated authoring form's own section tabs (Identity & Metadata / Compatibility / Dependencies / one tab per Contribution type) were a *second*, independent horizontal `nav-tabs` row nested inside the Meta/Items stepper — for a Pack Draft with many contribution types, this could run to 8+ tabs, a worse case of "too many tabs" than the surface the CR originally named. Converted the same way, wrapped in its own flex row inside the partial (it owns both its tab list and its content, unlike the other three surfaces where the *calling* page does the wrapping).
- **Responsive fallback, no JS**: `verticalTabs.ejs`'s own CSS switches the tab column to a horizontal, wrapping pill row below the `md` breakpoint (`767.98px`), while the outer `flex-column flex-md-row` wrapper stacks it above the content column instead of squeezing a sidebar into a narrow viewport.

### Design decisions
- **`_generatedFieldGroups.ejs` was explicitly out of scope when the CR was first raised, then pulled in.** The original CR text called it "a different, already-vertical-ish UI element" — written from memory of the Meta/Items *stepper*, without having actually opened the file. Once opened, it turned out to be a second, independent horizontal-tabs implementation one layer deeper (the stepper is a two-step wizard; this is a `nav-tabs` row *inside* one of the wizard's own steps) — squarely the kind of surface the owner's complaint named. Flagged transparently, confirmed by the owner, then built — not silently expanded.
- **One shared component over four separate implementations**, per the CR's own stated direction — `paneIdPrefix`/`activePaneIndex` exist only because the generated-form case has requirements (id-prefix collision avoidance across the stepper's two panes, a non-default active tab) none of the other three callers need; both default to the simpler per-verb-authoring-tabs behaviour so that caller needed no changes beyond the markup itself.
- **No accordion/dropdown collapse on narrow screens** — a wrapping horizontal pill row was simpler to build and matches how Bootstrap's own default `.nav-pills` already behaves without extra JS; revisit if it proves cramped in practice.

### Not in scope
- Any change to which tabs exist, what each shows, or the authorization/visibility logic behind them (`buildAuthoringTabs`, `listAuthoringByVerb`, `listAuthoringQueue`, `groupFieldsForDisplay`) — all untouched.
- Any other tab/nav surface outside the SDK/Authoring group (e.g. the authoring form's own Meta/Items *stepper* itself, which is a different, non-`nav-tabs` widget the owner didn't flag).
