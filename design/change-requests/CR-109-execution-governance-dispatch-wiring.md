# Execution / Governance / Dispatch Wiring — Design Note

Started 2026-09-17. Spec-only design trace: how WorkItem, Deliverable, Command, Dispatch Engine, Evidence, Decision, Knowledge, Governance and Obligation connect, per the governing chapters (21, 23, 31, 32, 33, plus 9, 12, 16, 17, 19). Current-build gaps are ignored here on purpose — those are already recorded in each chapter's own §19/§17 Implementation Specifics (Ch.21 §17, Ch.31 §19, Ch.32 §19). This note is about the wiring the specs call for, not what exists.

No code in this note. Nothing here is approved for build until called out explicitly.

---

## 1. One line per entity, as the specs define it

- **Deliverable** (Ch.15) — the persistent engineering asset; the only thing with real state.
- **Command** (Ch.31 §10) — a request for engineering action, generated by the Execution Engine. Expresses *what*.
- **Work Item** (Ch.32) — a transient, Participant-specific execution plan derived from a Command. Expresses *how, for this Participant*.
- **Dispatch Engine** (Ch.33) — selects *who* (which eligible Participant) executes a given Work Item, right now.
- **Capability Fulfilment** (Ch.12) — the slower-moving service of record for *which Participants are eligible at all* to provide a Capability. Upstream of Dispatch, not part of it (Ch.33 preamble).
- **Governance Model** (Ch.21) — the pure evaluation layer that decides whether a transition is *permitted*. Authority + Policy + Obligation + Quality Gate + Review are its components (Ch.21 §7).
- **Obligation** (Ch.23) — a real, resolvable governance work item; raised when a Policy blocks a transition; its resolution is itself a governance-relevant event.
- **Evidence → Knowledge → Decision** (Ch.17, 16, 19) — the trust pipeline: Evidence is the raw verifiable fact, Decisions are conclusions reached by weighing Evidence/Knowledge, Knowledge is what gets carried forward for reuse. All three are declared inputs to later Governance evaluation (Ch.21 §7 lists none of them directly, but Ch.31 §7/Ch.33 §7/§12 do).

## 2. The pipeline, per spec (Ch.31 §3/§9 + Ch.32 §3 + Ch.33 §3, merged)

```
Engineering Events (incl. Obligation resolution, Evidence/Decision/Knowledge published)
        │
        ▼
Execution Engine  ── observes Events, evaluates Dependency readiness,
        │             evaluates Transition Definitions
        ▼
Governance Evaluation (Ch.21) ── Authority + Policy + Obligation + Quality Gate
        │             (Approved / Approved-with-Conditions / Deferred / Rejected / Escalated / Waived)
        ▼   (only on a non-blocking outcome)
Capability Fulfilment request (Ch.12) ── resolves required Capability →
        │                                  eligible-Participant pool (Eligibility Policies applied here)
        ▼
Command generated (Ch.31 §10) ── entityType/entityId/fromState/toState + governance rationale
        │
        ▼
Work Item Generator (Ch.32) ── one Work Item per Participant-adaptation needed,
        │                        each carrying Execution Context (Ch.32 §11)
        ▼
Dispatch Engine (Ch.33) ── selects among the eligible pool using Dispatch Context
        │                    (Ch.33 §7/§12: Knowledge, Decisions, Obligations, Policies, Authority)
        ▼
Participant executes
        │
        ▼
Deliverable State Transition + Event published
        │
        ▼
Evidence / Decision / Knowledge recorded as outputs of this execution (Ch.17/19/16)
        │
        └──────────────► feeds back into "Engineering Events" at the top
```

This closes the loop the way Ch.16 §3 states it: Knowledge "bridges one SEU to the next" — a Decision made during Deliverable X's execution becomes an input the next Governance evaluation or Dispatch decision can read.

## 3. Three distinct checkpoints, not one — this is the part worth being precise about

The same underlying data (Policies, Obligations) gets consulted three times in this pipeline, for three different questions. They are not duplicates of each other; conflating them is the wrong design.

| Checkpoint | Question | Chapter | When |
|---|---|---|---|
| **Governance Evaluation** | Is this transition *permitted at all*? | Ch.21 | Before a Command is generated |
| **Capability Fulfilment eligibility** | Which Participants are *eligible in principle* to provide this Capability? | Ch.12 §8 | Before/independent of any specific Command — a standing pool |
| **Dispatch selection** | Given the eligible pool, *who executes this specific Work Item now*? | Ch.33 §7/§12 | After the Command/Work Item exist |
| **Work Item Execution Context** | What does the *assigned Participant* need to know to do the work correctly? | Ch.32 §11 | Attached to the Work Item at generation, read by the Participant |

CR-104's own two Policies map cleanly onto two different rows of this table, and that mapping is itself confirmation the four-checkpoint model is right, not an accident of this one demo:

- **`cr104-demo-seu-commence-work`** — `scope: "Transition"`, governs `SEU|Activated|Operational`. This is a **Governance Evaluation** input (row 1) — it blocks a *transition*, not a Participant selection, and its resolution raises a real Obligation (Ch.23) whose own later resolution is what should re-trigger Governance Evaluation for the transition it blocked.
- **`cr104-demo-background-check`** — `scope: "Eligibility"`, checked against a candidate Participant's own `behaviour_context`, "never against a transition" (per the Policy's own seed description). This is a **Capability Fulfilment eligibility** input (row 2) — it never blocks a transition; it removes a Participant from the eligible pool.

So "the blocking background check is cleared" in your scenario is specifically a Capability Fulfilment-level event (a Participant's `behaviour_context` now satisfies the Eligibility Policy), not a Governance Evaluation event. It changes *who can be in the pool*, not *whether the transition is allowed*.

## 4. Walking your CR-104 scenario through the pipeline

Given: CR-104 Profile commissioned, EBM composed with its Deliverables, and the background-check Eligibility Policy is now satisfied for some candidate Participant.

1. **Trigger.** Some prior Event makes a Deliverable's next transition dependency-ready (Ch.9 Dependency Engine) — e.g. an upstream Deliverable reached the state this one depends on, or the SEU itself reached `Operational` (which itself required its own Obligation, from the *other* CR-104 Policy, to resolve first — see §3 above; that is a separate, prior loop through this same pipeline, at SEU scope instead of Deliverable scope).
2. **Execution Engine** observes that Event, confirms dependency readiness, and resolves the applicable `transition_definitions` row for the Deliverable's eligible next hop (Ch.31 §9 steps 1–3).
3. **Governance Evaluation** (Ch.21) runs: Authority (does *some* actor/root have standing to authorise this hop — this is checked again per-actor at the actual apply step, Ch.21 §17.2), Policy (any `scope: "Transition"` Policy governing this hop — not the background-check one, which is `scope: "Eligibility"` and plays no role here), Obligation (any open, blocking Obligation against this Deliverable or its owning SEU — Ch.23), Quality Gate. Outcome: Approved (or Approved-with-Conditions if a Standard-constraint Policy deviated, Ch.21 §10).
4. **Capability Fulfilment** is consulted for the Capability this Deliverable's transition requires (Ch.31 §12: "Where engineering work is required, the Execution Engine shall request Capability Fulfilment"). This is where the background-check Eligibility Policy is applied — filtering the SEU's assigned-Capability Participant pool down to those with a satisfying `behaviour_context` entry. Only participants passing this filter are in the pool Dispatch will choose from.
5. **Command generated** (Ch.31 §10) — carries the Deliverable's `entityType/entityId/fromState/toState`, and should carry (per Ch.21 §12/Ch.31 §14 traceability requirements) a reference to *which* Governance outcome authorised it: the resolved Policy ids checked, the Obligation-clear state at evaluation time, the Quality Gate outcome. This is the rationale record both chapters require to be reconstructable.
6. **Work Item Generator** (Ch.32) derives one Work Item (or more, once Ch.32 FR-32.2's multi-Participant fan-out exists) from the Command. Each Work Item's Execution Context (Ch.32 §11) is populated by reading straight off what Governance already resolved in step 3/5 — not re-deriving it: relevant Deliverable, applicable Knowledge/Evidence linked to this Deliverable or its Capability, the governing Policies that were checked, the applicable Authority, and any *still-active* (non-blocking, since a blocking one would have stopped step 3) Obligations relevant to this Deliverable, for the Participant's own awareness.
7. **Dispatch Engine** (Ch.33) receives the Work Item plus the eligible-Participant pool from step 4, and applies its own Dispatch Context (Ch.33 §12: current Deliverable state, engineering stage, active Knowledge, active Decisions, active Obligations, current Participant state, Transition Definitions) and a Dispatch Strategy (Ch.33 §9 — Capability Match at minimum) to pick one Participant from that pool and assign the Work Item.
8. **Participant executes**, reports a result. The Deliverable transition is applied (this part — Ch.32 §12/WI-005 — is already correctly wired in the current build, per Ch.32 §19.3).
9. **Evidence/Decision/Knowledge** produced by this execution (if any — e.g. a Review's outcome, a recorded Decision) are persisted (Ch.17/19/16) and published as Events, which become inputs to the *next* pass through step 1–3 — closing the loop Ch.16 §3 describes.

## 5. What has to flow between stages — the actual "connective tissue"

The wiring gap in every case is the same shape: a downstream stage needs to *read* what an upstream stage already decided, rather than silently re-deriving it (which risks drift and breaks Ch.21 GM-004/Ch.31 FR-31.6/Ch.33 FR-33.4's traceability requirements — every one of those calls for a *reconstructable rationale*, not just a correct-in-the-moment decision).

Concretely, three data contracts are what's missing, in order:

- **Governance outcome → Command.** The Command needs to carry (or reference) which Policies/Obligations/Quality-Gate outcome authorised it, not just the bare `fromState/toState`.
- **Command/Governance outcome → Work Item Execution Context.** The Work Item Generator needs to read that same governance record (plus Knowledge/Evidence tied to the Deliverable/Capability) to populate Ch.32 §11's context, rather than the Participant having no visibility into why/under what constraints this work was requested.
- **Governance outcome + Capability Fulfilment pool → Dispatch Context.** Dispatch needs the same active-Obligations/active-Policies/active-Knowledge/active-Decisions view (Ch.33 §7/§12) to make a *governed* selection among eligible Participants — e.g. an Obligation naming a specific remediation owner, or a Policy requiring a specialist reviewer, should be able to steer Dispatch's choice, not just gate whether the transition happens at all.

## 6. Service contracts — the shape of what flows between stages

§5 named three connections. Each one is a real service contract — a defined shape one stage produces and the next one reads — not just "pass the data along." Naming the fields now, grounded in what each chapter already lists as that entity's required components, plus the connective fields §5 identified as missing. This is still a data-shape design, not a schema — no types, no table DDL.

### 6.1 Governance Evaluation Outcome (Ch.21 §10, §12)

Produced by Governance Evaluation (§4 step 3), consumed by Command generation (6.2) and nothing else — this is the one place the four-way outcome (§3's row 1) is decided, and it is decided exactly once per transition attempt.

| Field | Ch. source | Notes |
|---|---|---|
| `outcome` | §10 | One of Approved / Approved-with-Conditions / Deferred / Rejected / Escalated / Waived |
| `rationale` | §10, §12 | Mandatory on every outcome, not just Rejected — "every outcome shall include a recorded rationale" |
| `governingRule` | §12 | Which Policy/Obligation/Quality Gate/Authority rule actually decided it |
| `originatingPack` | §12 | Traceable to the Pack that contributed the governing rule |
| `applicableAuthority` | §12 | The badge/authority rule checked, and against whom |
| `satisfiedPolicyIds` / `deviatedPolicyIds` | §7, §10 | Standard-constraint deviations that let it through anyway (Approved-with-Conditions) vs Policy-constraint ones that would have blocked it |
| `consultedObligationIds` | §7 (GM-005) | Which open Obligations were checked, and their state *at evaluation time* — this is the field decision (B) turns on |
| `evaluatedAt` | §12 | Timestamp |

### 6.2 Command (Ch.31 §10, §14)

Produced by the Execution Engine once Governance Evaluation returns a non-blocking outcome. One Command per eligible transition (Ch.31 §10: "generated only when all prerequisite conditions have been satisfied").

| Field | Ch. source | Notes |
|---|---|---|
| `entityType` / `entityId` | existing | The Deliverable (or other entity) this Command targets |
| `fromState` / `toState` | existing | The transition this Command requests |
| `governanceOutcomeRef` | §14 (new — connective) | Reference to 6.1's record — "applicable Governance outcome" is explicitly named as something execution history must preserve |
| `triggeringEventId` | §14 | The Event that caused the Execution Engine to evaluate this in the first place |
| `requiredCapability` | §12 (Capability Integration) | What Capability Fulfilment must resolve before a Work Item can be generated |
| `eligibleParticipantPoolRef` | §12 (new — connective) | Reference to whatever Capability Fulfilment resolved for `requiredCapability` |
| `correlationId` / `causationId` | existing | Event-chain linkage, already a platform-wide convention |

### 6.3 Work Item — Execution Context (Ch.32 §7, §11)

§7 already names the components; §11 names what Execution Context specifically must include. The gap (Ch.32 §19.7) is that these fields aren't populated from anything. Once 6.1/6.2 exist, they're populated *by reference*, not by re-deriving:

| Field | Ch. source | Populated from |
|---|---|---|
| `commandRef` | §7 | 6.2 |
| `assignedParticipant` | §7 | Set by Dispatch (6.4), not at generation — a Work Item may exist briefly unassigned |
| `engineeringObjective` | §7 | The Deliverable's own name/description, off `entityId` |
| `inputReferences` / `expectedOutputs` | §7 | The Deliverable's Template-declared inputs/outputs (existing Deliverable model, not new) |
| `constraints` | §7, §11 | `governingPolicies` (6.1's `satisfiedPolicyIds`) + `applicableAuthority` (6.1) |
| `relevantKnowledge` / `supportingEvidence` | §11 | Knowledge/Evidence linked to this Deliverable or Capability (Ch.16/17) — a query, not a copy |
| `activeObligations` | §11 | 6.1's `consultedObligationIds`, filtered to non-blocking (a blocking one would have stopped 6.1 from reaching Approved) |
| `priority` | §7 | From the Command / SEU priority, not invented here |

Note what this contract deliberately does *not* do: it doesn't re-run Policy/Obligation evaluation. It reads 6.1's already-decided record. Re-deriving here is exactly the "different picture than what Governance approved" risk decision (B) below is about.

### 6.4 Dispatch Decision (Ch.33 §8, §12, §13)

Produced by the Dispatch Engine once it selects among the eligible pool (6.2's `eligibleParticipantPoolRef`).

| Field | Ch. source | Notes |
|---|---|---|
| `workItemRef` | §13 | 6.3 |
| `selectedParticipant` | §8, §13 | The chosen Participant (or set, for parallel/one-to-many, FR-33.3) |
| `dispatchStrategy` | §13 | Which named strategy (§9) selected them |
| `evaluationCriteria` | §13 | The Dispatch Context actually read: `activeKnowledge` / `activeDecisions` / `activeObligations` (§12) — same 6.1-derived view Work Item's Execution Context reads, reused, not re-queried separately |
| `rationale` | §13 | Why this Participant over others in the pool |
| `outcome` | §8 | Assigned / Parallel / Deferred / Redispatch / Escalation |
| `timestamp` | §13 | |

Reusing 6.1's Obligation/Policy/Knowledge/Decision view for both 6.3 and 6.4 (rather than each stage independently querying `obligationsDB`/`decisionsDB`/etc.) is what keeps the three checkpoints in §3 consistent with each other — Dispatch and the Participant then see the *same* governance picture Governance itself decided against, at the times each of them ran.

## 7. Open design decisions — need your call, not mine

These are the points where the spec is clear on *what* must connect but doesn't dictate *how* the runtime should be built to do it. Three real decisions:

**(A) Does the Execution Engine become reactive, or stay caller-triggered?**
Ch.31 §9's cycle (Observe Events → Evaluate State → Identify Eligible Transitions → Evaluate Governance) describes an autonomous loop. Today, nothing plays that role — a human/API call to `transitionDeliverable` is what starts the chain. Minimal: keep it caller-triggered, but make the *SEU reaching Operational* (once its own Obligation resolves) and *an Obligation resolving against a specific Deliverable* real Events that a subscriber uses to auto-attempt the now-unblocked Deliverable's next hop — extending the one existing precedent (`executionEngineKickoff`'s SEU-only retry) to Deliverables generically. Full: build the always-on reactive cycle Ch.31 §9 literally describes, watching all Events. This is a big scope difference — minimal is an extension of an existing, working pattern; full is a new always-on service.

**(B) Snapshot governance rationale onto the Command, or re-query live at each downstream stage?**
Snapshotting (Command carries `{satisfiedPolicyIds, obligationStateAtEvaluation, qualityGateOutcome}`) gives Work Item/Dispatch a consistent, reconstructable record matching what Governance actually decided — but it can go stale if state changes between Command generation and dispatch (e.g. a new Obligation is raised in between). Live re-query keeps everything current but means Work Item/Dispatch could see a *different* Obligation/Policy picture than what Governance actually approved against, which is arguably worse for traceability (GM-004 wants "every governance decision explainable" — explainable against what was true *then*, not what's true *now*). My reading of the spec favours snapshotting for the rationale (what was decided) plus a live read for anything genuinely time-sensitive (Participant availability) — but this is a real trade-off, not a default I should just pick.

**(C) Does Capability Fulfilment become Execution-Engine-triggered, or stay a manual UI action feeding a pool Dispatch draws from?**
Ch.31 §12 says the Execution Engine "shall request Capability Fulfilment" — reactive. Today, fulfilling a Capability (assigning a Participant to it) is a manual "Fulfil" action on the SEU detail page (`core/capabilities.ts`), and Dispatch/Execution never call it. Minimal: leave Capability Fulfilment as the standing, manually-maintained pool it is today (Ch.33's own framing — "slow-moving, structural," changes "when a Participant is onboarded... not on every unit of work" — actually supports leaving this manual); Dispatch simply reads whatever pool currently exists, and if it's empty, defers (already-built behaviour, `deferredReason: "no_eligible_participant"`). Full: make an empty pool trigger an automatic Capability Fulfilment request rather than just deferring forever. Given Ch.33's own stated rationale for keeping Capability Fulfilment slow-moving, I'd lean minimal here — but flagging it as a decision, not assuming.

## Proposed flow

Summary of what we settled walking through 1–9 above, corrections included. Numbering continues from the Command/Work-Item-Generator discussion.

10. **EBM, settled definition:** the EBM is just the composed set of every rule and reference an SEU needs. Nothing more elaborate than that — not decomposed into named "categories" as a working model; that framing (§7's Behaviour Categories) is spec text, not how to reason about what's in it day to day.

11. **Objective ≠ Requirement (Ch.1 §4, explicit).** "An Objective is not a Requirement. A Requirement is a system property the Objective motivates." Engineering Objectives are not where "which requirements this SEU covers" lives — that mapping was wrong and is retracted.

12. **Requirement scope is SEU-instance data, and it doesn't fit Profile, Template, or Pack — all three are reusable definitions** (Ch.7 §1/§4: "A Profile contributes configuration... does not contribute engineering behaviour," reusable across SEUs; same reusability property rules out Template and Pack). A specific list like "these 5 of 100 requirement IDs" can't live on any of them without breaking reuse for every other SEU commissioned from the same Profile/Template/Pack.

13. **The Deliverable instance itself is SEU-scoped (Ch.15 FR-15.2: "every Deliverable shall belong to exactly one SEU")** — so unlike Profile/Template/Pack, the Deliverable instance is the right *kind* of object for SEU-specific data to attach to. But its own Structure (Ch.15 §8) has no content field for it — only `Knowledge References` and `Evidence References`, both outward pointers, not inline data.

14. **The actual scoping decision — "this Deliverable instance covers requirement IDs X, Y, Z" — is a Decision (Ch.19), specifically a project-scope Decision, wired in as a Decision Dependency (Ch.9 §8: "Execution requires an approved decision").** Ch.19 §8's own Decision Structure already has the right shape to hold it: Engineering Question, Context, Alternatives Considered, Selected Alternative (the chosen requirement IDs, expressed via Supporting Knowledge/Evidence references), Assumptions, Consequences. Per Ch.19 §9, "Only Approved Decisions may influence Deliverable state transitions" — so this Decision reaching `Approved` is what satisfies the Decision Dependency gating this Deliverable's `Defined → In Progress` readiness, alongside its existing Capability Dependency.

15. **Open gap, flagged not resolved: there is no described authoring surface anywhere in the spec for creating this Decision.** Someone holding the relevant Authority needs to author it (populate §8's fields, walk it through §9's lifecycle to Approved) before this Deliverable's readiness can ever be satisfied. This is real, necessary, missing scaffolding — not something any existing chapter names a mechanism for.

16. **Where the raw candidate content (the 100 requirements) comes from, so the Decision has something to select from:** a **Commissioning Parameter on the Profile** (Ch.7 §10: "Parameter semantics are defined by the consuming Pack") — the Profile (reusable) declares that a "requirements document location" parameter slot exists; the actual value (a pointer, e.g. a document location) is supplied per-SEU at commissioning (Ch.8 §5's "Commissioning Parameters," distinct from the reusable Profile definition itself). This keeps the reusability property intact — the *pointer slot* is reusable, the *pointer value* is per-SEU.

17. **Pack-declared Engineering Capital (Ch.15 §9, Ch.16 §13) is the other, genuinely reusable half** — e.g. an engineering-practices location, meant to propagate *across* SEUs by definition (Capability/Enterprise/Platform Acquisition Scope). Composed in via Pack, same as any other Pack contribution.

18. **Composition Engine (Ch.4) composes the *definition* — the resolved set of these pointers (Profile's + Pack's) — into the EBM, and does not fetch or store the Knowledge instances themselves** (Ch.4 §4, explicit: "shall not... preserve Knowledge"). This holds without contradiction once you keep #10 in mind: the pointer is just one more reference the EBM carries, same status as a Policy or Quality Gate reference — composing a reference is not preserving Knowledge.

19. **Settled: it comes from the Profile.** The Commissioning Parameter value supplied at commissioning (#16) *is* the resolution — there's no separate "fetch/derive the pointer" step to design. The Profile (via its Commissioning Parameter) is the source; no additional open mechanism needed here.

9. Work item generator + Paricipant pool to the dispatch engine. For this Command (one eligible pool from Capability Fulfilment, one Work Item for Requirements Analysis Model), Dispatch Engine does, per Ch.33:
- Narrows the eligible pool by §7's Inputs — Participant availability, type, applicable Authority, active Policies, active Obligations, organisational constraints — down to who's actually available now, not just eligible in principle.
- Reads §12's Dispatch Context — current Deliverable state, engineering stage, active Knowledge, active Decisions, active Obligations, current Participant state, Transition Definitions — the same governance/Knowledge/Decision view Work Item's Execution Context already carries, applied here to selection rather than instruction.
- Applies a Dispatch Strategy (§9) to pick among whoever's left — Capability Match at minimum; Specialist Preference, Cost, Confidence, Load Balancing, Locality, Organisation Preference where more than one candidate remains.
- Produces one of §8's Outputs: Participant Assignment (the normal case here — one Work Item, one selected Participant), or Deferred Assignment if nobody's currently available, or Parallel Assignment if this Command fanned out to multiple Work Items/Participants.
- Records §13's Dispatch Traceability — originating Command, the Work Item, selected Participant, which strategy, the evaluation criteria actually used, rationale, timestamp — and publishes the corresponding event (§14: ParticipantSelected/WorkItemDispatched, or DispatchDeferred).

11. Deliverable state only changes through its own separate Governance-gated transition, triggered afterward by the platform's own reactive chain.
