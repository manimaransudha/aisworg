### What's built here

**Template ownership (foundation for inheritance)**
- `templates.tenant_id UUID NOT NULL REFERENCES tenants(id) DEFAULT <Platform>` — migration `062`, mirroring `packs.tenant_id` (migration `044`) exactly; every existing row backfilled to the Platform tenant. `templates_code_version_key UNIQUE(code, template_version)` (CR-024) replaced by `templates_code_version_tenant_key UNIQUE(code, template_version, tenant_id)` — the same one-dimension-further move CR-024 made over the original bare-`code` constraint.
- `templatesDB.ts`: `upsert`/`createDraft` accept `tenantId` (default Platform, mirroring `packsDB.create`); `findByCodeAndVersion`/`findActiveByCode` accept an optional `tenantId` to scope the lookup (omitted = unscoped, preserving every pre-existing caller's behaviour — Profile's `baseTemplateCode` resolution, `findCandidateTemplates`, `compositionEngine`, none of which have a tenant concept and none of which needed to change); new `findAllVisibleTo`/`findActiveVisibleTo(viewerTenantId)`, mirroring `packsDB`'s exactly, feeding the Inherit dropdown. `findByStatus` (the authoring "Queue" tabs) gained the same `viewerTenantId` scoping Pack's already had — Template Drafts sitting in another tenant's queue no longer leak into a different tenant's view now that ownership is real.
- `core/templates.ts` / `core/sdkAuthoring.ts`: `reactivateAsNewVersion`'s version-bump (`nextAvailablePatchVersion`) and supersede lookup (`findActiveByCode`) are now scoped to the reactivating row's own `tenant_id` — a tenant's own reactivation only competes with its own rows, never Platform's or another tenant's. `advanceTemplateOneStep`'s `Published → Active` supersede step likewise. `assertTemplateCodeVersionFree` gained a required `tenantId` parameter — `createAuthoringDraft`'s Template branch passes the real author's tenant; `saveAuthoringDraft`'s branch fetches the Draft's own row first (it has no other tenant context) and uses *its* `tenant_id`, the same fix applied to the equivalent Pack branch. `listAuthoringByVerb`'s Active-tab filter and `listAuthoringQueue`'s Template branch gained the same tenant-ownership filtering Pack's already had.

**Template Inheritance (Ch.6 §9)**
- **Identity model — Option A, per explicit owner agreement** ("Add a tenant_id column. For platform users, this will be platform — does this close the question? I agree"): a Derived Template keeps the **same `code`** as its parent (not a new category value the way §9's own "Healthcare Web Application" example implies — see *Design decisions* below), disambiguated by the new Draft's own `tenant_id`. `templates.parent_template_id` (migration `002`, present since MVP, never wired) is now set once, at Draft creation, and never revisited by Save — `updateDraftContent` doesn't touch it, so an inherited Draft's lineage is fixed the moment "Inherit" is chosen.
- **The dropdown + button** (owner: "show a dropdown of codes (Platform published + tenant published). Give a button to inherit"): a new "Inherit from an existing Template" card on the Template `new`-draft form, shown *only* to a real Tenant author (`viewer.tenantId` set and not Platform — root and Platform authors never see it, satisfying "no change to the way template is created by a platform user"), listing every Active Template visible to that tenant (`templatesDB.findActiveVisibleTo`, `core/sdkAuthoring.ts`'s new `listInheritableTemplates`). Choosing one and clicking "Inherit" reloads the same `new`-draft page with `?parentTemplateId=`, which pre-fills the generated form from the parent's *real, materialised* content (`inheritedTemplateContent`: required Capabilities, mandatory Packs, deliverable catalogue, and `purpose` reconstructed the same way `reactivateAsNewVersion` clones a row for a new version — not the parent's possibly-stale `draft_content` blob) and carries the chosen parent id through a hidden `parentTemplateId` field on the main form (not a schema property — `parseFormBody` would otherwise drop it, so it's read directly off `req.body` in the web route and passed through `createAuthoringDraft` as its own top-level input, the same shape `tenantId` already used).
- **Code lock, enforced server-side, not just by the UI**: `createAuthoringDraft`'s Template branch overrides whatever `code` the submitted form carries with the chosen parent's own `code` whenever `parentTemplateId` is present; `saveAuthoringDraft`'s branch does the same for the life of the Draft (`existingTemplate.parent_template_id` set ⇒ `seed.code` forced back to `existingTemplate.code` before the collision check runs) — a tampered or stale form submission can't drift an inherited Draft's identity away from its parent's.
- **The mandatory-packs-superset validator** (owner: "All mandatory packs in the parent template have to remain mandatory in the inherited one also... Only mandatory packcodes are in templates" — the "other packs may be overridden" half of the original ask was explicitly dropped by the owner mid-conversation, leaving this as the *only* inheritance rule): `validateTemplateSeed` (`core/templates.ts`), when `seed.parentTemplateId` is set, fetches the parent's *current* `mandatoryPackCodes` live (not frozen at inheritance time — a parent that later adds a mandatory Pack binds its existing children too) and rejects publish if any are missing from the child, and separately rejects if the child's `code` doesn't match the parent's (belt-and-suspenders alongside the server-side lock above — Ch.6 §9's "Derived Templates shall not modify parent Templates"). Gates the same place Pack's own structural validation does — the first hop out of Draft (`publishAuthoringDraft`) — consistent with "an incomplete document must never leave Draft."

**Pack tenant-scoped versioning (the widened-scope half)**
- `packs_code_version_key UNIQUE(code, pack_version)` (migration `010`) replaced by `packs_code_version_tenant_key UNIQUE(code, pack_version, tenant_id)` — migration `063`. No new column needed; `packs.tenant_id` has existed since migration `044`, it just was never part of this constraint.
- `packsDB.findByCodeAndVersion`/`findActiveByCode` gained the identical optional-`tenantId` treatment as Template's own (above). `core/packs.ts`: `createPackDraft`'s rerun-safety check, `nextAvailablePatchVersion`, and both `advancePackLifecycle`'s and `advancePackOneStep`'s supersede-on-activate steps are all now scoped to the Pack's own `tenant_id` — a real correctness fix, not just a uniqueness-constraint tidy-up: before this, a tenant publishing the exact `(code, packVersion)` as an *already-existing Platform (or other tenant's) row* would have silently resolved to that other tenant's row (`createPackDraft`'s "already exists, treat as no-op" branch) instead of creating their own. `core/sdkAuthoring.ts`'s `assertPackCodeVersionFree` gained the same required-`tenantId` treatment as Template's — `createAuthoringDraft`'s Pack branch uses the real author's tenant; `saveAuthoringDraft`'s Pack branch now fetches the Draft's own row first (previously it had no tenant context at all for this check) and scopes by its `tenant_id`.

### Design decisions
- **Option A over §9's literal chain model.** §9's own example (`Enterprise Web Application → Healthcare Web Application → Healthcare Claims Platform`) implies each generation is a *new, distinct identity* — which Chapter 6's own §20.4 review (pre-dating this CR) had already noted is structurally incompatible with `code` = `template-categories` concept (CR-021): `Healthcare Web Application` isn't a root category and structurally never will be. Confronted with that tension, the owner chose the simpler, cheaper model directly: **same code, disambiguated by tenant ownership** — "a tenant's own variant of a Platform (or their own) category" rather than a multi-generation product-name chain. This satisfies the concrete ask (a tenant starts from a Platform Template, keeps its mandatory Packs, makes the rest their own) without requiring an open-ended category-naming scheme. A literal §9 chain (new identity per generation) remains unbuilt and is a different, larger feature if ever wanted.
- **"The other packs may be overridden" was dropped, not built.** The owner's original ask included a second clause about non-mandatory Packs; on reflection they withdrew it ("Only mandatory packcodes are in templates. Ignore that requirement") before implementation began — Template has no *optional* Pack concept at all (only `mandatoryPackCodes` — §20.5 already documents Recommended Packs as unmodeled), so there was nothing for that clause to attach to. Left out entirely rather than half-built.
- **No re-parenting, no un-inheriting.** `parent_template_id` is set once, at creation, and locked for that Draft's entire life (including every future reactivated version, which inherits the same `parent_template_id` off the row it reactivates — `reactivateAsNewVersion` now carries `tenantId`/`parentTemplateId` through explicitly, the same way it already carried `tenantId` for Pack). Nothing in this CR builds a way to later attach/detach/change a Template's parent after the fact — not asked for, and would reopen exactly the "Derived Templates shall not modify parent Templates" question §9 exists to close.
- **The Pack half was scoped in mid-conversation, not planned from the start** — flagged transparently as a pre-existing, separate gap when Template's own tenant-scoping work began, then explicitly brought back in scope by the owner one message later. Built as a byte-for-byte mirror of the Template fix rather than a new design, since the underlying defect (a uniqueness/supersede model with no tenant dimension) and the fix (add the dimension, scope the collision/supersede checks by it) are identical.

### Not in scope / notes
- **A literal §9 multi-generation chain** (a Derived Template with its *own*, different identity from its parent, further derivable itself) is not built — see *Design decisions* above. `parent_template_id` does support a chain structurally (nothing stops a Derived Template from itself being inherited from again, same code, same tenant, which is a no-op resolution today since `code` doesn't change generation to generation) but nothing exercises or tests that beyond one level.
- **No Registry-style admin page for Template** (mirroring Pack's, §20.12) — the Inherit control lives only on the `new`-draft authoring form, not a separate "reactivate" or "re-parent" affordance elsewhere. Same gap §20.3/CR-024 already flagged for reactivation; unchanged by this CR.
- **Profile is unaffected**, consistent with CR-024's explicit "stay pinned to the authored version" decision — a Profile's `base_template_id` still resolves to one frozen row, inherited or not.
