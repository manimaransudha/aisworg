## Step 2 — critical review of the 11 `*.template.json` files (findings, 2026-09-03)

All 11 files under `src/dblayer/seed/data/` read in full. Four findings, roughly in order of how much they should drive the actual cleanup:

### Finding 1 — `deliverableCatalogue[].name` has never actually been Ontology-backed, despite the wiring existing since CR-038

Migration `079_template_deliverable_catalogue_ontology.sql` made `deliverableCatalogue[].name` a `x-referential: "deliverable-name"` picker in the SDK Authoring form — options come from the Ontology concept's own `default_label`. But the seed JSON's actual stored strings were hand-typed independently and were **never aligned to the vocabulary they're supposed to be drawn from** — not even the original 23-code list, let alone the new 62. Across all 11 files, only two names match a canonical `default_label` exactly: "Requirements Specification" and "Source Code." Every other name is free text with no real concept behind it:

| Seed name (used in 9 of 11 files) | Nearest canonical `deliverable-name` | Match quality |
|---|---|---|
| Architecture Document | `solution-architecture-document` ("Solution / Architecture Document") | close, but not exact — will not resolve against the picker as stored |
| Technical Architecture & Discovery Document | *(none)* | no equivalent in the 62 at all |
| Security & Compliance Review | `security-assessment-report` or `compliance-audit-evidence` | ambiguous — could be either, or split into both |
| Platform & Developer Experience Setup | *(none)* | closest is `infrastructure-as-code-environment-configuration` or `configuration-files`, both weak |
| Quality Engineering Report | `test-report-results` | loose |
| Launch Readiness Review | `review-report` or `release-package` | ambiguous |
| Operations Runbook | `runbook-operational-documentation` | close, not exact |

`ebook-library.template.json`'s own two domain-specific names ("Catalog Metadata Design," "Circulation Rules Specification") have no canonical equivalent either and aren't obviously meant to — they read as legitimate per-Template specialisations, but nothing about the current schema distinguishes "a real specialisation" from "just not aligned yet."

**This predates today's session** — CR-086 explicitly scoped Template's `deliverableCatalogue`/`dependencyGraph` `producingCapabilityCode`/`fromCapabilityCode` remap (its own capability-name vocabulary) but never touched the `name`/`toName`/`fromName` side, since `deliverable-name` wasn't being reworked yet at that point.

### Finding 2 — 9 of 11 Templates share one boilerplate 9-item deliverable list, verbatim

`api-platform`, `ai-platform`, `data-platform`, `embedded-software`, `enterprise-web-application-parent`, `legacy-modernisation`, `mobile-application`, `package-implementation`, and `saas-product` all carry the **exact same** 9 `deliverableCatalogue` entries and the **exact same** `dependencyGraph` (same names, same `producingCapabilityCode`, same edges), word for word. Only `code`, `name`, and `mandatoryPackCodes` differ between them. Nothing about what's actually distinctive between an AI Platform, a Data Platform, Embedded Software, and Legacy Modernisation shows up in what they deliver or how those deliverables depend on each other.

### Finding 3 — the dependency graph is a naive strict linear chain everywhere

In every one of the 9 boilerplate files (and, less severely, in `web-application` and `ebook-library`), each deliverable depends on exactly **one** thing: whichever deliverable happens to sit immediately before it in list order, plus its own `producingCapabilityCode` as a same-named capability gate. There's no fan-in (e.g., Source Code realistically depends on Architecture Document, Technical Architecture Document, *and* Security & Compliance Review reaching a done state — not just whichever one is textually adjacent) and no fan-out. The chain encodes list order, not real prerequisite structure.

### Finding 4 — two Templates collide on the same `code`, and one file looks like a stray test fixture

- `ebook-library.template.json` (`code: "enterprise-web-application"`, `templateVersion: "1.1.0"`) and `enterprise-web-application-parent.template.json` (`code: "enterprise-web-application"`, `templateVersion: "1.2.0"`) **share the identical Template identity code**, distinguished only by version. Since `(code, template_version, tenant_id)` is the real identity (CR-024/026), these look, to the platform, like two versions of *one* Template lineage — except their content is completely unrelated (E-Book Library's Catalog/Circulation deliverables vs. the generic "Enterprise Web Application (Standard)" boilerplate). This reads as an authoring mistake, not an intentional versioning relationship.
- `web-application.template.json` has `code: "test-enterprise-web-application"` and `name: "Web Application"` — a `test-` prefixed code sitting in the real (non-`test-fixtures/`) seed data directory, alongside a 3-item deliverable list that's a strict subset of the 9-item boilerplate. Looks like a leftover fixture rather than an intentionally minimal real Template.
- Separately, in `ebook-library.template.json`'s own `dependencyGraph`, the "Architecture Document" entry gates on `fromCapabilityCode: "requirements-analysis"` — its own `producingCapabilityCode` is `architecture-design`. Every other file in this review gates a deliverable on its *own* producing capability; this one gates on the *previous* deliverable's capability instead, which looks like a copy-paste error.

## Step 7 — Capability-type `dependencyGraph` edges retired (2026-09-05)

While reviewing `output.txt` (a real `pnpm test` run, 191 pass / 11 fail, post Steps 5–6's migrations), traced 8 of the 11 failures to `materialiseDependencyGraph.ts` never actually materialising a Capability-type edge into a `dependency_definitions` row: `capabilitiesDB.findByCodes` can return more than one row for the same `capability-name` code (every Pack that contributes a shared Ontology capability creates its own row), and building a `Map` from `[code, id]` pairs off an unordered query silently keeps whichever row's id happens to come back last — not necessarily the one the actual Service rows (`servicesDB`) are attached to. Confirmed directly against the DB: `test-enterprise-web-application` had zero Capability-type `dependency_definitions` rows despite two Capability-type edges in its authored graph.

Proposed fixing the lookup (de-dupe by code, union Services across every row sharing it) — owner instead used the investigation to settle a deeper, standing architectural question: **"there is no Capability-type edge. Canonical Capabilities do not depend on each other. They are a network of capabilities required to accomplish the objective. What has dependency is the deliverable."** Capability is purely the Ontology `capability-name` shell (no inputs/outputs/service-level of its own — those belong to the Service it provides); the `capabilities`/`services` runtime tables are execution-dimension materialisations of that shell, not a second definition of it; and the sequencing a Capability-type edge was trying to express was always already fully expressible Deliverable-to-Deliverable, via each Service Definition's own `inputs`/`outputs`.

- **`materialiseDependencyGraph.ts`** — the `fromType === "Capability"` branch (and the `capabilityCodes`/`capabilities`/`capabilityIdByCode`/`servicesByCapabilityId` pre-computation feeding it) commented out, not deleted, along with the now-unused `capabilitiesDB`/`servicesDB` imports and `DEFAULT_CAPABILITY_REQUIRED_STATE`. A Capability-type entry in a Template's `dependencyGraph` now produces no row at all. The Deliverable-type branch is completely untouched.
- **Deliberately left alone** (dormant, not broken, out of this step's scope): `core/templates.ts`'s `validateTemplateSeed` still validates `fromCapabilityCode` against derived capabilities for any Capability-type entry that's still present in seed JSON; `dependencyDefinitionEngine.ts`'s `resolveNamedNode` still carries its `entityType === "Capability"` evaluation branch. Neither has anything left to act on, but neither was asked to be touched.
- **Not yet decided**: whether to also strip existing Capability-type entries out of the 9 live templates' own `dependencyGraph` JSON (they're now inert data, materialising nothing), or leave them as historical record. Not actioned — no instruction to.
