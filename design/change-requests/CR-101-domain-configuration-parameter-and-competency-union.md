# CR-101 — `domain` Configuration Parameter + EBM composition competency union, closing CR-099's own open consumption-wiring item

**Raised:** 2026-09-11 · **Origin:** owner, immediately following CR-099: *"I want domain as an additional profile-configuration parameter. ui_grouping is Profiles, text_type is text. In the EBM composition, the primary programming language should be unioned with the technology competencies in the packs. It is an union. Same with domain as well. Now, the capability fulfilment helper has to include this technology and domain check as well. The dropdown should show all participants matching any of them"* · **Status:** 🟢 Built.

## Three parts

1. **`domain` as a ninth Profile Configuration Parameter** (Ch.7 §10, alongside the existing eight from CR-091 Part 2). Its own `profile-configuration` catalogue row carries `ui_grouping = 'Profiles'` (owner, explicit — every other one of the eight carries `'SEU Configurations'`) and `text_type = 'text'`. Its VALUES reuse the `domain` concept type CR-099 already seeded (25 real values, migration 196) — same "parameterCode is both its own profile-configuration code and its own value concept type name" convention every other Configuration Parameter already follows (`core/profiles.ts` `CONFIGURATION_PARAMETER_FIELDS`).
   - Migration `199_profile_domain_configuration_parameter.sql` — the catalogue row + Profile's own schema field, mirroring migration 174/175's exact shape.
   - `ProfileSeedInput.domain?: string` + a `CONFIGURATION_PARAMETER_FIELDS` entry (`core/profiles.ts`) — validation, draft-inheritance, and the render-time mandatory-asterisk override (`web/sdkAuthoring.ts`) are all already fully generic loops over this one array; no further per-field code needed there.
   - `formGenerator.ts`'s `CONFIGURATION_PARAMETER_FIELD_NAMES` — `domain` added, so it renders in the "Configuration Parameters" display group rather than falling into `other`.

2. **EBM composition — competency union.** `domain/engine/profileCompositionUnravel.ts`'s `unravelComposition` (the REAL, live composition mechanism — `compositionEngine.compose()` is dead in this flow, explicitly commented out per owner: *"I want compose() commented out as the very first step"*) gains a new `competencyRequirements: Record<string, string[]>` on its own return shape, computed by `computeCompetencyRequirements`:
   - Every selected Profile's own `primaryProgrammingLanguage` value unions into dimension `"Technology"`; every selected Profile's own `domain` value unions into dimension `"Domain"` (`CONFIGURATION_PARAMETER_COMPETENCY_UNIONS` — these two named pairs only, not a generic rule for every Configuration Parameter).
   - Every composed Pack's own declared `contributions.competencies[]` (CR-099, `{dimension, value}`) unions in by its own dimension — every dimension a Pack declares, not just Technology/Domain, matching CR-099's own "Ontology-extensible to any Pack category" design.
   - A genuine union, not a conflict — deliberately NOT added to `unravelComposition`'s own conflict-detection `pool` (a Profile's `primaryProgrammingLanguage` and a Pack's own `Technology` value simply both become eligible values, never flagged as disagreeing).
   - `domain` also joins the existing per-Profile `simpleFields` pool entries (same treatment as the other eight Configuration Parameters) — so two Profiles disagreeing on `domain` is now a real, detected composition conflict, same as any other Configuration Parameter.
   - Carried onto the EBM itself: `compositionCompleted.ts` (the sole place `ebmsDB.create()` is called from) now also reads `stashed.unraveled.competencyRequirements` into `ebm.behaviors.competencyRequirements`, alongside the existing `pool`/`resolvedCompositionConflicts`. No new column — `ebms.behaviors` is already a loosely-typed jsonb bag.

3. **Capability Fulfilment eligibility — wired.** `core/participantEligibility.ts`'s `EligibilityCriteria.competency` filter existed (CR-098) but nothing populated it. New `getSeuCompetencyRequirements(seu)` reads `ebm.behaviors.competencyRequirements` off the SEU's active EBM (a fresh `ebmsDB.findById` when no `ebm` is already in scope; `core/seus.ts`'s `getSeuDetailView` instead reads it straight off the `ebm` row it already fetched, same pattern its own `ebmPool` already uses, avoiding a duplicate query) — the single shared place both call sites get it from, matching `findEligibleParticipants` itself already being that one shared place for the base capability-compatibility check:
   - `core/seus.ts` `getSeuDetailView` — the Fulfil dropdown's own `eligibleParticipants` now filters by `competencyRequirements`.
   - `core/capabilities.ts` `resolveMasterParticipant` — the server-side re-check `fulfilCapability`/`fulfilCapabilityWithParticipants` both share now re-validates the SAME requirement, so a submitted participant id can never bypass what the dropdown itself offered.
   - `matchesCompetency`'s own pre-existing semantics (CR-098) are exactly what the owner asked for here — ANY-within-a-dimension (*"the dropdown should show all participants matching any of them"*), ALL-across-required-dimensions — reused unchanged, no new matching logic needed.

## Closes CR-099's own open item

CR-099's own Build status explicitly left this open: *"Consumption wiring (`getSeuDetailView`'s Technology/Domain columns actually filtering `findEligibleParticipants` by real competency, the `composed_packs` fix) — 🚩 not built, still open."* Part 3 above closes it — via the EBM's own real `composed_packs`/`behaviors`, not by re-deriving from `getProfilePackSelections` alone.

**Update 2026-09-11 (same day) — `requiredTechnologyPacks`/`requiredDomainPacks`, corrected twice, now show the real union.** Two wrong intermediate states before landing right, both owner-corrected:
1. First left reading `getProfilePackSelections` alone (a narrower, Profile-selection-only *display* list) — owner: *"Technology and Domain on capability fulfilment should come from profile composition."*
2. Switched to `ebm.composed_packs` filtered by `category`, displaying each matching Pack's own `name` (e.g. "Node.js Engineering Practices") — still wrong. Owner: *"I have been saying the fulfilment should show the EBM unionised values."* A Pack's `name` is a free-text label, not the competency value, and this approach silently dropped any Configuration-Parameter-only value with no matching Pack (`typescript`, which came from `primaryProgrammingLanguage`, has no Pack representation at all).
3. **Landed**: both fields are now `string[]`, read directly off `ebm.behaviors.competencyRequirements.Technology`/`.Domain` — the exact same real values (`["typescript", "nodejs", "react"]`) `findEligibleParticipants` itself filters against, not a Pack-shaped proxy for them. `getProfilePackSelections` and `packsDB.findByIds` are no longer used by `getSeuDetailView` at all; `detail.ejs` renders each value as a plain badge (no `.code`/`.name`, no title attribute — there's no Pack underneath any more).

## Known issues, found and fixed while diagnosing a live SEU

- **Vocabulary mismatch, found live**: a real SEU's Profile had `primaryProgrammingLanguage: "typescript"` — a valid `primary-programming-language` concept (migration 174) with no matching `technology` concept (`technology`'s own 25 values, migration 196, had no `typescript`) — so the union silently carried an orphan value into the Technology competency requirement that no Participant or Pack could ever match. Owner: *"All configuration parameters in the profile should have been ontology driven. If typescript is not in Ontology, that should have not been allowed for selection."* Fixed two ways:
  - **Data**: migration `200_technology_typescript.sql` adds `typescript` as a real `technology` concept — every other `primary-programming-language` value (javascript/python/java/csharp/go) already had one; this was the sole gap.
  - **Going forward**: `validateProfileSeed` (`core/profiles.ts`) gained a new check, specific to `primaryProgrammingLanguage` (the one Configuration Parameter whose own Ontology source, `primary-programming-language`, is a *different* concept type from the competency dimension it unions into, `technology` — `domain`'s own Configuration Parameter already sources directly from the `domain` concept type, migration 199, so it has no equivalent gap) — publishing now fails if the chosen `primaryProgrammingLanguage` value has no matching `technology` concept, rather than silently accepting it and only breaking downstream at EBM composition.
- **The seed data gap that surfaced this**: `enterprise-web-application-parent-development.profile.json` set `primaryProgrammingLanguage: "typescript"` but selected no Technology Pack at all (`technologyPackCodes` was absent) — the two are independent fields, nothing derives one from the other. Fixed: added `"technologyPackCodes": ["technology-nodejs", "technology-react"]`, matching the same Node/TypeScript pairing `saas-product-development.profile.json` already uses.
