# CR-047 — dependencyGraph authoring widget: full type vocabulary, symmetric TO side, and Pack/Profile schemas

**Raised:** 2026-08-20 · **Origin:** owner, reviewing Chapter 9 §19's own Implementation Specifics — the Dependency Engine already evaluates 6 of the chapter's 7 dependency types (Deliverable, Capability, Decision, Obligation, Evidence, Knowledge — everything but External), confirmed real and tested. Only 2 of those 6 can actually be authored into a real row today, and only through Template's own schema. Owner's explicit framing: this is not a Dependency Engine gap — the engine's own scope is closed (Chapter 9 §19.1/§19.2) — it's an authoring-surface rollout, tracked here as its own CR, not folded into the chapter's implementation review. · **Status:** 🟡 Proposed (not scheduled)

## The settled design this closes the gap against

A dependency node is `(entity_type, name?, state)` — `name` required only for types with a stable, pre-declared identity (Deliverable, Capability); for Decision/Obligation/Evidence/Knowledge, `state` alone is already a complete, unique identity ("any Obligation, Verified" needs no further disambiguation). This applies **symmetrically** to both sides of a `dependency_definitions` row (FROM the prerequisite, TO the gated node), and to any owner kind (Template, Pack, Profile) — confirmed in conversation with the owner, consistent with CR-039's own original node model (§7's own text never restricted which side of an edge a type may sit on). This is not an open design question — see Chapter 9 §19.1/§19.2 for the full review.

## What's currently blocking it, at three layers

- **Schema**: `dependency_definitions.to_name` is `TEXT NOT NULL` (`072_dependency_definitions.sql:46`) — the database cannot represent an unnamed gated (TO) node at all today. `from_name` is already correctly nullable.
- **Materialisation**: `materialiseDependencyGraph.ts` hardcodes `toEntityType: "Deliverable"` (`:69, 88`) and `toState: GATED_TO_STATE` (`:34`, always `"In Progress"`) as literals, never read from an authored entry.
- **Widget**: the Template `dependencyGraph` field — the only authoring surface that exists — restricts `fromType` to `{"Deliverable", "Capability"}` (`076_template_dependency_graph_field.sql:37`) and has no `toType`/`toState` field at all. It also only exists on Template's own `schema_definitions` row — CR-041 built the underlying self-referential authoring mechanism generically (its own text: "Whichever entity kind's Draft authors it owns the resulting rows... Template is simply the first, not the only, caller"), and CR-043 built ownership generically at the DB/engine layer — but the `dependencyGraph` field itself was never added to Pack's or Profile's schemas. CR-041's own "Not in scope" section named this directly and it was never picked back up.

## Scope

1. `dependency_definitions.to_name` → nullable (migration).
2. `materialiseDependencyGraph.ts` reads `toEntityType`/`toState` from the authored entry instead of hardcoding them — preserving the current side-effect fix (a transition attempt only ever finds rows for the exact state being attempted, never every transition) deliberately, not losing it as a regression.
3. **`fromType`/`toType` become data-driven, not a widened static enum** (owner's own correction: "the dependency engine widget can hold anything that is in the transition definition"). Today's schema (`"enum": ["Deliverable", "Capability"]`) is a fixed 2-item list — the same static-enum mistake CR-039's own migration comment already warned against for `entity_type` at the DB layer ("widening the type vocabulary... no migration required"). The widget must inherit that same principle: source `fromType`/`toType` from the real, live, already-governed noun vocabulary — `authorityVocabularyDB.listActiveNouns()` (`authority_nouns`, already real — Deliverable/Decision/Evidence/Knowledge/Obligation/ExternalInteraction all confirmed live, per CR-039's own migration comment) plus `Capability` appended (the one addition specific to this table, since Capability isn't an independently governed-transition noun). A new `x-referential` source key (e.g. `"authority-noun-or-capability"`), resolved in `loadReferentialOptions` the same generic way every other `x-referential` source already is — so a future noun added to `authority_nouns` becomes a valid dependency type automatically, no widget schema change, matching the DB layer's own "no migration required" promise all the way up the stack.
4. Add the `dependencyGraph` field to Pack's and Profile's own `schema_definitions` rows, reusing the same generic self-referential/derived-options mechanism CR-041 already built — Template is not architecturally special here.
5. Once 1-4 exist, extend push-evaluation wiring (`evaluateAndPublishFromTransition`) to Decision/Obligation/Evidence/Knowledge transitions, the same pattern CR-042 already used for Deliverable/Capability — not meaningful to build before rows of these types can exist.

## Not in scope

- **Building External-type evaluation in the engine.** Worth flagging precisely because of how item 3 above works: `authority_nouns` already includes `ExternalInteraction` (confirmed live per CR-039's own migration comment), so a data-driven `fromType`/`toType` picker will offer it in the dropdown for free — but `isUnnamedNodeSatisfied` still has no evaluation branch for it and fails closed. Making it selectable is a side effect of item 3, not the same as making it work; the engine-side gap (Chapter 9 §19.2) stays open regardless, and needs its own design pass, not just a wiring fix.
- Constraint Detection, Flow Optimisation, circular-dependency detection — unrelated, separate, still-unbuilt chapter aspirations (Chapter 9 §11/§14/FR-9.5).
- Any change to the Dependency Engine itself (`dependencyDefinitionEngine.ts`) — its own evaluation logic already correctly implements the full symmetric design; this CR is authoring-surface and materialisation only.
