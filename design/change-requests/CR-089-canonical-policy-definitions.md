## Real schema built (2026-09-05)

`167_policy_definitions.sql` — the `policy_definitions` table (mirroring `service_definitions`' own shape, migration 153) plus its `schema_definitions` (entity_kind `'Policy'`, version 1) authoring-form row. `SchemaDefinitionEntityKind` (`seuTypes.ts`) widened to include `"Policy"`, the 7th authored kind.

- **Lifecycle**: Chapter 24 §13's own 7-state diagram verbatim (`Draft → Validated → Published → Active → Deprecated → Retired → Archived`) — checked against Service Definition's own, different 6-state lifecycle (no `Validated` step) before choosing, per the owner's own earlier resolution: "Stick to the policy lifecycle defined in chapter 24 for policy." Matches the `Policy` noun/transitions already seeded into `authorityVocabulary.json`.
- **`configurable` realised as `x-configurable: true`, not a nested envelope** — checked `formGenerator.ts`'s real item-field kinds first (`string`/`enum`/`boolean`/`referential`/`referential-multi`/`nested-list` — no "object" kind exists), so the fragment's literal `configurable: { severity }` nesting isn't renderable by the real authoring form without extending the form generator. Owner, accepting the trade: "Let us go with flat fields + x-configurable: true." `constraintType` and the three `applicability*` fields carry the flag; a downstream system discovers what's tunable by inspecting the schema for it, schema-level, before any content exists — arguably a stronger answer to "how will downstream systems know this is configurable" than requiring every record to nest correctly.
- **`applicabilityDeliverableNames`/`applicabilityEnvironments`** — real Ontology-backed multi-selects (`x-widget: "referential-multi-select"`, `x-ontology: true`), against `deliverable-name` and `category:environment` (migration 166) respectively.
- **`applicabilityDeliverableLifecycle`** — plain comma-separated string, not a multi-select — it names real `transition_definitions` states (`Defined`/`In Progress`/`Approved`/`Baselined`), a different canonical source with no Ontology backing and no existing "fixed-enum multi-select" widget in this schema mechanism. Same simple convention `contributionPolicies[].conditionValues` already uses (migration 109).
- **`conditions`** — `x-widget: "json"`, not `referential-list`. Each condition nests its own `requiredEvidence`/`exceptionRules`/`relatedObligations` arrays of objects — a third level of nesting `nested-list` (Checklist's own two-level precedent) doesn't reach — so kept as the fragment's full rich shape via raw JSON rather than lossily flattened to fit the generic mechanism.

**Not built yet**: `policyDefinitionsDB.ts` (the DB access layer — upsert/findByCode/etc., mirroring `serviceDefinitionsDB.ts`), the `policy-authoring`/`policyRegistry` web routes, `KIND_BY_SLUG`'s own entry, and anything that actually reads `x-configurable` to enforce the cascade. This migration is schema/table only.

## Scope (owner, settled)

> "Do not confuse what is existing with what we are doing. We are defining canonical policies similar to canonical services. So this will be a new table `policy_definitions` - is this clear."

This is the same architectural move CR-086 made for Services: a new, standalone, canonical catalog table — `policy_definitions` — not owned by any Pack, existing independently of any single Pack's own authoring. **Not** an addition to the existing `policies` table, which stays exactly what it is today: Pack-owned, `(originating_pack_id, code)`-keyed, no cross-Pack sharing, no registry of its own.

One structural difference from Service confirmed directly: Service Definition is 1:1 with Capability — every Capability has exactly one canonical `service_definitions` row. Policy has no such tie. Owner: "there is no relationship with any other entity" — `policy_definitions` is a fully standalone catalog, not keyed off or constrained by Capability, Deliverable, or anything else the way Service is.

**Retrofit confirmed**: owner — "yes, we will retrofit existing policy definitions anywhere to the canonical ones." Existing Pack-owned `policies` content, wherever it matches a canonical entry, gets rewritten to reference `policy_definitions` rather than re-authoring content inline — the same shrink CR-086 already did to `contributionServices[]` when `service_definitions` was introduced.

**Working the Service analogy through, not just accepting it (owner: "let us work through to see if there are also differences")** — what holds, what doesn't:

- *Holds*: reference-by-code, no re-authoring of canonical content in the Pack layer, retrofit of existing content into the new catalog.
- *Doesn't hold / not yet settled*: **(a)** Service's picker is naturally scoped by Capability (`contributionServices[]`'s own options narrow to whichever Capabilities a Pack already declares); Policy has no such narrowing signal, since it has no relationship to any other entity — every canonical Policy would be a candidate for every Pack, unfiltered, and `category:policy` doesn't help since a Policy's own category is independent of whatever it's attached to (Ch.24, already established). **(b)** Service's override mechanism exists because `serviceLevel.target` is a legitimately Pack-specific number; none of Policy's real fields (`category`, `severity`, `conditionType`/`conditionField`/`conditionValues`, `constraintType`, `governedTransition`) is an obvious "target" the way a number is — whether a Pack adopts a canonical Policy wholesale with zero override capability, or has some real per-Pack tunable dimension (e.g. promoting a canonical "Standard" to mandatory "Policy" in a stricter context, or adjusting `severity`), hasn't been named. **(c)** If (b) turns out to have a real overridable dimension, that reopens CR-088's own not-yet-walked Policy component — the same four-layer question already settled for Service Level (Definition → Pack → Template-exposes → Profile-overrides) would apply again here, and the two CRs' overlap is worth resolving together rather than separately.

## The gap (checked directly against the live build, 2026-09-05)

Chapter 6/24's own implementation history already established that the *actual* Policy shape diverged from §8's ideal on purpose (CR-061 — see the definition-side walkthrough this session covered separately). This fragment was written against the ideal, not the built shape, so nothing in it is directly usable as-is:

1. **Field shape doesn't match.** Real `contributionPolicies[]` (`schema_definitions`, Pack v1) fields are: `code`, `name`, `category` (Ontology-backed, `x-referential: "category:policy"`), `severity`, `conditionType`/`conditionField`/`conditionValues`, `constraintType`, `governedTransition`. The fragment's `identifier`, `required_evidence`, `related_obligations`, `exception_rules`, `version` fields don't exist anywhere in the schema — CR-061 deliberately collapsed all of them into simpler mechanisms (Required Evidence/Related Obligations resolve through whichever Gate references the Policy; Exception Rules is fully covered by `constraintType` itself; there is no `version` field at all — identity is `(originating_pack_id, code)`, no separate versioning).
2. **`governedTransition` — a *required* field on the real schema — is absent from every one of the 26 entries.** None of the fragment's YAML blocks declare one. As currently drafted, none of these 26 could actually be saved as a real Policy.
3. **`conditions` is free prose describing threshold/percentage checks** ("coverage >= threshold," "zero errors," "all declared SLA targets met") that the real `conditionType` enum can't express yet — it supports exactly two types today, `always_true` and `field_in`. Per CR-061's own note, a generic threshold/percentage `conditionType` "gets added incrementally... only as a real need surfaces" — it hasn't yet. The majority of these 26 policies need that unbuilt condition type to mean anything beyond `always_true`.
4. **`originating_pack` values don't correspond to real seed Packs.** `PACK-GOVERNANCE-STYLE` (18 of 26 entries) and `PACK-COMPLIANCE-OWASP` (3 entries) have no real counterpart anywhere in `src/dblayer/seed/data/` — checked directly, neither exists. `PACK-TECH-NODEJS`/`PACK-TECH-JAVA` (2 entries) are close but not exact — the real files are `technology-nodejs.pack.json`/`technology-java.pack.json`.
5. **Numbered `capability: N` references** (5, 6, 8, 9, 10, 11, 12, 13, 16, 50, 53, 56, 60...) don't correspond to the real `capability-name` Ontology vocabulary, which is code-based (`requirements-analysis`, `architecture-design`, ...), not numbered. These numbers appear to come from a separate/earlier planning document (the same one `example.md` and this fragment both cite), not CR-086/087's real 63-code vocabulary.
6. **`deliverable_type`/`deliverable_category` values are a mix of real and non-existent labels.** Spot-checked against the real 71-code `deliverable-name` vocabulary: `Source Code` and `Release Package` are real (`source-code`, `release-package`). `Architecture` (used bare, as a `deliverable_type`) isn't — the real codes are `architecture-decision-record` or `solution-architecture-document`. `Operational Guide` (D3) has no exact real match — the closest is `runbook-operational-documentation`.
7. **"Already built" claims don't hold up under the real codes.** The live `policies` table has 144 rows today — a real, substantial body — but under entirely different naming (`no-hardcoded-secrets`, `policy-openup-change-control-baseline-standard`, `policy-backlog-readiness-standard`, `policy-zero-critical-defects-release-standard`, ...), scattered across `openup-development.pack.json`, `openup-configuration-and-change-management.pack.json`, `sdlc-phase-*.pack.json`, and 33 `compliance-*.pack.json` files. None of the fragment's 26 proposed identifiers (`POL-ARCH-DOC-REQUIRED`, `POL-TEST-COVERAGE-THRESHOLD`, etc.) exist among them. Some of the fragment's "Already built" entries likely correspond to one of these 144 in substance (e.g. S2 "Secrets Management" and the real `no-hardcoded-secrets` look like the same policy under different names) — but this was **not verified entry-by-entry**, and category:policy's own real vocabulary already has 10 values (the fragment's 7 plus Compliance/Privacy/Ethics, added for the 33 real Compliance Packs), so a proper duplication check needs to happen before any of these 26 get built, not after.

## Question 2 resolved: three real configurable dimensions, structurally marked (2026-09-05)

Walked every field of the fixed §8 structure (owner: "do we need more configurable parameters than what I mentioned?") and settled on exactly three, none invented beyond what's asked:

- **`constraint_type`** (Policy/Standard) — policy-level, restored (it had been dropped from the fragment entirely at some point despite Ch.24 §4 requiring it on every Policy).
- **`severity`** — per condition (already nested there, not at the Policy level, since a Policy-level severity couldn't say which condition's violation it describes once there's more than one).
- **`deliverable-name`, `environment`, `deliverable_lifecycle`** — the three real Ch.24 §9 Applicability dimensions actually used (Capability/Engineering-stage/Organisation/Domain/Technology/Compliance-requirement deliberately excluded — see the fragment's own header for why each one is redundant or ungrounded). All three are lists, all three configurable, for the same reason `deliverable-name` needed to be: "deliverable-name has to be a list... if it is a list then this also should become configurable."

**Structural rule, not a prose claim**: owner — "I am repeatedly saying applicability is configurable. Where is this captured? How will downstream systems know this is configurable?" Resolved by making `configurable` a literal, always-present key at exactly three levels — policy (`constraint_type`), applicability (`deliverable-name`/`environment`/`deliverable_lifecycle`, all lists, `[]` meaning "matches everything today, still overridable"), condition (`severity`) — so a downstream system discovers what's tunable by checking for the key, never by reading a comment. `applicability` itself is never omitted even when empty on every dimension, for the same reason: "dropping it completely is going to cause issues downstream on how to configure it" — an absent key gives nothing to attach a future override to; an always-present, empty one does.

**Not configurable, confirmed with reasoning**: Identifier/Name/Description (identity), Category (fixed Ontology classification), Required Evidence/Related Obligations/Exception Rules (define what proves a condition, not how strict it is — making these tunable would mean different contexts verify different things for the "same" condition), Version (not a configurable-parameter concept).

Every condition also now always carries `required_evidence`, `related_obligations`, `exception_rules` explicitly (`[]` where empty, never omitted) — the same structural-completeness rule, applied one level down.

## `contributionPolicies[]` rebuilt against the canonical catalog (2026-09-05)

Same architectural move CR-086 made for `contributionServices[]`, but flatter: `contributionPolicies[]` is now a plain `string[]` of canonical Policy Definition codes — check/uncheck, no per-item sub-fields at all (Service kept target overrides per row; Policy keeps nothing). Migration `168_pack_contribution_policies_from_definitions.sql`. `x-widget: "referential-multi-select"`, not `"referential-list"` — a checkbox grid submits only its checked boxes, which qs/Express collapse into a clean array with no sparse-array holes; rendering is bespoke (`_generatedFieldGroups.ejs`, `f.name === 'contributionPolicies'`) since a canonical Policy isn't an Ontology concept the generic multi-select branch could source from.

**Capability-scoped narrowing** (closes open question 1 below): a canonical Policy has no direct Capability tie, but its `applicabilityDeliverableNames` does, indirectly — `deliverableNamesFromCapabilityCodes` (`core/packs.ts`) walks this Pack's declared Capabilities → their canonical Service Definitions → those Definitions' own `outputs`, then checks each adopted Policy's `applicability_deliverable_names` intersects that set (or is empty, "matches everything"). Mirrored client-side (`referentialListGroup.js`'s `refreshPolicyFilter`) off a small capability→deliverable-names map, dimming (never hiding/disabling) policies that don't obviously apply as Capabilities change live, same advisory-only discipline the Pack Codes tab's own coverage callouts use.

**`governedTransition` derived, not authored** — required on the real Pack-composed `policies` table (Quality Gate's `requiredPolicyCodes` depends on it) but deliberately absent from `policy_definitions` ("no relationship to any other entity"). Owner: "is not deliverable_lifecycle equivalent of that?" — yes: `deriveGovernedTransitionFromDeliverableLifecycle` resolves the `transition_definitions` edge landing on the most-advanced state named in the Definition's own `applicability_deliverable_lifecycle` (or landing on `Baselined`, the final gate, when empty). Every one of the 34 canonical policies derives to `Deliverable|Approved|Baselined` today (none currently scope to an earlier-only state) — the mechanism still generalises the moment one does. `severity` on the materialized row is the highest among the Definition's own per-condition severities (a defensible reduction, not real per-condition evaluation — the engine still only consults `always_true`/`field_in` on `condition`, hardcoded to `always_true` for every canonically-sourced row now, same "declaration only for now" status this whole path already carried).
