### Design decisions

**Tenant scoping mirrors Pack's ownership model exactly** (`packsDB.findAllVisibleTo` / migration 044) — no new pattern invented. A Platform-tenant concept is canonical and visible to everyone; a tenant's own concept is theirs alone; root sees and can write to any tenant's. Uniqueness moved from `(concept_type, code)` to `(concept_type, code, tenant_id)`, so a tenant can mint their own `healthcare-web-application` (or even shadow an existing code like `saas-product` with their own row) without colliding with Platform's or another tenant's.

**Authority moved onto the same noun × verb badge system as everything else**, replacing the original `requirePlatformBadge("root")` gate from CR-020: a new `Ontology` noun with a single `define` verb (`ontology_define` gates the whole CRUD surface — add and retire both — the same one-badge-per-surface shape Authority's own nouns/verbs management already uses, not a separate verb per action). Holding it lets an actor manage **their own tenant's** vocabulary only; only `root` can write to Platform's shared rows, enforced in `core/ontology.ts`, independent of the badge gate (the badge says "you may use this surface," not "you may write to any tenant's data").

**EOOM boundary — design note for later, not built now** (owner: "Think of it as platform provides a software engineering definition. Tenant can override it, but within the boundaries of what the EOOM wants to accomplish"). A purely descriptive concept type (`template-categories`, `deliverable-name`) is safe for a tenant to extend freely today — nothing in the engine pattern-matches its codes. A concept type that's the tenant-facing name for a *real* engine mechanism is different: the tenant's own code/label should stay free (their own methodology, their own words — "if a tenant calls it 'exit check', the exit check gets mapped to the quality gating functionality in the engine"), but it must resolve to one of a small, fixed set of real engine capabilities — carried as an explicit reference on the concept (e.g. an `engine_capability` field), never inferred by the engine pattern-matching the concept's own `code` string. That reference is the EOOM boundary: vocabulary is tenant-owned; the mechanics it must still satisfy are not. **Not built** — nothing today has an engine binding to attach it to (Quality Gates are the natural first candidate, once Pack's contribution types stop being hardcoded schema structure and become Ontology-driven, which is a separate, larger piece of work). Recorded here so the principle is on file before it's needed.

### What's built here
- `ontology_concepts.tenant_id` (migration 055), backfilled to the Platform tenant for all 8 pre-existing concept types (all genuinely platform-canonical). Every `ontologyDB` read (`findConcept`, `findConceptsByType`, `listDistinctConceptTypes`) takes an `OntologyViewer { isRoot, tenantId }` and filters to `[Platform, viewer.tenantId]` (or unscoped for root). Writes (`upsertConcept`, `retireConcept`) always target an explicit `tenantId`.
- `core/ontology.ts`: `addConcept`/`retireConcept` take an `OntologyActor` — root may target any tenant (defaulting to Platform for add); anyone else is always forced onto their own tenant, regardless of what's submitted. `assertCanonicalCategory`'s `viewer` parameter is **optional**, defaulting to Platform-only visibility (`{isRoot: false, tenantId: null}`) — deliberately, so the five pre-existing category:* consumers (`createDeliverable`/`createEvidence`/`createDecision`/`createKnowledgeItem`/`createObligation`) need **zero changes**: none of them has any tenant/actor context available at its call site today (there's no SEU→tenant resolution anywhere in that path), and none of those five concept types has ever had a tenant-owned row. Threading real tenant context through Deliverable/Evidence/Decision/Knowledge/Obligation creation is out of scope for this CR.
- **Pack's own category/installationClassification checks** (`core/packs.ts`) now scope by the Pack's own `tenantId` (`seed.tenantId ?? PLATFORM_TENANT_ID`) — a tenant-owned Pack validates against Platform's + its own tenant's vocabulary; an unauthored (CLI/seed-published) Pack sees Platform's only, unchanged from before this CR.
- **Real bug fixed along the way**: `packRowToContent` (used to re-validate a Draft at publish time) never carried the Pack row's real `tenant_id` into the reconstructed seed — every Pack, regardless of its actual owner, would have silently validated against Platform-only Ontology visibility at publish time. Caught by tracing the scoping through end to end, not by a failing test (nothing exercised a tenant-owned Pack with a tenant-only category value yet).
- **Ontology Management admin page**: an "Owner" column (Platform / Your tenant), the retire button hidden client-side for a Platform row unless the viewer is root, and the retire form submits which tenant's row it targets (necessary now that the same code can legitimately exist for more than one tenant).
- **Pack/Template authoring's ontology-backed pickers** (CR-020 Part 2's `loadOntologyOptions`) now take the viewer, so an author sees Platform's shared `capability-name`/`category:pack`/`installation-classification`/`template-categories` values plus their own tenant's additions — the same visibility the admin page has, automatically, with no picker-specific code (this is the generic mechanism from CR-020 Part 2 paying off again: the only change needed anywhere in the picker path was threading one already-computed `viewer` value one level further).

### Scope cuts, noted rather than silently skipped
- **Root's add form has no tenant selector** — it always adds to Platform's shared vocabulary. `core/ontology.ts`'s `addConcept` supports targeting a specific *other* tenant as root (`targetTenantId`), but nothing in the UI exposes it yet.
- **The five legacy `category:*` consumers stay Platform-only scoped** (see above) — this is the exact behaviour they had before this CR, not a regression; making them tenant-aware needs SEU→tenant resolution that doesn't exist anywhere in this codebase today, a separate and materially larger piece of work.
- **Deliverable/Evidence/Decision/Knowledge/Obligation categories are not yet tenant-extensible** as a consequence of the above — only `capability-name`, `deliverable-name`, `category:pack`, `installation-classification`, and `template-categories` are, via the Pack/Template authoring pickers and the admin page.
