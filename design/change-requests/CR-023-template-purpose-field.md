### Design decisions
- **`description` lives on `ontology_concepts`, generically** — not a `template-categories`-specific column. Same discipline as `is_active`/`tenant_id`: one shared shape for every concept, usable by any future concept type that wants "when to use this" guidance, not just this one.
- **`purpose` is free text, not Ontology-backed** — it's the author's own words about *this* Template, not a picker. The category's description is a *default*, not a constraint: nothing enforces that `purpose` agrees with the selected category once an author edits it.
- **A new, generic `textarea` widget kind**, not a one-off for this field — `x-widget: "textarea"` joins `json`/`referential-select` as a first-class schema-driven widget, available to any future long-text field on any of the three kinds, round-tripped through the CR-017 meta-schema form too.
- **Pre-fill, never overwrite** — `withDefaultTemplatePurpose` only fills `purpose` when it's genuinely empty, at both Draft creation and Save. An author who clears it and writes their own text keeps it; a Save never silently reverts to the category default.
- **Guidance is generic, not Template-specific** — the `.ontology-select` / `data-description` / `id="<field>-guidance"` wiring in `_generatedFieldGroups.ejs` and `edit.ejs`'s script works for any `x-ontology` field on any kind, the same way CR-020 Part 2's picker resolver did. Template's `code` is the first field to use it; nothing about the mechanism is Template-only.

### What's built here
- 9 real "when to use" descriptions (migration 057), one per `template-categories` concept, in the register the owner demonstrated for Enterprise Web Application.
- `purpose`: required textarea field on Template's schema (§5/§7's "Purpose," Ch.6 §20.7 — closes half of that gap; "Objectives" is still unbuilt, a separate, structured field this CR doesn't attempt).
- Live guidance: the category `<select>`'s options carry `data-description`; a small `<div>` under the dropdown shows the selected option's guidance, updated on `change` and on page load (so an already-set value shows its guidance immediately in edit/view mode too).
- Server-side default-fill: a new Template Draft's `purpose` is seeded from the chosen category's description when the author hasn't supplied their own — the literal "seed... populate this field" from the owner's clarification.
- View-mode subtitle: the Template's `purpose` (once set) renders under the page's title, on both the edit and view (disabled-form) rendering of the authoring page — Template/Pack/Profile share this template; it's simply blank for the other two kinds, which have no `purpose` field.
- Ontology Management's admin page also gained a `description` textarea on its add form and shows it under the label in the concept list — CRUD completeness, not scoped to `template-categories` alone.

### Not in scope / notes
- **Objectives** (§5, §7) — still no field; `purpose` is one free-text field, not the structured "engineering objectives" list §7 separately names.
- **Enforcement between `code` and `purpose`** — deliberately absent; guidance, not validation.
- **Profile has no `purpose` field** — this CR is Template-specific, matching CR-021's own scoping ("the owner's instruction was Template-specific").
