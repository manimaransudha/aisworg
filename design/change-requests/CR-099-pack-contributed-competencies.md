## The gap

`findEligibleParticipants` (`core/participantEligibility.ts`, CR-098) already accepts a `competency` filter (`{dimension: [values]}`), but nothing populates it — the SEU detail page's Technology/Domain columns are display-only (previous session pass) because there is no real, declared mapping between a Technology/Domain Pack (`technology-nodejs`, `domain-banking-payments-markets` — Ch.5 §6.3/§6.5) and a `competency-dimension` value (`nodejs`, `banking` — migration 195). The two vocabularies coincide by accident for some codes and diverge for most (`domain-banking-payments-markets` has no equivalent competency code at all). Inferring the mapping from Pack code/name text would be guessing, not declaration — this platform's own established discipline (Service code, Capability, Policy, Quality Gate — the CR-058→065 series, Ch.5 §19.4) already rejected exactly this kind of coincidental-match approach in favour of a Pack declaring the real fact itself.

## Design — settled by the owner

1. **New Pack contribution kind: `contributionCompetencies[]`.** One entry per `{dimension, value}` pair a Pack represents. **Revised — `dimension` is sourced from `category:pack`, not a separate `competency-dimension` parent concept type.** Owner: *"Haven't we created Ontology for participant competencies? Dimension should be categories:pack. Value should be from competency ontology."* `category:pack` already carries exactly the real vocabulary a Pack's own competency-dimension is ("Compliance"/"Domain"/"Engineering"/"Organisation"/"Integration"/"Technology" — migration 049) — inventing a second, parallel parent concept type for the same concept space was redundant. `technology-nodejs.pack.json` now declares `[{"dimension": "Technology", "value": "nodejs"}]`; a Domain Pack declares `{"dimension": "Domain", "value": ...}`. `value` still comes from "the competency ontology" (migration 195's own `technology`/`domain` child concept types) — but **note the casing mismatch this creates**: `category:pack` codes are capitalised (`Technology`, `Domain`), while a concept_type's own name must be lowercase-hyphenated (`assertOntologyCodeFormat`) — resolving `dimension` to its child concept_type needs a `.toLowerCase()` bridge (`"Technology"` → concept_type `technology`), not a like-for-like string match. Flagged, not yet built.
2. **Declaration only** — no new table. Same precedent as Obligation Definitions (CR-062) and Engineering Capital (CR-082): nothing else needs to cross-reference one of these by id, so it stays in `packs.contributions` (JSONB) only, read directly off the Pack row wherever it's needed (no `seedContributions` materialisation step).
3. **Not a configurable/exposable parameter — Profile cannot override it.** Owner: *"These are not configurable parameters. So profile cannot override this."* A Pack's declared Competencies are fixed at Pack-authoring time; a Profile only ever chooses *which* Packs are in scope (its existing `technologyPackCodes`/`domainPackCodes`/etc.), never what those Packs' own Competencies say.
4. **Backfill required — and now mandatory, not just planned.** All 49 real Technology (24) + Domain (25) Pack seed files get real `contributionCompetencies` entries; the `technology`/`domain` child concept types (migration 195, still just `competency` "ontology" regardless of which parent now names them — see point 1) need their real, full value sets seeded (today: 3 placeholder `technology` values, 2 placeholder `domain` values — nowhere near the 24/25 real Pack identities this backfill represents). **Owner: "Pack has to now define mandatory competency. Otherwise it will lead to gaps. Don't you think so?"** — agreed: `validatePackSeed` (`core/packs.ts`) should require at least one `contributionCompetencies` entry whenever `pack.category` is `Technology` or `Domain` (a new, category-conditional required-field check — same shape as other category-conditional validations already in that file), so a future Technology/Domain Pack can't ship silently invisible to every competency-based eligibility check. Every real Technology/Domain Pack file must pass this at backfill time, not just "ideally" carry the field.
5. **New tab on Pack Registry and Pack Authoring — turns out to be ONE build, not two.** Owner: *"When a pack is viewed, each of the contributions is a tab. Same thing in authoring page."* Checked directly: Pack Registry's own "View" link (`views/seu/packs/index.ejs:113`) already points at `/aisworg/seu/sdk/pack-authoring/<id>` — the *same* `GET /sdk/:slug/:draftId` route Authoring itself uses (`sdkAuthoring.ts`), rendering the *same* `seu/sdk/authoring/edit.ejs` → `_generatedFieldGroups.ejs`. That partial already renders one real Bootstrap `tab-pane` per schema field group (`_generatedFieldGroups.ejs:147`) — genuinely schema-driven, not hardcoded per contribution kind. So adding `contributionCompetencies` to the Pack grammar (with its own field group, same as every existing `contribution*[]` field) produces the tab automatically on **both** surfaces at once, because they're literally the same page. No separate "Registry view" work needed — this closes what was an open question.

## Design — checked against Profile composition (owner: "Check Profile composition")

- **`compositionEngine.ts`'s own Pack resolution** (`resolveActivePack` + the union of Template's mandatory codes and every one of a Profile's 7 category-scoped selection buckets, lines ~375-429) confirms: a Technology or Domain Pack can enter an SEU's scope via **either** a Template's mandatory set **or** a Profile's `technologyPackCodes`/`domainPackCodes` — not only the latter. **This means the Capability Fulfilment screen's current Technology/Domain columns (built last pass, reading only `getProfilePackSelections`) are narrower than correct** — they should read the SEU's actual **`ebm.composed_packs`** (the real resolved set, already computed at commissioning) instead of re-deriving from the Profile alone. Flagged as a fix needed alongside this CR, not a new problem this CR introduces — it already existed in the Technology/Domain display built last pass.
- **`detectGovernanceConflicts`** (`compositionEngine.ts`) — checked directly: only inspects `authorityRules` and `qualityGates` for cross-Pack disagreement. Competencies are purely additive declared facts, not governance assignments — two Packs both declaring `{"technology","nodejs"}` is not a conflict the way two Packs assigning different authorised roles to the same transition is. **No change needed here.**
- **`deriveExposableParameterCandidates`** (`core/templates.ts`, CR-088) — checked directly: a **closed enumeration** over `sourceType: "service" | "policy" | "checklist" | "dependency"` only, explicitly not a scan over every contribution kind (Capability/Review Gate/Quality Gate/Authority Rules were deliberately excluded when this was built). A new contribution kind is invisible to this mechanism unless someone adds a 5th `sourceType` for it. **Confirms point 3 above is already the natural default — no extra guard needed to keep Competencies out of Profile's override surface.**

Already updated: migration 195 (drops the `competency-dimension`/`hyper-scale` inserts, keeps `technology`/`domain` as plain child concept types), `core/participantsMaster.ts` (`assertCanonicalCategory("category:pack", dimension)` then `dimension.toLowerCase()`), `seuTypes.ts`, `core/participantEligibility.ts`'s comments, and all 4 mock onboarding adapters (`Domain`/`Technology` keys, no hyper-scale value generation). ## Design — settled by the owner (continued)

6. **Authoring form: `value` is a live, Ontology-driven dependent dropdown on `dimension` — genuinely new item-level work, corrected twice now.** Owner: *"dimension→value picker in the authoring form needs live dependent-dropdown ontology driven."*
   - First pass: called this "a new form-generator capability... nothing in this codebase makes one field depend on a sibling's value." Wrong — CR-079 step (d) already built `x-referential-source-by`/`x-referential-source-suffix` for exactly this shape.
   - Second pass (this correction): checked *which* mechanism CR-079 actually built, and it's narrower than assumed. `generateFields`'s dynamic-driver handling (`formGenerator.ts:299-327`) only resolves a driver field's value off `content[driverField]` — a **top-level** schema property (Pack's own `code`, driven by Pack's own top-level `category`). `dimension`/`value` for Competencies both live **inside the same row** of a `referential-list` (`contributionCompetencies[].dimension`/`.value`) — item-level fields, built by `buildItemFields`/`buildRow` (`formGenerator.ts:196-247`), which only ever produces `nested-list` / `referential-multi` / `referential` (static source only) / `enum` / `boolean` / `string` — **no dynamic-driver-by-sibling-item-field case exists there at all.** CR-079's mechanism doesn't reach into a repeatable row.
   - Net: real, new work — `buildItemFields` needs its own dynamic-driver case (mirroring `generateFields`'s, but resolving the driver off the *same row's* other fields, not top-level `content`), plus the corresponding view/client-side swap in `edit.ejs` for per-row driver→dropdown. Scoped, not huge (one new item-field kind following an existing pattern closely), but not a schema-only change the way point 6 twice claimed. Not built.
   - **This does not block the seed-data work** (Ontology values, Pack JSON backfill) — those are validated by `validatePackSeed` directly, no authoring form involved; a real Pack seed file can carry `contributionCompetencies` correctly today even before the interactive form can author it.

## Not in scope

- Any change to `compositionEngine.ts` beyond the fix noted above (Technology/Domain display should read `composed_packs`, not just Profile's own selections) — Competencies themselves need no composition-engine involvement, per the "declaration only, read straight off the Pack row" design.
- Extending `contributionCompetencies` to any Pack category beyond Technology/Domain — mechanically available to any Pack (same as Capabilities aren't category-restricted), but not this CR's job to seed for other categories.
- `hyper-scale` as a competency dimension — dropped, not deferred (see "checked against Profile composition" / "What else" above). No Pack category maps to it, and there is no longer a non-Pack-sourced dimension mechanism for a Participant to declare one either.
