> **Generic, schema-driven mechanism (owner: "The form generator should say which fields are from ontology and use a generic function so this is still driven by the schema pointing to the ontology... do not hard code in the schema").** A referential-select field is Ontology-backed when its schema property carries `"x-ontology": true`; `x-referential-source` is then the *exact* Ontology `concept_type` to resolve (`capability-name`, `category:pack`, `installation-classification`) — never an arbitrary registry key translated somewhere in code. One function reads this off any schema (`formGenerator.ontologyConceptTypesIn`), one function resolves it (`web/sdkAuthoring.loadOntologyOptions`), and one view branch renders it (`_generatedFieldGroups.ejs`, `f.kind === 'referential-select' && f.ontology`) — all three are generic over Pack/Template/Profile and over however many ontology-backed fields exist; a new one (on any of the three kinds) is a schema change + an Ontology Management data change, never new code. Round-tripped through the CR-017 meta-schema authoring form too (`schemaCompiler.ts`'s `AuthoredField.ontology`), so a schema author using that form can mark a field ontology-backed without a code change either.

> **Two deliberate Title-Case exceptions to the "lowercase, hyphenated" code convention:** `category:pack` and `installation-classification` both keep their exact historical wording (`Compliance`/`Domain`/`Engineering`/`Organisation`/`Integration`/`Technology`; `Mandatory`/`Recommended`/`Optional`/`Conditional`) rather than lowercase-hyphenated codes. Both concept types *replace* an already-live mechanism with real data riding on the exact strings: ~370 `packs.category` rows plus the Dependencies tab's client-side category filter (strict `!==` match against `packs.category`, no case normalisation) for the former; ~440 `packs.installation_classification` rows for the latter. Lowercasing either would either silently break that filter or instantly invalidate hundreds of existing rows' classification for no reason. `capability-name`/`deliverable-name` had zero real consumers when seeded, so no such exception was needed there. Consequence: if either a `category:pack` or `installation-classification` row is ever retired, reactivating it via the Ontology Management **Add** form (which enforces lowercase) won't work by typing the same code back — it needs a migration, the same way it was seeded. Narrow edge case, flagged here rather than silently accepted.
>
> **`category:pack`'s `"Platform"` is dropped, not carried forward** — the owner's list (Compliance/Domain/Engineering/Organisation/Integration/Technology) doesn't include it; `"Engineering"` is the one genuinely new value. Existing `Platform`-categorised Packs are unaffected (same "retired drops out of new-picks" discipline as `capability-name`'s `architecture` fold in CR-020's first Built note) — `"Platform"` just stops being offered to new Pack authoring, which is what broke `tests/engine.test.ts`/`tests/sdk-authoring.test.ts`'s fixtures (fixed by repointing to `"Engineering"`, then further repointed to `"Engineering"` for the other 3 files that had used the still-valid-but-now-superseded `"Technology"`, per the owner's explicit "make the category as engineering" for Pack test seeds).
>
> **`code`'s format is a UI convention, not a server-side constraint** — unlike `category`/`installationClassification`, `validatePackSeed` does **not** check that `code` resolves to a real `capability-name` concept. The dropdown guides an interactive author to a real concept; a JSON import or the seed/CLI path can still set an arbitrary `code` string (same as it always could, `toPackSeedInput`'s `randomUUID()` fallback is unchanged) — matching how `mandatoryPackCodes`/`baseTemplateCode` and every other referential picker in this codebase already tolerate an off-list value (rendered with a "⚠ not currently active" fallback option). What *is* new and server-side: since `code` is now realistically shared across unrelated Packs (a small ~20-value vocabulary, not a UUID), `assertPackCodeVersionFree` turns a `(code, packVersion)` collision with a genuinely different Pack into an actionable validation error instead of a raw `packs_code_version_key` constraint violation.

### Background
Chapter 18's Ontology Model was already built in a deliberately scoped-down form (`design/mvp-build-plan/Ontology Plan.md`, "✅ Built 2026-08-12"): `ontology_concepts` (canonical registry) + `tenant_concept_aliases` (per-tenant rename-only), with write-path enforcement wired into 5 `category:*` concept types. Two things were missing for what the owner now wants to build on top of it:
1. **No real content for `capability-name`** — seeded in migration 030 with 3 illustrative rows, zero consumers anywhere in the codebase.
2. **No way to manage the vocabulary except a migration** — `upsertConcept` existed in `ontologyDB.ts` but had zero callers; adding a concept meant writing SQL.

### Decision (owner)
- Seed the real 20-item `capability-name` list (owner-provided) — fold the 3 existing illustrative rows into it ("nothing that is live, so safe to").
- Add "Ontology Management" to the navbar.
- Build a CRUD UI for concept types/concepts, "similar to nouns and verbs," so **any further addition is a data change, not a code change**.
- **No separate `concept_types` governance table** — considered and explicitly rejected ("this is an ontology table... there will be no end to this"). CRUD lands directly on `ontology_concepts`; the only guard-rail is a naming convention: **lowercase, hyphenated, no spaces** (e.g. `capability-name`), enforced by validation on write, not a second table.
- Wiring Pack authoring's `code` picker to `capability-name` (the actual "code engine" step motivating this) was **initially deferred** — "There is no pack capability. So ignore this condition" — but **built as Part 2 of this same CR the next day** (2026-08-19) once the owner returned to it, alongside `category`/`installationClassification` and dropping `owner`/`publisher`. See the Part 2 update note above.

### What's built here
- **Seed** (migration 046): the 20 `capability-name` concepts, folding in the 3 pre-existing rows (`requirements-analysis` and `development` matched exactly; `architecture` → `architecture-solution-design`). Scoped to the `ontology_concepts` row only — the real `capabilities.code = 'architecture'` row (referenced by ~30 test files + 3 seed JSON files) is untouched, since nothing consumes `capability-name` concepts today and reconciling real capability codes is the deferred step above.
- **Soft-retire** (migration 047): `ontology_concepts.is_active BOOLEAN NOT NULL DEFAULT TRUE`, matching the `authority_nouns`/`authority_verbs`/`pack_category` "add + soft-retire, never hard delete" discipline. `findConceptsByType` defaults to active-only (the picker/validation view); the admin list passes `includeInactive: true`. `upsertConcept`'s `ON CONFLICT` now also reactivates (`is_active = TRUE`), so re-adding a retired code brings it back. `assertCanonicalCategory` now rejects a retired concept the same as an unknown one — a retirement means "no longer valid for new writes," not "gone."
- **Format validation**: `ONTOLOGY_CODE_RE = /^[a-z][a-z0-9-]*$/` in `core/ontology.ts`, applied to both the concept's `code` and the `conceptType` itself (same discipline both ways, since a concept type is just another string in this table).
- **Admin page** at `/aisworg/seu/sdk/ontology` — root-only (`requirePlatformBadge("root")`), same rationale as Schema Registry: canonical platform vocabulary is platform-administrative, a bigger blast radius than the `{kind}_define`/`{kind}_publish` badges that gate ordinary authoring. Concept types render as tabs, **derived from the data itself** (`SELECT DISTINCT concept_type`) — there's no fixed list to maintain; typing a brand-new `conceptType` into the add form starts a new type on the spot. Each tab is a searchable/sortable list (code, label, status) with add + retire forms, mirroring the Authority nouns/verbs page's shape.
- **Navbar**: "Ontology Management" added to the SDK/Authoring dropdown, next to Schema Registry (Authority's own nouns/verbs/mapping pages are *not* in the navbar today — only linked inline — so this is a more prominent placement than Authority currently gets, per the owner's explicit ask).

### Not in scope / notes
- Pack-contributed concepts (`contributed_by_pack`) — the column and `upsertConcept` support it, but nothing writes it yet; still deferred per the original Ontology Plan.
- `tenant_concept_aliases` (the per-tenant rename layer) is unaffected — this CR only touches the canonical registry side.
- Template/Profile have no Ontology-backed fields yet — the generic mechanism (Part 2) supports them the moment a schema declares one; no code changes needed when that happens.
- `code`'s Ontology membership isn't enforced server-side (see the Part 2 note above) — only `category`/`installationClassification` are hard-validated at publish time.
