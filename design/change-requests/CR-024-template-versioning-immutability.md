# CR-024 — Template versioning and immutability, mirroring Pack

**Raised:** 2026-08-19 · **Origin:** owner — "Versioning and immutability - Let us version the template similar to pack." Closes Chapter 6 §20.3 (FR-6.2, FR-6.8, §14), open since the chapter's own §20 review first flagged it: `templates.template_version` existed as a column but was never read or written, and `code` alone was the unique identity, so republishing under an existing code silently overwrote the row in place — the exact defect Pack's own CR (migration `010`) had already fixed for Pack. · **Status:** ✅ Built 2026-08-19

> **Built 2026-08-19.** `tsc` clean; full suite **142 pass / 1 known-environmental fail** (the one failure is `web-flow.e2e.test.ts`'s Phase 8 attention-inbox assertion, root-caused to the shared dev DB's `attention_items` table having grown past the test's own hardcoded `pageSize=500` — 542 rows at the time, sorted by priority not recency — confirmed via direct DB query that the real "is blocked by Quality Gate" attention item WAS created correctly, timestamped exactly when the test ran; unrelated to this CR, pre-existing test fragility). Smoke-verified over real HTTP + direct core-function calls (temporary root badge on a fixture user, revoked after, all test rows deleted): a Draft's `templateVersion` field renders as a real readonly+"Next version"-button widget, pre-filled `1.0.0`; creating a second Draft at the *same* `(code, templateVersion)` is rejected with a friendly message; a second Draft at a *different* version for the same code is now allowed (the old CR-021 "one Template per category forever" cap is lifted); and — the real versioning mechanism — deprecating an Active Template and then transitioning it back to Active does **not** resurrect the old row: it creates a genuinely new row at the next free patch version, carries the old row's content over, lands the new row Active, and supersedes (deprecates) whatever was previously Active for that code, leaving the original row exactly as it was.

### What's built here
- **`templates.template_version`** converted from an unused `INTEGER` counter to a semver `TEXT` column (mirroring `packs.pack_version` exactly) — migration `059`. Uniqueness moved from `UNIQUE(code)` to `UNIQUE(code, template_version)` (`templates_code_version_key`, mirroring `packs_code_version_key`, migration `010`). Every existing row was already `code`-unique under the old constraint, so backfilling every row to `'1.0.0'` is exact, not a guess.
- **A new, generic `x-widget: "version"`** schema widget (`formGenerator.ts`) replaces what used to be a hardcoded `f.name === 'packVersion'` check in the view — Pack's own `packVersion` field was migrated onto the same generic marker (migration `060`) so there is exactly one mechanism, not two; Template's `templateVersion` (migration `061`, required) uses it identically. Readonly, advanced only by its own "Next version" patch-bump button (`edit.ejs`'s script, now generic over every `.version-field` on the page, not one hardcoded pair of element ids).
- **`templatesDB.ts`**: `findByCodeAndVersion`, `findActiveByCode` added (mirroring `packsDB`'s exactly); `findByCode` fixed to return the latest by `created_at` (previously assumed at-most-one-row-per-code, silently correct only because that used to be true); `upsert`/`createDraft`/`updateDraftContent` all version-aware, `upsert`'s `ON CONFLICT` target updated to match the new constraint (defaults `templateVersion` to `"1.0.0"` — every existing seed-script caller needed zero changes).
- **`core/templates.ts`**: `reactivateAsNewVersion` + `nextAvailablePatchVersion` + a `TERMINAL_REACTIVATABLE_STATES` check in `transitionTemplate` — a byte-for-byte mirror of `core/packs.ts`'s `reactivateAsNewVersion`/`nextAvailablePatchVersion`/`transitionPack`'s own terminal-reactivation branch (Ch.41 VM-002: a terminal-state row transitioning to Active never resurrects itself, it publishes a new Version). `advanceTemplateOneStep`'s `Published → Active` hop now supersedes whatever else is currently Active for the code, mirroring `advancePackOneStep` exactly.
- **A real seed-data gap this surfaced and fixed**: Pack's `transitionDefinitions.json` has always carried four edges into `Active` (`Published`, `Deprecated`, `Retired`, `Archived → Active`, all verb `activate`) — Template only ever had the one (`Published → Active`). Without the other three, `transitionEngine.evaluate` refused the reactivation transition outright (`no_transition_definition`) before `core/templates.ts`'s own logic ever ran. Added the same three edges for Template, in both `transitionDefinitions.json` and `authorityVocabulary.json` (verb `activate`, matching Pack), then re-ran `seedTransitionDefinitions`/`seedAuthorityVocabulary` against the dev DB.
- **`core/sdkAuthoring.ts`**: `assertTemplateCodeFree` → `assertTemplateCodeVersionFree(code, templateVersion, excludeId?)`, mirroring `assertPackCodeVersionFree`'s exact shape — the collision is now scoped to the specific version, not the whole code. `templateVersion` threaded through `createAuthoringDraft`/`saveAuthoringDraft`/`getAuthoringDraft`/`publishAuthoringDraft`'s Template branches, pulled from the real column (not `draft_content`) wherever content is reconstructed for re-validation, mirroring `packRowToContent`'s `packVersion: pack.pack_version`.

### Design decisions
- **No UI trigger for reactivation was built.** Pack's own reactivation trigger lives on its dedicated Registry page (`POST /packs/:id/transition` with an arbitrary `targetState`, including jumping back to `Active` from a terminal state) — Template has no equivalent page (Ch.6 §20.12, a separate, already-flagged gap). The *mechanism* (`transitionTemplate`, `reactivateAsNewVersion`) is fully built and verified directly; there is currently no button anywhere that calls it with `targetState: "Active"` from a Deprecated/Retired/Archived row. Flagged here rather than silently built around — a Template Registry page (or a smaller "Reactivate" affordance on the existing per-verb queue tabs) is the natural follow-up, not attempted in this CR.
- **Profile is unaffected**, per explicit owner decision during this CR's design conversation: `profiles.base_template_id` stays a frozen row FK, pinned to the exact Template version a Profile was authored against, never re-resolved to a newer Active version the way Pack references are. This was a deliberate choice weighed against mirroring Pack's `(code, packVersion)`-resolved-fresh-at-commissioning model for Template references too — the owner chose pinning.

### Not in scope / notes
- **§20.4 Inheritance** (`parent_template_id`, `templates.tenant_id`) remains open and unaffected — versioning (many rows, one code, one Active at a time) and inheritance (many rows, one code, a *parent-child* relationship) are different axes; this CR only builds the former.
- **§20.10 Events** — the generic `TemplateTransitioned` event this CR's `transitionTemplate` used to publish unconditionally is replaced by real per-state-named events under a separate, immediately-following CR-025, since the owner asked for it as a distinct item ("20.10 will also be a CR").
