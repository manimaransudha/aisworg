# CR-046 — Registry "View" button, view-page data-source fix, Capability dependency widget fix, and real server-side Ontology code validation

**Raised:** 2026-08-20 · **Origin:** owner: "In the template, pack and profile registry, include a view button as well." Investigating that surfaced four more real, connected issues, all fixed in this same pass: the required-field `*` leaking into view mode; a Pack-code reference rendering as a noisy "Item N" card instead of a compact name+code+link; the view page reading from an empty `draft_content` blob instead of the real relational data for anything not authored through the form; and — while checking why a Template's dependencyGraph looked empty — a Capability-type dependency could never actually be authored through the real web form at all. Investigating THAT surfaced the actual root concern the owner raised separately: "why are test scripts adding code that is not in the ontology??? I thought we fixed this" / "the test script should use a code present in the ontology" / "Make sure the pack and profile view pages are also cleaned up and test data population does not corrupt the database." · **Status:** ✅ Built 2026-08-20

### What changed

**1. Registry "View" button (the original ask).** Template/Pack/Profile Registry list items each gained a "View" link to that row's own authoring/view page (`/aisworg/seu/sdk/<kind>-authoring/:id`), always visible — not badge-gated like the existing Copy button, since viewing needs no authoring authority. This required loosening the GET `/sdk/:slug/:draftId` route: it no longer carries `requireAuthoring("any")`, matching the Registry list pages' own gating (login only, via the global Gatekeeper middleware — no badge requirement). `renderAuthoringForm` already computes `canEdit`/`canPublish` independently of the route's own gate, so a badge-less viewer correctly gets a genuine read-only page (CR-045's plain-text rendering), never a disabled-but-visible edit form. Every mutating action (save/publish/transition/import) keeps its own separate `requireAuthoring` gate, unaffected.

**2. View-mode bug fixes (owner, looking at a real view page):**
- The required `*` no longer shows in view mode (`_generatedFieldGroups.ejs`) — it's an editing affordance, meaningless once a field is just being displayed.
- A referential-list row that's just one Pack-code reference (Template's six category fields, its legacy `mandatoryPackCodes`, Profile's `optionalPackCodes`/four category fields, Pack's own Dependencies) now renders as a compact list line — Pack name, code, version, and a "View" link straight to that Pack's own page — instead of an "Item N" card with a "Pack Code" sub-label (`_referentialListGroup.ejs`). Any other referential-list shape (Deliverable Catalogue, Dependency Graph — no Pack reference) keeps the card layout, unchanged. `PackDependencyOption` gained an `id` field (`sdkAuthoring.ts`) so the view link has somewhere to point.

**3. View-page data-source bug.** `getAuthoringDraft` (`core/sdkAuthoring.ts`) read Template's Pack Codes/Deliverable Catalogue/Dependency Graph and Profile's Pack selections exclusively from `draft_content` — a JSON blob only ever populated by the authoring **form**. Anything created outside the form (`seedSdlcStandardTemplates.ts`, `tests/testFixtures.ts`, and by extension every SDLC standard Template/Profile shipped) has an empty `draft_content`, even though its real data is genuinely materialised in `template_packs`/`profile_packs`/the `deliverable_catalogue` column/`dependency_definitions`. The view page showed "None" for data that was real and in effect. Fixed: once a Template/Profile is no longer a Draft, `getAuthoringDraft` now reads the real relational data instead (`getPackSelectionsByCategory` — already existed; a new `getDependencyGraphContent`, `templates.ts`; a new shared `getProfilePackSelections`, `profiles.ts`, deduplicating the same logic `reactivateAsNewVersion`/`copyProfileAsNewDraft` already had inline). A second bug surfaced while wiring this up: `getPackSelectionsByCategory`/`getProfilePackSelections` return the seed-level shape (bare `string[]` codes), but the schema's own referential-list item shape expects `Array<{packCode}>` — without converting, every resolved code silently rendered as blank. Fixed with a small `packSelectionsToFormShape` converter.

**4. Capability-type dependencyGraph rows were unauthorable through the real form.** The dependencyGraph widget's schema (migration 076) only ever exposed `fromName` — but `materialiseDependencyGraph`/`validateTemplateSeed` both read `fromCapabilityCode` for `fromType: "Capability"` rows (the field every hand-authored seed JSON file has always actually used). A Capability-type dependency typed into the real browser form was silently dropped at materialisation, no error. Fixed (migration 080): added `fromCapabilityCode` to the schema, sourced the same live-derived way `deliverableCatalogue.producingCapabilityCode` already is (`derived:requiredCapabilityCodes`) — no code change needed beyond the schema, since both the derived-options resolver and the self-referential resolver are already generic over which field carries the marker. `fromName` also picked up `self:deliverableCatalogue` (matching `toName`) now that it only ever needs to mean "a Deliverable name" — narrower and safer than the old free-text field that used to double for both purposes.

**5. Real server-side Ontology validation for `code` (the actual "why are test scripts adding code that is not in the ontology" gap).** `validatePackSeed`/`validateTemplateSeed` already called `assertCanonicalCategory` for `category`/`installationClassification`/`compositionStrategy`/Profile's `category` — every Ontology-backed field except `code` itself (Pack's `capability-name`, Template's `template-categories`), which only ever got a non-empty check. In the browser, the dropdown made this invisible — a real author can't type an invalid code. Every other caller (tests, scripts, a future API client) could. Fixed by adding the same `assertCanonicalCategory` check for `code` in both functions.

### Test fixes (owner: "the test script should use a code present in the ontology")

19 tests across `tests/pack-sdk.test.ts`, `tests/engine.test.ts`, `tests/governance-ebm-sharpening.test.ts`, and `tests/web-flow.e2e.test.ts` minted arbitrary `sdk-test-pack-*`/`test-conflict-*`/`webflow-phase9-pack-*`-style strings as a Pack's or Template's `code` and published them — legal before this CR's validation fix, rejected after. Two different repairs, depending on what each test actually needed:

- **`tests/sdk-authoring.test.ts`** (Pack/Template authoring pipeline tests): switched to a **fixed, real** pre-seeded Ontology concept (`"development"` for Pack, `"mobile-application"` for Template) — per-test uniqueness (needed since this file runs repeatedly against the same, never-reset dev database) moved to `packVersion`/`templateVersion` instead, which carries no Ontology constraint. Lookups switched from "most recently created row for this code" (`findActiveByCode`/`findByCode`) to exact `findByCodeAndVersion`, avoiding a real race a shared fixed code would otherwise open against concurrently-running test files.
- **`tests/pack-sdk.test.ts`, `tests/engine.test.ts`, `tests/governance-ebm-sharpening.test.ts`, `tests/web-flow.e2e.test.ts`**: these need many simultaneously-distinct Pack identities within a single run (version-history counting, two-tenant comparisons, deliberate code conflicts) — a fixed shared code doesn't work here. Instead, a new shared helper (`registerTestOntologyCode`, `tests/testFixtures.ts`) **registers a real Ontology concept** via the actual Ontology Management `addConcept` function before each test uses it — genuinely present in the Ontology, not coincidentally matching a pre-seeded value. Every test file that calls it now tracks the codes it registered and deletes them in its own `after()` (`deleteTestOntologyCodes`), matching the pre-existing user/grant/Template cleanup discipline `sdk-authoring.test.ts` already had — `pack-sdk.test.ts` additionally gained Pack-row cleanup it never had before at all (every prior run left its Active Packs behind permanently).

### Follow-up, same day — the seed dependency graphs were redundant, not just present

Owner: "Do the template seeds now have a dependency graph for the deliverables in a meaningful way?" Checked the actual content (not just presence/wiring) across all 11 seed files. The `Deliverable`-type half of every row was genuinely meaningful — a real linear prerequisite chain. The `Capability`-type half was not: in all 9 standard SDLC templates (128 rows), every Capability-type row referenced the **predecessor** deliverable's producing capability, never the **gated** deliverable's own. That condition was always already true by the time it was checked (the predecessor's Deliverable-Approved condition on the same row already implies its own producing capability was fulfilled — you can't approve output from an unstaffed capability), so it added no real constraint.

Fixed: all 9 standard templates' Capability-type rows now reference the gated deliverable's own `producingCapabilityCode` — a genuinely independent condition ("someone is now staffed to build *this* artifact," on top of "the previous artifact is approved"). `ebook-library.template.json` (not one of the 9 — a separate, older fixture) already had a more sophisticated, genuinely non-redundant fan-in structure and was left untouched; `web-application.template.json` (also not one of the 9) has the same redundant pattern the 9 had, also left untouched — not raised in scope.

Verified: a script confirmed every Capability-type row across all 9 files now matches its own deliverable's `producingCapabilityCode` (0 mismatches), deliverable/graph-row counts unchanged (9 deliverables / 16 rows each, same as before), all 9 files still parse as valid JSON. `npx tsc --noEmit` clean, full suite **149/149**. The diff also normalises these 9 files' array formatting (one item per line) to match `web-application.template.json`'s own established convention — the files' formatting had drifted from each other; this brings them back in line, and is why the diff is larger than the 72 changed values alone would suggest.

### Not in scope

- The pre-existing backlog of junk Template/Profile/Pack rows already accumulated in the shared dev database from test runs **before** this fix (roughly 43 Templates, 41 Profiles, 253 Packs at time of writing) — these predate this CR's cleanup additions and were created by code paths (`templatesDB.upsert`/`profilesDB.upsert` direct calls in `pack-sdk.test.ts`/`engine.test.ts`/`governance-ebm-sharpening.test.ts`) that still have no tracked cleanup at all. `pnpm db:clean-slate` is the existing, established mechanism for clearing this — not run as part of this CR, since it resets the whole dev database (tenants, identity, seed baseline) and is the owner's own call on timing.
