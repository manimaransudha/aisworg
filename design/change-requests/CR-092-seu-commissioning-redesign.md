**Raised:** 2026-09-06 · **Origin:** owner, exercising the "Commission SEU" action from the Objectives tree for the first time. · **Status: ✅ CLOSED 2026-09-07 — all 9 parts built.** Parts 1-3, 5 built 2026-09-06. ## The gap (found live, in order)

- **The "Commission SEU" button was undiscoverable and, once found, failed opaquely.** The tree/list rows' own action existed in code but required expanding past the Strategic-root level to find; clicking it against a real Objective failed with a raw `Commissioning failed at "select_template": no Template satisfies every required Capability` — no indication of which Templates existed or which Capability was the problem.
- **Root cause of the failure**: `findCandidateTemplates` requires ONE Template to cover the Objective's ENTIRE declared Capability set — a hard, all-or-nothing gate. Investigating the specific failing case (a Capability named `continuous-requirements-validation`) found a real, separate platform gap: it's a `capability-name` Ontology concept (migration 046) with **no Pack ever contributing it as a real Capability** — along with five siblings from the same seed batch (`continuous-compliance-verification`, `engineering-decision-explainability`, `evidence-based-organisational-reasoning`, `predictive-engineering-risk-assessment`, `continuous-quality-assurance`, `organisational-memory-synthesis`) — an entire tier of aspirational Capabilities with Ontology names and Service Definitions (migration 154) but no Pack backing, making them structurally uncommissionable no matter which Template exists. Not fixed here — flagged, and worked around by design (see Part 2).
- **Owner correction on where the fix belongs**: *"The commission SEU should get onto the SEU screen and the messages has to be on that screen. Not on the objective screen."* — the diagnostic/picker belonged on a real SEU-area screen, not decided inline on the Objective's own detail page.
- **Owner correction on the underlying model**: *"Objectives only propose capabilities. They do not take the final call. The correct way to show this information is like a tree. capability-name -> templates -> profile And allow the user to choose a profile. If an additional capability is required, profiles have provision for that."* — a Capability an Objective declares is a proposal to weigh while browsing, not a filter the system enforces; a Template's own gap is what a Profile's `additionalCapabilityCodes` (CR-091 §5) exists to cover.
- **Same anti-pattern found on the OTHER commissioning entry point**: the freeform "Commission a new SEU" form (`/seu/seus/new`, no Objective yet) auto-created an Objective from a bare statement + capability checkboxes and auto-matched both Template and Profile — no real choice at all. Owner: *"the SEU is commissioned against an objective... If the commissioning happens from SEU, then Objective also has to be picked."*
- **A related bug, found while testing the fixed picker**: a child Objective could not be added under an Active parent at all (`createObjective`'s own "parent must be Proposed" gate applied uniformly, no tier exception), and the "Move" action (`reParentObjective`) had never mirrored that gate onto the *new* parent in the first place — only the moved node's own status was checked. Owner: *"That check makes it impossible to make a strategic objective be an umbrella... allow children to be created if a parent is in a proposed or active state. It will become a setup overhead otherwise every time we want to introduce some new feature or request."*
- **SEU's own noun×verb model**: Chapter 8 §18 names 10 Commissioning events (`CommissionRequested`, `CommissionValidated`, `CompositionStarted`, `CompositionCompleted`, `RuntimeAllocated`, `KnowledgeInitialised`, `ParticipantsRecruited`, `SEUActivated`, `CommissionCompleted`, `CommissionFailed`), but the SEU noun has exactly one governed transition for the whole span (`Pending -> Commissioned`, verb `commission`) — everything else happens un-gated inside `commissionSeu`. Owner: *"SEU is a noun and has verbs should correspond to the events... The transition definition does not have the correct verbs."*

## Design & Build (owner, settled 2026-09-06)

### Part 1 — Objective decomposition: Proposed-or-Active parent gate

`DECOMPOSABLE_PARENT_STATUSES = ["Proposed", "Active"]` (`core/objectives.ts`), applied consistently in the three places that gate whether a parent can receive children:
- `createObjective` — adding a new child now succeeds under a Proposed *or* Active parent (previously Proposed only).
- `reParentObjective` — the new-parent check (a genuine bug fix — it never existed before this pass; only the *moved node's own* status was ever checked) uses the same rule.
- `listReParentCandidates` — the "Move to" picker offers Active objectives again, consistent with the validation (previously mismatched: candidates included Active while validation rejected it).

Achieved/Superseded/Retired/Archived parents remain closed to new decomposition. Editing an Objective's own statement/Capabilities, and moving an Objective that is itself already Active, are unaffected — this only changes *whether a parent can receive children*.

### Part 2 — SEU commissioning: capability → Templates → Profiles picker

`getObjectiveDetail` (`core/objectives.ts`) now computes `commissioningOptions: ObjectiveCommissioningBranch[]` — one branch per required Capability, each listing every currently-visible Template that carries it (independently — a Template need not cover every other branch too) and each Template's own real Profiles (`listRealProfilesForTemplate`, `core/profiles.ts`). A branch with zero Templates is still shown, not hidden — the gap itself stays visible. Replaces the earlier strict-match `commissioningPreview`/`commissioningDiagnostic` pair entirely.

`commissionFromExistingObjective` (`core/commissioning.ts`) no longer derives or validates a Template against the Objective's Capabilities — `templateId` is now a required, explicit human choice (same as `profileId` already was). The `"select_template"` failure stage is gone from this function; whatever `commissionSeu` itself would reject is the only way it can still fail. (`commissionFromForm`'s own separate, still-strict auto-matching pipeline — used directly by ~35 test files as a one-shot fixture helper — is untouched.)

The picker renders on `/aisworg/seu/seus/new?objectiveId=<id>` (`seus/new.ejs`) as grouped radio rows (`templateProfile` = `templateId|profileId`), submitted to the existing `/aisworg/seu/objectives/:id/commission` route, which now parses the chosen pair instead of auto-deriving one.

### Part 3 — Commissioning always starts from a real Objective

The Objective detail page, the Objectives tree, and the Objectives list all link "Commission SEU" to `/aisworg/seu/seus/new?objectiveId=<id>` instead of deciding anything inline — routing per-row Template-match checks away from an expensive per-row query, onto the one Objective actually being acted on.

The freeform "Commission a new SEU" entry point (`/seu/seus/new`, no Objective yet) is retired: `listCommissionableObjectives` (`core/objectives.ts`, `commissionable`-filtered) now backs a picker of real, already-decomposed, eligible Objectives; choosing one links into the same `?objectiveId=` screen as Part 2. `POST /seus` (the old statement+checkbox submit route, calling `commissionFromForm`) is removed — nothing submits there anymore. `commissionFromForm` the *function* is untouched for the same reason as Part 2's own carve-out.

Both entry points now converge on one shape: an Objective (carried forward, or picked), then the same capability-driven Template/Profile tree.

### Part 4 — SEU transition-definition vocabulary (Ch.8 §18 events)

Transition-definition (seed/vocabulary) layer only, by explicit instruction — *"this has to be just a change to the transition definition for now and then we review the actual transition details."* No code wiring yet.

Added a parallel, additive chain alongside the existing `Pending -> Commissioned` row (untouched — `commissionSeu` still calls it directly, and it's what every existing commissioning test relies on):

```
Pending --(validate)--> Validated --(compose)--> Composed
  --(allocate_runtime)--> RuntimeAllocated
  --(initialise_knowledge)--> KnowledgeInitialised
  --(recruit_participants)--> ParticipantsRecruited
  --(commission)--> Commissioned
```

`transitionDefinitions.json` gets the 6 new `(entityType, fromState, toState)` rows; `authorityVocabulary.json` gets 4 new verb codes (`compose`, `allocate_runtime`, `initialise_knowledge`, `recruit_participants` — each described as "vocabulary only for now, not yet wired," mirroring the existing `approve_exception` precedent) plus the matching 6 transition entries (reusing the already-existing `validate` and `commission` verb codes for two of the hops). `CommissionRequested` gets no transition of its own (SEU row creation, not a state hop — consistent with this platform's existing "creation is a granted badge, not a transition" rule); `CommissionFailed` gets no new state (stays an event-only rejection outcome, as today). `CompositionStarted`/`CompositionCompleted` deliberately share one verb (`compose`) rather than getting one each — they bookend a single synchronous `compositionEngine.compose()` call, not two persisted states; flagged explicitly for the next review.

**Explicitly deferred to that next review, not decided here**: whether `commissionSeu` actually routes through this new 6-step chain (replacing today's single `commission` check) or keeps it as a fallback; which badges get granted to which roles for the 4 new verbs; whether the existing `Pending -> Commissioned` row is retired once the new chain is live.

### Part 5 — Commissioning lock + SEU link (built same day, two follow-on fixes)

- `commissionSeu` already refuses a second attempt once an SEU row exists for an Objective (`seusDB.findByObjectiveId`, checked before `SEUCommissionRequested` even fires — the row is created, and the event published, on the *first* attempt regardless of whether it goes on to succeed or fail) — but the UI never reflected this, so the "Commission SEU" action kept offering itself on an already-requested Objective. Owner: *"The corresponding objective should not allow any more commissioning requests against the same objective."* `getObjectiveDetail` now exposes `commissionedSeuId`; the Objective detail page and the `?objectiveId=` picker screen both show "Already commissioned — view SEU" instead of the action once it's set, and `commissioningOptions` itself is `null` in that case.
- The Objectives tree/list's own "Commissioned" badge was inert text. Owner: *"Link the seu id on the Commissioned status on the Objectives page."* `seusDB.commissionedObjectiveIds()` (bare ids) replaced with `commissionedObjectiveSeuIds()` (objectiveId -> seuId pairs); `toListItem`/`ObjectiveListItem` carry a real `commissionedSeuId` (with `commissioned` now derived from it, one source of truth); the tree/list badge links straight to `/aisworg/seu/seus/<id>`.

### Part 6 — Commissioning is one-or-more Templates × one-or-more Profiles, with cross-Profile conflicts surfaced (built 2026-09-06)

Ch.8's FR-8.2/FR-8.3 read as strict singulars ("every commissioning request shall reference one Template"/"one Profile"), and everything built in Parts 1-3 above matches that literal reading (`commissionSeu(templateId: string, profileId: string)`, `seus.template_id`/`seus.profile_id` as single FKs, the Part 2 picker's own single `templateProfile` radio choosing exactly one Template+Profile pair). Owner: *"Forget what exists in the code. that is what we are trying to cleanup against what the chapters say."* **Chapter 8's own text is left as-is — FR-8.2/FR-8.3/§5 are not being edited.** The real intent is narrower than a blanket rewrite of those FRs, and owner-stated directly rather than inferred from chapter text:

*"Ideally, if the user has setup the objectives and profile correctly, it should be one profile per SEU. But I expect organisations to start at a less maturity. So allow multiple profiles and surface the conflicts."*

Settled:
- **Templates**: one or more may be selected; genuinely more than one is an edge case (owner: "typically this is going to be one template"), not the common path.
- **Profiles**: one or more may be selected; **more than one is the expected, common case for a less-mature organisation** — not an edge case to merely tolerate. This is *why* Composition (§10) and Validation (§9) exist as real pipeline stages at all, per the owner: *"Multiple profiles are very much possible. That is why composition exists. That is why validation is required."*
- **Workflow** (owner): once Template(s) are chosen, that Template's (or Templates') own Profiles are displayed; the user picks one or more Profiles; the request is then explicitly **queued to validate** — a deliberate, named step, not an immediate commit.
- **Validation view**: surfaces every conflict arising from having multiple Profiles (and/or Templates) in play, before the user may proceed — both classes below have to surface here, not just the first:
  - **Pack-level conflicts** — the composition engine's own existing `compositionReport.conflicts` mechanism, extended to run across the *union* of every selected Profile's Pack selections (all six categories), not just one Profile's own.
  - **Parameter-level conflicts** — owner's own worked example: two Profiles both overriding the same exposed Commissioning Parameter (CR-088's `exposedParameterOverrides`) to two different values. A genuinely new conflict class; no existing mechanism detects this today (each Profile's own overrides are only ever validated against its own base Template in isolation, never against a sibling Profile's).

**Built, no schema migration** (owner's own "ideally one profile" framing made this the right minimal shape, not a bigger N:N redesign): `seus.template_id`/`profile_id` and `ebms.template_id`/`profile_id` stay `NOT NULL` single FKs, populated with the *primary* (first) Template/Profile of the selection; the full set that actually composed together is recorded in `CommissioningReport.identity.templateCodes`/`profileCodes` (new, alongside the existing singular `templateCode`/`profileCode` — additive, no migration). The SEU/EBM detail *pages* still render only the primary Template/Profile; the full set is only visible in the Commissioning Report.

`compositionEngine.compose()` (`src/domain/engine/compositionEngine.ts`) takes `templateIds: string[]`/`profileIds: string[]` now — mandatory Pack codes unioned across every given Template, optional Pack codes across every given Profile. The existing Override-by-code resolution and `detectGovernanceConflicts` needed no changes at all — both already operate on a flat `PackRow[]`, so multi-source Pack conflicts already fall out of the same logic once the input union is bigger. New: `detectParameterOverrideConflicts` — reads each given Profile's own `exposedParameterOverrides` (via a new exported `extractExposedParameterOverrides` helper, `core/profiles.ts`, mirroring `extractExposedParameters` in `core/templates.ts`), groups by `(sourceType, sourceCode, parameterName)`, and flags any key where two-or-more given Profiles disagree on the value — appended into the same `compositionReport.conflicts` array the Pack conflicts already use, so there is exactly one blocking rule (FR-8.6), not two.

`commissionSeu`/`commissionFromExistingObjective` (`core/commissioning.ts`) both take arrays now (`commissionFromExistingObjective`'s own shape is `selections: Array<{templateId, profileId?}>`, so a per-pair omitted `profileId` still falls back to `findOrCreateDefaultProfile` for that specific Template). `commissionFromForm` is untouched externally — it wraps its own single Template/Profile in one-element arrays internally, so none of the ~35 test files calling it directly needed to change.

New `previewCommissioningValidation` (`core/commissioning.ts`) is the "Queue to validate" action's own backend — calls the same `compositionEngine.compose()` and returns just the report, writing nothing to the database (there is no SEU row yet to roll back if conflicts are found). The picker (`seus/new.ejs`) changed from a single radio to checkboxes, posting to a new `POST .../validate-commission` route (`web/objectives.ts`) that stashes the report and redirects (post/redirect/get, the same `stashFormInput` convention `GET /seus/new`'s own freeform-form bounce-back already used) to a new `GET .../validate-commission`, rendering the new `seu/seus/validate.ejs` — Pack-level and parameter-level conflicts both surface in one list there, since they already share one array. A clean report (no conflicts) shows a "Commission" button re-submitting the exact same selection to the existing `/commission` route; a report with conflicts offers only a way back to the picker, no override.

**Explicitly not decided/built here** *(superseded — see Part 7 and the corrections below)*: whether "Queue to validate" should instead be the `validate` verb/transition Part 4 above already added to the vocabulary — it isn't; there's no SEU row yet at "queue to validate" time for a transition to apply to, so this stayed a plain pre-creation preview action, and Part 4's own chain remains unwired, as already recorded there. ~~Conflict-*resolution* UX (picking a winning value, Profile priority ordering, an acknowledge-and-proceed override) — conflicts are a hard block, matching FR-8.6's "shall fail" wording exactly, no override mechanism added.~~ **Correction, same day**: this was built after all — see Part 7's "parameter-conflict resolution" note; a human-resolvable radio choice per conflicting parameter was added to the Validation view, feeding a new `resolvedParameterOverrides` map back into `commissionSeu`. §9's own validation list is not edited to add an explicit "cross-Profile conflicts" line, consistent with leaving Chapter 8's text untouched throughout this CR.

### Part 7 — Reversed same day: exactly one Profile, not one-or-more

Owner, later the same day, after using the Part 6 UI directly: *"Let us impose the condition that only one profile can be chosen."* This reverses Part 6's own central premise — "more than one Profile is the expected, common case for a less-mature organisation" — outright. **Chapter 8's FR-8.2/FR-8.3 singular reading turns out to be the correct one after all**; Part 6's "allow multiple, surface conflicts" framing does not survive contact with actually using the picker. Part 6's text above is left standing rather than deleted, since the reasoning that led to it (the TCS-style org-standard-vs-project-tailoring analogy that follows below) is itself real and still governs how a *single* Profile's own overrides are resolved — only the "how many Profiles" question was reversed.

A second, larger correction landed in the same conversation, independent of the multi-vs-single question: *"You have to understand the intent of what we are doing here. Imagine TCS. TCS has a set of Standard process and templates. When a project has to be executed, as a part of the project setup, they tailor the organisation process to fit the project. So if org standard says 100% milestone meet, project can relax it to 90%. And that is what we are trying to do. When you commission from a profile, you are basically taking everything that is used for creating the profile in the first place. And if there are overrides, you take the overrides. You do not have to save what is already in the template as the template_id is the reference to it."* Part 6's own build had stopped at *detecting* that two sources disagree on an exposed parameter; it never computed what the *actual effective value* commissioning should run with (default from the Template, or the Profile's own override where set). That resolution step is what got built now, as `resolveEffectiveParameters(profile)` (`core/profiles.ts`): for every parameter the base Template exposes, effective value = the Profile's own override if present and the parameter is `overridable`, else the Template's own default — never re-persisted, always resolved live off `template_id`/`draft_content`, exactly as instructed.

Settled and built:
- **Exactly one Profile** (and exactly one Template, its base) may be commissioned against — enforced at three layers: `commissionSeu` rejects `input.profileIds.length > 1` outright (`stage: "validate_request"`), the `validate-commission`/`commission` web routes both reject `selections.length > 1` before calling into the core, and the picker (`seus/new.ejs`) reverted from Part 6's checkboxes back to **radio buttons** (`type="radio"`, shared `name="templateProfile"`) — one choice only.
- **The picker itself was inverted**, per a separate owner correction: *"The whole selection of template+profile is messed up. It has to be inverted. Show the list of all applicable profiles first — which template they correspond to and the capability name as a list — no duplication of profiles."* `seus/new.ejs` now lists one row per real, distinct Profile (deduplicated — a Profile that satisfies more than one branch is shown once), each row naming its base Template and the Capabilities involved; a Template with no real Profile yet still gets its own row, grouped under that Template (owner: agreed as-is, no changes requested). Rebuilt as a card grid (`.card-tile` per Profile) with a **sticky action toolbar** (`position: sticky; top: 0`) — owner: *"If there are 100 profiles, it is not desirable to scroll all the way down"* — rather than the earlier flat list with a bottom-anchored submit button.
- **The Validation page shows real content, not just a verdict**: owner pushed back hard when the page rendered only `Environment`/`Description` for a chosen Profile — *"Where is the pack information? where are the exposed parameters?... I am unsure why you are being selective about what you want to process."* `previewCommissioningValidation` now also returns `composedPacks` (the actual composed Pack set the choice would produce) and `profileDetails` (`extractProfileDetails`, `core/profiles.ts`) — every field the Profile itself carries (environment, all 8 Configuration Parameters, all 6 Pack-selection categories, `additionalCapabilityCodes`, `deploymentTargets`, `environmentConfiguration`, `exposedParameterOverrides`), plus an "Effective Parameters (Template default, or Profile override where set)" section built from `resolveEffectiveParameters` above. A later correction sharpened this further — *"It has to show what all got resolved without conflicts as well"* — the Effective Parameters section shows every exposed parameter's resolved value, not only the ones a Profile happened to override.
- **The dependency graph became a 4th exposable-parameter source type**, alongside `service`/`policy`/`checklist` (CR-088). Owner, after confirming the deliverable dependency graph is itself Template-authored and already implemented: *"Now, this is exposable and a profile should be able to modify it."* `deriveExposableParameterCandidates` (`core/templates.ts`) gained a `dependency` source-type loop over the Template's own `dependencyGraph`, one candidate per edge (`parameterName: "requiredState"`, default taken from the edge's own `requiredState`); `resolveEffectiveParameters`, `ParameterConflict.sourceType`, and the parameter-conflict UI all extended to match (`seuTypes.ts`, `sdkAuthoring.ts`'s `loadExposableParameterRows`).
- A latent consequence of the single-Profile reversal, left in place deliberately rather than torn out: `detectParameterOverrideConflicts`/`ParameterConflict` and the Validation page's radio-pick conflict-resolution UI (`resolvedParameterOverrides`) can no longer actually fire in practice — a conflict by definition needs two-or-more *given* Profiles to disagree, and exactly one Profile is now selectable. The machinery is correct and stays wired (dormant, not dead: still exercised directly by `tests/profile-composition-strategies.test.ts` against the real composition engine, and would immediately become reachable again if the single-Profile constraint were ever relaxed) rather than removed, since ripping it out would also mean re-deriving it from scratch later.

Files touched (Part 7, additive over Part 6's own list): `core/commissioning.ts` (`profileIds.length > 1` guard, `resolvedParameterOverrides` threaded through `commissionSeu`/`commissionFromExistingObjective`/`previewCommissioningValidation`), `web/objectives.ts` (`selections.length > 1` guard on both routes, `parseResolvedParameterOverrides`), `core/profiles.ts` (`resolveEffectiveParameters`, `extractProfileDetails`, `setDraftContent` wiring), `core/templates.ts` (`dependency` source-type candidates, `setDraftContent` wiring), `dblayer/profilesDB.ts`/`dblayer/templatesDB.ts` (new `setDraftContent`), `seuTypes.ts` (`ParameterConflict.sourceType` gains `"dependency"`), `views/seu/seus/new.ejs` (inverted picker, card grid, sticky toolbar, radios), `views/seu/seus/validate.ejs` (`profileDetails`/`effectiveParameters`/`composedPacks` rendering). Two unrelated persistence bugs found and fixed along the way, same root cause on both entities: neither `profiles.upsert()` nor `templates.materialisePackSelectionsAndCapabilities()` ever wrote `draft_content` — fixed via the new `setDraftContent` DB methods, called at the end of each entity's own materialisation step. A second, separate bug found the same way: `compositionEngine.compose()` only ever read a Profile's `list_kind='optional'` Pack selections, silently ignoring the other five category slots (technology/domain/compliance/integration/engineering/organisation) that the UI already let authors fill in — fixed by switching to `getProfilePackSelections()`, which unions all seven.

### Part 8 — Conflict detection rebuilt from scratch: a flat, source-agnostic pool over *everything* (built 2026-09-06/07)

Owner, unprompted by any specific bug: *"My problem is this — I am not confident you are unravelling every detail to check for conflicts... a profile has to unravel everything except the metadata."* Part 6/7's own conflict detection (`compositionEngine.compose()` → `detectGovernanceConflicts`) only ever checked two contribution types (Authority Rules, Quality Gates) — every other Pack contribution (Capabilities, Services/Service Levels, Policies, Checklists, Review Gates, Obligation Definitions, Engineering Capital, Pack Dependencies) and every Profile/Template field was composed but never cross-checked for disagreement at all. Owner, ruling out the obvious shortcut: *"detectGovernanceConflicts is not your reference. build the conflict detection from scratch as a separate feature so it is easy to work on if we have to change it."*

Built as a wholly new, independent module — **`src/domain/engine/profileCompositionUnravel.ts`** — with zero dependency on `compositionEngine.ts`:
- `unravelComposition()` reads a Template+Profile selection's every real value — Profile Configuration Parameters, Template's own declared fields, every Template-exposed parameter (resolved through the existing `resolveEffectiveParameters` cascade — a Template default vs. a Profile's own override is a single-lineage resolution, never a two-source disagreement), and every transitively-composed Pack's own `capabilities`/`services`/`authorityRules`/`qualityGates`/`checklists`/`reviewGates`/`obligationDefinitions`/`engineeringCapital`/`dependencies` — into **one flat pool**, `{propertyName, value, source}`, keyed by whatever identifies "the same real thing" for that entry's type (`code`/`name` by default; `governedTransition` for Authority Rules, aggregated *per Pack* first so one Pack's own legitimate multi-role design is never mistaken for a disagreement; `(governedTransition, category)` for Quality Gates; the target Pack's own code for Pack Dependencies).
- `detectCompositionConflicts()` groups the pool by `propertyName` and recurses into every shared key **to full depth** (owner: *"EVERYTHING. Go as deep as you have to"*) — nested objects and arrays (matched by their own `code`/`name` identity) both recurse, reporting a conflict at the exact leaf path a real disagreement exists, not the whole containing object.
- Pack Dependencies are ordinary pool entries, not a special section (owner: *"when you create the flat pool create everything"*) — a `required`/`conditional` dependency whose target isn't in the composed set, or an `incompatible` one whose target is, reports as a conflict with no resolvable field (`hasAction: false` — the fix is changing the Pack selection).
- Policies are informational only, keyed by their own code, never compared against each other — corrected mid-build after an initial version wrongly grouped them by `governedTransition` and flagged differing `constraintType` as a conflict; owner: *"two policies do not have to agree on constraintType at all. Quality gate handles both constraint types."*
- Conflict **resolution** reuses exactly one piece of existing machinery, by explicit instruction (*"Only resolution will use the composestrategy mechanism already built for packs"*): `applyConflictStrategy` (`core/commissioning.ts`) hands a conflict's disagreeing sub-field to the real `compositionEngine.specialize`/`merge`/`union`/`intersection`/`supplement` functions — which sources participate is always an explicit human checkbox/radio choice on the Validation page, never inferred from array order (owner, repeated: *"you dont assume any base"*) — with a scalar-specific shortcut for union/intersection (direct set union/intersection) since `combineFields` itself has no principled answer for two bare disagreeing scalars.

Test coverage: `tests/profile-composition-unravel.test.ts` (new).

### Part 9 — Event-driven Commissioning: Chapter 3/8 alignment, "Validate Request" vs "Compose EBM" (built 2026-09-07)

The final gap Part 4 (§42 above) explicitly deferred — *"whether `commissionSeu` actually routes through this new [event] chain"* — closed by reading Chapter 8 §8 directly rather than continuing to extend `commissionSeu` as one monolithic function. §8's own canonical workflow names two *separate* steps this build had collapsed into one: **Validate Request** (§9, shallow — existence, authorisation, live references) and **Compose EBM** (§10, deep — Part 8's own unravel/conflict mechanism). Owner, correcting an early draft of this section that wrongly placed the deep work *before* validation: *"What we have built now is the EBM composition and build a shallow validation for SEU validation."*

**Validate Request is real, new logic, not just event-wrapping.** A Profile's own `status = 'Active'` says nothing about whether what it *references* still is — Pack codes and Ontology-backed values can be retired independently, and nothing re-checks a Profile after authoring (`assertCanonicalCategory` is write-path only). Owner: *"am I working off a current live abstraction?"* `checkRequestLiveness` (`core/commissioning.ts`) now re-checks, at commissioning time: Template status, every selected Pack code (`packsDB.findActiveByCode`), every `additionalCapabilityCodes` entry (`capability-name` Ontology liveness), and every Service-sourced `exposedParameterOverrides` entry — failing fast, before any composition work, with `CommissionFailed`/SEU `lifecycle_state → Failed`.

**`compositionEngine.compose()` is no longer called anywhere in this flow, at all** (owner, repeated: *"For the 100th time do not use compose()"*) — `commissionSeu` now does only the shallow gate, publishes `CommissionValidated` (Ch.8 event, replacing `SEUCommissionRequested`/`SEUCommissionRejected`), and returns; a new **`src/domain/engine/ebmComposer.ts`** — a real, subscribed event-bus consumer (`event_subscriptions`, handler `ebmComposer`) — picks up `CommissionValidated`, publishes `CompositionStarted`, runs Part 8's own unravel/conflict pass for real, and on success persists the `ebms` row itself (status `Composed`, not `Active`) and publishes `EBMCreated`; on conflict, publishes `CommissionFailed` and transitions the SEU to `Failed`.

**Validate and Activate are two separate, independently human-triggered actions, not a cascade** — Chapter 3's own `EBMValidated`/`EBMActivated` events, owner: *"I can validate an EBM and not yet activate it — I can have a project plan ready but not yet start it."* `EbmStatus` gains `Composed → Validated → Active → Superseded` (migration 178); `transitionEbm` (`core/commissioning.ts`) is a new, ordinary governed transition (`entityType: "EBM"`, manual/ungoverned like `AUTOMATIC_STEPS`, no Authority Rule required) exposed as a plain transition form on the SEU detail page (`POST .../seus/:id/ebm/transition`) — the same generic pattern the page's other six entity types already use, not a new UI concept. **Retry after a failed commission — Chapter 1 §18.9's own "Open: SEU decommissioning semantics" closed for this one case.** A `Failed` SEU is never deleted (audit/traceability — owner: *"delete a row will remove audit/traceability"*; the authoritative record of what happened is always `seu_id` + its own `CommissionFailed` event, never a column). `seus.lifecycle_state` gains `Failed` (migration 177 — distinct from `Retired`, which Chapter 2's own real state graph reaches only from `Operational`).
