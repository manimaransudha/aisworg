## Settled design

| # | Decision | Date |
|---|---|---|
| 1 | A Pack is the only place a quality gate is defined. | 2026-11-16 |
| 2 | The rows a Pack's contributions name (G9: Capabilities, Services, authority rules, Policies, Checklists, review gates, quality gates) are written when the Pack becomes Active, and not when the Draft is created. The call in `createAuthoringDraft` is commented out. The Transition Definition `Pack Published -> Active` names the action `materialise-pack`, which runs `materializeContributions` on the Pack's stored contributions. The precedent is `unravel-template` on `Template Validated -> Published`. | 2026-11-16 |
| 3 | `quality_gates.originating_pack_id` is `NOT NULL` (G3). The only insert is `qualityGatesDB.upsert`, which already requires a Pack id. | 2026-11-16 |
| 4 | The `category` field of a Pack quality gate is `x-referential: category:quality-gate` (G4). It is no longer `category:evidence`. | 2026-11-16 |
| 5 | Each quality gate criterion has its own implementation in a new folder src/qualitygates, registered by code, in the way src/policies registers the Policies whose condition type is `implemented` (G5, A1). The shape of the implementation and the use of the registry are open. | 2026-11-16 |
| 6 | A quality gate implementation returns what Chapter 26 asks of an evaluation: for §10 the satisfied criteria, the unsatisfied criteria, the applicable waivers, the blocking conditions and the supporting rationale; for §14 the objects it relied on (governing Policies, supporting Reviews, Evidence and Decisions, active Obligations); and one of the six outcomes of §11. The implementation reads and writes nothing else, as a Policy implementation does. | 2026-11-16 |
| 7 | A quality gate has a field `evidenceCategory` (`x-referential: category:evidence`) that names the Evidence category the Evidence criterion checks. It replaces the use of `category` for that purpose. A gate of that criterion type without it is refused by Pack validation, and the engine blocks it with a configuration message. | 2026-11-16 |
| 8 | The criteria types, the default category and the default criteria of a quality gate are Ontology-driven (G5). They are not literals in qualityGatesDB.ts, qualityGateEngine.ts, packs.ts or seuTypes.ts. How each is held in the Ontology is open. | 2026-11-16 |
| 9 | No `is_default` is added to the Ontology. `category` and `criteriaType` of a quality gate are mandatory: the Pack schema requires them, the Pack validation refuses a gate without them, and no code supplies a default. The caller states both. The criteria types as an Ontology concept type (decision 8) are built. | 2026-11-16 |
| 10 | The `severity` fields of the Obligation Definition, the Policy condition and the related Obligation are mandatory in the schema. | 2026-11-16 |
| 11 | The checklist item fields `configurableKey` and `configurableValue` are mandatory; the seed items take `type` and `required` as placeholders. | 2026-11-16 |
| 12 | A quality gate has a `code` that is a field of the Pack schema (`contributionQualityGates`), is mandatory and is driven by the Ontology. It replaces the `code` that `qualityGatesDB.upsert` sets equal to `category` (G2). The readers of `code` change with it (transitionEngine.ts:84 and :194, transitionDefinitionsDB.ts:266, `findByCode`). A Pack author can pick an existing code or propose a new one (the Pack `code` pattern: `x-ontology` with `x-ontology-composable`), so the list is open. The concept type name and the slot of a gate (Still open item 12) are open. | 2026-11-16 |
| 13 | The slot of a quality gate (its identity for the active row and the version bump) is its `code`, with no transition and no category in it. The owner said "code + tenant" and then "slot only by code", and will give the reason later. Whether the Pack is part of the slot (as for Policies: `originating_pack_id, code`) or the slot is `code` within the tenant of the Pack is not yet confirmed. | 2026-11-16 |
| 14 | A quality gate is defined in its own authoring (a Quality Gate Definition, as a Policy Definition is), and a Pack lists only the identifiers (codes) of the gates it takes. The scope and the open points are in Still open item 14. Not built. | 2026-11-16 |
| 15 | The references of a quality gate (`checklistIds`, `recommendedChecklistIds`, the review gate named by `deliverableName`, `requiredPolicyCodes`) resolve against the registry of the Platform and of the tenant, and are not limited to the Pack. The blocker in Still open item 14 (a) stays open until each reference has its source. | 2026-11-16 |
| 16 | No file except `src/utils/db.ts` calls `pool.connect()`. Database code uses `query`, `bulkInsert`, `withTransaction` and `withAdvisoryLock`. | 2026-11-16 |
| 17 | A Pack's `contributionQualityGates` entry is not a plain code. It holds the quality code (the code of a Quality Gate Definition, resolved by code and tenant), `governedTransition` (the exact transition the gate applies to, picked from the Transition Definitions), `deliverableName` (a pick from the Ontology concept type `deliverable-name`), the Checklist ids with a mandatory or optional flag, and `requiredPolicyCodes`. These references belong to the Pack because the Checklists and the Policies are the Pack's own. The property definitions (help text, referential sources) are reused from the schema before CR-145 (commit 3e8df97, `contributionQualityGates`). This reverses the part of decision 15 that placed these references on the Quality Gate Definition. Built the same day (see "Built (2026-11-16), decision 17"). Settled with it (owner): `checklistIds`, `recommendedChecklistIds`, `deliverableName` and `requiredPolicyCodes` are removed from the Quality Gate Definition schema. The Pack entry holds the Checklists as one list of `{ checklistId, mandatory }`, optional by default. Every listed id is checked by `validateChecklistIds`, whether mandatory or optional, so the validator does not depend on the flag. `materializeContributions` may write the two lists `checklist_ids` and `recommended_checklist_ids` of the `quality_gates` row from the one list (the owner holds that the split does not matter. Search: `grep -rnE "checklist_ids|checklistIds|recommended_checklist_ids" src`, excluding review gate, Definition, seed and JSON lines. qualityGateEngine.ts is not among the hits. The readers of the two columns of a gate row are the CR-139 conflict code, `unravelQualityGates.ts` and `settleQualityGates.ts`, and `entityAdapters.ts:242`). `governedTransition` and `applicabilityDeliverableNames` also leave the Definition (the single `deliverableName` of the Pack entry replaces `applicabilityDeliverableNames` and the review gate pick, since a review gate is keyed by a Deliverable type). The Definition keeps `code`, `name`, `description`, `category`, `criteriaType`, `evidenceCategory` and the descriptive fields in `draft_content`. | 2026-11-16 |
| 18 | A transition has two Quality Gate checks, and each is its own call. The gates a Transition Definition names (`required_quality_gate_ids`) are evaluated by `qualityGateEngine.evaluateByIds`. The gates of the SEU's EBM are evaluated by `qualityGateEngine.evaluate`, which reads the SEU's active EBM and nothing else: the fallbacks to every active gate for the hop (a null SEU, an SEU with no active EBM) are removed, and an SEU with no active EBM has no gates. | 2026-11-16 |
| 19 | The platform starts a Quality Gate evaluation, not a user. The author, the badge and the tenant of every evaluation of an entity in an SEU are those of the SEU's system actor (`getSystemActor`), as the Execution Engine already does for a Deliverable. An entity outside an SEU has no system participant and the `quality_gate_evaluations` scope check admits a null SEU only for a Pack and an Objective, so a gate cannot be pinned on the Transition Definition of an SDK-authored entity (Pack, Template, Profile, DeliverableDefinition, Service, Policy, QualityGate, Capability).
