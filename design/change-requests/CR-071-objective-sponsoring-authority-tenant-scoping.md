Other transitions are available as buttons depending on whether the user has the badge." · **Status:** ✅ Built 2026-08-28

Queried `transition_definitions.verb` directly for Objective: `activate`/`achieve`/`retire`/`supersede`/`archive` — 5 distinct badges, not one. > **Second real bug, found via the owner's own manual test (`obj-propose@athens.com`, holds a real Active `objective_propose` grant, Delete still didn't show):** `session.user.platformBadges` — the mechanism this whole CR was built on — structurally can never contain a noun_verb badge, for any user, ever. `getPlatformBadges` (`domain/identity/badgeBootstrap.ts:21-38`) only keeps a grant whose badge type resolves to `scope_kind === "None"` via the `badge_types` catalog table, which has exactly 3 rows: `root`, `tenant_admin`, `viewer`. `objective_propose`/`objective_retire`/etc. have no row there at all, so they resolve to an empty scope_kind, fail silently, and never reach the session. Confirmed this was always the wrong mechanism for a noun_verb badge by checking precedent: `web/packs.ts`'s own existing "Copy" button (gated on `pack_define`, also noun_verb) already uses a **live** `badgeAuthorityEngine`-backed check, never `platformBadges` — that precedent should have been followed from the start. Fixed: `getObjectiveViewerContext` is now `async`, doing one live `badgeGrantsDB.findActiveForHolder(actorId)` call per page load (not per row/button — cached in a `Set` for that one request, checked in-memory for as many rows/buttons as the page needs), still honoring "no live per-button check" (too expensive) while actually returning correct data. `root`'s own bypass is untouched — `root` genuinely does have a "None"-scope `badge_types` row, so `platformBadges.includes("root")` was always correct.

### The gap today, verified against the live code

- **No tenant scoping at all.** `GET /aisworg/seu/objectives` (`web/objectives.ts:43-72`) — both browse mode (`getObjectiveRootsPage`) and search mode (`searchObjectives`) — return every Objective in the platform, unfiltered by tenant. `objectives` has no tenant field of any kind: no `tenant_id` column, no JSONB attribution column. The only path to a tenant today is indirect and was built for a different purpose (CR-068's root-sequence numbering): `objectives.requested_by → users.id → users.tenant_id`.
- **No badge-awareness in the list UI at all.** `_nodes.ejs` (tree rows) and `index.ejs` (search-mode rows) render every action button — "Add {tier}", "Commission SEU", "Delete", "Retire" — purely off the row's own **entity state** (`node.commissionable`, `node.deletable`, `node.retirable`, `childTiers[node.tier]`), never off the viewing user's own badges. "View" is the only button not tied to a governed action already.
- **Not every one of those actions is actually badge-gated server-side today, which matters for scoping this CR** — checked directly, not assumed:
  - **Status transitions** (`POST /objectives/:id/transition`, and `retireObjectiveSubtree`'s own calls) go through `transitionObjective` → `transitionEngine.evaluate` → `badgeAuthorityEngine.authorise` — a real, governed, badge-checked path (`core/objectives.ts:455-490`).
  - **Commission SEU** (`commissionSeu`, `core/commissioning.ts:117`) also runs through `transitionEngine.evaluate` — real, badge-gated.
  - **Create** (`createObjective`) and **Delete** (`deleteObjective`, `core/objectives.ts:319-334`) — grepped both functions directly — call **no** `transitionEngine`/`badgeAuthorityEngine` check at all. Delete is gated only by plain business rules (Proposed status, no children, no SEU); anyone who can reach the route can delete. This is a real, pre-existing gap this CR surfaces, not something to silently paper over.

### The rule, as specified (owner)

1. Add `sponsoringAuthority` to `objectives` as a JSONB column. For now it holds exactly `{ tenant: tenant_id }`; the shape is deliberately open-ended so a later multi-tenancy phase (Phase 12, `design/mvp-build-plan/MVP Build Plan.md`) can add more without a schema change.
2. The Objectives list (`GET /aisworg/seu/objectives`) shows only Objectives whose `sponsoringAuthority.tenant` matches the logged-in user's own tenant.
3. "View" is always shown. Every other action button is shown only if the logged-in user holds the badge that specific action's governed transition actually requires; otherwise it's hidden.

### Design considerations found while grounding this against the live model

1. ~~**A real mechanism for "does this user hold badge X" already exists and is cheap to reuse, with one real tradeoff.**~~ **Wrong — corrected same day, via the owner's own manual test.** `session.user.platformBadges` cannot represent a noun_verb badge at all, for anyone: `getPlatformBadges` only keeps grants whose badge type resolves to `scope_kind === "None"` in the `badge_types` catalog (exactly 3 rows: `root`/`tenant_admin`/`viewer`) — `objective_propose`/`objective_retire`/etc. have no row there, so they're silently dropped, always. Not a login-time-staleness tradeoff as originally framed — a structural incapability. The real, already-established precedent for a noun_verb badge is `web/packs.ts`'s own "Copy" button (`pack_define`), which uses a **live** `badgeAuthorityEngine`-backed check. Fixed the same way, but batched to once per page load (`badgeGrantsDB.findActiveForHolder`, cached in-memory for that request) rather than once per button, so it still respects "no live per-button check" while being correct. `root`'s own bypass via `platformBadges` was never wrong — `root` genuinely has a "None"-scope `badge_types` row.
2. ~~**Turned out simpler than expected: every Objective transition needs the same one badge.**~~ **Wrong — corrected same day.** `authority_rules.code` (`authority-transition-objective`) is the same for every Objective transition, but that's just the governance rule row's own label — it's *not* what `badgeAuthorityEngine` actually checks. The real badge is computed per-transition as `` `${entityType}_${verb}` `` (`transitionEngine.ts:74`), from `transition_definitions.verb` — for Objective that's 5 distinct badges (`objective_activate`/`achieve`/`retire`/`supersede`/`archive`), not one. See the "Built" banner's own correction note, above, for the fix (`findPossibleNextTransitions`, per-option filtering).
3. **Recognize the connection to CR-068, without duplicating it.** CR-068 already resolves a tenant per Objective — but only for the Strategic root's own display-id sequence counter, via the same indirect `requested_by → users.tenant_id` join, and explicitly chose *not* to add a real column ("acceptable but redundant if the join is easy enough" — [CR-068](CR-068-objective-hierarchical-display-id.md), point 3). A denormalized `sponsoringAuthority` column is a second, independent motivation for that same information (direct list-filtering, not just root numbering) — worth building for real now, not a reason to consider CR-068 wrong for skipping it earlier (that CR's own counter logic still only needs the join, and stays as-is).
4. **Precedent for "app enforces shape, not the schema"** — this CR's own session already settled this exact question for `objectives.requested_by` ([CR-068](CR-068-objective-hierarchical-display-id.md), point 4): no DB-level constraint, validation lives in the app layer. The natural default here is the same — `sponsoring_authority JSONB`, no `NOT NULL`, no `CHECK` on its shape, validated (if at all) in `createObjective`. Flagged as a default, not yet confirmed for this field specifically.

### Not in scope for this CR

- Changing the actual server-side authorization boundary anywhere — `badgeAuthorityEngine.authorise` stays the real, live-checked gate on every action route, unchanged. This CR only changes what the UI *shows*, never what the server *allows*.
- Retrofitting badge-gated button rendering onto any other entity type's list view (Pack, Template, SEU, ...) — Objective-only, first of its kind in this codebase.
- Anything from Phase 12's own multi-tenancy work — `sponsoringAuthority`'s shape is deliberately left open for that, not designed here.

### Open questions

1. ~~**Every Objective, or only Strategic roots?**~~ **Settled (owner): keep it on all Objectives.** Every row gets a real `sponsoring_authority` value, not just Strategic roots — a child copies its **parent's** value at creation (never independently re-derived from whoever happens to author that specific child), so a whole subtree always shares one sponsoring authority with its root, matching the tree's own real invariant. Cheap to build on top of CR-068's own transaction in `objectivesDB.create`: the same `UPDATE objectives SET next_child_seq = next_child_seq + 1 ... RETURNING ...` that already fetches the parent's `display_id` for a child (`objectivesDB.ts`) can return `sponsoring_authority` in the same statement — zero extra queries. A Strategic root (no parent) derives it fresh from the creating user's own tenant, same as today's `requestedBy -> users.tenant_id` resolution CR-068 already built. Both browse mode (`getObjectiveRootsPage`) and search mode (`searchObjectives`) can now filter with a flat comparison on the row's own column — no ancestor-walk needed.
2. ~~**Do Platform/root users see everything?**~~ **Settled (owner): the root identity sees every tenant's Objectives, at least for now; every other user — including any other Platform-type user — gets the same tenant + badge restrictions as anyone else.** This is narrower than a "Platform tenant" carve-out: it's specifically the one bootstrapped root identity, not every Platform-type account. Proposed detection mechanism (not yet confirmed): `session.user.platformBadges?.includes("root")` — the real badge-model representation of root (`badge_grants`' `holder_id '1' -> 'root'` seed), rather than an email match against `SUPERUSER_EMAIL` (`dev/actAs.ts`'s own convention for the same identity, but a less direct fit for an authority-model decision than checking the actual badge). Flag if a different check is intended.
3. ~~**Which actions does this cover?**~~ **Settled (owner), then extended same day: the Objective lifecycle buttons, plus Delete — no change to Commission SEU or Add-{tier}.** Originally scoped to just the status-**Transition** dropdown+button and the **Retire** button (both real, badge-gated paths via `transitionEngine`/`badgeAuthorityEngine`). Owner's same-day follow-up added **Delete**, gated on `objective_propose` — a real, already-seeded noun_verb badge, even though `deleteObjective` itself still runs no governed check (see the "Built" banner's own note on this). Commission SEU and Add-{tier} remain unchanged, keeping their own existing business-rule gating (`commissionable`/`childTiers`).
4. ~~**Confirm the badge-check mechanism.**~~ **Settled (owner): no live per-button check — "that will be too expensive."** The mechanism itself changed after a real bug (design consideration 1, above — `platformBadges` can't hold a noun_verb badge at all): now one live `badgeGrantsDB.findActiveForHolder` call per page load, not per button, which is what the owner actually asked to avoid.
