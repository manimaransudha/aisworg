### Background
Chapter 6 §7 ("Template Structure") lists `Identifier` as one of Template's fields; §8 ("Template Categories") gives 9 worked examples and explicitly closes with "Additional categories may be introduced through Packs" — a data-driven vocabulary was the chapter's own intent from the start. Migration 045 (this session, earlier) had made Template's `code` a hidden, server-minted system UUID, mirroring CR-015's treatment of Pack. The owner now wants Template's `code` to *be* its category — the same "code engine" idea CR-020 Part 2 just built for Pack (`code` ← `capability-name`), applied to Template's own natural vocabulary (`code` ← `template-categories`) instead of a UUID.

### What's built here
- **Seed** (migration 053): the 9 `template-categories` concepts, verbatim from Ch.6 §8 — Enterprise Web Application, Mobile Application, API Platform, Legacy Modernisation, Data Platform, AI Platform, Embedded Software, SaaS Product, Package Implementation. Fresh, zero-consumer concept type (no existing `templates.code` value uses any of these strings — every real row today is a UUID-ish test/bootstrap identifier), so the standard lowercase-hyphenated convention applies with no exception, unlike `category:pack`/`installation-classification`.
- **Schema** (migration 054): Template's `code` is back as a required field — `x-widget: "referential-select"`, `x-ontology: true`, `x-referential-source: "template-categories"`. **No formGenerator/view code changes were needed at all** — this is exactly the payoff of CR-020 Part 2's generic mechanism (`ontologyConceptTypesIn` / `loadOntologyOptions` / the one `f.kind === 'referential-select' && f.ontology` view branch): a third kind, a third concept type, zero new code, only a schema + data change.
- **Profile is untouched** — the owner's ask was Template-specific; Profile's `code` stays a system UUID (migration 045) until/unless the same decision is made for it separately.

### The identity consequence, flagged explicitly
*Resolved 2026-08-19 by CR-024 — recorded here as it stood at the time, not silently rewritten.* `templates.code` was a single-column `UNIQUE` constraint with **no version dimension** (Template was upsert, not `(code, version)`-immutable like Pack — real Template versioning was a separate, open gap, Ch.6 §20.3). Rooting `code` in a 9-value fixed vocabulary meant **at most one Template could exist per category, platform-wide, ever** — stricter than Pack's equivalent change (CR-020 Part 2), where a `(code, packVersion)` collision could still be resolved by picking a different version; there was no such escape hatch here, a second "SaaS Product" Template was a hard collision, full stop, not "start a new version." CR-024 built real `(code, template_version)` identity for Template, mirroring Pack exactly — the cap described below is now "one *Active* Template per category at a time, many versions over time," the same as Pack, not "ever."

This reads as consistent with how the platform already works, not an accident: Profile is the customisation layer (`baseTemplateCode` + environment + config parameters + optional Packs) built *on top of* one canonical Template per category — so "one Template per category, many Profiles on top" is the existing Template/Profile relationship, just now made structurally explicit through `code` itself. Proceeded on that basis rather than blocking on confirmation, but recording the reasoning here since it's a materially stronger constraint than Pack's version got.

- **`assertTemplateCodeFree(code, excludeId?)`** (`core/sdkAuthoring.ts`) — turns what would otherwise be a raw `templates_code_key` Postgres violation (`templatesDB.createDraft` is a plain `INSERT`, no `ON CONFLICT`) into an actionable message, on both create and save. *Superseded 2026-08-19 by CR-024's `assertTemplateCodeVersionFree(code, templateVersion, excludeId?)` — same purpose, rescoped to `(code, template_version)` once versioning made the collision unit narrower than the whole code.*
- **Bug fix surfaced by this change**: `templatesDB.updateDraftContent` never had a `code` column in its `SET` clause — before this CR, `code` wasn't a form field at all, so this was moot; now that it's a real, editable dropdown, a Save that changed it was silently discarded (the DB kept whatever `code` `createDraft` first set). Fixed alongside — `code` is now correctable on Save while the row is still Draft, the same way Pack's `category`/`packVersion` already are (VM-002 immutability applies once a version leaves Draft, not to the working draft).
