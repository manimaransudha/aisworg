# CR-067 — Composition Strategy: a real, generic engine (Chapter 4)

**Raised:** 2026-08-24 · **Origin:** split out of CR-066 (Pack dependency-type semantics + circular-dependency detection) — CR-066's own ancestry-list design turned out to depend on how composition actually works, which isn't designed yet. Owner: "Composition strategy we have now is just a placeholder. We have to build this out. And has to be generic. So if I have an alias composition on template, it should be treated the same way a capability alias will look like. (in template, we call it as inheritance, I suppose). So we have to define this." Continuing the same audit discipline CR-058 through CR-065 used, applied to Chapter 4 (Composition Engine) — the chapter every one of CR-058, 059, 061, 064, and 065 punted their own composition/conflict-detection questions to ("revisit alongside the Composition Engine itself"). Full findings written into Chapter 4 §21, its first-ever audit section. **Status: design mostly settled (2026-08-25)** — all 7 strategies defined (`Alias` renamed `Specialization`), Delegation/Decomposition explicitly excluded, Supersession folded into Override, build scoped to `compositionEngine.ts` only for now (Template/Profile migration deferred); 2 open items remain (below) before build.

## The gap, precisely

Grounded directly in live code — full findings in Chapter 4 §21. The headline finding: the Composition Engine composes *Packs*, not the *behavioural content inside them* — `compositionEngine.compose()` produces an ordered list of whole Packs plus a thin `{warnings, conflicts, resolutions}` report, never a decomposed Engineering Behavior Model. Of the chapter's own 7 named composition strategies (Merge, Override, Supplement, Union, Intersection, Alias, Conflict Detection), exactly **one** has any real implementation — `Override`, and only at the whole-Pack level (a Pack `code` appearing in both a Template's mandatory set and a Profile's optional set — the later one wins, wholesale). The other 6 are pure Ontology vocabulary (`composition-strategy` concept type, 7 seeded values) with zero behaviour behind them.

**This is exactly what the owner wants built out — generically, not just for Capability.** Template already has a real, independently-built "inheritance" mechanism (a Derived Template must keep its parent's code, its parent's mandatory Packs, and its parent's decomposition/derivation edges unaltered — `templates.ts`) that plausibly maps onto one of these same 7 strategies (most likely `Alias`, per the owner's own framing) — but today it's a separate, hand-built mechanism, not an instance of a shared, generic Composition Strategy engine. Building the 7 strategies out for real means defining, for each one, in entity-agnostic terms: what it means for two (or more) contributions to the same target to combine, and what data each strategy needs beyond the strategy name itself (e.g. does `Merge` need a merge key? does `Supplement` need ordering? does `Conflict Detection` need a severity/threshold?) — none of which is decided yet.

**CR-066 (Pack dependency-type semantics + circular-dependency detection) stays parked on this CR.** The ancestry/lineage list CR-066 needs for cycle detection is a byproduct of however composition actually works (e.g. `Union`/`Merge` producing one Capability from several contributing Packs) — designing it before this CR settles would mean guessing at a shape this CR could immediately invalidate.

## Not in scope (for this CR specifically — real findings, not this CR's job)

Chapter 4 §21's audit surfaced several gaps beyond composition strategy itself — real, but each its own separate concern, not folded in here:
- Missing mandatory Packs only warn, never block commissioning (§21.9) — a validation gap, not a strategy question.
- Zero deterministic/non-deterministic conflict classification, zero auto-resolution (`resolutions` permanently `[]`) (§21.7/21.8).
- 0 of the chapter's 11 named Composition Engine events exist (§21.13).
- Recomposition (§16) has real version-increment SQL but is never triggered, and nothing marks a prior EBM `'Superseded'` (§21.12). **Governing principle for whenever this is picked up** (owner, 2026-08-24, noted for later — not this CR's job to build): *"The EBM is authoritative for the lifetime of the commissioned SEU unless superseded through a governed recomposition process."* I.e. an EBM's own `'Superseded'` transition is itself a governed event (an Override, per this CR's own settled definition — version bump, prior marked retired/superseded) triggered only by a real recomposition, never silently — the missing piece §21.12 found (nothing today ever performs that transition) is this exact mechanism, still unbuilt.
- The Engineering Behavior Model itself stays a Pack list, never a decomposed/categorized model (§21.2) — the single largest gap in the chapter, but a separate, much bigger undertaking than defining composition strategies.

## Design, as settled

A corpus-wide search (2026-08-24) checked whether other chapters name additional derivation/composition mechanisms beyond Chapter 4's own 7 — full findings below informed the final set. The result: **the same 7 named values stay the vocabulary**, one renamed, none added.

### The final strategy set

**Specialization** (renamed from `Alias`) — owner: "The alias and specialisation are the same. So let us call it Specialization" (resolves a real naming collision: Ontology (Ch.18 §7) already has its own, unrelated "Alias" concept — organisation-specific terminology synonyms, e.g. "Design Review" = "Architecture Review" — renaming Composition Strategy's own term removes the clash). Definition: one parent id. Creation is an exact copy of the parent; code and/or name may be changed (a code change must be registered into the Ontology — the Pack-feeds-Ontology mechanism, CR-056's own territory). Every other field/property may be changed or left as-is — free to diverge in any direction once created. Starts at version `1.0.0`, goes through the same entity lifecycle as any other instance of its type — no special "specialized" lifecycle. Platform and tenant scopes apply; a tenant cannot specialize another tenant's entity. Confirmed as a real, already-independently-implemented pattern in two places — Template's own "inheritance" (Ch.6, keeps parent's code, mandatory Packs, decomposition/derivation edges) and Profile's own "inherit from other Profiles" (Ch.7 §9, same identity-lock shape) — both real precedent for what this CR generalizes.

**Override** — same code, complete replacement of existing content, no identity change. Version number bumps (existing entity, not a new one). The prior version is retired. **The only strategy that changes an existing entity's/its predecessor's status** — every other strategy below produces a brand-new entity at `1.0.0` and leaves whatever it was derived from completely untouched. Also covers what other chapters call "Supersession" (Ch.15/16/20/41's own recurring "new version replaces old, old becomes historical" language) — owner: "Supersession is Override" — same mechanism, no separate treatment needed.

**Merge** — two or more parents, **same code required** (all parents claim to be the same logical entity). Field-by-field: union together whatever combines unambiguously; whatever can't (two parents set the same field to different values) gets flagged for the author to resolve explicitly — this *is* Conflict Detection, not a separate strategy an author picks instead (below). Produces a new entity at `1.0.0`; contributing parents' status is unchanged (owner: "Only override changes parent status? ... Everything else is a new pack starting v1.0.0").

**Union** — two or more parents, **no same-code requirement** — a collection-level combination (e.g. a Checklist's items, a set of required Capabilities), not an identity-level one. Same union-with-flag-on-conflict algorithm as Merge, just applied to collection membership rather than single-valued fields. New entity at `1.0.0`; parents unchanged.

**Intersection** — two or more parents, keep only what's unanimous across all of them; anything they disagree on is simply dropped, never flagged (unlike Merge/Union, Intersection never attempts to combine disagreeing values, so there's nothing to escalate). New entity at `1.0.0`; parents unchanged.

**Supplement** — one base parent, one or more supplementing contributions. Purely additive: may only add fields/items the base doesn't already have; can never override or remove anything the base declares. Owner: "Supplement will need its own identity and version. Parent status does not change" — its own identity, own version at `1.0.0`, base left untouched (closer in shape to Specialization than to Override — starts empty/additive rather than as a full copy).

**Conflict Detection** — not an independent, author-selectable strategy. It's the escalation path *inside* Merge and Union for whatever they can't automatically combine — surfaced to the author to resolve, the same real, working "block until resolved" mechanism `compositionEngine.ts` already has today (Chapter 4 §21.8), just now triggered from inside Merge/Union rather than only from the 2 narrow governance checks that exist now. **Depth, settled**: owner — "Composition should go deep into contributions at pack level and whatever is the deepest at every other identity. Goal should be to identify definition conflicts." Detection is a real scope expansion over today's implementation, not just a relocation of the existing 2 checks: it walks *into* each Pack's own contributions, and for any contribution kind that itself nests further (a Checklist's `items[]`, a Service's `serviceLevel[]`), keeps walking to whatever depth that entity's own real structure has — not a fixed depth, entity-specific. Scope is definition-level throughout: comparing declared/authored content across Packs, never runtime/execution state — the same boundary this whole CR series has held to since CR-058.

**Fallback rule**: owner — "If a strategy does not have definition it will fall to override." Anything not covered by the 6 real strategies above defaults to Override's own behaviour.

### Explicitly excluded from this taxonomy

- **Delegation** (Ch.22 Authority §11 — a scoped, time-bound, revocable grant of authority from one entity to another) — owner: "Delegation is not composition. It is very specific to authority and execution." Not part of Composition Strategy at all.
- **Decomposition** (Ch.1 Objective §9 — one parent splitting into many children, the inverse shape from every strategy above) — owner: "Let us keep Decomposition unscoped for now. This can anyway be indirectly achieved by one or more of the above composition strategies" (e.g. several Specializations off one parent). Not formally defined as its own strategy.
- `dependency_definitions.relationship_kind` (`dependency`/`derivation`/`implementation`/`decomposition`) — a different layer entirely, labelling edges between already-existing entities (Deliverable depends-on Deliverable), not how one entity's own content gets produced. Untouched by this CR.

### Where the engine lives — settled, staged

Owner: "For now we build the strategies within `compositionEngine.ts`. When it is stable, we will look at migrating template into this." Phase 1 (this CR): the 6 real strategies get built generically *inside* `compositionEngine.ts` — Template/Profile's own hand-written inheritance-validation code (`templates.ts`) stays exactly as it is, untouched, not yet reframed as an instance of the generic engine. Phase 2 (explicitly deferred, not this CR): once Pack composition has proven the strategies stable in real use, revisit Template/Profile and migrate their own mechanism onto the same shared engine, retiring the duplicate hand-written logic. This CR's own build only needs to keep the strategy definitions themselves entity-agnostic in *how they're written* (per the "Design, as settled" definitions above) — it does not need to solve the extraction/sharing question now.

## Open design questions — still unresolved

1. **Does this change `compositionEngine.ts`'s own existing Pack-level `Override`** (a Pack-list dedup when the same Pack code appears in both a Template's mandatory set and a Profile's optional set)? **Parked pending Chapter 7 (Profile) — not yet audited this session.** Owner's own tentative lean: "My thinking is it should be using the compositionEngine that is built out" — i.e. the existing bespoke dedup logic gets refactored to call the new generic `Override` rather than keeping its own separate implementation, once built. Not settled — revisit once Profile gets the same audit treatment as Template/Capability/Service/etc.
2. **Merge/Union's own conflict-resolution UX — mostly settled.** Owner: "flagged for the author to pick should be built as UI at the EBM UI layer. Conflict resolution is EBM's job. Composition just flags it." Clean separation, consistent with Chapter 4's own "the Composition Engine performs no software engineering work itself" boundary — `compositionEngine.ts` stays pure/stateless (detect + flag only, exactly what it already does today), and resolution becomes an interactive EBM-layer UI, not something Composition itself does. **One real sub-question left**: this is a genuine workflow change from today's real behaviour, not just a UI addition — today a detected conflict does a hard reject (`SEUCommissionRejected`, Ch.4 §21.8), requiring the author to fix the underlying Pack content and re-attempt commissioning from scratch. Does the new EBM UI *replace* that reject-and-retry cycle (propose the composed set with the conflict still flagged, let the author resolve it in place before the EBM finalizes), or sit alongside it as an additional path? Not yet specified.
