# CR-068 — Objective hierarchical display identifier (1, 1.1, 1.1.1 — system-assigned, never editable)

**Raised:** 2026-08-28 · **Origin:** owner — "Objectives have a unique id. I suppose they are UUID. I want a user friendly identifier. So a Strategic objective will be numbered 1, 2, 3, etc. The Operational obj under 1 get 1.1, 1.2 etc. The Engineering obj get 1.1.1, 1.1.2 etc. This should be an autoincrement so user does not get to modify it. It is easy for user to refer using this user friendly id instead of a UUID." · **Status:** ✅ Built 2026-08-28

> **What's built, against the design above:**
> - **Schema** (migration [121](../../src/dblayer/migrations/121_objective_display_id.sql)): `objectives.next_child_seq` (a child-segment counter living on the parent's own row) and `objectives.display_id` (the frozen "1", "1.2", "1.2.3" string); a new `objective_root_sequences` table, one row per tenant, for Strategic-root segments. No DB-level `NOT NULL`/`UNIQUE` on `display_id` — same app-enforced-not-schema-enforced treatment as `requested_by` (point 4), and a plain `UNIQUE` couldn't express root uniqueness being per-tenant anyway without a real `tenant_id` column this CR treats as redundant (point 3).

RETURNING` on its tenant's counter row (resolved through `requestedBy -> users.tenant_id`) — then the Objective itself is inserted with its computed `display_id`, all in one commit, so a rolled-back create never burns a segment with nothing to show for it.
> - **`objectivesDB.update`**: now accepts `requestedBy` and heals a null via `SET requested_by = COALESCE(requested_by, $n)` — fills a legacy null, never overwrites a real original requester.
> - **`createObjective`** (`core/objectives.ts`): throws if `requestedBy` is null, for every tier, no exceptions — the app-level enforcement point 4 calls for, not a DB constraint. `ObjectiveListItem`/`ObjectiveSearchHit.path` both carry the new `displayId`.
> - **`updateObjective`**: threads `requestedBy` through to the DB layer's backfill.
> - **Routes** (`web/objectives.ts`): `POST /objectives/:id/update` now passes the session user through (point 4's second sub-bullet); the detail page's `<title>` uses the real `display_id`, falling back to the old UUID-prefix only for a legacy null row.
> - **Views**: the UUID's textual display is replaced (not supplemented) by a `.display-id-pill`-styled display id everywhere a statement is shown — `detail.ejs` (header, parent link, children list), `_nodes.ejs` (tree rows), `index.ejs` (search-mode rows and breadcrumbs), `new.ejs` (parent context line). The move-picker's `<option>` labels get a plain-text prefix instead, since `<option>` can't render nested HTML.

### The gap today

Verified directly against the live codebase: `objectives.id` is a bare UUID (`002_seu_platform.sql`), and no entity anywhere in this platform has a human-friendly sequential identifier — grepping for `sequence_number`/`display_id`/`short_code`/`serial_number` across `src/dblayer` returns zero matches. The UUID is what's actually shown to a person today: printed in full on the detail page (`views/seu/objectives/detail.ejs:31`), used as the URL segment on every Objective link, and even the page `<title>` falls back to an 8-character UUID prefix (`routes/seu/web/objectives.ts:177`) for lack of anything better. Nothing lets a person say or type "the objective" any more precisely than clicking through the tree or copying a UUID.

### The rule, as specified (owner)

- A Strategic (root) Objective gets the next whole number in sequence: **1, 2, 3, ...**
- An Operational Objective decomposed under Strategic "N" gets **"N.1", "N.2", ...** — next in sequence among that parent's own children.
- An Engineering Objective decomposed under Operational "N.M" gets **"N.M.1", "N.M.2", ...** — same rule, one level deeper.
- System-assigned only, at creation — **never user-editable**.

This maps directly onto the real hierarchy already built by CR-009: `objectives.tier` (`Strategic`/`Operational`/`Engineering`) and `parent_objective_id` (a real self-referencing FK, `002_seu_platform.sql`) already give exactly this tree shape — no change to the hierarchy mechanism itself, only a new, computed label alongside it.

### Design considerations found while grounding this against the live model

1. **A gap-tolerant scheme is required, not optional.** `deleteObjective` (`core/objectives.ts:305`) really does hard-delete a `Proposed` leaf with zero children and no commissioned SEU (`objectivesDB.delete`, `objectivesDB.ts:248`) — so, e.g., "1.2" can be created and then deleted before ever being activated. The display id must never be reused or compacted after a delete (an already-shown "1.3" must never silently become "1.2" later), which also rules out computing it live from a `COUNT(*)` at render time — it has to be a real, stored, monotonically-issued value per parent scope. [Sudha: Agreed]
2. **No existing "safe next-in-sequence" primitive to reuse.** Checked directly: no Postgres `SEQUENCE` object, no `SELECT ... FOR UPDATE`, anywhere in this codebase (`grep` across `src/dblayer`/`src/routes` — zero hits). The two nearest analogs are both race-prone by inspection, not safe patterns to copy: `ebmsDB.create`'s `INSERT ... VALUES (..., (SELECT COALESCE(MAX(version),0)+1 FROM ebms WHERE seu_id = $1))` (`ebmsDB.ts:16`), and `nextAvailablePatchVersion`'s check-then-insert retry loop (duplicated verbatim in `core/templates.ts:504` and `core/packs.ts:920`). Neither serializes two concurrent creations under the same parent, and neither is backstopped by a unique constraint that would even catch the collision afterward — `nextAvailablePatchVersion`'s own eventual write resolves `ON CONFLICT ... DO UPDATE`, a silent overwrite, not an error. This CR needs a real, deliberately safe mechanism, not a copy of either. [Sudha: Agreed]
3. **Settled (owner): the Strategic (root) counter is tenant-scoped, via the existing indirect path — no `can't` about it.** `objectives` has no direct `tenant_id` column (confirmed: `026_tenancy.sql` never touches this table), but a tenant is always reachable via `objectives.requested_by → users.id → users.tenant_id`, and that's sufficient — owner: "whatever sequence counter you are using, use the tenant_id... it is indirectly related to the objective through the user that proposes it," a real `tenant_id` column on `objectives` being acceptable but redundant if the join is easy enough. Note this only matters for the **root** counter — child-level counters ("N.1", "N.2", ...) are already naturally scoped by `parent_objective_id` regardless of tenant, so this is really one decision: Strategic Objectives get numbered 1, 2, 3, ... **per tenant**, not one global platform-wide sequence.
4. **Settled (owner): `requested_by` must never be null — every Objective is attributed to a real proposing user, no exceptions.** "Root user belongs to the platform" — even a system-triggered Objective (e.g. `ensureOneShotContainer`'s one-shot commissioning root, CR-009) is really an action taken by a real actor (root, if nothing else), never a genuinely user-less "system" action. This removes the need for any `PLATFORM_TENANT_ID` fallback branch: `users.tenant_id` is itself `NOT NULL` (`033_user_tenant_membership.sql:47`), and root/Platform users already live in the real, reserved `'platform'` tenant — so `requested_by → users.tenant_id` always resolves, once `requested_by` itself is guaranteed non-null.
   - **Enforcement is app-level, deliberately not a DB `NOT NULL` constraint** (owner: "the schema does not need the constraint. It has to be imposed by the app. I will explain when we get to transitions"). `objectives.requested_by` stays schema-nullable; every creation path (`createObjective`, `ensureOneShotContainer`, and anything else calling `objectivesDB.create`) must be audited to always pass a real actor id. Confirmed reachable today, not just theoretical: `web/seus.ts:78`'s `requestedBy: req.session?.user?.id ?? null` is one live path that can still produce a null — and checking the actual data, 118 of 132 Objectives in the current dev database already have `requested_by IS NULL`, though every one sampled (both null and non-null rows) is a test-suite-generated fixture (`phase5-...`, `webflow-...`, `stall-...` statements) — this is test-fixture noise in a shared dev database, not evidence of a real production data-integrity problem, but it does prove the gap is genuinely reachable, not hypothetical.
   - **Settled (owner): the update path must also persist `requested_by`, not just create.** Confirmed today it doesn't even try: `POST /objectives/:id/update` (`web/objectives.ts:191-206`) never reads `requestedBy` from the request, and `updateObjective` (`core/objectives.ts:235`, input type `{ statement?: string; tier?: ObjectiveTier }`) has no parameter for it at all — so a null left over from creation can never be fixed by a later edit, and `objectivesDB.update`'s `SET` clause has no way to write it even if it were passed through. In scope for this CR: thread the acting user's id through `updateObjective` → `objectivesDB.update` on every edit, so a row missing `requested_by` gets it backfilled by whoever next saves a change to it, the same app-level enforcement point 4 already establishes for creation.

### Not in scope for this CR

- Any change to `parent_objective_id`, tier-rank validation, or delete rules (CR-009/CR-012's own territory) — this CR only adds a display label, it doesn't touch the real hierarchy mechanism.
- Removing the UUID from the schema, or from URLs/the API — it stays the real primary key and the URL segment/API identity, unchanged. Only its *textual display* wherever a statement is shown (detail page, tree/list views, move picker, page title) is replaced by the pill-prefixed display id — see open question 4, now settled, below.

### Open design questions — not yet resolved

1. ~~**Concurrency-safe issuance.**~~ **Settled (owner: "only strategic objectives need unique sequence number").** That framing simplifies things: child levels never need a *dedicated* counter at all, because each child's counter can live as a column on its own **parent's existing row** — only Strategic objectives lack a parent row to hold one, so they're the one case needing a small counter table of their own.
   - **Child segments (Operational under Strategic, Engineering under Operational):** add `objectives.next_child_seq INTEGER NOT NULL DEFAULT 1`. Assign atomically: `UPDATE objectives SET next_child_seq = next_child_seq + 1 WHERE id = $parentId RETURNING next_child_seq - 1 AS assigned_seq`. Safe under concurrency with no explicit locking — the `UPDATE` itself takes a row lock on `$parentId`, so two children created under the same parent at once serialize automatically (one blocks until the other's transaction commits, then gets the next value).
   - **Root segments (Strategic):** a small per-tenant counter table, `objective_root_sequences (tenant_id UUID PRIMARY KEY REFERENCES tenants(id), next_seq INTEGER NOT NULL DEFAULT 1)`. Same atomic pattern, with `ON CONFLICT` handling a tenant's first-ever Strategic Objective in one statement: `INSERT INTO objective_root_sequences (tenant_id, next_seq) VALUES ($tenantId, 2) ON CONFLICT (tenant_id) DO UPDATE SET next_seq = objective_root_sequences.next_seq + 1 RETURNING next_seq - 1 AS assigned_seq`.
   - No Postgres `SEQUENCE` objects (awkward to create dynamically per-parent), no `SELECT ... FOR UPDATE`, no serializable-isolation-with-retry — the atomic `UPDATE`/`INSERT ... ON CONFLICT ... RETURNING` pattern is the standard safe counter idiom in Postgres and covers both cases uniformly.
   - The full display string ("1.1.2") is each ancestor's own assigned segment joined with `.`, walkable via the existing `findAncestorPath` recursive CTE (`objectivesDB.ts:158`) — whether to also store the precomputed full string on the row (vs. compute on read) is folded into open question 2 below, since re-parenting is what would ever invalidate it.
2. ~~**Re-parenting.**~~ **Settled (owner): freeze-on-move, no extra code, for this CR.** `reParentObjective` (CR-009) already lets a node move to a different parent, whole subtree included — but this CR does not touch `POST /objectives/:id/move` at all. Confirmed against the live routes: the id is issued once, at Save — inside `objectivesDB.create` (`objectivesDB.ts:9-28`, today a single bare `INSERT ... RETURNING *`, no transaction wrapper), called from `POST /objectives` (`web/objectives.ts:144`). Clicking "Add Objective" only reaches `GET /objectives/new` (`web/objectives.ts:96`), which renders a blank form with zero DB writes — so nothing is reserved before a row actually exists. Since the segment is written once at INSERT time, changing `parent_objective_id` later simply never touches it, with zero extra code required. Renumber-on-move (recompute + cascade through a moved subtree's descendants) is real, separate work — split out to **[CR-069](CR-069-objective-display-id-renumber-on-move.md), deferred, not designed**.
3. ~~**Existing Objectives.**~~ **Closed: no backfill needed, no clean-slate change needed.** `db:clean-slate` already truncates `objectives` unconditionally (`cleanSlate.ts`'s `USAGE_DATA_TABLES`, line 150, wiped via the step-1 `TRUNCATE ... CASCADE`) — confirmed by reading the file directly, not assumed. `cleanSlate.ts` itself needs **zero changes** for this CR: that gap doesn't exist. Its own comment is explicit that this is "a dev/test-only reset (never run in production)," so there is no persistent dev/test data this CR needs to migrate forward; every Objective in the dev DB today is already regenerated test-fixture data, consistent with the earlier sampling (point 4, above) that found nothing but `phase5-*`/`webflow-*`/`stall-*` fixture statements.
   - **In scope for this CR:** audit and update whatever test fixtures create Objectives directly (unit/integration tests, any seed data) so they align with the new `next_child_seq`/`objective_root_sequences` columns and the now-mandatory `requested_by` once built — since a full `db:clean-slate` regenerates all Objectives from these fixtures, a fixture that doesn't supply a real `requested_by` would otherwise immediately violate this CR's own app-level rule (point 4). No separate backfill migration or "unlabelled legacy row" handling is needed — fixture alignment is the entire closing action.
4. ~~**Where it's surfaced.**~~ **Settled (owner): replace the UUID; wherever an Objective's statement is displayed, prefix it with the display id, rendered as a pill.** Not "alongside" — the raw UUID stops being shown as text anywhere the statement appears; it stays only as the real primary key and the URL/API identity (see "Not in scope," below — unchanged, just clarified).
   - **Detail page** (`detail.ejs:31`, currently prints the full UUID) — replace with a pill showing the display id, followed by the statement.
   - **Tree/list views** (`index.ejs`/`_nodes.ejs`) — same pill-prefix treatment wherever a statement is rendered as a row/node label.
   - **Parent-move picker's option labels** (`detail.ejs:159`, currently `tier: statement.slice(0,60)`) — prefix each option's label with its pill.
   - **The not-yet-built Objective picker** (`listSelectableObjectives`, `core/objectives.ts:144` — doc-commented for a parent-picker/commission-from-existing-Objective UI, no callers anywhere today) — same treatment, once it gets a caller; noted here so it isn't missed when that UI is eventually built.
   - **Page `<title>`** (`web/objectives.ts:177`) is the one exception by necessity: it's currently *always* the 8-char UUID prefix (`` `Objective ${detail.objective.id.slice(0, 8)}` ``, not a fallback — confirmed reading the line directly), and a browser tab title is plain text with no HTML/pill rendering. This CR replaces it with the plain display id string (e.g. `Objective 1.2.1`), no pill markup, since a title can't render one.
