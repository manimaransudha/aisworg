# CR-096 — Ontology concept-type grouping (navbar + vertical tabs)

**Raised:** 2026-09-11 · **Origin:** owner: "I want the sublists grouped and the items within the group will be the vertical tabs on that particular page. For example, I want ai-provider-preference, development-methodology etc as a SEU Configurations." · **Status:** ✅ **Built 2026-09-11.**

## The gap

The Ontology navbar dropdown (CR-096's own predecessor turn) and the Ontology Management page's vertical tabs both listed every one of the ~28-36 concept_types flat, with no structure — `ai-provider-preference`, `development-methodology`, `target-cloud-provider` and 5 other `profile-configuration`-owned concept_types (Ch.7 §10 Configuration Parameters, migration 174) sat in the same undifferentiated list as `capability-name`, `category:evidence`, `template-categories`, etc.

## Design

**Detection is fully generic/data-driven, not hardcoded** (user-confirmed choice): `profile-configuration`'s own 8 codes (`ai-provider-preference`, `development-methodology`, `target-cloud-provider`, `deployment-strategy`, `default-repository-structure`, `documentation-level`, `primary-programming-language`, `source-control-provider`) are themselves concept_type names elsewhere in the Ontology — a real, existing relationship already in the data (migration 174), not something invented for this CR. `ontologyDB.findConceptTypeGroupPairs` is one query: every concept_type whose own codes match another concept_type's name is a group, with those matches as its members. No new table, no schema change — a future group (a Pack-contributed one, say) is picked up automatically.

**Labeling is the one thing that can't be derived from data** — a concept_type is a bare string, not a row with its own label (only its own codes have labels). `GROUP_LABEL_OVERRIDES` (`core/ontology.ts`) is a small, explicit map for this alone (`profile-configuration` → `"SEU Configurations"`); a group with no override falls back to a humanized slug (`Some-Type` → `"Some Type"`). Detection itself needs no entry here — only display polish does.

**Navbar**: a group's own concept_type collapses to ONE dropdown entry (relabeled, marked with a small group icon); its members no longer appear as separate top-level entries. Viewing any one member still highlights the group's own entry (membership-aware active-check), not just an exact match.

**Vertical tabs** (user-confirmed: the group-definer's own rows get their own tab inside the group, not dropped): landing on the group's own concept_type OR any one of its members renders the SAME tab strip — the group type itself first (its own "Parameters"-style catalogue: `profile-configuration`'s 8 name+`is_mandatory` rows), then each member. Landing on an ungrouped concept_type still gets the full flat top-level strip, just narrower now (excludes every grouped member). Tab labels stay raw concept_type slugs throughout, unchanged from before — only the navbar/top-level entry point uses the friendlier override label.

## Built 2026-09-11

**`ontologyDB.ts`**: new `findConceptTypeGroupPairs(viewer)` — one query, `SELECT DISTINCT concept_type, code FROM ontology_concepts WHERE code IN (SELECT DISTINCT concept_type FROM ontology_concepts)`, tenant-scoped the same way every other read here is.

**`core/ontology.ts`**: new `GROUP_LABEL_OVERRIDES`/`humanizeConceptType`, new `getConceptTypeNav(viewer, conceptTypes?)` (returns `topLevel`/`groupMembers`/`memberToGroup`) and `tabsForActiveType(nav, activeType)`.

**`app.js`**: the navbar's own per-request Ontology data now calls `getConceptTypeNav` instead of the flat `listConceptTypes`, exposing `res.locals.ontologyConceptTypes` (the `topLevel` array, `{type, label, isGroup}`) and `res.locals.ontologyConceptTypeGroups` (for the navbar's own membership-aware active-highlight).

**`web/ontology.ts`**: `GET /sdk/ontology` now resolves `activeType` against the full concept_type list (so a direct link to a member, e.g. `?type=ai-provider-preference`, still works) but defaults to the first **top-level** type when no `?type=` is given (never defaults into a group's interior); `tabsForActiveType` computes the page's own vertical-tabs list.

**`navbar.ejs`**: renders `entry.label` (not the raw type) with a group icon on group entries; active-check considers group membership, not just exact match.

**Verified**: `npx tsc --noEmit` clean. A live-DB smoke script (`getConceptTypeNav`/`tabsForActiveType` run directly against the dev database, not through the browser — see CR-095's own note on why: several long-running pre-existing dev-server processes already served this app, so a competing instance wasn't started) confirmed: `profile-configuration` correctly collapses to one `"SEU Configurations" [GROUP]` top-level entry; its 8 members vanish from the top-level list; both the group type itself and any one member (`ai-provider-preference` tested directly) resolve to the identical 9-tab group strip (`profile-configuration` first, then its 8 members); an unrelated type (`capability-name`) still gets the full ungrouped top-level strip.

## Not in scope

- Multiple/nested groups, or a group whose own type is itself a member of another group — the mechanism doesn't forbid it, but nothing in the current data exercises it and it wasn't asked for.
- A UI to define new groups (e.g. an admin picking "make X a group") — groups emerge purely from existing concept data (a concept_type whose codes happen to name other concept_types); there's no separate authoring step for "this is a group."

## Follow-up 2026-09-11 — migration 191: `ui_grouping` column replaces inference, plus `text_type`

Owner: "a few things to add so it gets easy and this becomes a data change than code change every time." Two additive columns on `ontology_concepts`:

- **`ui_grouping`** (TEXT, nullable) replaces this CR's own original detection mechanism outright — no more "a concept_type is a group whenever its codes happen to name other concept_types" inference, and no more `GROUP_LABEL_OVERRIDES` hardcoded map in `core/ontology.ts`. A row's own `ui_grouping` value now does both jobs directly: setting it (e.g. on `profile-configuration`'s own `ai-provider-preference` row) marks that row's `code` as a group member AND supplies the group's display label, in one place, as data. `ontologyDB.findConceptTypeGroupRows` replaces `findConceptTypeGroupPairs`; `getConceptTypeNav`/`tabsForActiveType` (`core/ontology.ts`) read `group_label`/`defining_type`/`member_type` straight off it. Backfilled onto the same 8 `profile-configuration` rows this CR's own build already identified (`ui_grouping = 'SEU Configurations'`); `participating-organisations` deliberately left unset (names no concept_type of its own yet). A **new** group going forward is a row edit — set `ui_grouping` on whichever rows should belong to it — not a code change, closing the exact gap the owner named.
- **`text_type`** (`'text' | 'markdown'`, default `'markdown'`) makes CR-094's "every description renders as markdown" a per-concept author choice instead of a blanket rule — set once when a concept is added/versioned, inherited automatically on every later version (`createConceptVersion`'s own base-inherit logic) unless explicitly overridden.

**Built**: migration [191](../../src/dblayer/migrations/191_ontology_text_type_and_ui_grouping.sql), applied directly and verified via `psql`. `ontologyDB.ts` (`findConceptTypeGroupRows`, `insertConceptVersion` now threads `textType`/`uiGrouping`), `core/ontology.ts` (`getConceptTypeNav`/`tabsForActiveType` rewritten off the column; `addConcept`/`createConceptVersion`/`composeConcept` thread the two fields through, inheriting from the prior Version when not explicitly given), `web/ontology.ts` (new `textType`/`uiGrouping` form fields on `/add`, exposed per-row in the GET view model), `ontology/index.ejs` (Text type selector + UI grouping input on the Add form with a JS toggle between the markdown editor and a plain textarea — mirroring the Compose panel's own strategy toggle; a `ui_grouping` badge per row; the description-preview modal now branches on `text_type` — `innerHTML` for already-sanitized markdown, `textContent` for plain text, never the wrong one for the other, since plain text was never run through `sanitize-html`). `seuTypes.ts`'s `OntologyConceptRow` updated with both fields.

**Verified**: `npx tsc --noEmit` clean throughout. A live-DB script confirmed `getConceptTypeNav`/`tabsForActiveType` produce the identical "SEU Configurations" grouping as before, now sourced entirely from the `ui_grouping` column rather than the retired inference query.

## Follow-up 2026-09-11 — direct edit CRUD for `ui_grouping`/`text_type`

Owner: "a CRUD to manually set the ui_grouping / text_type." The prior build only let these be set at creation/versioning time (the Add form). This adds a genuine edit path for an already-existing concept — and, deliberately, it's a different write shape from every other mutation on this table: `ui_grouping`/`text_type` are administrative/display metadata, not the semantic content Ch.18 §12's versioning targets, so editing them happens **in place on the current Active row** — no new Version, no status change, no `transitionEngine` gate (same "not a governed transition" territory as the plain create/edit action, gated only by the route's own `ontology_define` badge).

**Built**: `ontologyDB.updateConceptMeta(id, {textType?, uiGrouping?})` — a raw partial `UPDATE`. `core/ontology.ts`'s `updateConceptMeta(conceptType, code, targetTenantId, updates, actor)` — same ownership rule as every other write here (root: any tenant; everyone else: only their own), resolves the current Active row, applies the update. New route `POST /sdk/ontology/update-meta`. UI: a pencil-icon "Edit" button per row (gated the same as the lifecycle-action buttons) opens a shared modal — same relatedTarget-refill pattern as the description-view modal — pre-filled with the row's current `text_type`/`ui_grouping`, posting the two fields back. Blank `ui_grouping` in this form means exactly that — clear it — since the form shows the current value, unlike the Add form's "blank = inherit from prior Version."

**Verified**: `npx tsc --noEmit` clean. A live-DB script called `updateConceptMeta` directly on a real row, confirmed `text_type` changed with `version` unchanged and `ui_grouping` left untouched, then reverted the test edit.

The per-row pencil button, `editMetaModal`, and its JS were removed from `ontology/index.ejs` entirely — that page's own `ui_grouping` badge is now view-only, its tooltip pointing readers to Ontology → Metadata. `app.js` now also sets `res.locals.currentPath` (alongside the existing `currentQuery`) so the navbar can highlight the Metadata entry specifically, distinct from the Ontology-dropdown-wide `seu-sdk-ontology` `activePage` match both pages share.

## Follow-up 2026-09-11 — grouping redesigned to be concept_type-level (real bug found and fixed)

Owner set `ui_grouping` directly on several existing concept_types' own value-rows to merge siblings (`category:obligation` + `category:obligation-origin` → "Obligation"; `category:pack` + `category:policy` → "Packs"; `checklist-configurable-value` + `checklist-configurable-dimension` → "Checklists"; single-member groups for "Templates"/"Environments"/"Evidence"/"Engineering Capital"). Then asked "How are the vertical tabs generated? Within a group, the concept_types should be the vertical tabs - makes sense?" — a direct comprehension check that surfaced a real bug, confirmed by tracing the code and running it live before answering (not guessing):

**The bug**: the original mechanism (`findConceptTypeGroupRows`) read a row's own `code` as *naming a child concept_type* — correct only for `profile-configuration`'s own shape, where its 8 codes genuinely are other concept_types' names (migration 174). It was never designed for "tag several sibling concept_types' own rows with the same label so they merge." Run live against the owner's new data, `category:obligation` and `category:obligation-origin` produced **two separate duplicate navbar entries**, both labelled "Obligation" — and `tabsForActiveType('category:obligation')` returned `['category:obligation', 'Customer', 'Audit', 'Operational', 'Security']`: its own *code values*, not the sibling concept_type. Confirmed identically broken for "Packs" and "Checklists."

**Redesign** (owner-confirmed: "The navbar in Ontology should reflect ui grouping. When the ui grouping is selected, the vertical tabs should be concept_types"): one rule, at the concept_type level — a concept_type belongs to a group whenever *its own rows* carry `ui_grouping`; every concept_type sharing that value merges into one navbar entry, and each one is a tab inside it. No more "defining type whose codes name children" — that was never a generalisable model, just a coincidence that happened to fit `profile-configuration`'s own original shape.

**Built**: `ontologyDB.findConceptTypeUiGroupings` replaces `findConceptTypeGroupRows` — `SELECT DISTINCT concept_type, ui_grouping ...` (a type whose rows disagree on the label surfaces as more than one row here — a real data inconsistency for the Metadata page's review table to catch, not swallowed silently). `core/ontology.ts`'s `getConceptTypeNav`/`tabsForActiveType` rewritten around groups-as-sets-of-sibling-types instead of parent/child; `ConceptTypeNav`'s external shape (`groupMembers`/`memberToGroup`, both anchor-keyed) kept unchanged so `navbar.ejs` and `web/ontology.ts` needed zero changes. **Migration [193](../../src/dblayer/migrations/193_ui_grouping_concept_type_level.sql)**: `profile-configuration`'s own 8 children (`ai-provider-preference`, `development-methodology`, etc.) never had `ui_grouping` on their OWN rows before — only `profile-configuration` itself did (migration 191) — so under the new one-rule model they'd have silently dropped out of "SEU Configurations" entirely. Backfilled onto all 8, applied directly.

**Verified**: `npx tsc --noEmit` clean. Live-DB script confirmed the fix: `category:obligation`/`category:obligation-origin` now merge into one "Obligation" entry with both as tabs of each other (no more duplicate entries, no more codes-as-tabs); same for "Packs" (`category:pack`/`category:policy`) and "Checklists"; "SEU Configurations" now correctly lists all 9 types (`profile-configuration` plus its 8 former "children," now symmetric siblings) as tabs of one another.
