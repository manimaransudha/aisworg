## The gap, precisely

**Chapter 5 §9 gives Checklist one line** ("Engineering checklists.") — unlike Quality Gate/Review Gate, no dedicated model chapter existed anywhere in `design/foundations/` until the owner pointed to it directly: **Chapter 47 – Checklist Model**, `design/foundations/03_Book 3 (Refined)/07_Part 7/Chapter 47 copy.md` (untracked in git as of this CR; the owner edited it live during this same discussion — see "Design, as settled" below for what changed from its original form).

**Live schema** (`schema_definitions`, `entity_kind='Pack'`, confirmed via direct query, unchanged since migration `040_pack_structured_contributions.sql`):
```json
"contributionChecklists": {
  "type": "array", "x-widget": "referential-list",
  "items": { "type": "object", "properties": {
    "checklist": {"type": "string"}, "statement": {"type": "string"},
    "classification": {"enum": ["machine-verifiable", "judgment", "human-attested"]},
    "externalEvidence": {"type": "boolean"}, "prompt": {"type": "string"},
    "participant": {"enum": ["AI", "AI+human", "human"]},
    "outputContract": {"enum": ["passed-failed-notes", "assessment-acceptance"]},
    "assurance": {"type": "string"}
  }}
}
```
No `code`, no `x-property-order`, no per-field `x-help`, no `required`, no Ontology backing — the pre-CR-058/059 raw shape both Quality Gate and Review Gate started from.

**Real data has already drifted from this schema.** All 22 Pack files that populate `checklists` (the 6 OpenUP + 16 SDLC-phase Packs) key each row by `code` — a field the schema never declares — confirmed by grep: zero real files populate the schema's own `checklist` field. `formGenerator.ts`'s `rowHasContent` (line 317) only happens to keep these rows visible in the SDK authoring tool because its fallback checks `code` before `checklist` — a display heuristic, not real schema support. Real example (`openup-development.pack.json`):
```json
{"code": "design-the-solution", "statement": "The design for this increment is consistent with the Architecture Notebook.", "classification": "judgment", "prompt": "...", "participant": "AI+human", "outputContract": "passed-failed-notes"}
```
Three such rows exist for this Pack (`design-the-solution`, `implement-solution`, `integrate-and-create-build`) — each reads as its own independent concern, with no shared grouping key populated anywhere, even though Chapter 47 describes a genuine two-level Checklist-*containing*-Items structure.

**Never materialized, never connected to anything**: no `checklists` table exists (`information_schema` confirms zero matching tables), no `checklistsDB.ts`, and `core/packs.ts` has zero references to "checklist" anywhere (confirmed by grep) — `seedContributions` doesn't process it, `validatePackSeed` doesn't check it. Chapter 5 §19.4's own "Materialisation caveat" bullet already documents this as declaration-only, JSONB-only.

## Design, as settled

### Chapter 47 itself was edited during this discussion
The owner directly edited Chapter 47 while this CR was being scoped (now at `07_Part 7/Chapter 47 copy.md`) to remove Checklist's independent lifecycle/versioning:
- CKM-003 changed from "Checklists are independently versioned" to: *"Checklists possess no independent version or lifecycle of their own. Both are inherited entirely from the originating Pack... a Checklist's content changes only when its Pack's version changes."*
- FR-47.10/11 changed to explicitly prohibit independent versioning/lifecycle state.
- §16 (retitled "Checklist Versioning and Lifecycle") now argues this directly against Quality Gate/Review Gate's own precedent: those two need independent identity because other records reference them by id *across Pack versions* (a Waiver references a specific Quality Gate; a Review references a specific Review Gate) — "*nothing outside its own Pack ever holds a stable reference to a specific Checklist*," so no separate reconstruction mechanism is required.
- §17 (Events) now publishes no lifecycle events of its own — only the three runtime execution events remain.
- §20 (Deliverables) now explicitly states: *"No Checklist registry or independent versioning service is required."*
- §8 (Checklist Structure) dropped the `Version` field it originally listed.
- §9 (Checklist Item Structure) dropped `Identifier` — a Checklist Item now has no identifier of its own beyond its position within its Checklist's declared item list.

This CR's design builds on the **edited** Chapter 47, not its original form.

### Checklist Structure — narrowed further than Chapter 47's own edited text
Discussed live, settled beyond what's currently written in the chapter: **Category, Capability, Applicable Deliverable Type, and Applicable Transition are dropped from Checklist entirely** — not merely deprioritized. Owner: *"Name, Category, Capability, Applicable Deliverable Type, Applicable Transition - all of this is already in the review gate... Checklist is just the mechanism for review and quality gate."* That scope information is fully carried by whichever gate(s) reference the Checklist (Review Gate's `code`/`governedTransition`, Quality Gate's `category`/`governedTransition`) — duplicating it onto Checklist itself was redundant. Chapter 47 §7/§8/§14/§15 (Checklist Category, the Evidence-Category-vocabulary reuse, Category-based Required-Evidence matching, Category-based Union composition) are all **superseded** by the FK design below and need rewriting in the chapter as part of this CR's own build (same discipline CR-059 used to update Ch.5/Ch.25 after building).

Settled Checklist Structure: **Identifier** (Pack-scoped, not Ontology-governed — per Ch.47 §8's own existing text, unchanged), **Name**, **Description**, **Items**, **Originating Pack** (provenance, see below).

### Checklist Item Structure — Classification dropped, then everything else (superseded by the revision below)
Owner: *"Participant can be used. Classification can be dropped."* The existing `classification` (machine-verifiable/judgment/human-attested) and `participant` (AI/AI+human/human) fields already map close to 1:1; keep `participant`, drop `classification` entirely. **This paragraph describes the FIRST build pass only** — its "Settled Item fields" list (Statement, Prompt, Participant, Output Contract, Assurance, External Evidence flag, Mandatory Designation) did not survive contact with the built form. Owner, looking at the actual rendered result: *"Why is the checklist form having a participant?"*, then *"you cannot determine a checklist item to be mandatory. Checklist is generic. Pack has the specifics."* Final, actually-built shape: a Checklist Item is **just Statement** — see "Revision, same day" below. No per-item Identifier (Ch.47 §9, unchanged either way) — items are addressed only by position within their Checklist's own item array.

### Revision, same day: Mandatory/Recommended and Participant both moved off the Item entirely
Not a refinement of the paragraph above — a reversal of it, on a sharper principle than "these fields happen to be redundant." Owner: *"you cannot determine a checklist item to be mandatory. Checklist is generic. Pack has the specifics."* A Checklist is reusable, context-free content; every fact about how it's checked, who checks it, and whether completing it is required belongs to the Pack referencing it, not to the Checklist itself. Concretely:
- **Checklist Item → just `statement`.** No Mandatory Designation, no Participant, no Output Contract/Assurance/External Evidence/Prompt.
- **Participant needs no new field anywhere**: Review Gate already has its own top-level `participant` (VerifiableItemFields), which covers everything that gate does, including whichever Checklists it references. Quality Gate is engine-evaluated, never participant-driven, so needs none either.
- **Mandatory/Recommended moves to the gate's own *reference*, not the Checklist**: `checklistIds` (already built, required — AND) stays; a new `recommendedChecklistIds` (advisory — doesn't block the gate) sits alongside it, reusing the `"referential-multi"` mechanism already built rather than a third new form-generator capability. The same Checklist can be `checklistIds` for one gate and `recommendedChecklistIds` for another.

### A real, persisted `checklists` table — despite no lifecycle
Chapter 47 §16/§20 (as edited) say no registry/versioning service is needed — but Review Gate and Quality Gate both need a real FK to point at, which requires Checklist to have a stable, queryable identity. Owner resolved the apparent tension directly: *"'nothing outside its own Pack ever holds a stable reference to a specific Checklist' - this is still true because quality and review gates are not independent, they are scoped within a pack. Checklist can be in a table to get a fk. the chapter does not impose the implementation details."* §16's statement is about model/governance reach (no independent lifecycle to track, no cross-version reconstruction problem), not a ban on a physical table. So: **`checklists` becomes a real table** — `id`, `name`, `description`, `originating_pack_id`, and **`items` as a single `JSONB` array column** (not a child table — owner: *"Inside the checklist table, the list of actual checklist items can be an array."*). No `version`/`is_active`/lifecycle columns — content simply changes when the originating Pack republishes.

### Checklists are cross-Pack referenceable — same reach as Policy
Owner: *"any Pack's gate can point at any Pack's checklist, same reach as Policy."* This was checked against a "must the Pack codes match" reading and explicitly rejected: *"code is not unique. so how does it matter?"* (`packs.code` is not a unique identifier — CR-026's own constraint is `(code, pack_version, tenant_id)`). Settled: a Checklist is referenced purely by its own real, unique `id`; `originating_pack_id` on the row is **provenance only**, carrying no reference-scoping meaning. This is a deliberate departure from Review Gate's own CR-059 precedent (`self:contributionReviewGates`, same-Pack-only, "if something is global, it has to be a policy") — Checklist is being placed in Policy's reach category, not Review Gate's.

### Review Gate and Quality Gate both gain `checklistIds`
Owner: *"A review and quality gate can have multiple checklist ids."* Both gates gain a `checklistIds` field — an **array** of real `checklists.id` values, not a single FK.

### `checklistIds` semantics — AND within one gate, dedup across gates
Two distinct questions, both settled:
- **Within one gate's own list: AND.** Owner: *"Every quality gate is defined by category and that is an AND"* — matching the discipline the old (pre-edit) Ch.47 §14 already established for a gate with multiple populated Required-Evidence-Category entries ("a structural AND across the gate's populated Required Evidence entries"). Every checklist a gate lists must complete; this is not the old Category union's OR-semantics (which only existed because the old design *couldn't* enumerate specific checklists — an explicit list doesn't have that constraint).
- **Across different gates referencing the same checklist: dedup, not re-execution.** Owner: *"If gates point to same checklist, it is taken once."* Worked through with a concrete example (2 Quality Gates + 3 Review Gates all pointing at the same checklist) — the checklist executes once; every referencing gate reads that same result. This is Chapter 47's old §15 Union composition surviving in substance — only the discovery mechanism moved from implicit Category-matching to explicit `checklistIds` enumeration + id-based dedup. Not a special union *service* to build — an emergent property of (a) execution happening once per checklist, however that gets built later, and (b) each gate independently checking for its own listed checklists' completion, the same shared-Evidence/shared-fact pattern the rest of the platform already uses.

### Execution is explicitly out of scope
Owner: *"There are 2 parts to the chapter. definition and execution. The execution aspects come into picture only during seu commissioning. Pack are declarative. They only define the checklist."* This CR builds the Pack-side declaration only (schema, table, validation, gate FK-lists). Chapter 47 §11–12 (Participant executes every item, produces one itemized Evidence record) and any Quality Gate/Review Gate logic that actually *checks* whether a referenced checklist has been completed are both deferred to whatever CR eventually builds SEU-commissioning-time execution.

## Open — settled

- **`checklists.id` stability across a Pack republish — it stays.** Owner: *"It stays. You can add a version number to a checklist, but that does not change because pack version number changes. It will just be a dead field. Someone wants to update the checklist with a new item, they can without a version change. If you put a version number then all pack definitions have to change which is the reason why there is no lifecycle for it in the first place."* `seedContributions` upserts a Checklist's row **in place** — same `id` persists across every republish of its originating Pack, keyed by `(originating_pack_id, name)`. Content (`items`) can change on any republish without a version bump and without touching any other Pack's or gate's `checklistIds` reference, since those reference by stable `id`, never by content/version. **No `version` column on `checklists`** — explicitly decided against: nothing would ever read it, and adding one would reintroduce exactly the cross-cascade problem ("all pack definitions have to change") the no-independent-lifecycle decision (Ch.47 §16, CKM-003) exists to avoid.
- **Cross-Pack `checklistIds` in raw seed JSON — it cannot, so seed Packs stay same-Pack-only.** Owner: *"It cannot. So there has to be some meaningful minimum checklist for the seedpacks."* The platform capability (any Pack's gate referencing any Pack's checklist by real `id`) is real and stays in scope for the SDK authoring UI (which resolves against live, already-persisted `checklists` rows) — but the hand-authored `*.pack.json` seed files can only ever express same-Pack self-references (resolved by name at `seedContributions` time, mirroring `reviewGateIdByCode`), because no real `id` exists yet at authoring time for a cross-Pack pick. Each of the 22 real seed Packs therefore needs its own minimal Checklist(s), referenced only by its own gates — never a cross-Pack reference in seed data.
