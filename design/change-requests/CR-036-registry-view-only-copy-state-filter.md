> **Built 2026-08-20.**

### What's built
- **Registry pages (`packs/index.ejs`, `templates/index.ejs`, `profiles/index.ejs`)** — the transition form is gone; each card now shows only its status badge (already there) plus, if the viewer holds `{noun}_define` (or root), a **Copy** button.
- **State filter** — a chip row (All states + the 7 real lifecycle states) above each Registry list, composing with the existing category-tab sidebar. Threaded through the shared list infrastructure the same way CR-029's category filter was: `ListResult.status` (`utils/listQuery.ts`), `listQueryString`/`listControls.ejs`'s own querystring builders.
- **Copy** — `copyPackAsNewDraft`/`copyTemplateAsNewDraft`/`copyProfileAsNewDraft` (`core/packs.ts`/`templates.ts`/`profiles.ts`): reconstruct the source row's real current content (same pattern each entity's own `reactivateAsNewVersion` already used), land in a fresh **Draft** at the next available patch version (`nextAvailablePatchVersion`, already existed) under the *same* code and tenant — not Inheritance (no new lineage; a Derived Template/Profile's own `parent_template_id`/`parent_profile_id` carries through unchanged, since copying a Derived row is still a copy of that same Derived thing). New `POST /:id/copy` routes, badge-gated server-side via `badgeAuthorityEngine.authorise`, redirect to the new Draft's own Authoring edit page.
- **Lifecycle governance relocated to Authoring** — Registry going view-only removed the *only* place Active → Deprecated → Retired → Archived (and reactivation) could happen; `nextHop`'s existing single-match logic (built for the linear Draft pipeline) doesn't cover branching post-Active states, so a new `possibleNextStates` lookup (`transitionDefinitionsDB.findPossibleNextStates`) and `POST /sdk/:slug/:draftId/transition` route were added to the Authoring surface, with a "Lifecycle" card on the entity's own edit page shown once it's left Draft. Authority is enforced exactly where it always was, inside `transitionPack`/`transitionTemplate`/`transitionProfile`'s own `transitionEngine` call — this route is a relocation, not a new authorization model.
- `web-flow.e2e.test.ts`'s "Phase 9" test updated to exercise the relocated route (`/sdk/pack-authoring/:id/transition`) instead of the removed one, and to check the Authoring page's own status badge in addition to the Registry's (still view-only) display.
- Fixed a real UX bug found while testing this: the Registry's "no results" empty state ("No Packs published — run `pnpm seed:seu`...") didn't account for the new filters — filtering to a state/category with zero matches showed the same "nothing published at all" message. Now distinguishes: search / filtered-to-empty / genuinely-nothing-published, across all three Registries.

### Design decisions
- **Copy, not Inheritance** — a copy is a new, independently-editable Draft starting from a row's current content; it records no new lineage. This is deliberately distinct from CR-026's Inheritance model (a different tenant deriving from a parent, code locked, disambiguated by `tenant_id`) even though both "start a new Draft from an existing row's content."
- **Server-side authority is unchanged** — the Copy routes' own badge check and the relocated Lifecycle form's underlying `transitionPack`/etc. calls enforce the exact same noun_verb authority that always governed these actions; nothing about *who* can do *what* changed, only *where* the control lives.
