## The gap

Chapter 13 defines Participant abstraction/identity/lifecycle, but the implementation only ever covered the lifecycle half:

- **3 Participant Types hardcoded** (TS union + DB `CHECK`), not Ontology-backed like every other canonical platform vocabulary (`capability-name`, `category:environment`, etc.).
- **No onboarding mechanism.** A Participant is created inline (`type` + `displayName`) wherever a Capability happens to get fulfilled. Nothing models "provisioning a participant resource" as its own concept, and there's no seam to plug in a different provisioning mechanism per client/technology-provider without touching platform core — the owner's stated goal from the start of this conversation: *"as we onboard a new client, only this [adapter] layer has to change and the platform should not need major changes."*
- **§8's Identity field list is missing from the schema entirely.** `participants` (migration 002) only ever carried `id/seu_id/type/display_name/state/user_id` — no Assigned Capabilities, no Competency, no Authority/Behaviour Context, nothing.
- **No reusable, cross-SEU participant resource.** Every Capability Fulfilment creates a brand-new `participants` row from scratch — the same real person, AI agent configuration, or integration can't be tracked or reused across multiple SEU engagements over time.

## Design — settled by the owner (chronological)

1. **Participant Types.** Ch.13 §7 revised from 3 types (AI/Human/External) to 4, and the owner already edited this directly in `Chapter 13.md`: **AI**, **Human**, **Automated** (takes over the old External's "autonomous service" examples — CI/CD Pipeline, Static Analysis Platform, Security Scanner, Cloud Deployment Service), **External** (redefined — outside oversight/authority parties: Auditors, Certifying Authorities).

2. **`ParticipantType` becomes Ontology-backed** — concept_type `participant-types` (codes AI/Human/Automated/External), same discipline CR-086 gave `capability-name`. No DB `CHECK`; validated dynamically via `assertCanonicalCategory`, same precedent already set by `deliverables.lifecycle_state`.

3. **`participants_master`** — a new, tenant-scoped, **cross-SEU resource registry**, separate from `participants` (which stays the per-SEU lifecycle/engagement record, Ch.13 §9's state machine). One `participants_master` row = one real identity (Harry the human, an AI agent configuration, a registered CI/CD integration, an accredited External auditor), reusable across many SEU engagements over time.
   - Fields: `id`, `tenant_id`, `type` (Ontology `participant-types`), `display_name`, `capabilities` (array of Ontology `capability-name` codes — owner's example: *"Harry can fulfil development and code-review capabilities"*), `competency` (jsonb, Ontology-backed — see 4), `is_active`, `user_id` (nullable, Human-only — the real login this identity maps to).
   - `participants.user_id` is repointed and renamed to `participant_id`, now FK → `participants_master.id` (previously FK → `users.id` — a stopgap migration 014's own comment already called *"ahead of real Participant deployment"*; `participants_master` is that real deployment).
   - Participant-to-SEU stays 1:1 (existing `participants.seu_id`); a single `participants_master` resource can be engaged into many different SEUs' `participants` rows over time.

4. **Competency** — jsonb field on `participants_master`, shape `{<dimension>: [<values>]}`, e.g. `{"domain": ["health","banking"], "technology": ["nodejs","react","rust"], "hyper-scale": ["aws"]}`. Both the dimension names *and* their values are Ontology-driven: a parent concept_type `competency-dimension` (codes: `domain`, `technology`, `hyper-scale`, ...) whose codes each name their own child concept_type holding that dimension's real values — the same two-layer shape `profile-configuration` already established (migration 174). Grouped under `ui_grouping = "Competencies"`, `text_type = "text"`.

5. **Engineering History (§8) — dropped** as a stored field. Derivable via a query joining `capability_fulfilments → seus` for a given participant.

6. **Behaviour Context (§14) — revised mid-conversation, now settled.** Initial reasoning: since Participant→SEU is 1:1 and SEU→EBM is already 1:1 (`seus.active_ebm_id`), "the EBM governing execution" is fully derivable through that existing chain — no separate stored field needed. The owner then clarified the intended meaning is broader than a bare EBM reference: **tenant-specific eligibility/compliance policy gating whether this identity may work at all** — *"some clients have policy that a human participant should have completed a background check to work in their organisation."* This is inherently an **identity-level** property (belongs to the resource, not to one SEU engagement), confirmed onto `participants_master`, not `participants`. **Shape, settled:** a jsonb array of `{policy, payload}` objects, e.g. `[{"policy":"background-verification","payload":{}},{"policy":"qualitygate","payload":{...}}]` — deliberately no fixed sub-schema (owner: *"I do not have an exact shape and so leave it as a jsonb"*); each policy's own payload is whatever that policy needs. `policy` values are plain strings for now, **not** Ontology-backed — open whether they should be (see Open questions).

7. **Onboarding adapters — now built.** One per Participant Type (AI/Human/Automated/External), same registry-per-mode seam the existing delivery-side `ParticipantAdapter`/`adapterRegistry.ts` already uses, but a **distinct** interface/registry — `ParticipantOnboardingAdapter` + `participantOnboardingRegistry.ts` (`src/adapters/`). Today's `ParticipantAdapter` stays scoped to assignment *delivery* (keyed by tenant+Capability's `ExecutionMode`) and is untouched by this CR.
   - **No associated events** — owner: *"Onboarding adapter will not have any associated events. They are just resources that are available to the platform."* Creating a `participants_master` row is not a governed/transitioned action the way `participants` lifecycle transitions are (Ch.13 §16's event list stays exactly as-is). Confirmed: `onboard()` returns proposed data only; `createParticipantMaster` is the one write path, no event published.
   - Owner: *"clean-slate has to call the adapter. But the adapter has to be an 'adapter'. For every client deployment this will change to integrate with their specific details."* `seedParticipantsMaster.ts` no longer generates any mock data itself — it's pure orchestration: for every tenant × every `listRegisteredOnboardingTypes()` entry, resolve that type's adapter and call `onboard()`, then write the result through `createParticipantMaster`. Onboarding a new client's real HR system / AI platform / CI registry / audit board is a single `registerOnboardingAdapter` call, no change to `cleanSlate.ts`/`seedParticipantsMaster.ts`/`core/participantsMaster.ts`.
   - **AI and Automated Participants use the same `participants_master` shape as Human/External** — `capabilities[]` and `competency` both still apply, just interpreted as *declared operating scope* rather than certified/earned skill (an AI agent's tuned domain/tech scope; an Automated integration's supported tech stack; an External authority's accredited domain), not a different schema or separate tables per type. Each of the 4 mock adapters populates a different, narrower slice of `competency` reflecting this (Automated: `technology` only; External: `domain` only; AI/Human: all three dimensions).
   - **50 seeded per tenant PER Participant Type** (owner: *"the 150 rows... is human participants seed. Similarly other participant types have to be seeded across the tenants"*) — 3 tenants × 4 types × 50 = 600 `participants_master` rows total, not 150 split across types.
   - **When adapters become real** (not mocked), adapter-specific connection config (model/provider for AI, webhook/endpoint for Automated, accreditation reference for External, etc.) should **not** get its own table per Participant Type — same generic, opaque-to-the-core config shape `execution_targets` already uses for delivery (`mode`/`adapter_endpoint`/`adapter_auth_ref`), not a bespoke schema per adapter. Still not built — no column/table exists for this yet, since every adapter is mocked; `OnboardParticipantRequest`/`OnboardedParticipant` (the adapter I/O contract) carry no such field today.

## Open questions

- Should Behaviour Context's `policy` values (e.g. `"background-verification"`, `"qualitygate"`) be an Ontology-backed vocabulary — a concept_type like `behaviour-context-policy` — the way `competency-dimension` is, or stay plain free-text strings given tenants define their own custom checks? **Resolved:** owner confirmed *"all context will be ontology backed directly or indirectly"* — `behaviour-context-policy` concept_type added to migration 195.
- Who sets/clears a Behaviour Context entry, and does clearing one (e.g. a background check expiring) need to affect *existing* SEU engagements, or only gate new ones? Still open.
- Migration 195's exact FK naming — owner said *"fk to master_id"*; implemented as `participants.participant_id → participants_master.id` (every table's PK stays named `id`, this codebase's own convention) rather than literally naming a column `master_id`. Owner acknowledged ("fine") — treated as settled.
- Whether `fulfilCapability`/`replaceParticipant` should be refactored to *select* an existing `participants_master` row (a true "engage an existing resource" flow) vs. continuing to create an ad hoc identity inline — **Resolved, built later this same session** (owner: *"The participants dropdown should be multi-select. It chooses as many as it wants as eligible"*). `resolveMasterParticipant`/`fulfilCapabilityWithParticipants` (`core/capabilities.ts`) now select from `findEligibleParticipants`'s own real `participants_master` rows, server-re-validated against the same eligibility check the dropdown itself used — never an ad hoc inline identity.
- Adapter-specific real connection config shape (model/provider for AI, webhook for Automated, etc.) — still open, deferred until a real (non-mock) adapter is actually being wired in.

## Not in scope
