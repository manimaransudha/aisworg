# CR-091 — Profile Structure completion (Book 3 Ch.7 §5/§7)

**Raised:** 2026-09-05 · **Origin:** owner, reviewing Book 3 Chapter 7 (Profile) §5 (Responsibilities) and §7 (Profile Structure) against the current build, following on from the same day's Chapter 7 audit (§19.7's composition-engine finding). · **Status:** ✅ Closed 2026-09-05 — all three parts built. Part 1: `deploymentTargets`/`additionalCapabilityCodes`/all-six Pack categories (migration `173`). Part 2: `profile-configuration` Ontology catalogue + ten per-parameter concept types, ten named Configuration Parameter fields replacing `configParameters`, tenant-overridable `is_mandatory` (migrations `174`/`175`). Part 3: `category` retired from use (field/validation/Registry grouping — column and Ontology rows left in place, untouched).

## The gap (confirmed live, 2026-09-05)

Auditing §5's 9 "may define" items against `ProfileSeedInput`/the real schema found two with **no field at all** — not even a declared-but-inert one the way `configParameters`/`featureFlagCodes` already are:

- **"Deployment targets"** — no corresponding item even in §7's own 14-field structural list, and nothing in the schema. Not the same concept as `environment` (checked: the two are never unified anywhere in the code).
- **"Optional capability enablement"** — same: no field, no column, no concept distinct from anything else Profile has.

And one structural under-coverage: §7's four category-scoped Pack-selection fields (`technologyPackCodes`/`domainPackCodes`/`compliancePackCodes`/`integrationPackCodes`, migration `066`) only cover 4 of Pack's real 6 `category:pack` values — Template's own `PACK_SELECTION_SLOTS` (`core/templates.ts`) already covers all six; Profile was missing Engineering and Organisation.

## Design (owner, settled 2026-09-05)

- **Deployment Targets — a new field, distinct from `environment`.** Owner: *"Deployment targets is not the same as environment. This has to be defined in the structure. Environment can be development. Deployment target can be something very specific that a CI/CD pipeline should be able to pick. For now, it will be a json so there is flexibility to add what is required."* Built as `deploymentTargets` — `x-widget: "json"`, free-form object, the same "declared for documentation today, not yet enforced" treatment `compositionOptions` already has (Ch.5 §19.9's precedent). No real column — lives only in `draft_content`, same as `compositionOptions`/`featureFlagCodes`.

- **Optional Capability Enablement — a new field, the Profile-level escape hatch for genuine per-commissioning excess.** Owner: *"this has to be included. This allows addition of capability-name not available in the template. Note we mentioned there should be no excess or no missing in template. If excess is required, it gets added here. just a list of capability-names from ontology not already there coming from the templates."* Built as `additionalCapabilityCodes` — a `referential-list` of `capability-name` Ontology codes (the same shared vocabulary Pack's own `contributionCapabilities` uses), same shape as `featureFlagCodes` (one item field, `capabilityCode`), `x-ontology: true` so options resolve to a real label. "Not already there coming from the templates" is a **candidate-list curation**, not a hard validation rule: `web/sdkAuthoring.ts`'s `renderAuthoringForm` resolves the Profile's own `baseTemplateCode` → the Template's real Pack selections (`getPackSelectionsByCategory`) → `deriveCapabilityCodesFromPackCodes`, and filters those codes out of the offered `capability-name` options. A resubmission of an already-covered code (e.g. via JSON import) isn't rejected server-side — redundant, not wrong, the same discipline every other Ontology-backed picker on this page already follows.

- **Selected Technologies/Domains/Compliance/Integration — extended to all six Pack categories.** Owner: *"should cover all pack categories coming from ontology."* Added `engineeringPackCodes`/`organisationPackCodes`, mirroring the existing four exactly (`x-referential: "pack-code:<Category>"`, same widget, same `PACK_SELECTION_SLOTS` pattern `core/profiles.ts` already had) — Profile's own category-scoped Pack fields now match Template's six exactly.

- **Environment — clarified, not a CR-088 "configurable parameter."** Owner asked directly: *"Environment - we already have this as a configurable parameter - don't we?"* No — `environment` is a plain, always-required field authored directly on Profile (§7), with no Template-side flagging/exposing step; it predates and sits outside CR-088's Template-exposes/Profile-overrides cascade entirely (that mechanism covers Service Level, Policy, Checklist only). Its own separate gap — nothing downstream reads it to vary composed/commissioned behaviour — is tracked at Book 3 Chapter 7 §19.7's own addendum, not here and not CR-088.

- ~~Participating Organisations — deliberately left open. Owner: "Hmm, I think this should be in capability fulfilment. leave it open for now." Not addressed by this CR; revisit once Capability Fulfilment itself is designed.~~ **Superseded 2026-09-05, same day, once `organisationPackCodes` existed to check against.** Owner, looking at §12 directly: *"organisation composition is implemented as organisation packs. so no specific implementation for a profile."* Resolved — no "capability fulfilment" mechanism needed after all; §12/Participating Organisations is satisfied by the general Pack-selection mechanism (specifically the Organisation-category slot, `organisationPackCodes`, this same Part), the same way Selected Packs/Technology/Compliance/Domain already are. See Chapter 7 §19.7's own refinement (superseding its earlier "Integration Packs" mapping, written before Profile had an Organisation-category slot to point to).

## Built

Migration `173_profile_structure_completion.sql` — the four schema additions above (`deploymentTargets`, `additionalCapabilityCodes`, `engineeringPackCodes`, `organisationPackCodes`) on Profile's `schema_definitions` grammar. `core/profiles.ts`: `PACK_SELECTION_SLOTS`/`ProfileSeedInput` extended; `getProfilePackSelections`/`materialiseProfileDraft` cover the two new list_kinds; `validateProfileSeed` checks `additionalCapabilityCodes` against the real `capability-name` Ontology (same baseline as `featureFlagCodes`'s `feature-flag` check); `reactivateAsNewVersion`/`copyProfileAsNewDraft` carry `deploymentTargets`/`additionalCapabilityCodes` forward from `draft_content` the same way `compositionOptions`/`featureFlagCodes` already do. `core/sdkAuthoring.ts`'s `toProfileSeedInput` normalises both new fields. `formGenerator.ts`'s `METADATA_FIELD_NAMES` includes both new field names (the two new Pack-selection fields need no change — `PACK_SELECTION_FIELD_NAMES` already named them, added originally for Template). `web/sdkAuthoring.ts`'s `renderAuthoringForm` narrows the offered `capability-name` options for Profile specifically, per the design above.

**Not built, deliberately**: any consumption of `deploymentTargets`/`additionalCapabilityCodes` by `compositionEngine`/`commissioning.ts` — both are declared-only, the same honest limitation `configParameters`/`featureFlagCodes`/`compositionOptions` already have (Ch.7 §19.5/§19.6), and consistent with the still-open, logged-not-fixed composition-engine gap (§19.7) that the *existing* four category-scoped Pack fields already have. Building consumption for the two new Pack-selection fields while the other four remain unconsumed was deliberately avoided as inconsistent scope.

## Part 2 — Configuration Parameters (§10), design in progress, nothing built yet

Owner: *"In Ontology, create profile-configuration concept type. Section 10 examples and other similar have to be added here. There should also be concept-types for each of these. So Target cloud providers could be AWS, Azure etc. Same way Programming language can be Node, React etc."* — followed by an explicit *"Don't rush into coding. Let us design first."*

**Decision: `configParameters` (the free-form, inert JSON blob, §19.5) is retired outright**, not kept alongside the new mechanism — one real way to set a configuration parameter, not two, so nothing can drift onto a key/value pair the vocabulary doesn't recognise.

**Mechanism, revised 2026-09-05 (superseding the first pass below).** The first design (`configParameters` as a repeatable `{parameterCode, value}` row-list, `value` dynamically driven off that row's own `parameterCode`) was wrong — over-engineered for a problem that doesn't exist here. Owner, correcting it directly: *"why will this happen? If both AWS and Azure are required, each will be a separate profile, isn't it?... Environment Configuration has to be appropriately defined in the schema? why are we moving away from a schema definition for profile?"* Right: the set of configuration parameters is known and fixed (the ~9 below), not open-ended and user-chosen the way Checklist items are — a dynamic row-list (and the per-row dynamic-source-by swap it would have needed) is the right tool for an open-ended set, and the wrong one here. **Settled instead: each configuration parameter is its own explicit, named schema field on Profile** — exactly how every other Profile field already works, no generic list mechanism at all:
- `targetCloudProvider`, `primaryProgrammingLanguage`, `sourceControlProvider`, `deploymentStrategy`, `aiProviderPreference`, `defaultRepositoryStructure`, `documentationLevel`, `developmentMethodology` — each `x-widget:"referential-select"`, `x-ontology:true`, sourced from its own concept type named identically to its `profile-configuration` code (same static, direct pattern `category` used before Part 3 retired it).
- `participatingOrganisationCodes` — same pattern, sourced from `participating-organisations` (currently empty; populated when multi-tenancy is designed).
- `environmentConfiguration` — its own field, `x-widget:"json"`, identical treatment to `deploymentTargets` (Part 1) — no ontology involvement, no flag, no special-case lookup; it just is what it is, declared directly.
- `profile-configuration` (the Ontology concept type) still exists as the catalogue of what these parameters are conceptually — useful for documentation/discoverability — but doesn't drive form rendering. The fields above are declared directly, the same way Pack's six category slots are a fixed array in code (`PACK_SELECTION_SLOTS`), not generated by iterating an Ontology list at runtime.

This makes moot: the row-level dynamic-source-by extension (no row, nothing to drive), and whether a Profile could set the same parameter twice (no row to duplicate — each parameter is its own field, appearing exactly once by construction).

**Proposed seed lists** (open/extensible afterward, same as every other Ontology vocabulary on this platform — a starting set, not a closed enum):

`profile-configuration` — §10's own 7 examples, verbatim, plus two more:
`target-cloud-provider`, `primary-programming-language`, `source-control-provider`, `deployment-strategy`, `ai-provider-preference`, `default-repository-structure`, `documentation-level`, `development-methodology`, `participating-organisations`.

**`development-methodology` added 2026-09-05** — this is Ch.6 §13's own odd-one-out example ("Development methodology... doesn't map onto anything built" — CR-088's own gap analysis, and one of CR-088's three still-open "Explicitly not decided here" items: "whether Development Methodology... is a missing sixth category-scoped Pack-selection slot, or something this new configurable-parameter mechanism should carry instead"). Settled here: it's a Configuration Parameter, not a Pack-selection slot — a Profile picks a methodology the same way it picks a cloud provider or a language, not by selecting a whole Pack for it. Closes that CR-088 open item.

**`participating-organisations` added 2026-09-05** — Part 1's own "Participating Organisations — deliberately left open... I think this should be in capability fulfilment" (§5) isn't reversed by this: no dedicated Profile field is being built for it. This just gives §12's own concept a *named slot* in Configuration Parameters, with its value vocabulary deliberately empty for now. Owner: *"add this also to the configuration parameters. The values for these parameters will be populated when implementing multi-tenancy. Will be empty list for now."* The `participating-organisations` concept type gets created but seeded with nothing — real tenant/organisation identities (TCS, Cigna, in §12's own example) don't exist as a concept worth naming until multi-tenancy itself is designed; until then the parameter is declarable but has nothing to pick.

One new concept type per parameter, named identically to its own code above:

| `development-methodology` | Scrum, Kanban, Waterfall, SAFe, Lean, Extreme Programming (XP) |

**Consumption, clarified 2026-09-05.** Owner: *"SEU commissioning will use it. Profile only defines it."* This CR builds Profile's own definition/authoring side only (the named fields above) — `compositionEngine`/`commissioning.ts` reading these values to actually vary a commissioned SEU is real, intended, future work, just not part of this build. Same "declared now, consumed later by commissioning" position as `deploymentTargets`/`additionalCapabilityCodes` (Part 1) and everything §19.5/§19.6/§19.7 already track — not a new instance of the gap, the same one, now with one more field added to it.

**`environmentConfiguration` — its own field, not a special case, settled 2026-09-05.** Owner: *"environment configuration has to be a json that is free text written by the user. Similar to deployment targets."* — then, when asked how the code should tell it apart from the ontology-driven fields: *"Environment Configuration has to be appropriately defined in the schema? why are we moving away from a schema definition for profile?"* Right — with each parameter now its own named field (above), this was never a case needing a runtime flag or special-cased lookup at all. `environmentConfiguration` is just declared directly as `x-widget:"json"` in the schema, exactly like `deploymentTargets` — `SUPABASE_URL`/`DATABASE_URL`/whatever else a real deployment needs are inherently arbitrary key/value pairs, so this field simply has no Ontology concept type behind it, the same honest way `deploymentTargets` and `compositionOptions` already have none.

**Mandatory-or-not is Ontology-driven, per parameter, tenant-overridable — settled 2026-09-05.** Owner: *"let Ontology specify if a parameter is mandatory or otherwise. So a tenant can override it if required - makes sense?"* Yes — and it reuses an existing pattern rather than inventing one: `ontology_concepts` is already unique on `(concept_type, code, tenant_id)` (migration `055`), so a tenant can already shadow a Platform-seeded concept with their own row under their own `tenant_id`, and lookups already prefer the tenant's own row when both exist (`policyDefinitionsDB.findActiveByCodeVisibleTo`'s own pattern). Adding a new generic `is_mandatory BOOLEAN` column to `ontology_concepts` follows the same "generic, nullable, meaningful per concept_type" discipline `description`/`is_active` already established on that table (migrations `056`/`047`) — meaningful only for `profile-configuration` concepts, unused elsewhere.

- **Platform seeds `is_mandatory = true` on**: `development-methodology`, `primary-programming-language`, `source-control-provider`. Everything else in the list (`target-cloud-provider`, `deployment-strategy`, `ai-provider-preference`, `default-repository-structure`, `documentation-level`) seeds `is_mandatory = false`.
- A tenant disagreeing inserts their own `(profile-configuration, <code>, their-tenant-id)` row with the opposite `is_mandatory` value; it wins for them automatically via the existing tenant-preference lookup — no new override mechanism, just data.
- `participating-organisations` and `environmentConfiguration` are outside this mechanism entirely: the former has no seeded values to require yet (moot until multi-tenancy), the latter has no `profile-configuration`-concept backing at all (it's a plain JSON field, not ontology-sourced) — neither carries an `is_mandatory` flag; both stay optional by default.
- **Real new mechanism this requires**: required-ness moves off the static JSON Schema `required` array (same for every tenant, checked once) onto a per-field, per-tenant Ontology lookup — none of these ten fields appear in `schema.required` at all; `validateProfileSeed` (and the form's own asterisk-rendering) instead resolves each field's underlying `profile-configuration` concept for the authoring tenant and checks *its* `is_mandatory` flag. This is genuinely new — no other field on this platform has ever needed tenant-overridable required-ness before.

**Form placement, settled 2026-09-05: its own "Configuration Parameters" tab.** Owner: *"Yes Exposed parameters in one tab and Configuration parameters in another."* This CR's ~10 new fields get a dedicated tab, the same way Template's own configurable-parameter fields got "Exposable Parameters" (CR-088) rather than being folded into Identity & Metadata. The owner's phrasing also fixes the tab name for CR-088's own still-deferred Profile-side work (reviewing/overriding whatever Template flagged as configurable — Service Level, Policy, Checklist) once that gets built: **"Exposed Parameters"**, kept as its own separate tab, never merged with "Configuration Parameters" even though the names sound adjacent — matching this CR's own earlier point that the two are genuinely different mechanisms (§5's "commissioning parameters" vs. §10's "Configuration Parameters"). Only "Configuration Parameters" is being built now; "Exposed Parameters" stays exactly as deferred as CR-088 already left it — this only reserves its name and tab placement for when that work happens.

**§5 cross-references clarified, same pass, 2026-09-05:**
- **"Commissioning parameters" (§5) is NOT §10's Configuration Parameters.** Owner: *"commissioning parameters - these are the parameters that the template exposes."* This §5 item refers to CR-088's own Template-exposes/Profile-overrides mechanism (Service Level, Policy, Checklist) — specifically the Profile-side consuming half CR-088 explicitly deferred ("2 & 3 will get addressed when we review profile"), not the `profile-configuration` mechanism this CR is building. Two genuinely separate things sharing similar-sounding names in §5 vs §10 — worth keeping distinct going forward.
- **"Feature selections" (§5) is already ontology-driven — no gap.** Owner: *"feature selections should be ontology driven. Will defer the detailed implementation on this later."* Confirmed already true: `featureFlagCodes` has been Ontology-backed (`feature-flag` concept type, migration `065`) since 2026-08-19 (Ch.7 §19.6). Nothing to build here now; any further richness deferred, per the owner's own words.
- **§13 Versioning "should be automatic similar to pack or template" — already is, no gap.** Owner, reviewing §13 directly: *"Versioning should be automatic similar to pack or template."* Checked: `profileVersion` already carries the same `x-widget:"version"` marker `packVersion`/`templateVersion` use (migration `066`), and `generateFields()`'s own dispatch on that widget (`formGenerator.ts`) is entirely name-agnostic — Profile gets the identical readonly-field-plus-"Next version"-button behaviour automatically, new Drafts already default to `1.0.0` the same way, and §19.2 already confirmed the backend immutability/reactivation mechanics are a byte-for-byte mirror of Template's own CR-024 model. Nothing to build.
- **§14 Lifecycle and §15 Events — owner confirmed already handled, no further review needed.** Both already ✅ in Chapter 7 §19.1 (entity-direct authoring, full seven-state lifecycle, mirrors Pack/Template exactly) and §19.9 (all seven events, built 2026-08-19) — nothing new surfaced revisiting them today.
- **Several of §5's 9 items are the same mechanism wearing different labels — one Pack-selection mechanism, not several.** Owner: *"these are all packs from an implementation standpoint though the abstraction calls it out as separate items."* Selected Packs, Technology selections, Compliance selections — plus Domain selections (named in §7, not separately in §5) and Participating Organisations (§19.7's own refinement: satisfied via `organisationPackCodes`) — all resolve to the exact same category-scoped Pack-selection fields (`optionalPackCodes` + the six `<category>PackCodes` fields, Part 1). §5's prose lists them as five distinct responsibilities; the implementation has always had one mechanism underneath, parameterised by category. Of §5's 9 items, this collapses 5 of them into 1, leaving 5 genuinely separate mechanisms total: Pack selection (5 items), Configuration Parameters (`profile-configuration`, this CR Part 2), Commissioning Parameters (CR-088, deferred), Feature Selections (built), Optional Capability Enablement (Part 1).

## Part 3 — §8 Profile Categories: remove `category` entirely, not decided until now

Owner: *"Restricting the profiles to categories should not be present. Profile is not supposed to be restrictive."* §8 itself frames Startup/Enterprise/Healthcare/Banking/Prototype/Production as "illustrative examples," but the 2026-08-19 build turned that into a required, single-select classification (`category`, `profile-categories` Ontology, migration `065`/`066`) — forcing every Profile into exactly one bucket, even though §9's own inheritance example shows a Profile naturally being *several* of these traits at once ("Healthcare Enterprise Production"). Assessed and agreed: a Profile's real identity should come from what it actually selects (Packs, Configuration Parameters), not a label chosen up front.

**Decided: remove `category` entirely from use** — no longer a schema field, no longer validated, no longer authored or shown on the form. **Corrected 2026-09-05, on being asked directly**: Owner: *"profile-categories - do not delete. But do not use them."* Nothing gets dropped — the `profiles.category` database column and the `profile-categories` Ontology concept rows both stay exactly as they are, permanently, just orphaned: no code writes to the column any more, no code reads the concept type any more, and neither is deleted by a migration. (An earlier pass here said "the `profile-categories` concept type itself is retired" — that was wrong; superseded by this.)

**Registry consequence, decided:** the Profile Registry page (§19.10, currently tabbed by `category`) regroups **by base Template's code**, labelling each group using whichever Template version is currently Active for that code (owner: "whatever is active") — not the specific, possibly older version an individual Profile happens to be pinned to (§19.8's own frozen-reference design).

## Part 2 — Built

Migration `174_profile_configuration_ontology.sql` — `profile-configuration` (9 codes) + one concept type per single-value parameter (8 of them, seeded with the starter values in the table above) + the new generic `is_mandatory` column on `ontology_concepts`, seeded per the table above. Migration `175_profile_configuration_parameters_schema.sql` — `configParameters` removed from Profile's schema; ten named fields added (eight `referential-select`, `participatingOrganisationCodes` as `referential-list`, `environmentConfiguration` as `json`); `required` no longer lists any Configuration Parameter (mandatory-or-not is resolved at validation/render time, not declared in the schema).

`core/profiles.ts`: `ProfileSeedInput` carries the ten new fields; `CONFIGURATION_PARAMETER_FIELDS` (exported) maps each field to its own profile-configuration code; `validateProfileSeed` checks each set value against its own value-vocabulary concept type and enforces `is_mandatory` per the authoring tenant; `reactivateAsNewVersion`/`copyProfileAsNewDraft` carry all ten fields forward from `draft_content` (none have a real column). `core/sdkAuthoring.ts`'s `toProfileSeedInput`/`inheritedProfileContent` updated to match — the latter was also found missing `engineeringPackCodes`/`organisationPackCodes` (Part 1's own fields, never wired into inheritance) and `additionalCapabilityCodes`/`deploymentTargets`, fixed in the same pass. `formGenerator.ts` gained a `configurationParameters` field group + its own tab (`_generatedFieldGroups.ejs`, `type: 'simple'` — these are ordinary generated fields, not a bespoke grid like Template's Exposable Parameters). `web/sdkAuthoring.ts`'s `renderAuthoringForm` overrides each Configuration Parameter field's `.required` from the tenant-resolved `is_mandatory` flag before rendering, so the asterisk reflects the real, per-tenant answer. Bug fix along the way: `ontologyDB.findConcept` had no `ORDER BY` preferring a viewer's own tenant row over Platform's when both exist for the same code — silently harmless for every existing caller, but would have made `is_mandatory` resolution non-deterministic; fixed to always prefer the tenant's own row, benefiting every other Ontology-backed field too.

**Not built, deliberately**: any consumption of the ten new fields by `compositionEngine`/`commissioning.ts` (owner: "SEU commissioning will use it. Profile only defines it") — declared-only, the same position as `deploymentTargets`/`additionalCapabilityCodes` and the still-open, logged composition-engine gap (Ch.7 §19.7).

## Part 3 — Built

Migration `175` also removed `category` from Profile's schema (folded into the same file as Part 2's own schema change, since both touch Profile's schema in one pass). `core/profiles.ts`: `category` dropped from `ProfileSeedInput`, its `assertCanonicalCategory` validation removed. `profilesDB.ts`: `category`/`configParameters` dropped from `upsert`/`create`/`createDraft`/`updateDraftContent`'s signatures and SQL — the `profiles.category`/`profiles.config_parameters` **columns themselves are untouched**, just no longer written to. `core/sdkAuthoring.ts`: every Profile-branch call site rebuilding these DB calls fixed to match (`createAuthoringDraft`, `saveAuthoringDraft`, `getAuthoringDraft`, `publishAuthoringDraft`'s own seed reconstruction) — three of these were genuinely broken (still passing the now-removed parameters) until fixed in this same pass. `web/profileRegistry.ts`: Registry now groups by base Template's code (resolved per Profile via `templatesDB.findById(base_template_id)`), labelled with whichever Template version is currently Active for that code (`templatesDB.findActiveByCode`) — a new `templateCode` list-state key added to the shared `listQueryString` helper (`partials/helpers.ejs`) alongside `category`, which Pack's/Template's own Registries still use unchanged. `views/seu/profiles/index.ejs` updated to match. Test fixtures updated in the same pass (`testFixtures.ts`, `engine.test.ts`, `tenant-contract.test.ts`, `pack-sdk.test.ts`, `governance-ebm-sharpening.test.ts`, `commission-profile-choice.test.ts`) — all were calling `profilesDB.upsert`/`publishProfile` with the now-removed `configParameters`/`category` parameters.
