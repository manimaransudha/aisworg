## The gap, precisely

Grounded directly in live code and the running database — full findings written into Chapter 10 §18, its first-ever audit section (this CR's own companion). **Revised same day** — several of the first pass's own findings turned out to be intentional design, not gaps; corrected below with the owner's own framing, cross-checked against the running code.

**Database** (`capabilities` table, 8 columns): `id`, `code` (**globally unique** — `capabilities_code_key`, not Pack-scoped — still a real, unresolved gap), `name`, `description`, `category` (free text, not yet validated against anything), `originating_pack_id` (nullable — 4 real rows have none, seeded directly by early migrations), `version` (`INTEGER DEFAULT 1`, vestigial — real versioning lives on the owning Pack instead, see below), `created_at`. **No `status` column** — deliberate, not a gap: owner, "Capability is defined as a type of pack... lifecycle etc are implemented using the pack model," confirmed real: Pack already publishes a complete, named lifecycle-event set (`PackRegistered/Validated/Published/Activated/Deprecated/Retired/Archived`, `packs.ts:761-768`) and `packs.pack_version` is the real, immutable-once-published version identity — Capability's own lifecycle and version genuinely *are* its owning Pack's.

**Stability (CM-001) is real for a concrete reason, not by absence.** Owner: "overwrite is allowed only during a draft state, not otherwise." Confirmed: `sdkAuthoring.ts:728`'s `canEdit = canDefine && isDraft` gates the only real path back into `capabilitiesDB.upsertFromPack` to a Pack still in Draft — once Published/Active, the authoring form is view-only. (The core `createPackDraft`/`seedContributions` functions themselves have no independent Draft-only check — this holds because of the UI-layer gate, not defense-in-depth at the function level; worth noting, not a gap.)

**Category — dropped entirely, revised again same day.** First correction (still visible above in spirit) proposed validating against `category:pack`; owner's follow-up went further: "Field category can be dropped. code already carries the required intelligence." `category` is removed from `contributionCapabilities[]` outright, not fixed — `code` alone (e.g. `code-review`, `requirements-analysis`) is judged sufficient to convey what a Capability is, without a separate taxonomy field.

**`code`'s bare global uniqueness — a real gap, and a settled fix, not an open question.** Owner: "This is already implemented in pack model. so what is the question?" Correct — the earlier framing as "open" was overthinking it. Every downstream FK (`services`, `seu_capabilities`, `objective_capabilities`, `template_capabilities`, `dependency_definitions`) points at `capabilities.id`, a stable UUID, never at `code` directly — so scoping the *uniqueness constraint* on `code` to `(originating_pack_id, code)` touches none of them. Mechanically identical to the fix Checklist/Policy/Service already got; the larger fan-out changes how much a live collision would corrupt (motivation for fixing it), not the shape of the fix itself. Settled: same treatment, no new decision needed. No collision exists today (30 rows, 30 distinct codes) — but it does have a concrete versioning consequence worth building the fix for: since `code` stays globally unique across Pack *versions* too, an older Pack version's Capability content silently gets repointed to whichever version most recently republished that code.

**Authoring schema** (`contributionCapabilities[]`, unchanged since migration `040_pack_structured_contributions.sql`): `code`, `name`, `description`, `category` only — the same pre-CR-058 raw shape every other contribution kind had before its own CR. Zero validation beyond within-Pack duplicate `code` checking (`checkDuplicates`, `packs.ts:235`).

**Capability Relationships (§9) map onto a real, existing mechanism — Pack `dependencies[]` + Composition — genuinely partial, not unbuilt.** Owner: "this is already in terms of dependent packs within the pack. And existing packs are also extended by tenants through composition. We have still not implemented what each of the composition means, there is no check for circular dependencies yet." Confirmed: `validatePackSeed` (`packs.ts:440-443`) only gives `required` real semantics; `optional`/`conditional`/`incompatible` validate for shape only, no differentiated behaviour. Zero circular-dependency detection anywhere, despite §9's own explicit requirement. (`dependency_definitions`'s `"Capability"` entity type, checked in the first pass, is a different mechanism entirely — Deliverable-depends-on-Service, Ch.11 §18.6 — not this.) **Split out as CR-066** — shared, platform-wide infrastructure, not Capability-specific (below).

**Structure (§8) — all 6 previously-missing fields resolved, and all 6 are dropped, not built.** First asked for as in-scope-content-pending; owner's follow-up, field by field:
- **Supported Participant Types** — dropped. "particpants are AI and humans always. it's already modeled — at a finer grain than Capability. Ch.5 §19.3's three classifications (Machine-verifiable / Judgment / Human-attested)." Participant type at the Capability level would be both near-trivial (AI/Human, always) and the wrong grain — the real, meaningful signal already lives one level down, on each verifiable item's own `classification` (§20's `VerifiableItemFields`, shared across Checklist/Quality Gate/Review Gate/Obligation items already).
- **Success Criteria** — dropped. "Policy is the what, Quality Gate is the where/when it gets checked. That pairing is what 'Success Criteria' was trying to name as a single Capability-level field." Already fully expressed by the existing Policy (declares the condition) + Quality Gate (declares which transition it's checked against) pairing — a separate Capability-level field would be redundant with a mechanism that already exists and already works.
- **Inputs, Outputs, Required Knowledge, Expected Deliverables** — all four dropped together. "These are determined at template authoring and not at capability authoring." A Capability is reused across many different Templates/SEUs; what it consumes/produces in a specific engineering context is a Template's own Deliverable Catalogue/dependency-graph concern (Ch.6), not a fixed property of the Capability itself.

Net: Capability Structure (§8) settles at just **Identifier, Name, Description** — 3 of the chapter's 10 named fields, with Category also dropped (above). Every other named field maps onto a mechanism that already exists somewhere else in the platform, at a more appropriate grain.

**Events (§14) — confirmed not a gap for the definition-lifecycle ones.** Owner: "I already said events will be tracked as pack events except for Capability Fulfiled." Confirmed: Pack's own real event set (above) covers Registered/Updated/Deprecated by design. `CapabilityFulfilled` (`capabilities.ts:70-77`) is the one genuinely Capability-specific runtime fact, and it's real. `CapabilityRequested`/`Unavailable`/`Released` remain genuinely unbuilt — runtime fulfilment-state events, not definition-lifecycle ones, so the Pack-events reframing doesn't cover them. Deferred to execution-side work, not this CR (below).

**Capability Evolution's Obligation-driven loop (§13) is the same half-real shape Ch.23 §19.9 already found** — Telemetry→Obligation is real; nothing turns a resolved Obligation into an actual new Pack/Capability version. Owner: "Obligation to Capability is open and to be addressed later" — acknowledged, real, explicitly deferred (below), not this CR's job.

**Two genuine positives, unaffected by this revision**: Capability Fulfilment (§10) and Selection (§12) are both real and match the chapter closely. Discovery-by-objective (`objectivesDB.getRequiredCapabilities`) and discovery-by-Pack are both real, working query methods.

## Design, as settled

- **No independent lifecycle/status for Capability** — confirmed intentional, not a gap. Deprecation/retirement happens by deprecating the owning Pack.
- **No independent versioning for Capability** — confirmed intentional. `packs.pack_version` is the real mechanism; `capabilities.version` becomes a denormalized copy of it (owner: "capabilities.version just copies over the pack's version"), kept in sync on every upsert — not independently incremented.
- **Category — dropped entirely.** `code` alone carries the required intelligence; no replacement field, no Ontology validation to wire up.
- **Supported Participant Types — dropped.** Already modeled at a finer grain, on each verifiable item's own `classification` field.
- **Success Criteria — dropped.** Already fully expressed by the existing Policy + Quality Gate pairing.
- **Inputs, Outputs, Required Knowledge, Expected Deliverables — all four dropped.** Template-authoring concerns (Ch.6's own Deliverable Catalogue/dependency graph), not Capability-authoring ones.
- **Net Capability Structure**: Identifier, Name, Description only — `contributionCapabilities[]`'s real, final field set (beyond `capabilityCode` linkage on the contributing side, unchanged).
- **Events** — no change needed for the definition-lifecycle ones (Pack events already cover them). `CapabilityRequested`/`Unavailable`/`Released` deferred to execution-side work (below).
- **`code`'s identity scope — settled, not open.** `(originating_pack_id, code)`, same mechanical fix Checklist/Policy/Service each got — no FK anywhere references `code` directly (all go through the stable `id`), so this doesn't touch anything else. Owner: "This is already implemented in pack model."

## Deferred, not this CR's job — all 3 resolved as out-of-scope, not open questions

Runtime-fulfilment events, deferred to whenever execution-side work on Capability Fulfilment is picked up — not a separate CR right now, just explicitly not part of this definition-side CR.

Acknowledged, real, explicitly deferred — same platform-wide Composition Engine gap Ch.23 §19.9 already found for Obligation→Pack generally; not this CR's job, and not yet scheduled anywhere else either.
