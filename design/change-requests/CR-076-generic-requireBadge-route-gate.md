### The gap today, verified against the live code

Three separate files each hand-roll the identical "resolve this request's held badges" logic from scratch:

- `web/objectives.ts` — `getObjectiveViewerContext(req)`: queries `badgeGrantsDB.findActiveForHolder`, builds a `Set<string>`, checks for `root`, then derives `canRetireObjective`/`canProposeObjective`/`canComment`/`hasObjectiveBadge(verb)`.
- `web/sdkAuthoring.ts` — its own `heldBadges(req)` (near-identical query/Set/root-check), plus `canWriteAuthority(req)` and `requireAuthorityAdmin` (a bespoke, one-off Express middleware that just calls `canWriteAuthority` and denies).
- `web/ontology.ts` — its own third `heldBadges(req)` copy.

Each copy is correct on its own, but the duplication is exactly what it looks like: nobody shares the query, the Set-building, or the root-bypass check. Two consequences, both real and both already observed this session:

1. **Routes ship with no badge check at all, silently.** `POST /objectives` (create) and `GET /objectives/new` had zero badge enforcement until a very recent, separate fix — nothing forced anyone building those routes to even ask the question. `deleteObjective`/`createObjective` still run no `transitionEngine`/`badgeAuthorityEngine` check at the core-function level (CR-071's own "gap today" section flagged this as a known, accepted gap — badge gating on those two is UI-only, by design, today).
2. **The one existing generic gate, `requirePlatformBadge` (`middleware/requirePlatformBadge.ts`), doesn't fit this case.** It's built for the small, fixed, three-code Platform vocabulary (`root`/`tenant_admin`/`viewer`) and is a pure binary route gate: one static `badgeCode`, request proceeds or is denied, done at the top of one route. The noun × verb vocabulary (`${entity}_${verb}`, CR-006) is dynamic and typically needs *several* different badges resolved for one single page render (which buttons show), including per-row checks inside a list where the verb differs row to row (`hasObjectiveBadge(node.nextTransitionVerb)` in `_nodes.ejs`'s tree loop) — a single static-string gate middleware can't express that on its own.

### The rule, as specified (owner)

1. **Every route** — no exceptions, no silent omissions — is preceded by a `requireBadge([...])` declaration.
2. `requireBadge(['None'])` is a real, explicit, visible value meaning "no badge required to reach this route's execution" — not an *absence* of a check, but a positive, reviewable statement that this route was deliberately left open. A view/list route that's readable by anyone still writes this, so a reviewer (or the next person touching the file) sees the authority decision was made on purpose, not skipped.
3. `requireBadge(['badge_a', 'badge_b'])` means the actor must hold those badge(s) to reach the route's execution — **settled (owner): AND, not OR.** All listed badges are required; there is no built-in "any one of these" shape. A route whose real requirement is "any one of a family" (e.g. today's `canComment` — "root, or at least one `objective_*` badge") doesn't fit this array and needs its own resolution when it's converted (see the `objectives.ts` conversion notes) — most likely its own dedicated verb/badge rather than an OR-list, consistent with point 5 below.
5. **Settled (owner): a route handler that would need different badges depending on the request is a design smell, not a case for `requireBadge` to accommodate.** "One function cannot do multiple things requiring different badges. They have to be split." A generic, multi-target route like today's `POST /objectives/:id/transition` (Achieve, Supersede, Retire, or Reject, chosen by `req.body.targetState`, each needing a different `objective_<verb>` badge) must be split into one route per governed action, each with its own single, static, honest `requireBadge([...])`. This is a real, structural rollout item for `objectives.ts` (see below), not just a middleware-adoption exercise.
6. **Button visibility stays a separate, hardcoded, per-page concern** — explicitly *not* part of this CR's scope. `hasObjectiveBadge(verb)`-style closures used to decide what a page renders keep being written by hand, per page, as they are today. The reason given: the route-level `requireBadge` check is the actual safety net — if a button is ever wrongly shown (a UI bug, a stale render, a direct URL/POST), the route itself independently re-verifies and refuses. Centralizing button-visibility logic is a different, smaller problem than this CR, and conflating the two risks turning `requireBadge` into a page-rendering framework instead of a route gate.

### Extended scope (owner, same session): tenant-scope checks get the same treatment

"I am thinking even tenant id checks that we have in the code has to be directed through a middleware. The db level checks are okay, but any scope check we do should hardcoded in the code also has to be a common middleware."

This is a second, parallel axis to badge authorization (which *action* an actor may attempt) — tenant scope is *which row* an actor may reach at all — but the same complaint applies: it's currently hand-written per file, not shared. Grounded against the live code, there are two distinct shapes, both in `web/objectives.ts` today:

1. **The URL-param shape** — `router.param("id", ...)`: given the `:id` already in the route path, look up that row, compare its `sponsoring_authority.tenant` against the viewer's own tenant, and respond "not found" (never a distinguishable 403 — never confirms another tenant's row exists) on a mismatch or a null on either side ("NULL never matches," the fail-closed rule already established for this). This one is *already* middleware-shaped (it's a real `router.param` callback) — it just isn't generic or reusable; it's hand-written once, specifically for Objective's own `sponsoring_authority` field.
2. **The referenced-entity shape** — `GET /objectives/new?parent=<id>` and `POST /objectives` (create): the entity to check isn't the route's own `:id`, it's a *different* row named by a query-string or body field (`parentObjectiveId`). Same underlying check (resolve the row, compare tenants, fail closed), but it can't hang off `router.param` since it's not a route parameter.

**Proposed (not yet confirmed by owner)** — a `requireTenantScope` pair mirroring that split, both built on one shared "does this row's tenant match this viewer's tenant" primitive:
- `requireTenantScope.forParam(paramName, lookup)` — generalizes the existing `router.param("id", ...)` gate so any router can declare it in one line instead of hand-writing the comparison.
- `requireTenantScope.forField(source, fieldName, lookup)` — the referenced-entity shape (`source` is `"query"` or `"body"`), covering the `?parent=`/`parentObjectiveId` case and any future one shaped like it.

`db-level` filtering (e.g. `objectivesDB.findAll(tenantId)`'s own `WHERE sponsoring_authority->>'tenant' = $1`, used for list/search scoping) is explicitly **not** touched — the owner's own words: "the db level checks are okay." This is only about the hand-written, in-application-code comparison checks.

### What this does *not* change

- The underlying primitives: `badgeAuthorityEngine.authorise({ actorId, requiredBadge })` (root bypass + live `badge_grants` lookup) for badges, and each entity's own `sponsoring_authority`-style tenant comparison for scope. `requireBadge`/`requireTenantScope` are thin, generic wrappers around these; neither reimplements authorization/scoping logic.
- `requirePlatformBadge` — untouched. It already correctly serves the small, fixed Platform-badge vocabulary and its own three call sites (Pack Registry, Identity screens). `requireBadge` is a parallel, separate mechanism for the noun × verb vocabulary, not a replacement.
- DB-level tenant filtering in list/search queries (`objectivesDB.findAll`/`findRootsPage`'s own `tenantId` parameter) — owner: "the db level checks are okay."
- Button-level visibility logic (see point 6, above) — stays hand-written, per page.

### Design considerations found while grounding this against the live model

1. **The reusable primitive already exists conceptually — it's just not shared.** `ontology.ts`/`objectives.ts`/`sdkAuthoring.ts`'s three copies of `heldBadges(req)` do the same three things every time: resolve `actorId` from the session, call `badgeGrantsDB.findActiveForHolder(actorId)`, build a `Set<string>` of `badge_type`, and special-case `root` (via `session.user.platformBadges.includes('root')`, per CR-071's own corrected finding that `platformBadges` can never hold a noun_verb badge — only the flat Layer-1 codes). `requireBadge` should be built on top of one single shared function doing exactly this, once, rather than each route re-deriving it.
2. **A route needing "any one of several badges" is a real, existing shape, not hypothetical.** `getObjectiveViewerContext`'s `canComment` is already exactly this: "holds root, OR holds at least one `objective_*` badge" — an OR across a whole family. Whether `requireBadge(['a', 'b'])` should default to AND or OR (or need an explicit marker for each) is the biggest open question below — real examples exist on both sides and guessing wrong here means redoing every call site.
3. **A single route can require a *different* badge depending on the request, not a fixed set known at route-registration time.** `POST /objectives/:id/transition` is one route, but it can target Achieve, Supersede, Retire, or Reject — four different `objective_<verb>` badges — depending on `req.body.targetState`. `transitionEngine.evaluate` already resolves the exact required badge dynamically, per attempt (`${entityType}_${definition.verb}`, `transitionEngine.ts:79-83`), and is arguably already `requireBadge`'s real safety net for that specific route today. A static, route-registration-time `requireBadge([...])` array can *describe* the family of badges this route can ever require (useful for the "reviewable declaration" goal), but can't by itself *enforce* the one that actually applies to a given request — that still needs either a request-aware variant of the middleware, or an acknowledgment that `transitionEngine.evaluate`'s own dynamic check already *is* this route's real gate and `requireBadge` here is documentation-plus-coarse-filter (e.g., "must hold at least one Objective badge") rather than the final word.
4. **Denial behavior needs both a web (redirect + flash) and an API (JSON status) shape**, exactly like `requirePlatformBadge` already branches on `req.method !== 'GET'`. If `requireBadge` is meant to gate `api/` routers too (CSRF-exempt, JSON-only), it needs the same two-shape denial `requirePlatformBadge` already has, not just the web-flash version the current `heldBadges` copies use informally.
5. **This is a large, cross-cutting change if taken literally as "every route."** A non-exhaustive count of `router.get`/`router.post` across `web/` and `api/` is in the dozens of files. Doing this as one pass risks becoming exactly the kind of sweeping, hard-to-review change this codebase's own working style avoids. A staged rollout (mechanism + one reference router first, the rest as tracked follow-up) is the more likely shape, but that's the owner's call, not mine to assume.

### Not in scope for this CR

- Rewriting button-visibility logic anywhere — stays hand-written per page (owner's own explicit instruction).
- Changing `requirePlatformBadge` or its three Platform-badge call sites.
- DB-level tenant filtering in list/search queries (owner: "the db level checks are okay").
- Retrofitting `transitionEngine`/`badgeAuthorityEngine` checks onto routes that structurally don't have one today (`createObjective`, `deleteObjective`) — `requireBadge` can gate the *route*, but making the *core function* itself governed is a separate, previously-flagged gap (CR-071) this CR doesn't resolve on its own, though it would likely surface it more visibly once every route has to state its badge requirement out loud.

2. A route needing different badges per request is split into one route per badge, not accommodated by a dynamic/resolver form.
3. Rollout: build the mechanism, convert `objectives.ts` (web) as the reference router first; the rest of `web/`/`api/` is tracked follow-up, order/pace to be set later.

### Open questions (remaining)

1. **The `requireTenantScope.forParam`/`.forField` split above is my own proposal, not yet confirmed** — in particular whether "referenced entity named by a field" needs to generalize beyond Objective's own `parentObjectiveId` case at all right now, or whether that one call site can just stay a direct, local check until a second real example shows up.
2. **Web routers, API routers, or both?** `requirePlatformBadge` already handles both shapes (redirect+flash vs. JSON 403). This rollout starts on `routes/seu/web/objectives.ts`; whether/when `routes/seu/api/*` follows is open.
3. **Where do the shared primitives live?** A new module (`middleware/requireBadge.ts`, `middleware/requireTenantScope.ts`, plus a shared "resolve held badges for this request" helper) — replacing `ontology.ts`/`objectives.ts`/`sdkAuthoring.ts`'s three separate `heldBadges` copies. Exact naming/location settled during the build, not blocking on it.
