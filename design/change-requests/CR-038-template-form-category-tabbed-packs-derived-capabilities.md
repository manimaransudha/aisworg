# CR-038 — Template form: category-tabbed Pack pickers, derived Required Capabilities, Ontology-backed Deliverable Catalogue

**Raised:** 2026-08-20 · **Origin:** owner, notes.md — "Changes to the template form (new CR). Code, Name, Purpose, Template Version - no changes. The next field to show is the pack categories (Engineering, Domain etc.)... For each of the categories, there will be a multi-select dropdown. The dropdown should have active platform + tenant ones for the particular category. The Required Capability codes need not be an UI field. It is derived from the selections the user makes. The next field should be Deliverable Catalog. This should be a multi select dropdown and the values will be the ones from Ontology." · **Status:** ✅ Built 2026-08-20

> **Built 2026-08-20.** Sequenced after CR-039 (canonical dependency engine), CR-041 (self-referential authoring widget), and CR-043 (polymorphic owner) — all three were genuine prerequisites, not just nice-to-haves: CR-041's `dependencyGraph` field is what let this CR drop `deliverableCatalogue`'s embedded dependency codes entirely, and CR-043's owner model is what makes the whole authoring pipeline coherent going forward.

### What changed

**1. Pack selection, category-scoped (mirrors Profile's own `list_kind` model exactly).** `mandatoryPackCodes` (one flat `referential-list`) replaced by six category-scoped fields — `compliancePackCodes`/`domainPackCodes`/`engineeringPackCodes`/`integrationPackCodes`/`organisationPackCodes`/`technologyPackCodes` (migration 078) — the full `category:pack` vocabulary, not just Profile's four optional-supplement categories, since a Template's mandatory Packs can span any of them. Storage mirrors Profile's `list_kind` discriminator precisely: `template_packs` gained a `list_kind` column (migration 077); `templatesDB.setPackSelection`/`getPackSelection` are new scoped primitives; `setMandatoryPacks` became a thin wrapper over the `'mandatory'` slot instead of an unfiltered delete (a real bug fix in passing — the old unfiltered delete would have wiped category-specific rows if both were ever touched for the same Template). `getMandatoryPackCodes` (unfiltered) stays the "every mandatory Pack regardless of category" convenience composition/commissioning already relied on.

**2. `requiredCapabilityCodes` — fully derived, no UI field at all, not even readonly.** `deriveCapabilityCodesFromPackCodes` (`core/templates.ts`) resolves the selected Pack codes to their Active rows, then every Capability they contribute (`capabilitiesDB.findByOriginatingPackIds`, new). Wired into `publishTemplate`, `materialiseTemplateDraft`, the two seed scripts that build Templates through their own direct path (`seedSdlcStandardTemplates.ts`, and `tests/testFixtures.ts`'s shared fixture), and the web route's own live render-time picker options for `producingCapabilityCode` (below) — one function, every caller.

**3. Deliverable Catalogue — Ontology-backed, `code` dropped entirely (migration 079).** `deliverableCatalogue` moves from `x-widget: "json"` to a real `referential-list`: `name` picked from the `deliverable-name` Ontology concept (23 codes, seeded since migration 048, genuinely zero consumers until now), `category` from `category:deliverable`, `producingCapabilityCode` from whichever Capabilities the Draft's *currently selected* Packs actually derive (live, not stale — re-resolved on every render). `TemplateDeliverableSeed.code` is gone outright: `name` is the real identity now (matches `deliverables.name`/`dependency_definitions` throughout the runtime system), and `code` had no remaining functional use once `dependencyGraph` moved to name-based cross-references (see the bug fix below) — commissioning's own use of it was purely a diagnostic report-list convenience, now name-keyed instead.

**4. A new resolver class in the web route (`sdkAuthoring.ts`)**, alongside the existing `loadReferentialOptions`/`loadOntologyOptions`/`loadSelfReferentialOptions` (CR-041): Ontology-backed item-field sources (`deliverable-name`, `category:deliverable` — submitting the concept's `default_label`, not its code, since the value has to become `deliverables.name` at runtime) folded into `loadReferentialOptions` itself; a new `loadDerivedPackCapabilityOptions` for `producingCapabilityCode`, computed live from the Draft's own currently-posted Pack selections. No change to the rendering layer (`_referentialListGroup.ejs`/`formGenerator.ts`) at all — every one of these is just another key in the same `referentialOptions` dictionary the existing `x-referential` mechanism already reads from.

### Real bug found and fixed along the way (not in the original plan)

Building this surfaced a genuine defect in CR-041's own shipped code: the live widget's self-referential `dependencyGraph` picker posts `{toName, fromName}` (matching `deliverableCatalogue`'s own `.name` values, since that's what `loadSelfReferentialOptions` populates its options from) — but `TemplateDependencyGraphEntry`/`materialiseDependencyGraph` expected `{toCode, fromCode}`. CR-041's own smoke test only verified the GET-rendering half (that the dropdown populates), never a real POST→materialise round trip, so this went uncaught at the time. Fixed at the root, not patched around: `TemplateDependencyGraphEntry` now uses `toName`/`fromName` throughout, `materialiseDependencyGraph` does direct name-membership validation (no code-to-name resolution step needed — `dependency_definitions` was always name-keyed anyway), and all 11 seed Templates' `dependencyGraph` arrays were converted from codes to names. `validateTemplateSeed`'s referential checks were updated to match.

### Retrofit — seed JSON corrected directly, consistent with CR-041's "no bridge" precedent

All 11 Template seed JSON files: `deliverableCatalogue` entries lost their `.code`; `dependencyGraph` entries converted from `toCode`/`fromCode` to `toName`/`fromName` (the bug fix above). 10 of 11 files (the 9 CR-034 standard Templates + `web-application`) also had their now-redundant `requiredCapabilityCodes` field removed — **verified, not assumed**: queried the live `template_capabilities` rows after a real `db:clean-slate` run and confirmed the derived set matches the previously-explicit list exactly, for every one of the 9. `ebook-library.template.json` and its own seed script were deliberately left untouched — `domain-ebook-library`'s real contributed Capabilities aren't currently verifiable in this database (the Pack isn't Active), and this script has no test coverage to catch a silent mismatch, so changing its derivation behavior wasn't a safe call to make blind.

### Verification

- `npx tsc --noEmit` clean throughout every step.
- Full suite: **149/149** passing after each phase (Pack categorization, derived capabilities, the toName/fromName bug fix, the Ontology-backed catalogue).
- `pnpm db:clean-slate` run live repeatedly across the build — including the specific check above comparing derived vs. previously-declared Capability sets for all 9 CR-034 Templates.
- **Live HTTP smoke tests** (in-process `app.listen` + real session, same harness as CR-041's own): a Draft seeded with a real Pack selection (`engineeringPackCodes: ["platform-core-engineering"]`) and one catalogue entry (`Requirements Specification` / `Documentation`) → its edit page correctly pre-selects both Ontology-backed fields, and `producingCapabilityCode` correctly offers exactly the three Capabilities that Pack derives (`architecture`, `development`, `requirements-analysis`) — proving the live derivation, not just the static rendering.

### Not in scope

- Cycle detection over `dependencyGraph` — still parked at CR-041/CR-039's own authoring-time-widget framing, not built here either.
- Retrofitting `ebook-library` onto derived capabilities — deliberately deferred (see above); its own script still reads the explicit JSON field.
- Any Pack-side or Profile-side reuse of the new Ontology-backed/derived resolver patterns — Template is the only caller so far, though the mechanism (another `referentialOptions` key) is exactly as generic as CR-041 left it.
