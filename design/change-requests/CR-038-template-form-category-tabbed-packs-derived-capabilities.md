# CR-038 — Template form: category-tabbed Pack pickers, derived Required Capabilities, Ontology-backed Deliverable Catalogue

**Raised:** 2026-08-20 · **Origin:** owner, notes.md — "Changes to the template form (new CR). Code, Name, Purpose, Template Version - no changes. The next field to show is the pack categories (Engineering, Domain etc.)... For each of the categories, there will be a multi-select dropdown. The dropdown should have active platform + tenant ones for the particular category. The Required Capability codes need not be an UI field. It is derived from the selections the user makes. The next field should be Deliverable Catalog. This should be a multi select dropdown and the values will be the ones from Ontology." · **Status:** 🟡 Proposed (not scheduled)

### Current state (verified against the live schema, migration 062's version-latest grammar)
- `mandatoryPackCodes` — already `x-widget: "referential-list"`, `x-referential: "pack-code"` — one flat multi-select across every Pack, not grouped by `category:pack` (Compliance/Domain/Engineering/Integration/Organisation/Technology).
- `requiredCapabilityCodes` — `x-widget: "json"`: a raw JSON-array textarea (`["requirements-analysis", ...]`), hand-typed, no dropdown, no derivation from anything else on the form.
- `deliverableCatalogue` — `x-widget: "json"`: a raw JSON-array textarea of `{code, name, category, producingCapabilityCode?, dependsOnDeliverableCodes?[], dependsOnCapabilityServiceCodes?[]}` objects (Ch.6 §7/§10).
- `deliverable-name` is already a real, seeded Ontology concept type (migration 048, 23 codes: Requirements Specification, Solution/Architecture Document, Source Code, …) — seeded in anticipation of exactly this, per its own migration header ("nothing reads concept_type='deliverable-name'" at the time) — never wired into any real form until now.

### Proposed design
1. **Code / Name / Purpose / Template Version** — unchanged.
2. **Pack selection, tabbed by `category:pack`** — one horizontal (or vertical, matching CR-027's own precedent) tab per Ontology `category:pack` value actually in use; each tab holds a multi-select scoped to that category, sourced from `packsDB.findActiveVisibleTo(viewerTenantId)` filtered to that category — Platform's own Active Packs plus this tenant's own, mirroring the visibility model CR-035 just made canonical elsewhere. Mechanically this reuses `_referentialListGroup.ejs`'s existing `x-referential: "pack-code:<Category>"` suffix-filter (built for Profile's technologyPackCodes/domainPackCodes/compliancePackCodes/integrationPackCodes, CR-028) — six new schema properties (one per category) replacing the one flat `mandatoryPackCodes` field, OR one field per *category actually present* if some never apply to a Template. Open question below.
3. **Required Capability codes — derived, no UI field.** On save/publish, the real `requiredCapabilityCodes` is computed as the union of every selected Pack's own contributed Capability codes (`templatesDB.getRequiredCapabilities`-style resolution, but computed from the *selection*, not read back from a prior save) — the field stops being independently editable; whatever a human typed into the old JSON textarea is no longer the source of truth.
4. **Deliverable Catalogue — Ontology multi-select.** Each entry's `name`/`code` comes from picking one or more `deliverable-name` concepts (multi-select, Ontology-backed, same generic `referential-select`/`referential-list` mechanism as everything else) instead of hand-typing JSON. Open question below on how much of the entry (category, producingCapabilityCode, dependency wiring) is still manually configured per selected deliverable vs. defaulted/inferred.

### Open questions (not decided — need the owner's call before scoping a build)
- **One flat `mandatoryPackCodes` list still stored, or a genuine per-category split** (mirroring Profile's `list_kind` model — optional/technology/domain/compliance/integration)? The form UI is category-tabbed either way; this is about the *stored* shape.
- **Deliverable Catalogue entries beyond the name** — does picking "Requirements Specification" from Ontology fully populate the entry (category/producingCapabilityCode defaulted from some convention), or does the form still need a secondary per-entry configuration step (which capability produces it, what it depends on)? The current JSON shape carries real dependency-graph information (`dependsOnDeliverableCodes`, `dependsOnCapabilityServiceCodes`) that a bare multi-select doesn't obviously replace.
- **Which existing Templates need retrofitting** — `web-application`, `ebook-library`, the 9 CR-034 standard category Templates, and the SDK's own bootstrap-adjacent ones all currently have hand-set `requiredCapabilityCodes` that would need to reconcile with (or be silently recomputed by) the new derivation rule.

### Not in scope (yet)
- Build. This CR is a proposal only, per the owner's own "(new CR)" framing — matches CR-030/031's precedent (a design write-up first, scope/phasing confirmed before implementation).
