## The gap, precisely

Grounded directly in live code and the running database (full findings also written into Chapter 24 §19, its first-ever audit section).

**Database** (`policies` table): `id`, `code` (globally unique — `policies_code_key`), `name`, `category` (free text, default `'Engineering'`), `constraint_type` (`CHECK IN ('Policy','Standard')` — real, matches §8/PM-007), `governed_transition` (free text), `condition` (`JSONB`, default `{"type":"always_true"}`), `severity` (free text, default `'Medium'`), `originating_pack_id`, `created_at`. **No `version`, no `is_active`, no lifecycle column at all.**

**Authoring schema** (`contributionPolicies[]`, live-queried): exposes only `code`, `name`, `severity`, `constraintType`, `governedTransition`. **`category` and `condition` are real DB columns but aren't even authorable fields on the form.** No `x-referential`/`x-ontology` anywhere, no `x-property-order`, no per-field help — the pre-CR-058 raw shape.

**Against Chapter 24 §8's Policy Structure** (Identifier, Name, Description, Category, Constraint Type, Applicability, Conditions, Required Evidence, Related Obligations, Exception Rules, Severity, Version, Originating Pack):
- Built: Identifier, Name, Constraint Type, Severity, Originating Pack.
- Real column but not author-visible: Category (free text, no Ontology backing), Conditions (`evaluateCondition`/`policyCondition.ts`, 2 real types — `always_true`/`field_in` — but every Pack-authored Policy silently gets `always_true`, since the form never exposes the field).
- Missing entirely, confirmed via direct search — zero references anywhere: Description, Required Evidence, Related Obligations, Exception Rules. No exception/waiver mechanism exists (Quality Gate's `quality_gate_waivers`, CR-058, is the closest existing precedent — not reused here).
- Missing: Version — `policiesDB.upsert` is `INSERT ... ON CONFLICT (code) DO UPDATE`, an in-place overwrite with **no history preserved**, contradicting §13 ("Historical Policies shall remain available for engineering reconstruction").

**The most consequential finding — `governedTransition` is write-only, confirmed live.** The only read of `policies.governed_transition` anywhere in the codebase besides the upsert itself is `governanceModel.ts`'s own display list — never `transitionEngine.ts`'s real evaluation path. Real attachment of a Policy to a governed transition happens entirely on the *other* side: `transition_definitions.required_policy_ids` (`UUID[]`), populated exclusively from `transitionDefinitions.json`'s own `requiredPolicyCodes` at transition-definition seed time (`seedTransitionDefinitions.ts`) — a mechanism no Pack author can reach through Pack authoring at all.

**A Pack-contributed Policy's own declared `governedTransition` does nothing. The Policy only actually enforces anything if a completely separate, non-Pack-authorable seed file happens to reference its `code`.** This directly undercuts §9 ("Applicability shall be evaluated dynamically" — applicability today is static, baked into the Transition Definition at its own seed time) and sits in real tension with FR-24.2 ("Policies shall be contributed through Packs" — contributed, yes; functionally connected, no).

**Composition/conflict detection (§10, FR-24.7)**: `compositionEngine.ts`'s `detectGovernanceConflicts` treats a same-`code` collision as Override (last-wins, a warning) and explicitly treats multiple *different* co-applicable Policies as non-conflicting by design (own code comment: "multiple policies co-apply (not a conflict)"). No content-level conflict detection exists.

This is a substantially larger gap than Quality Gate, Review Gate, or Checklist had — those three each needed real structure added on top of a working foundation; Policy's foundation itself (identity/versioning, and the applicability mechanism connecting it to anything real) doesn't match the chapter's model yet.

## Design, as settled

All open questions resolved through direct discussion (2026-08-23). Nothing built yet.

### The governing principle: Policy doesn't evaluate anything; it states what a Gate should govern
Owner: *"Policy does not evaluate anything. It only states what the quality gate should govern."* Policy is a passive, declarative, domain-agnostic rule. It has no built-in awareness of Evidence, Obligations, or anything else — that meaning comes entirely from whichever Gate references it and what context it evaluates against. This principle is what several of the settlements below fall directly out of.

### Definition vs execution — the scope boundary for this whole CR
Owner: *"anything in the pack like a policy, review gate etc has a definition part and an execution part. So the definition is tied to a pack... When the execution happens, it is tied to an seu id and we are not addressing this here."* CR-061 stays entirely at the Pack-authoring/definition layer — schema, table, `validatePackSeed`, the SDK form. Whatever actually *consumes* these fields at runtime (a real transition attempt being evaluated against a real SEU) is execution, explicitly out of scope, same deferral discipline CR-060 applied to Checklist's own execution.

### Category — new Ontology concept type `category:policy`
Owner: *"category should be ontology driven. The policy categories are in section 7. Seed these categories as category:policy and category in policies form should be a dropdown."* Unlike Quality Gate (`category:evidence` reused) and Review Gate (`deliverable-name` reused), Policy gets its **own new concept type**, seeded with Chapter 24 §7's own 7 illustrative categories: Engineering, Security, Quality, Operational, Documentation, Customer, Organisation. `category` becomes a real, Ontology-backed referential-select on the authoring form (`x-referential-source: "category:policy"`, `x-ontology: true`), not free text.

**Fully independent of any Gate's own category — confirmed explicitly, not assumed.** Owner: *"quality gates have an evidence category. So policies are corresponding to a gate category. It does not change the policy category. So I can have a customer sign off policy category across any gate category."* A Policy's `category:policy` value never needs to match, or even relate to, the `category:evidence` value of whichever Quality Gate references it — a "Customer" (§7) Policy can be required by a gate of any category.

### Identity and versioning — same treatment as Checklist
Owner (via the definition/execution principle above): Policy's definition lives in a Pack, isn't global, so no independent version/lifecycle — matching CR-060's own settled treatment of Checklist exactly. **`policies_code_key UNIQUE (code)` is itself wrong** — it should be scoped like Checklist's `(originating_pack_id, name)`, so two different Packs can each declare their own Policy sharing the same `code` without colliding. `id` stays stable across a republish of the same Pack (upsert in place, same `checklistsDB.upsert`-style `ON CONFLICT` mechanism) — no `version`/`is_active` columns, matching why Checklist needed none: `transition_definitions.required_policy_ids` and Quality Gate's own `requiredPolicyCodes` (below) hold a Policy's real `id` as a stable external reference, and a stable id is exactly what avoids that reference going stale on every content change.

### Cross-Pack reach — scoped to matching Pack code, same as Checklist
Owner: *"Similar to checklist, if the pack code matches, that policy has to be visible to all other packs."* A Quality Gate's `requiredPolicyCodes` (below) can reference a Policy belonging to a Pack sharing its own `code` (any version/tenant) — not any Pack unconditionally, and not same-Pack-only either. Identical scoping rule and identical reasoning to Checklist's own corrected reach (CR-060).

### `governedTransition` — fixed to be real and validated; NOT made functionally live in this CR
Owner: *"the governed transition should be similar to what is in the quality gate (transition definitions in the ontology)."* Becomes a real `"EntityType|fromState|toState"` value, picked via the same `x-referential: "transition-definition"` picker Quality Gate/Review Gate already use, validated against real `transition_definitions` rows at publish time (same `parseGovernedTransition` parsing).

This is a *narrower* fix than it first looked. Quality Gate's own live evaluation has two paths — `qualityGatesDB.findAllActive(entityType, fromState, toState)`, a dynamic, self-contained lookup by the gate's own declared slot, and `transition_definitions.required_policy_ids`/`required_quality_gate_ids`, an explicit external reference. Whether Policy gains the *first* kind of path (the engine actually querying `policies` by their own declared slot, closing the "vestigial field" finding) is execution — per the definition/execution boundary above, **not part of this CR**. This CR only fixes the field's own shape and validation; it stays functionally inert, exactly as it is today, until whatever picks up execution wires it in.

### Required Policies — Quality Gate's `requires_active_policy` generalizes, not Policy itself
Owner: *"Required policy code comes into play only when quality gate criteria type is 'requires_active_policy'"* — confirming this stays scoped to that one existing criteria type, not a new parallel mechanism. Owner, on the actual generalization: *"(1) is right"* (accepting the proposed reading below). `requiredPolicyCode` (a single string) becomes `requiredPolicyCodes` (an array) plus a threshold (all / percentage) — *"we may add more types and each type may lead to some code change to the governance of the gates."* The aggregation logic — evaluating each referenced Policy's own `condition`, `constraint_type`, and `severity` to decide whether the threshold is met — lives entirely on the **Gate's own criteria evaluation**, execution-side, deferred. Nothing about this generalization touches Policy's own structure; Policy stays a single, standalone declarative rule regardless of how many Gates reference it or how.

### `severity` / `constraintType` — unchanged
Both already exist as real columns and are already authorable on the form. Owner: *"leave them as is."* Their actual behavioral role (whether a violation blocks, how much a deviation matters) is consumed by execution-side evaluation that already exists (`transitionEngine.ts` already reads `constraint_type` correctly) or, for the new `requiredPolicyCodes` threshold, by whatever execution-side code eventually evaluates it. No change to either field.

### `condition` — becomes a real authored field, starting minimal
Owner: *"we will start with this, but... we will refine this as we go along with corresponding code changes."* Gets a `criteriaType`-style picker on the form (mirroring Quality Gate's own criteria-type dispatch), starting with the 2 real types that already exist and are evaluated (`always_true`, `field_in`). New types (e.g. a generic threshold/percentage type, usable for "80% of gates pass," "90% of evidence present," or anything else a Gate supplies the context for) get added incrementally, each with its own execution-side evaluation code, as they're actually needed — not designed exhaustively up front.

### Required Evidence / Related Obligations — not separate structural fields
Falls directly out of the governing principle above. Owner: *"So if a quality gate refers to evidence, then there can be a policy [related] to evidence saying at least 90 percent of evidence is present or all evidence is present etc."* "Required Evidence" isn't a dedicated Policy mechanism with special Evidence-awareness — it's just an application of the same generic, extensible `condition` (a threshold type, once built) in a context where a Gate happens to be evaluating Evidence. Policy never gains any Evidence-specific (or Obligation-specific) field; the domain meaning comes entirely from the referencing Gate.

### Exception Rules — already covered by Constraint Type, no new mechanism
Owner: *"policy waiver is designed as standard through constraint type."* A Policy authored as Constraint Type "Standard" simply never blocks (§11, already built) — that's a permanent, definition-time choice, not a runtime waiver granted per-instance. No `policy_waivers` table, no exception-request flow. Explicitly distinct from — and doesn't touch — the existing **Gate waiver** mechanism (`quality_gate_waivers`, CR-058, badge-gated, waives a specific *blocked evaluation instance* at execution time): owner, *"Gate waiver is different from evidence waiver."* Both stay exactly as they are; Policy needs neither a new waiver table nor changes to Quality Gate's own.

### Conflict detection — deferred, not a definition question
Owner: *"let us resolve this when we get to composition engine. it is not a definition question."* The current `compositionEngine.ts` behavior (same-code collision = Override; different Policies always co-apply, no content-level conflict detection) is untouched by this CR — revisited separately, whenever composition-engine work is picked up.

## Scope (once built)

1. `policies` table: drop `policies_code_key`; add `(originating_pack_id, code)` unique index instead. No `version`/`is_active` columns.
2. New Ontology concept type `category:policy`, seeded with the 7 values from Ch.24 §7.
3. `contributionPolicies[]` schema: `category` becomes a real `category:policy`-backed referential-select; `governedTransition` becomes `transition-definition`-backed (same picker Quality Gate/Review Gate use); `condition` becomes a real authored field (a `criteriaType`-style dispatch, starting with `always_true`/`field_in`); per-field help, `x-property-order`, same discipline CR-058/059/060 established.
4. `policiesDB.upsert`: `ON CONFLICT (originating_pack_id, code)` instead of `ON CONFLICT (code)`, matching `checklistsDB.upsert`'s own shape.
5. `contributionQualityGates[]`'s `requiredPolicyCode` → `requiredPolicyCodes` (array), multi-select referential picker (reusing the `"referential-multi"` capability CR-060 built), scoped to Policies whose owning Pack shares the authoring Pack's own `code` (mirroring `checklistIds`'s own corrected scope exactly — same `findByPackCode`-style lookup, same picker-empty-until-code-is-chosen behavior). No threshold field on the Gate's own form yet unless/until a specific new criteria type needs one.
6. `core/packs.ts`: `validatePackSeed` validates each declared Policy (`name`/`category`/`governedTransition` required, `governedTransition` resolves to a real transition, `condition` structurally valid for its declared type) and each `requiredPolicyCodes` entry resolves either as this same Pack's own declared Policy code (not yet persisted, raw seed JSON) or a real, code-scoped cross-Pack `policies.id`/`code` — same dual-shape resolution `validateChecklistIds` already established. `seedContributions` upserts `policies` before `qualityGates` (mirroring `checklistIdByName`).
7. Test seeds/scripts updated in the same change, not after (standing discipline, restated in every CR since CR-058).

## Not in scope

- Making `governedTransition` functionally consulted by the evaluation engine (execution).
- Evaluating `requiredPolicyCodes`' own all/percentage threshold (execution — new `qualityGateEngine.ts` code, deferred).
- Any new `condition` type beyond `always_true`/`field_in` unless a concrete need surfaces during the build itself.
- Content-level Policy conflict detection (composition-engine work, deferred separately).
- Anything Gate-waiver-related — untouched, already correct.
