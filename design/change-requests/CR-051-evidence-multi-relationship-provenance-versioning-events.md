## Item 5 — Built 2026-08-21

The named-event gap, exactly as scoped: mechanical, no schema change, no new design decision. Reused the `EVENT_BY_TARGET_STATE` pattern already built three times (`core/packs.ts`, `core/templates.ts`, `core/deliverableDefinitions.ts`) — a lookup from target state to event type name, published instead of the generic `EvidenceTransitioned`.

- `src/routes/seu/core/evidence.ts` — new `EVENT_BY_TARGET_STATE` map (`Validated`→`EvidenceValidated`, `Accepted`→`EvidenceAccepted`, `Referenced`→`EvidenceReferenced`, `Archived`→`EvidenceArchived`, `Rejected`→`EvidenceRejected`, matching the exact set §16 names). `transitionEvidence()`'s `eventBus.publish` call now looks up the target state instead of hardcoding `EvidenceTransitioned`; the generic type stays as a defensive fallback only (never actually fires — every real Evidence target state in `transitionDefinitions.json` is covered).
- No route, schema, or view changes — this only changes which `eventType` string gets published on an already-existing code path.
- Tests: `tests/trust-pipeline.test.ts` — new test walks Evidence through Validated → Accepted → Referenced → Archived and confirms each named event appears in the `events` table (via `eventsDB.findByOriginatingObject`) and that the generic fallback never fires; a second Evidence Item is walked through the separate Rejected branch and confirmed to publish `EvidenceRejected`. Full suite green.
- No separate live HTTP smoke test — the automated test exercises `transitionEvidence` directly against the real database, the exact same code path the web/API transition routes call; nothing about routing or the HTTP layer changed.

## Item 4 — Built 2026-08-21

Versioning shipped as a single self-referential `supersedes_evidence_id` column — a supersession chain, not a `(code, version, tenant)` catalog identity (Evidence has no `code`). Before agreeing to build, the owner raised a sharp scenario: V1 supports Deliverables in both SEU1 and SEU2 (cross-SEU sharing, item 2). V2 corrects V1 but is only relevant to SEU2 — does superseding cascade and affect SEU1's still-valid reliance on V1? Confirmed design, resolved as three decisions before any code was written: (1) V2 starts with no relationships inherited from V1 — the corrector links it explicitly, exactly like any new Evidence; (2) no cross-SEU signal — SEU1's own page shows nothing different; (3) superseding is open, same permissiveness as cross-SEU linking, no new authority check. The core invariant: **superseding is a fact recorded between two Evidence rows only, never a bulk operation over `evidence_relationships`.**

- Schema: `src/dblayer/migrations/088_evidence_versioning.sql` — adds `supersedes_evidence_id` (self-referential FK, nullable). No uniqueness constraint (a predecessor could be corrected more than once by different actors for different consuming SEUs); no cycle risk (Evidence is immutable, EM-002 — the pointer is set once at creation and must reference an already-existing row).
- `src/dblayer/evidenceDB.ts` — `create()` accepts optional `supersedesEvidenceId`; new `findSupersededBy()` (reverse lookup) and `findLinkedToSeu()` — the latter a necessary supporting piece, not scope creep: SEU2's own Evidence section was built from `findBySeuId` (filters by origin), so a cross-SEU-shared Evidence Item like V1 was invisible on SEU2's own page even though it already satisfied SEU2's Quality Gates. Without this query, V1 had no way to be found as a supersede-predecessor from SEU2's page — exactly the scenario in the prompt.
- `src/routes/seu/core/evidence.ts` — `createEvidence()` validates the predecessor exists (same style as the existing Deliverable-existence check) and passes it straight through — no other special handling, nothing touches the predecessor's own row. Publishes `EvidenceSuperseded` (payload `{ supersedesEvidenceId }`) alongside the existing `EvidenceCollected`, same non-reactive announcement-only pattern as `EvidenceLinked`. New `listEvidenceLinkedToSeu()` and `findEvidenceSupersededBy()` wrappers.
- Routes: `POST /evidence` (api and web) accept optional `supersedesEvidenceId` (API) / `predecessorEvidenceId` (web form).
- View: `src/views/seu/seus/detail.ejs` — Evidence collection form gained a "Corrects" select (populated from `evidenceSupersedeCandidates`, which includes cross-SEU-shared candidates); the correcting row's own Title cell shows `(corrects: <predecessor title>)`. Nothing added to the predecessor's own row, per the owner's own decision.
- Tests: `tests/trust-pipeline.test.ts` — new test reproduces the exact scenario: V1 shared across SEU1/SEU2, confirmed discoverable from SEU2's own page via `listEvidenceLinkedToSeu`, V2 created superseding V1 and linked only to SEU2, then asserts V1's relationships (still 2), status (unchanged), and Quality-Gate standing for SEU1 (`findByRelatedObject` still finds it) are all completely untouched; asserts the reverse lookup finds V2 from V1; asserts a bogus predecessor id is rejected. Full suite green at build time.
- Live-verified over HTTP against a throwaway smoke-test server: reproduced the full scenario — collected V1 on SEU1, linked it to SEU2's own Deliverable, confirmed it appeared in SEU2's own "Corrects" dropdown (closing the discovery gap), submitted V2 there naming V1 as predecessor, confirmed V2's row showed the correct "(corrects: ...)" note and V1's own row on SEU1's page showed nothing extra, and confirmed via direct DB query that V1's relationships/status were byte-for-byte unchanged; smoke-test rows deleted afterward.

## Item 3 — Built 2026-08-21

Provenance shipped as five new nullable columns directly on `evidence`, not a per-relationship structure — provenance describes where an Evidence Item itself came from (singular, at creation time), which is a different question from what it now supports (plural, via `evidence_relationships` from item 1). The two turned out not to need the same shape after all.

- Schema: `src/dblayer/migrations/087_evidence_provenance.sql` — adds `originating_deliverable_id`, `originating_participant_id`, `originating_capability_id`, `originating_decision_id` (all FK, nullable), `originating_activity` (text, nullable). Backfills `originating_deliverable_id` for all pre-existing rows from each Evidence row's earliest Deliverable-type relationship.
- `src/dblayer/seuTypes.ts` — `EvidenceRow` gains the five fields.
- `src/dblayer/evidenceDB.ts` / `src/routes/seu/core/evidence.ts` — `create()`/`createEvidence()` accept all five as optional input. `originatingDeliverableId` auto-derives from `relatedObjectId` when the creating relationship is itself a Deliverable (the common case); the other four are never inferred — no reliable default exists for who/what actually produced a given piece of Evidence.
- Routes: `POST /evidence` (api and web) accept the four optional provenance fields (`originatingParticipantId`/`originatingCapabilityId`/`originatingDecisionId`/`originatingActivity` on the API; `participantId`/`capabilityId`/`decisionId`/`activity` on the web form).
- View: `src/views/seu/seus/detail.ejs` — Evidence collection form gained optional Participant/Capability/Decision selects and an Activity text input; the Evidence table gained a "Provenance" column listing whichever fields were captured.
- `src/routes/seu/core/seus.ts` — `SeuDetailEvidence.provenance` resolves the four FK fields to display labels; `SeuDetailView.participants` added as select options.
- Tests: `tests/trust-pipeline.test.ts` — new test creates Evidence with all five provenance fields set, confirms auto-derivation of `originatingDeliverableId`, confirms display labels resolve correctly through `getSeuDetailView`, and confirms Evidence created without any provenance still succeeds (all fields optional). Full suite green (160/161 — one pre-existing, unrelated failure in `web-flow.e2e.test.ts`'s Participant-replacement test, confirmed via diff to be untouched by this change) at build time.
- Live-verified over HTTP against a throwaway smoke-test server: fulfilled a Capability, created a Decision, collected Evidence naming Participant/Capability/Decision/activity through the actual web form, confirmed all five fields persisted in the database and rendered correctly in the "Provenance" column; smoke-test rows deleted afterward.

## Item 1 (and item 2) — Built 2026-08-21

Multi-relationship support shipped as `evidence_relationships`, a new join table replacing the single `evidence.related_object_type`/`related_object_id` pointer — one Evidence row can now relate to any number of objects. Cross-SEU sharing (item 2) fell out of the same fix for free, exactly as anticipated below: `findByRelatedObject` never filtered by matching `seu_id`, so once an Evidence row could hold >1 relationship, one relationship could simply point at an object belonging to a different SEU than the Evidence's own origin — the one thing actively blocking it (an ownership check in `createEvidence`) was removed.

- Schema: `src/dblayer/migrations/086_evidence_relationships.sql` — new `evidence_relationships` table (`evidence_id`, `related_object_type`, `related_object_id`, unique constraint, two indexes), backfills all pre-existing Evidence rows' single relationship, drops the two columns from `evidence`.
- `src/dblayer/seuTypes.ts` — `EvidenceRow` loses `related_object_type`/`related_object_id`; new `EvidenceRelationshipRow` interface.
- `src/dblayer/evidenceDB.ts` — `create()` now transactional (insert Evidence row + its first relationship row together); new `addRelationship()` (idempotent, `ON CONFLICT ON CONSTRAINT evidence_relationships_unique DO NOTHING`) and `findRelationshipsByEvidenceId()`; `findByRelatedObject()` reimplemented as a JOIN, same public signature — zero changes needed in `qualityGateEngine.ts`, `dependencyDefinitionEngine.ts`, `traceability.ts`, or `compliance.ts`.
- `src/routes/seu/core/evidence.ts` — new `assertRelatedObjectExists()` helper (Deliverable-existence check, deliberately no same-SEU check); `createEvidence()` uses it; new `linkEvidenceToObject()` (publishes `EvidenceLinked`, mirroring `EvidenceCollected`'s shape — announcement only, per the Event Bus's settled "pure transport, never decides" role) and `listEvidenceRelationships()`.
- Routes: `POST /evidence/:id/link` (`src/routes/seu/api/evidence.ts`), `POST /seus/:id/evidence/:evidenceId/link` (`src/routes/seu/web/seus.ts`).
- View: `src/views/seu/seus/detail.ejs` — Evidence table's "Deliverable" column replaced with "Supports" (lists every linked object), plus a "Link another" form per row.
- Tests: `tests/trust-pipeline.test.ts` — new test covers one Evidence row linked to two Deliverables (both found via `findByRelatedObject`), cross-SEU linking, idempotent re-linking, and rejection of an invalid Deliverable / unknown Evidence id. Full suite green (160/160) at build time.
- Live-verified over HTTP against a throwaway smoke-test server: created Evidence, linked a second Deliverable via the new route, confirmed the "Supports" column showed both and `evidence_relationships` held exactly 2 rows; smoke-test rows deleted afterward.

## What this covers

Five gaps identified in Chapter 17 §20 against the live `evidence` table/`core/evidence.ts`/`evidenceDB.ts` — all Part B (wiring), none of them Part A:

1. **Multi-relationship support** ✅ Built 2026-08-21 (§10, EM-004, FR-17.4/FR-17.7) — `evidence.related_object_type`/`related_object_id` is a single polymorphic pointer today; one Evidence row can only name ONE related object. The chapter's own "one Evidence Item may support many engineering artefacts" isn't built. Quality Gate evaluations consume Evidence by live query, with no persisted link recording which Evidence satisfied which evaluation; Reviews and Policies have no Evidence linkage at all. **Settled design direction** (owner's own worked example — the same test results supporting Source Code, a Deployment Readiness review, and a Compliance obligation simultaneously): Evidence stays its own independently-persisted, top-level entity, linked outward by reference — not nested/owned inside any one artefact. The fix is the relationship mechanism, not where Evidence lives.
2. **Cross-SEU sharing** ✅ Built 2026-08-21, as a confirmed side effect of item 1 (§7 External Evidence, FR-17.7) — confirmed requirement, not hypothetical: "an external evidence can be used across multiple SEUs." Today's mandatory single `seu_id` on `evidence` locks every row to exactly one SEU. Likely the same underlying schema fix as #1 — whatever structure lets one Evidence row relate to many *objects* probably also needs to let it relate to many *SEUs*.
3. **Provenance fields** ✅ Built 2026-08-21 (§12, EM-005, FR-17.2) — only `seu_id` and the single related-object pointer exist. Missing: originating Participant, originating Capability, originating Decision, originating engineering activity. Owner: "A participant (human or AI, running its own tools) produces the evidence and it gets attributed to them permanently." (§4's "Evidence is independent of Participants" doesn't conflict with this — confirmed against DM-006, Ch.15: existential independence, not optional attribution.)
4. **Versioning + supersede-link** ✅ Built 2026-08-21 (FR-17.3, §15) — no version column, no "corrections create a new Evidence Item linked to the previous one" mechanism at all. Evidence is an instance, not a catalog definition — it has no `code` — so this is a supersession chain, not `(code, version, tenant)` identity like Template's.
5. **Full named event set** ✅ Built 2026-08-21 (§16) — only `EvidenceCollected` (on creation) and one generic `EvidenceTransitioned` (fromState/toState in the payload) exist. The chapter names `EvidenceValidated`/`EvidenceAccepted`/`EvidenceRejected`/`EvidenceReferenced`/`EvidenceArchived` as distinct events; none exist as separate event types.

## Owner's own framing — 1, 2, 3 are one design question (4 folds in naturally)

"1, 2 and 3 can be combined as they would need data model changes" (original numbering — now items 1/3/4 above, with cross-SEU sharing added as item 2 once confirmed). These aren't independent fixes — multi-relationship support is likely the schema move that also carries provenance (a provenance field set may belong *per relationship*, not once per Evidence row) and cross-SEU sharing (same "one row, many links out" shape), and interacts with versioning (does a new Version inherit its predecessor's relationships, or restate them?). Whatever join-table/schema shape is chosen should be designed once, covering all of these, not built separately.

## Item 5 (events) — separate in kind, precedented

The named-event gap is mechanical and independent of the schema question above — the same `EVENT_BY_TARGET_STATE` map pattern already built twice (CR-025 for Pack/Template, CR-049 Phase 1 for Deliverable Definition): a lookup from target state to event type name, published instead of (or alongside) the current generic `EvidenceTransitioned`. Low risk, doesn't need the schema design above settled first, but bundled into this CR since the owner named it alongside the others.

## Explicitly out of this CR's scope, deliberately deferred (owner's own sequencing decision)

Part A's own authoring surface — `reviewGates` Pack contributions are declared but never materialised (`core/packs.ts` only processes `qualityGates`), and the `externalEvidence` flag (`VerifiableItemFields`) is declared but not enforced anywhere at runtime. Owner: "I wanted to get the underlying structures correctly first before changing the authoring so we are not in multiple cycles." Not tracked here; to be picked up once this CR's own schema design lands.
