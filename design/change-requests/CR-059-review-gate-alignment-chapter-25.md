## The gap, precisely

Live `contributionReviewGates[]` schema (`schema_definitions`, `entity_kind='Pack'`) authors only: `code` + the shared §20 verifiable-item fields (`statement, prompt, assurance, participant, classification, outputContract, externalEvidence`). Confirmed via `seuTypes.ts:129`: `reviewGates?: Array<{ code?: string } & VerifiableItemFields>;`. No `name` distinct from `statement`. No way to say *which deliverable* a Review Gate is for.

Five real Pack seed files (`openup-architecture`, `openup-configuration-and-change-management`, `openup-test`, `openup-development`, `openup-requirements`) already populate meaningful Review Gate declarations. Real example, `openup-architecture.pack.json`:

```json
{
  "code": "review-architecture",
  "statement": "The Architecture Notebook has been reviewed and accepted as sufficient to guide implementation.",
  "classification": "human-attested",
  "prompt": "Is the architecture sufficiently detailed, consistent, and approved to guide implementation?",
  "participant": "human",
  "outputContract": "assessment-acceptance"
}
```

Notice `code` is already trying to say "this is the Architecture Notebook's review" via a free-typed slug — the statement makes the real target explicit in prose, but nothing in the schema captures it structurally.

**Deeper than the form gap**: `core/packs.ts`'s `seedContributions` never processes `seed.contributions.reviewGates` at all — unlike every sibling contribution kind (`capabilities`, `services`, `authorityRules`, `policies`, `qualityGates`), which are all processed identically in that same function. So today, every Review Gate declared across the real Pack files is parsed by the SDK authoring tool for form rendering only, then silently discarded at publish time — not literally discarded (`packsDB.create` stores the whole `contributions` object, `reviewGates` included, verbatim as JSONB on the Pack row), but never materialized into any queryable table, never enforced, never referenceable by `requires_accepted_review`. This was already flagged in this session's earlier Chapter 25 audit as "the cleanest shovel-ready gap found this session."

**Clean-slate alignment, checked directly (unlike `platform-core-engineering`'s known-broken bootstrap): the 6 real OpenUP Pack files (5 of which declare `reviewGates` content) *do* have a genuinely working seed path.** `cleanSlate.ts`'s own step 6 calls `seedCapabilityPatternPacks()`, which loads all 6 `openup-*.pack.json` files and drives them through the real `publishPack` → `createPackDraft` → `validatePackSeed` → Draft→Validated→Published→Active pipeline — not a one-off script, the same code path every other Pack goes through. Their `code` values are already registered `capability-name` concepts (migrations 046/068), so this path isn't blocked the way `platform-core-engineering`'s permanently is. This means once `seedContributions` is updated to materialize `reviewGates` (Scope item below), clean-slate picks the change up automatically through this same existing path — no separate bootstrap fix needed, unlike the `platform-core-engineering` gap CR-058 hit. **The one real risk**: this CR also makes `governedTransition`/`name` mandatory and `code` Ontology-validated (`deliverable-name`-backed) — the 5 files' *existing* `reviewGates` entries (today just `code`/`statement`/`prompt`/`classification`/`participant`/`outputContract`, no `governedTransition`/proper `code`) will fail the new `validatePackSeed` checks and break `publishPack` for these Packs if not updated *as part of the same change*, not after. Updating those 5 files is not a follow-up — it's required for clean-slate to keep working at all once this CR ships.

**Review's own category has zero Ontology backing anywhere on the platform** — confirmed live:

```
   category   | count
--------------+-------
 Code         |     3
 Architecture |     9
 Design       |     3
 Security     |     3
```

Only 4 of Ch.25 §7's 8 named categories have ever been used, all free text, and no `category:review` Ontology concept type exists. `reviews.category` is the one categorized entity in the codebase that skips `assertCanonicalCategory` entirely. **This finding stands, but per the design below it turns out to be orthogonal to Review Gate's own structure** — see "Why category doesn't apply here."

## Why this matters now

Connects directly to the earlier `criteriaCategory` discussion this session: *"Needs review should point pack to one of the review gates. That is the correct way to do this."* For a Quality Gate's `requires_accepted_review` criteria to reference a specific Review Gate, Review Gates first need to actually exist as persisted, queryable rows — today `seedContributions` doesn't even get that far.

## Why category doesn't apply here (settled)

Initial draft of this CR proposed a `category:review` Ontology type, mirroring `category:evidence`. **Rejected, on a sharper basis than redundancy with Evidence's own "Review" value.** Owner:

> Category-as-gate-code exists to solve a specific problem — multiple independently-authored Packs (Go checklist, JS checklist) contributing separate checklist items that need to union-compose into one gate. Review doesn't have that problem. A review is a single reviewer's verdict on one specific deliverable version — there's no aggregation of checklist items from multiple Packs to reconcile, so there's nothing for a category code to disambiguate.

Category exists on Quality Gate specifically to let multiple Packs' checklist contributions merge into one enforcement point at a shared transition without clobbering each other (the active-slot uniqueness CR-058 built). Review Gate has no such multi-Pack aggregation problem, so it needs no such axis.

## Design, as settled

### The real key: deliverable type, not category
Review Gate's identity collapses to **`(deliverable-name, entity_type, from_state, to_state)`** — the same materialization-key shape Quality Gate uses (`entity_type, from_state, to_state, category`), with the deliverable's own type standing in for category as the disambiguating axis. This matches the real seed content directly: `review-architecture`'s statement is about the *Architecture Notebook* deliverable specifically, not a generic "Architecture" bucket.

Confirmed this is not a new vocabulary to invent: "deliverable type" is already a single, global, Ontology-backed concept type (`deliverable-name`, 23 codes, migrations 048/079) — Template's own Deliverable Catalogue already authors against it via `x-referential: "deliverable-name"`, and `sdkAuthoring.ts`'s `loadReferentialOptions` already exposes a `"deliverable-name"` referential-select source (reused directly by `TemplateDeliverableSeed`'s own `name` field). Same move CR-058 made reusing `category:evidence` instead of inventing a new type.

### `code` = the deliverable-name value, shown on the form
Unlike Quality Gate (where `code = category` collapsed a field the author never needed to see, and was removed from the form entirely), Review Gate's `code` collapses to the deliverable-name value **but stays visible and mandatory on the form** — authored via the same `x-referential: "deliverable-name"` picker Template's Deliverable Catalogue already uses. Owner: "a pack can hold multiple checklists for different deliverable-type-code" — i.e. a Pack can (and the real seed data implies it will) declare several Review Gates, one per deliverable type it wants a review checklist for. The picker is exactly how the author expresses that.

### `governedTransition`
Review Gate gains the same field/mechanism Quality Gate already has — a referential picker sourced from real `transition_definitions` rows only, never freely typed. Together with `code` (deliverable-name), this completes the 4-part key.

### Active-slot uniqueness
Mirrors Quality Gate's own: a partial unique index on `(entity_type, from_state, to_state, code) WHERE is_active` — one active Review Gate per deliverable type per transition, versioned the same way (new row per version, prior row deactivated).

### `name`, distinct from Statement
Ch.25 §8's Review Structure wants a Name distinct from criteria/statement, mirroring Quality Gate having both `name` and `statement`/`prompt`. Review Gate has no `name` today; adding it, mandatory.

### `requires_accepted_review`'s criteria: explicit `deliverableName` param, `criteriaCategory` dropped entirely
Two ways this could resolve were on the table — an explicit param on the criteria, or a fully implicit lookup from the transitioning Deliverable instance's own type. **Settled: explicit.** Owner: "Let us keep it explicit; save a db trip I suppose" — the implicit form would require resolving the instance's own deliverable-name at evaluation time; the explicit form is a direct key match, no extra query. Criteria shape becomes `{type: "requires_accepted_review", deliverableName: "Architecture Notebook"}`. `criteriaCategory` (Review's own free-text category, CR-058's restored field) is fully superseded and removed — its whole job was disambiguating "which kind of review," a job the deliverable-name key now does structurally.

**How the match against a real `reviews` row actually happens matters, and matching by `deliverableName` string alone is not enough** (see "Linking a real Review back to the Review Gate that produced it," below, now settled as in-scope): the criteria resolves the target `review_gates` row once via `(deliverableName, governedTransition)`, then the evaluation itself checks for an Accepted `reviews` row with that exact `review_gate_id` — a strict FK join, not a repeated string comparison.

**The `deliverableName` param must itself be a referential-select on the Quality Gate authoring form, not free text — settled.** Owner: "the qualitygate now has to show the reviews in the dropdown to completely define it." Same discipline as `governedTransition`'s own picker (CR-058: "the Pack must select an existing transition_definitions triple, never declare one that doesn't already exist") — a Quality Gate must not be able to reference a Review Gate that doesn't actually exist, since that would silently make the criteria permanently unsatisfiable (no `review_gates` row to resolve `review_gate_id` against). Two scoping questions, both settled:
- **Transition scope: any of the Pack's Review Gates, not just ones on the same `governedTransition` as the Quality Gate.** A later gate (e.g. final Approval) legitimately checks a Review that happened at an earlier stage (e.g. a Draft-stage review) — the same pattern `requires_accepted_evidence_or_approved_decision` already supports, where Evidence/Decisions accumulate over the SEU's lifecycle and are checked at gate time regardless of when they were created.
- **Pack scope: same Pack's own declared Review Gates only**, not cross-Pack. Keeps ownership/versioning simple — no cross-Pack dependency to track when a Review Gate changes, unlike `transition_definitions`/Policy codes which are genuinely global/shared. Owner's general principle, stated while settling this: "if something is global, it has to be a policy" — Review Gates aren't the platform's cross-Pack-sharing mechanism; Policy already is. If a genuine need for a Review Gate to be checked from another Pack ever arises, the answer is to express that through a Policy, not to widen Review Gate's own referencing scope.

### Closing the `seedContributions` gap
`core/packs.ts`'s `seedContributions` must start processing `seed.contributions.reviewGates`, matching the existing pattern for `qualityGates`/`authorityRules`/`policies`/`services`/`capabilities`: validate each entry (`deliverableName` resolves via the Ontology, `governedTransition` resolves via `transition_definitions`, active-slot uniqueness), then persist.

### New `review_gates` table
No table exists today — Review Gate declarations live only inside a Pack's `contributions` JSONB, parsed by the SDK authoring tool for form rendering, never persisted as first-class rows. New `review_gates` table mirrors `quality_gates`' shape: Pack/entity scoping, `code` (= deliverable-name value), `governedTransition`, `name`, `version`/`is_active`, the VerifiableItemFields columns.

### Linking a real Review back to the Review Gate that produced it — settled: build it now, not deferred
Originally proposed as a deferred follow-on ("minimal for this CR: leave `reviews` ungated"). **Rejected** — a string/category match without a real FK isn't a weaker version of the same guarantee, it's a genuine corruption risk specific to Review: (1) if the same deliverable type is reviewed at more than one transition in its lifecycle, a `deliverableName`-only match can't tell which transition's Review was intended, so an Accepted Review meant for one gate could silently satisfy a different one; (2) nothing stops a `reviews` row from being created directly with a coincidentally-matching deliverable name that never actually went through the gate's declared `prompt`/`participant`/`outputContract` — the match would report "satisfied" without the review having actually answered the gate's own question. Same class of gap CR-051 built provenance discipline to close for Evidence; Review shouldn't ship with a weaker guarantee than that precedent.

`reviews` gains `review_gate_id` (nullable FK to `review_gates.id` — standalone reviews unrelated to any gate remain allowed). `requires_accepted_review`'s evaluation stops matching by any string field entirely: it resolves the target `review_gates` row once via `(deliverableName, governedTransition)`, then checks for an Accepted `reviews` row with that exact `review_gate_id` — a strict join, not a coincidence match.
