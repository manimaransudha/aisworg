> **One transient full-suite flake found and root-caused, not a regression**: a single run showed `service-dependency.test.ts` and `telemetry-per-seu.test.ts` failing with "template not found," both inside `commissionFromForm` → `createProfile`. Both pass cleanly in isolation; a same-shape re-run of the full suite immediately after came back 148/148. Root cause: `findCandidateTemplates` (`core/templates.ts`) matches candidate Templates via `templatesDB.findAllActive()`, unscoped by tenant *or by which test created them* — the Template Inheritance tests (this CR's new one, and CR-026's existing ones) each walk an inherited, same-required-capabilities clone of `template-web-application` all the way to Active before deleting it in their own `after()` hook. In the same window, another concurrently-running test file's own capability-based commissioning can pick that transient row as a valid candidate, then find it deleted underneath it moments later. This is the same class of shared-dev-DB, no-reset, concurrent-test-file flake as this session's earlier "Phase 8" finding (CR-024) — pre-existing risk in `findAllActive`'s own unscoped-by-anything design, made marginally more likely to fire by this CR adding one more same-code Inheritance test, not a defect in the versioning/inheritance/schema work itself. Not fixed here — `findCandidateTemplates`/`findAllActive` scoping is a deliberate, separate design question (mirrors Ch.6/Ch.7's own "not part of what was asked" convention), flagged for a future CR if the flake rate ever becomes a real problem.

### What's built here

**Versioning, immutability, and inheritance (§19.2/§19.3, mirroring CR-024 + CR-026 combined)**
Profile had none of Pack's/Template's foundation — no `profile_version`, no `tenant_id`, no `parent_profile_id`, a bare `UNIQUE(code)` that let `publishProfile`'s `upsert` silently overwrite a "published" row in place. Migration `064` adds all three columns in one pass (Profile starting from zero, unlike Template which built this incrementally across two CRs) and replaces `profiles_code_key` with `profiles_code_version_tenant_key UNIQUE(code, profile_version, tenant_id)`. `profilesDB.ts` gained the full version/tenant-aware function set (`findByCodeAndVersion`, `findActiveByCode`, `findAllVisibleTo`, `findActiveVisibleTo`, `findAll`, tenant-scoped `findByStatus`), and `core/profiles.ts` gained `reactivateAsNewVersion`/`nextAvailablePatchVersion`/a `TERMINAL_REACTIVATABLE_STATES` check in `transitionProfile` plus tenant-scoped supersede logic in `advanceProfileOneStep` — all byte-for-byte mirrors of `core/templates.ts`'s own CR-024 shape. Three reactivation edges (`Deprecated/Retired/Archived → Active`, verb `activate`) added to `transitionDefinitions.json`/`authorityVocabulary.json`, the same gap CR-024 found and fixed for Template.

Inheritance (Ch.7 §9) reuses Template's exact Option A identity model: a Derived Profile keeps its parent's own `code`, disambiguated by the new Draft's own `tenant_id`. `listInheritableProfiles`/`inheritedProfileContent` (`core/sdkAuthoring.ts`) mirror `listInheritableTemplates`/`inheritedTemplateContent`; the "Inherit from an existing Profile" dropdown + button on the Profile `new`-draft form (`edit.ejs`) mirrors Template's exactly, shown only to a real Tenant author. The inheritance validator turned out simpler than Template's: Profile has no "mandatory" concept at all (every Pack selection is optional, §5), so §9's own rules ("add Packs; remove optional Packs; override configuration values") need no superset check — only the code-identity lock, enforced server-side (`createAuthoringDraft`/`saveAuthoringDraft`'s Profile branches force `code` to the parent's, ignoring a tampered submission) the same way Template's already is.

**The full §7 field set, at the schema level (§19.4/§19.6)**
Migration `066` added every remaining field to Profile's `schema_definitions` grammar, using only already-existing generic widget mechanisms — no new widget kinds:
- **`category`** — a new, real field (not folded into `code` the way Template's is — see *Design decisions*), Ontology-backed via a new `profile-categories` concept type (migration `065`, seeded with §8's 6 examples: Startup/Enterprise/Healthcare/Banking/Prototype/Production).
- **`profileVersion`**, **`description`** — the same `x-widget:"version"`/`"textarea"` mechanisms `packVersion`/`templateVersion`/`purpose` already use.
- **`featureFlagCodes`** — a `referential-list` sourced from a new Ontology concept type `feature-flag` (migration `065`, seeded with §11's 5 examples), resolved through the existing generic `referentialOptions` mechanism (`loadReferentialOptions`, `web/sdkAuthoring.ts`) rather than a new widget.
- **`technologyPackCodes`/`domainPackCodes`/`compliancePackCodes`/`integrationPackCodes`** — four category-scoped Pack-selection `referential-list` fields, alongside the pre-existing, unchanged `optionalPackCodes`. The one real generalisation this CR made: `_referentialListGroup.ejs`'s Pack-code picker now parses an `x-referential` value of `"pack-code:<Category>"`, filtering the offered Packs to that `category:pack` Ontology value (Technology/Domain/Compliance/Integration — already-seeded Pack categories, no new vocabulary) — so each field is a genuinely scoped picker, not four renamed copies of the same list.
- **`compositionOptions`** — declared, not yet enforced, the same "declared for documentation today" treatment Pack's own §8/§13 compatibility metadata has (Ch.5 §19.9's precedent).
- `profile_packs`' storage generalised from one implicit list to five, disambiguated by a new `list_kind` column (migration `067`) rather than four new tables — `profilesDB.setPackSelection`/`getPackSelection` replace the old hardcoded-to-"optional" `setOptionalPacks`/`getOptionalPackCodes` (kept as thin wrappers, so every pre-existing caller — including `compositionEngine.ts` — is unaffected).

**Real named events (§19.9, mirroring CR-025)**
`core/profiles.ts` gained the same `EVENT_BY_TARGET_STATE` map Pack/Template have; `transitionProfile`'s event publish reads from it instead of a hardcoded generic type. `ProfileCreated` now fires from `publishProfile` — closing a gap sharper than Template's own pre-CR-025 state: Profile previously had **no** "Created" event on any entry point, not even the informal generic one Template always had.

### What broke and was fixed
Two pre-existing tests called `publishProfile`/`createAuthoringDraft` without the newly-required `category`/`profileVersion` (`tests/commission-profile-choice.test.ts`, `tests/sdk-authoring.test.ts`'s "Profile authoring" test) — both were silently accepting an empty `category` before this CR, since nothing validated it. Fixed by adding valid values (`category: "startup"`, `profileVersion: "1.0.0"`) to both call sites; no other call sites existed (checked directly).

### Design decisions
- **`category` is its own field, not folded into `code` the way Template's is.** Template's CR-021 shortcut (code *is* the category) is exactly what made Template's own inheritance identity awkward later (Ch.6 §20.4/§20.14 — a Derived Template can't get a distinct category without also getting a new identity). Since Profile is getting inheritance in this same CR, keeping category and identity separate from the start avoids repeating that same tension.
- **§19.7's "Organisation Composition" finding was corrected, not built.** The section (written earlier the same day) had read Ch.7 §12's Platform+TCS+Cigna example as requiring multi-tenant Pack *visibility* — owner corrected this directly: a third-party org's contribution (Cigna) is onboarded as an **Integration Pack** owned by the primary tenant (TCS), never browsed cross-tenant. §12's model is fully satisfied by the `integrationPackCodes` field this CR added, under the same Platform-or-own-tenant visibility every other Pack picker already has — no visibility redesign was ever needed.
- **§19.5's Configuration Parameters (stored, never consumed by `compositionEngine`) was deliberately left untouched.** Orthogonal to everything else in this CR — nothing built here required reading `configParameters`. `compositionOptions` (new, this CR) is in the same position and isn't treated as a new instance of that gap, since §7 never implied it should do more than be declared.

### Not in scope
- A dedicated Profile parameter-substitution mechanism (§19.5) — flagged, not built.
- Registry pages for Template/Profile (Ch.6 §20.12) — built the same day but tracked as its own CR (CR-029), since it's a UI capability independent of Profile's identity model and also touches Pack's existing Registry.
